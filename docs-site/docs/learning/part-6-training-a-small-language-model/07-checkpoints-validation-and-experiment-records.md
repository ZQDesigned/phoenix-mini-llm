# 07. checkpoint、验证集与实验记录

## 为什么这些内容不是“训练结束后再考虑的附属工程”

很多初学者一开始会把下面这些事情看得很后置：

- 保存 checkpoint
- 跑验证集
- 记录训练日志

仿佛真正重要的是模型和优化器，等训练差不多了再补上这些外壳。

这是不对的。

对于一个真正可用、可学习、可复现的小型语言模型项目来说，这些东西属于训练本体的一部分。因为如果没有它们，你几乎无法稳定回答：

- 训练现在到底进行到哪里
- 当前最好结果出现在哪个阶段
- 中断后怎样恢复
- 两次实验到底差在哪

也就是说，它们不是附属脚本，而是在保证训练可以被观察、被恢复、被比较。

## checkpoint 到底在保存什么

先从最直观的东西说起。

checkpoint 的作用不是“留个备份心里踏实”，而是：

> 把某一时刻的训练状态冻结下来，让你以后能从那个状态继续，或者拿它做比较。

一个合格的训练 checkpoint，至少应当帮助你恢复：

- 模型参数
- 优化器状态
- 当前训练 step

如果训练里有学习率调度器，通常还应考虑保存：

- scheduler 状态

否则即使模型权重恢复了，训练节奏也可能已经对不上。

## 为什么只保存模型权重往往不够

这是学习项目里非常常见的误区。

很多人会觉得：

> 只要把 `model.state_dict()` 存下来，不就恢复了吗？

这对于“只做推理”可能够用，但对“继续训练”经常不够。

因为优化器内部往往还有自己的历史状态，例如：

- 动量相关统计
- 自适应缩放统计

如果这些状态丢了，那么恢复训练后：

- 表面上参数接上了
- 实际更新行为却像换了一套训练系统

因此只保存模型，不足以称为完整训练恢复。

## 为什么 step 也必须被当成状态保存

很多训练逻辑不是纯由权重决定的，而是由“训练已经进行到哪里”决定的。

例如：

- 当前 warmup 是否结束
- 当前学习率调度走到哪一段
- 下次是否该评估
- 下次是否该存档

如果 step 丢了，很多节奏型逻辑都会失真。

所以 step 不是普通日志数字，而是训练状态的一部分。

## 验证集为什么属于训练系统，而不是最后验收

很多人一开始只看训练 loss，直到训练结束才想：

> 我是不是该看看模型对没见过的数据怎么样。

这太晚了。

验证集的真正职责是：

> 在训练过程中持续提供“模型有没有真正泛化”的镜子。

如果没有验证集，你很难分清：

- 模型是真的越来越好
- 还是只是在越来越会记住训练集

所以验证不是“训练之后补一个成绩单”，而是训练过程中必须反复查看的仪表。

## 为什么训练损失和验证损失必须一起看

因为它们回答的问题不同。

### 训练损失

回答：

> 模型在已经见过、并用于更新参数的数据上表现如何。

### 验证损失

回答：

> 模型对未参与当前参数更新的数据，是否也在变好。

如果你只看训练损失，就很容易误把记忆增长当成能力增长。

一个成熟训练流程通常会明确规定：

- 每多少 step 评估一次
- 评估用哪些固定数据
- 如何记录 best validation result

## 为什么 checkpoint 和验证经常一起出现

因为一个很自然的训练策略是：

> 不只是定期保存，还要知道“哪个 checkpoint 是目前最值得保留的”。

这时验证集就起到筛选作用：

- 某个 checkpoint 训练损失更低
- 但另一个 checkpoint 验证损失更好

如果你的目标是泛化质量而不是单纯记忆训练集，那么后者往往更值得关注。

所以“保存什么”和“依据什么判断值得保存”，本来就是同一条链上的问题。

## 日志为什么是训练理解能力的一部分

日志的价值不只是让你“看起来很工程化”，而是帮助你把训练从黑箱变成可观察过程。

至少在学习项目里，下面这些量都很值得记录：

- step
- train loss
- validation loss
- learning rate
- grad norm
- tokens seen
- 保存 checkpoint 的时间点

这些日志的作用是让你能回答：

- 训练什么时候开始真正下降
- 哪一步之后出现不稳定
- 学习率变化是否和 loss 变化相关
- 当前最好结果是否出现在后期还是中期

没有日志，你很难形成真正可比较的实验结论。

## 为什么“我大概记得那次训练比较好”不算实验记录

因为人的印象非常不可靠。

如果你同时改了：

- learning rate
- sequence length
- gradient accumulation

然后只凭记忆说：

> 上一次好像更稳。

那几乎没有研究价值。

训练记录的职责就是把这种模糊印象变成：

- 可对比的 step 曲线
- 可回溯的超参数
- 可恢复的中间状态

这也是为什么实验记录并不是“团队大了才需要”的东西。学习项目同样需要它，因为它决定你能不能真正判断因果。

## 什么叫可恢复训练

可恢复训练不是指“我把模型文件留着了”，而是指：

> 如果训练中断，我能以尽量接近中断前的状态继续推进，而不是从一个外表相似、内部节奏却已经错位的状态重来。

这通常要求：

- 模型状态恢复
- 优化器状态恢复
- 调度器状态恢复
- step 恢复
- 配置来源明确

一旦这些缺一部分，你的 resume 很可能只是“半恢复”。

## 学习项目里最容易低估的事情：配置记录

除了张量状态，还应当尽量记录：

- 模型配置
- tokenizer 相关信息
- 训练超参数
- 数据来源或版本

否则几年后，甚至几天后，你都可能遇到这种情况：

> checkpoint 还在，但你已经说不清它是怎么训练出来的。

这时 checkpoint 的价值会大打折扣。

所以训练状态不仅是权重，也包括背景配置。

## 一个实用的保存策略应该回答哪些问题

即使不追求复杂平台，最简单的训练脚本也最好明确回答：

### 什么时候评估

- 每固定多少 step
- 还是每个 epoch 结束

### 什么时候保存

- 每固定多少 step
- 只保存最新
- 还是同时保存最佳验证结果

### 保存哪些元信息

- step
- 配置
- 指标
- 时间戳

### 如何恢复

- 从最新 checkpoint
- 从手工指定 checkpoint
- 恢复后学习率调度是否自动衔接

这些问题一旦在项目初期想清楚，后面训练会省很多混乱。

## 对小型 LLM 学习项目来说，什么是“足够好”的实验记录

你不需要一上来就搭一整套工业实验平台。

一个足够好的入门标准通常是：

- 每次训练有明确配置文件或配置输出
- 日志能看到核心指标变化
- checkpoint 可以继续训练
- 能明确标识当前 best validation checkpoint

只要做到这几件事，你就已经比“只会跑一遍然后截图”强很多了。

## 这一章结束后最该建立的判断

请把下面这件事牢牢记住：

> checkpoint、验证集和实验记录不是训练外壳，而是训练系统能够被理解、被恢复、被比较的基础设施。

如果没有它们，你也许仍然能偶尔把模型训起来，但你很难真正知道：

- 它为什么这次好
- 下次怎样复现
- 中断后怎样接着走

而这些，正是一个知识档案必须教会初学者的训练能力。
