# 05. 混合精度、GradScaler 与设备差异

## 为什么“开启 AMP 更快”不是一个足够好的理解

很多人第一次接触混合精度训练时，最常听到的说法是：

> 开 AMP，可以更快、更省显存。

这句话方向没错，但如果你只停在这里，后面很容易踩坑。

因为混合精度不是简单的“性能按钮”，它实际上同时影响：

- 数值表示方式
- 反向传播稳定性
- 不同设备后端的行为

也就是说，它不只是速度优化，而是训练数值系统的一部分。

## 什么叫“精度”

先从最基础的问题开始。

在深度学习里，张量里的数字不是无限精确存储的，而是用某种浮点格式表示。

常见的可以粗略理解为：

- `float32`：更传统、更稳妥
- `float16`：更省内存、运算更快，但可表达范围和精度更受限
- `bfloat16`：试图在部分场景下兼顾速度和动态范围

所以“精度”不是抽象概念，而是在决定：

> 这些数到底以怎样的数值格式存在。

## 为什么训练想要更低精度

因为它通常带来两类直接收益。

### 第一，显存占用下降

如果单个数使用更少比特表示，那么：

- 激活值
- 中间张量
- 部分梯度路径

都会更省空间。

### 第二，部分硬件上的吞吐提升

很多现代加速设备对低精度矩阵运算做了专门优化，所以：

- 同样时间里可以处理更多乘加
- 训练速度可能明显提升

这就是为什么混合精度几乎总会出现在训练优化讨论里。

## 为什么不直接全程都用低精度

因为低精度不是没有代价。

主要问题在于：

- 数值范围更小
- 更容易丢失很小的变化
- 某些运算更容易上溢或下溢

结果就是，虽然速度和显存更好，但训练稳定性可能变差。

所以真正成熟的方案往往不是“全都低精度”，而是：

> 在合适的地方使用较低精度，在关键地方保留更稳妥的表示。

这就是“混合精度”这个名字背后的核心思想。

## 混合精度里的“混合”到底混了什么

最实用的理解是：

> 并不是所有张量、所有计算都统一降到同一低精度，而是根据稳定性与性能权衡，让不同部分使用不同策略。

例如常见思路是：

- 某些前向计算使用低精度提高效率
- 某些更敏感的状态保留更稳的精度

你现在不必掌握所有内部规则，但要先建立一个判断：

> AMP 不是粗暴降精度，而是一套精度分配策略。

## 为什么低精度训练更容易遇到“太小的梯度消失”

这是理解 `GradScaler` 的关键。

在低精度里，某些很小的数值可能被表示得不够好，甚至直接下溢成 0。

如果梯度过小，而又被低精度吞掉，那么就可能出现：

- 反向传播看似跑了
- 但某些梯度信号实际上损失掉了

这会让更新失真，甚至让模型看起来“学不动”。

## GradScaler 在补什么

`GradScaler` 的核心思想非常朴素：

> 在反向传播前，先把 loss 放大，让梯度也随之放大，从而减少低精度下小梯度直接消失的风险；等到真正更新前，再把尺度还原回来。

也就是说，它不是在修改任务目标，而是在帮助梯度穿过低精度表示这段路时不那么容易损坏。

所以可以把它看成：

> 低精度训练里的一个梯度保护层。

## 为什么 `GradScaler` 常常和 CUDA 绑定更紧

在很多项目里，你会看到 AMP 与 `GradScaler` 主要在 CUDA 条件下启用。

原因不是因为其他设备绝对不能用，而是因为：

- 不同后端支持程度不同
- 低精度数值路径成熟度不同
- 项目通常更愿意把正式性能优化集中在主训练平台上

对你的项目场景来说，这一点尤其现实：

- macOS 上常用于开发验证
- Windows + NVIDIA CUDA 上用于正式训练

因此一个很稳妥的策略通常是：

> 先让所有设备在保守精度下逻辑正确，再只在主要训练后端上启用混合精度优化。

## 为什么 MPS 与 CUDA 不能被当成完全等价后端

这是跨平台开发时非常容易忽略的事实。

你可能在 macOS 的 MPS 后端上看到：

- 代码能跑
- loss 有下降

然后自然觉得：

> 那 Windows CUDA 上应该也差不多。

这并不可靠。

因为不同后端在下面这些方面都可能不同：

- 算子实现
- 混合精度路径
- 数值误差累积方式
- 内存管理行为

所以你追求的不能是“逐步浮点值完全一致”，而应该是：

> 逻辑一致、趋势一致、接口行为一致。

## 为什么初学阶段不应该过早把混合精度当默认前提

因为它会显著增加调试复杂度。

如果你一开始就在一个尚未稳定的训练闭环里同时引入：

- 新模型结构
- 新数据管线
- 混合精度
- 设备差异

那么一旦 loss 异常，你会很难判断问题来自哪里。

因此更稳妥的顺序往往是：

1. 先用更保守精度跑通训练逻辑  
2. 再确认 loss 和生成基本正常  
3. 最后再引入 AMP 和 `GradScaler` 优化  

这不是保守过头，而是在保护调试可解释性。

## 什么时候应该优先怀疑是混合精度问题

以下现象都值得把 AMP / 精度路径列为怀疑对象：

### 情况一：不开 AMP 正常，一开 AMP 就不稳

这通常说明：

- 数值路径对当前配置过于敏感
- 需要检查缩放、梯度裁剪或设备支持

### 情况二：不同设备后端表现差异显著

尤其是在：

- MPS 正常、CUDA 异常
- CUDA 开 AMP 异常、纯 FP32 正常

这说明问题可能不在“模型逻辑本身”，而在后端数值路径。

### 情况三：loss 突然出现 `inf` 或 `NaN`

这可能来自：

- 过大更新
- 某些运算溢出
- AMP 路径上的缩放和还原失衡

当然，不能一看到 `NaN` 就认定是 AMP，但它肯定是优先排查项之一。

## 对小显存学习项目来说，混合精度的正确定位是什么

最务实的定位是：

> 它首先是资源优化和吞吐优化工具，其次才是训练默认前提。

也就是说：

- 如果不用 AMP，链路都跑不通，那问题通常不在“还没开加速”
- 如果已经能稳定训练，AMP 才开始发挥真正价值

这种定位会让你更少踩“为了追性能，先牺牲可解释性”的坑。

## 这一章结束后你该带走的判断

最重要的不是记某个 API，而是稳住下面这条逻辑：

1. 混合精度通过更低精度数值表示换取速度和显存  
2. 低精度会带来数值稳定性风险  
3. `GradScaler` 在帮助低精度梯度不那么容易损坏  
4. 不同设备后端不能被当成完全等价  

只要这条逻辑稳定，后面你看到 AMP、FP16、BF16、GradScaler 这些词时，就不会把它们误当成单纯性能口号。
