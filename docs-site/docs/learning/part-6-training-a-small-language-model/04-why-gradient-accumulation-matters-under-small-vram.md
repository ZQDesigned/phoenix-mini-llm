# 04. 小显存下为什么要做梯度累积

## 为什么小模型项目也会很快撞上显存墙

很多人第一次做小型语言模型时，会直觉觉得：

> 既然模型不大，那显存问题应该不会太严重。

这往往低估了训练的真实开销。

因为训练显存不只装模型参数，还要装：

- 激活值
- 梯度
- 优化器状态
- attention 中间结果
- 临时缓冲区

尤其序列长度一上来，attention 相关成本会迅速增加。

于是你很快就会遇到一个现实问题：

> 我想要的 batch size 放不下。

梯度累积就是对这个问题最实用的回应之一。

## 先把问题说准确：你想要的通常不是“大 batch 这个数字”，而是“大一点的有效更新”

很多人看到显存不够时，会先觉得自己只是“少喂了几条样本”。

更准确地说，你真正损失的往往是：

> 一次参数更新前，模型能综合多少样本的信息。

如果你每次只能放一个很小的 batch，那么：

- 梯度波动更大
- 更新更容易受单批样本偶然性影响
- 训练曲线可能更抖

这时你想恢复的，不只是样本数量，而是：

> 一次更新所对应的有效 batch 规模。

## 梯度累积最朴素的思路是什么

它的核心非常直接：

> 如果一次放不下大 batch，那就把大 batch 拆成多个小 batch 轮流做反向传播，先把梯度攒起来，再统一更新一次参数。

例如你本来想要：

- effective batch size = 16

但显存只能支持：

- micro batch size = 2

那你就可以：

- 连续处理 8 个 micro batch
- 每个都做前向和 backward
- 暂时不 `optimizer.step()`
- 等累积完 8 次后再更新参数一次

这样从优化器角度看，就近似于：

> 一次更新吸收了 16 条样本的信息。

## 为什么它叫 accumulation

因为在反向传播之后，参数上的梯度并不是自动消失的。

如果你不立刻清空梯度，下一次 backward 的结果就会继续加到已有梯度上。

这意味着：

- 梯度可以被逐步累积
- 直到你决定真正执行一次更新

所以梯度累积不是另起一套训练算法，而是：

> 利用现有反向传播机制，把多个小批次的更新信号先合并起来。

## micro batch、accumulation steps 和 effective batch 的关系

这是必须说清楚的三个量。

### micro batch size

单次真正进入显存的小批次数量。

### gradient accumulation steps

累积多少个 micro batch 之后才更新参数一次。

### effective batch size

从“这次参数更新等价于综合了多少样本”来看的 batch 规模。

如果单卡情况下：

\[
\text{effective batch} = \text{micro batch} \times \text{accumulation steps}
\]

如果是多卡训练，还要再乘设备数。

这个关系一旦清楚，你看训练配置就不会再只盯着一个 `batch_size` 变量。

## 梯度累积为什么特别适合小显存学习项目

因为它让你在不提高单次峰值显存的前提下，得到更大的有效更新尺度。

这带来几个直接好处：

### 第一，你不用为了显存限制把训练逻辑完全改写

你仍然是同一套模型、同一套 loss、同一套优化器，只是把一次大更新拆成若干小步累积。

### 第二，你可以更灵活地平衡吞吐和稳定性

显存决定 `micro batch` 能有多大，而你仍然可以通过 accumulation 调节 effective batch。

### 第三，它让 6GB 这种受限显存环境仍然能跑相对完整的训练设置

这对你的项目场景尤其关键。

## 梯度累积不是“免费更大 batch”

这点也必须讲清。

虽然它很有用，但它不是没有代价。

### 代价一：每次真正参数更新要等更久

如果你要累积 8 次才更新，那么参数变化节奏会变慢到：

- 8 个 micro batch 对应 1 个 optimizer step

从 wall-clock 角度看，你不是白拿了一个大 batch，而是在用更多前向 / 反向换更大的有效更新。

### 代价二：日志口径更容易混乱

如果你不区分 micro step 和 optimizer step，很容易把训练进度记错。

### 代价三：实现顺序更容易写错

你必须清楚：

- 哪些地方每个 micro batch 都要执行
- 哪些地方只能在真正更新时执行一次

否则训练行为会悄悄偏掉。

## 实现梯度累积时，最重要的顺序是什么

最朴素的逻辑可以理解为：

1. 清空旧梯度  
2. 连续处理多个 micro batch  
3. 每个 micro batch 都做前向和 backward  
4. 等累积满了，再做一次梯度裁剪和优化器更新  
5. 再清空梯度，进入下一轮  

这里最容易错的地方有两个：

### 第一，loss 是否需要按累积步数缩放

如果你希望累积出来的梯度近似于“大 batch 平均 loss”的效果，那么每个 micro batch 的 loss 往往要先除以 `gradient_accumulation_steps`。

否则你累积的总梯度会比预期更大，等于隐式放大了更新。

### 第二，`optimizer.step()` 不能在每个 micro batch 后都执行

一旦你每个 micro batch 都更新参数，那就已经不是梯度累积，而是普通小 batch 训练了。

## 为什么梯度累积会影响学习率理解

因为它改变了“每次 optimizer step 对应了多少样本信息”。

也就是说，当你改变 accumulation steps 时，你其实也在改变：

- 每次更新所基于的数据规模
- 梯度噪声水平
- 参数更新节奏

因此学习率往往不能脱离 effective batch 单独理解。

如果你把 effective batch 扩大了很多，却完全不重新观察学习率行为，训练动力学可能就变了。

## 梯度累积和序列长度之间是什么关系

在语言模型里，显存压力往往同时来自两个方向：

- batch size
- sequence length

而且这两者不是同等成本。

特别是序列长度变长时，attention 代价上升很快。

这意味着你常见的取舍不是单选题，而是：

- 要不要缩短 `seq_len`
- 要不要缩小 `micro batch`
- 要不要增加 accumulation steps

这三者共同决定：

- 峰值显存
- 每 step token 数
- 有效 batch 规模

所以梯度累积通常不是单独调的，而是和上下文长度一起调。

## 小显存训练时的一个实用思路

如果你的目标是先把小模型可靠训起来，而不是一开始就冲极限配置，一个很务实的顺序是：

### 第一步：先确定放得下的 micro batch

先问：

> 在当前 `seq_len` 下，显存能稳定承受多大的 micro batch？

### 第二步：再决定想要的 effective batch

不是越大越好，而是找一个：

- 梯度不至于太抖
- 时间开销也还可接受

的平衡点。

### 第三步：用 accumulation 补足差额

如果你想要的 effective batch 大于显存允许的 micro batch，就用 accumulation 去补。

这样训练设计会清晰很多。

## 梯度累积不会自动解决所有训练问题

它能解决的是：

- 峰值显存不足
- 小 batch 导致的一部分更新噪声问题

但它不能自动解决：

- 学习率错误
- 数据错误
- mask 错误
- 训练目标构造错误

所以如果你开了梯度累积，训练还是不正常，不要立刻觉得“显存技巧已经用上了，那就不可能是训练链路问题”。

它只是训练系统中的一层补丁，不是根治一切的开关。

## 这一章结束后你应该建立的判断

你最该带走的是下面这个判断：

> 梯度累积的作用，不是让小显存机器假装变成大显存机器，而是在显存不变的前提下，把多个小批次的更新信号合并成一次更大的有效参数更新。

一旦这个判断稳了，后面你看任何训练配置里的：

- `micro_batch_size`
- `gradient_accumulation_steps`
- `effective_batch_size`

都会更容易知道它们分别在解决什么问题。
