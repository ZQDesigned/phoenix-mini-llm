# 04. 小显存下为什么要做梯度累积

前面三章我们已经把训练的计量单位、优化器角色和学习率节奏讲清楚了。现在要面对一个非常现实、也非常快会撞上的限制：

> 你想要的训练设置，显存往往放不下。

很多人第一次做小型语言模型时，会下意识地觉得：

```text
模型都已经是“小模型”了，显存问题应该不会太严重吧？
```

这通常低估了训练的真实成本。

因为训练显存装的远不只是参数本身。它还要装：

- 前向过程中保留下来的激活值
- 反向传播所需的梯度
- 优化器状态
- attention 相关中间量
- 临时计算缓冲区

只要序列稍微变长、batch 稍微增大，这些开销就会迅速显现。

于是你会很快面对一个问题：

> 如果我一次放不下理想的大 batch，是否就只能接受训练很不稳定？

梯度累积就是对这个问题最直接、最实用的回答之一。

## 4.1 先把问题说准确：你真正想要的通常不是“大 batch 这个数字”

初学者最容易把问题表述成：

```text
我想把 batch size 调大，但显存不够。
```

这句话方向没错，但还不够精确。

更准确的说法通常是：

> 我希望一次参数更新前，模型能综合更多样本的信息；但这些样本无法在一次设备前向 / 反向中同时放下。

为什么这种说法更好？

因为它直接揭示了两个层次：

1. 设备一次真正能处理多少数据
2. 优化器一次真正吸收多少数据的信息

这两个层次正好对应：

- `micro batch`
- `effective batch`

梯度累积的作用，就是在显存受限时，把二者重新连接起来。

## 4.2 为什么小模型项目也会很快撞上显存墙

要真正理解梯度累积，先得理解训练显存到底消耗在哪。

### 4.2.1 参数只是开销的一部分

模型参数当然占显存，但训练时还需要保存：

- 参数梯度
- 优化器状态

如果你用 AdamW，一份参数往往还对应额外的状态张量。

所以即使参数本身不算太大，训练态下的总开销也会明显高于“只做推理”时。

### 4.2.2 激活值常常是大头之一

反向传播需要知道前向时许多中间结果，因此这些激活不能像纯推理那样立即丢掉。

序列越长、层数越多、hidden size 越大，激活开销就越敏感。

### 4.2.3 attention 对序列长度尤其敏感

在标准 attention 中，序列越长，中间相关张量和计算成本都会迅速增加。

这也是为什么很多人明明模型参数不算夸张，但一把 `sequence_length` 提高，就立刻爆显存。

### 4.2.4 训练比推理重得多

很多人在推理时看到某个模型能跑，就直觉觉得训练应该也行。

但训练需要：

- 保存更多中间量
- 做反向传播
- 维护优化器状态

所以“能推理”绝不等于“能按理想 batch 训练”。

## 4.3 为什么小显存环境下，真正损失的是“每次更新的信息量”

假设显存限制迫使你只能把 `micro_batch_size` 设得很小。

这时最直接的后果不是“数字好看一点或难看一点”，而是：

> 每次参数更新基于的数据变少了。

这通常会带来几个连锁影响：

- 梯度估计噪声更大
- 更新更容易受偶然 batch 影响
- 训练曲线更抖
- 学习率选择可能更敏感

所以你真正想补回来的，不是某个好看的 batch size 标签，而是：

> 一次更新所对应的有效信息规模。

## 4.4 梯度累积的核心思想，其实非常朴素

它的本质可以用一句话说完：

> 如果一次放不下大 batch，就把它拆成多个更小的 micro batch，分别做前向和反向，先把梯度攒起来，等攒够了再统一更新一次参数。

例如你理想中想要：

```text
effective batch size = 16
```

但显存只允许：

```text
micro batch size = 2
```

那么你可以：

- 先处理第 1 个 micro batch
- backward，但先不 `optimizer.step()`
- 再处理第 2 个 micro batch
- 再 backward
- …
- 一共累积 8 次
- 最后才做一次参数更新

这样从优化器视角看，就近似于：

> 这次更新综合吸收了 16 条样本的信息。

## 4.5 为什么它叫 accumulation

因为在大多数深度学习框架里，梯度默认会累加在参数的 `.grad` 上，而不是每次 backward 都自动清零。

这意味着如果你不立刻 `zero_grad()`，那么：

- 第一个 micro batch 贡献一部分梯度
- 第二个 micro batch 再把自己的梯度加上去
- 第三个、第四个继续往上叠

直到你决定：

- 现在该统一执行一次参数更新了

从数学直觉上看，这很像是先把多个小批次的梯度求和或求平均，再交给优化器。

## 4.6 micro batch、accumulation steps 和 effective batch 的关系

这是整个主题的计量核心。

### 4.6.1 `micro batch size`

表示：

> 一次真正送进设备、完成一次前向和反向的样本数。

它主要受显存约束。

### 4.6.2 `gradient accumulation steps`

表示：

> 连续处理多少个 micro batch 后，才执行一次 `optimizer.step()`。

它决定你把数据处理节拍与更新节拍拉开了多少。

### 4.6.3 `effective batch size`

表示：

> 从一次参数更新的角度看，综合了多少条样本的信息。

在单设备、无额外并行的最朴素情形下：

```text
effective batch size
= micro batch size × gradient accumulation steps
```

如果还考虑序列长度，那么每次更新对应的 token 数大致是：

```text
tokens per update
= micro batch size × sequence length × accumulation steps
```

这就是梯度累积真正改变的地方。

## 4.7 为什么梯度累积特别适合 6GB 这种受限显存环境

受限显存环境的核心矛盾是：

- 你想让一次更新更“厚”
- 但设备一次装不下这么多数据

梯度累积恰好在这两者之间搭桥。

### 4.7.1 第一，它不要求你放弃完整训练逻辑

你不需要因为显存小，就把训练目标改成完全不同的东西。

模型、loss、优化器逻辑都可以保持一致，只是把：

- 一次性大批次

改成：

- 多次小批次累积后再更新

### 4.7.2 第二，它让你能更灵活地平衡“放得下”和“更新稳”

显存决定了你单次能塞多少，但 accumulation 让你不必被这个数直接绑死到优化器更新规模上。

### 4.7.3 第三，它是小显存项目最现实的恢复手段之一

对于 6GB 级别设备而言，很多设置本来就很难“一把放下理想 batch”。如果没有梯度累积，你往往只能被迫接受极小的更新规模。

而梯度累积能在不改变任务本质的前提下，把可训练空间明显扩回来。

## 4.8 梯度累积并不是“免费更大 batch”

这一点必须尽早说清楚。

很多介绍会让人觉得：

> 累积以后就等价于白拿一个更大的 batch。

这太乐观了。

梯度累积当然非常有用，但它不是零成本。

### 4.8.1 代价一：参数更新频率降低了

以前每处理一个 batch 就更新一次参数。

现在你可能要处理很多个 micro batch，才更新一次。

这意味着：

- 同样数量的样本处理下来，真正的 optimizer step 变少了
- 如果你按 step 计学习率调度，就必须重新理解这个“step”

### 4.8.2 代价二：每次更新的等待更久

从 wall-clock 角度看，你要做更多次前向 / 反向，才能得到一次参数更新。

也就是说，它不是无代价增大 batch，而是：

> 用更多串行小步计算，换来更大的有效更新规模。

### 4.8.3 代价三：日志和训练口径更容易混乱

如果你分不清：

- micro step
- optimizer step
- tokens per update

就会很容易误读：

- 学习率调度进度
- loss 记录频率
- checkpoint 间隔

### 4.8.4 代价四：并不总是与“一次性真大 batch”完全等价

在很多 LLM 训练设定中，它可以很好近似大 batch，但仍可能有细微差别，来源包括：

- dropout 随机性
- 数据排列差异
- 数值舍入路径
- 某些层或实现细节

所以更准确的说法是：

> 梯度累积通常能近似恢复更大的更新规模，但不应被神化成“完全零差异复制一个大 batch”。

## 4.9 为什么“更大的有效 batch”常常会让训练更平稳

这里的“更平稳”不是说 loss 从此毫无波动，而是指：

> 单次更新方向更少被少量样本偶然性主导。

如果一次更新前只看很少样本，那么：

- 某一小批次恰好很难或很怪
- 梯度就会明显偏向这批样本的偶然特征

而如果一次更新综合了更多样本，平均效果会更强，梯度方向通常会更稳一些。

这也是为什么很多训练讨论里，大 effective batch 往往与：

- 更平滑的曲线
- 更可控的学习率区间

联系在一起。

当然，稳定不等于一定更好。太大的 batch 也会带来自己的问题，但对受限显存的小项目来说，先从“极小更新规模带来的高噪声”中解放出来，往往更紧迫。

## 4.10 一个具体例子：理想 batch 放不下时到底发生了什么

假设你的目标设置是：

```text
batch = 16
seq_len = 256
```

可设备实际只能承受：

```text
micro batch = 2
seq_len = 256
```

如果你强行不用梯度累积，那么：

- 每次更新只基于 2 条样本
- 有效更新规模就是 2

如果你改用：

```text
micro batch = 2
accumulation = 8
```

那么你虽然每次设备仍只处理 2 条样本，但：

- 8 次 micro batch 后再更新一次
- 从更新视角看，相当于整合了 16 条样本

这就是梯度累积最核心的价值。

## 4.11 为什么梯度累积会直接影响你怎么看学习率

前一章已经讲过，学习率不能脱离更新节奏单独理解。

一旦引入梯度累积，这个道理会变得更明显。

因为此时“step”至少有两种：

- micro batch 处理步
- optimizer 更新步

而多数学习率调度真正绑定的是：

> optimizer step

这意味着如果你改变了 accumulation steps，就可能同时改变：

- 参数更新频率
- warmup 进度含义
- 同样 global step 对应的数据量

所以调梯度累积时，绝不能把学习率理解冻结不动。

## 4.12 为什么梯度累积会和序列长度一起被共同考虑

在语言模型里，显存压力最常由两个旋钮共同决定：

- `micro_batch_size`
- `sequence_length`

长序列会显著增加每个样本的成本。

所以很多时候，你想要的并不是单纯“把 batch 弄大”，而是要在三件事之间平衡：

- 每次设备能放多少条样本
- 每条样本多长
- 每次更新总共想吸收多少 token

梯度累积之所以重要，就是因为它允许你：

> 在不牺牲目标序列长度的前提下，继续扩大每次更新的总信息量。

如果没有它，你常常只能在：

- 序列长度
- 更新规模

之间做更痛苦的直接取舍。

## 4.13 实现梯度累积时，最重要的顺序是什么

这里不展开具体项目代码，只讲最核心的逻辑顺序。

一个典型的累积流程大致是：

1. 清空旧梯度
2. 取一个 micro batch
3. 前向计算 loss
4. 按累积步数对 loss 做适当缩放
5. backward，让梯度加到参数上
6. 先不更新，继续下一个 micro batch
7. 重复到累积次数达到目标
8. 执行 `optimizer.step()`
9. 再清梯度，进入下一轮

这里最常被写错的是：

- 每个 micro batch 后就立刻 `optimizer.step()`
- 忘记处理 loss 缩放
- `zero_grad()` 时机错误

这些都会让“看起来像在累积”的代码，其实没有得到你想要的更新语义。

## 4.14 为什么很多实现会对 loss 做除法

如果你想让累积后的总梯度量级接近“大 batch 平均 loss”的效果，常见做法是：

> 在每个 micro batch 上，把 loss 除以累积步数，再做 backward。

这样经过多次累积后，总梯度量级会更接近“一次性把这些样本放一起求平均 loss”的情况。

如果不处理这一步，累积后的梯度规模可能与预期不一致。

你不必现在就把所有细节都背下来，但要抓住原则：

> 梯度累积不是简单“多 backward 几次”，而是要让多次 backward 组合后对应到你真正想要的更新尺度。

## 4.15 为什么梯度累积会影响日志解读

这是一个很实际的问题。

假设你每 100 个 step 打一次日志，但你说的 step 到底是什么？

如果它指的是：

- micro batch 次数

那么 100 step 可能还没发生多少次真正参数更新。

如果它指的是：

- optimizer step 次数

那么每一步背后已经包含多个 micro batch。

所以一旦用了 accumulation，训练日志就最好明确区分：

- 当前处理到第几个 micro batch
- 当前真正更新到了第几个 global step

否则你很难把 loss、学习率和训练进度正确对应起来。

## 4.16 为什么梯度累积与吞吐是权衡关系

初学者常常只从“能不能放下”角度看 accumulation，但它也会影响训练效率。

因为它把原本可能并行更大的计算，变成了更多次较小的顺序计算。

这通常意味着：

- 真正参数更新的节拍更慢
- 单位时间内的 optimizer step 数减少

所以 accumulation 并不是“越大越好”。

你需要在：

- 显存能承受的 micro batch
- 想要的有效更新规模
- 可以接受的训练时间

之间寻找平衡。

## 4.17 为什么梯度累积不会自动解决所有训练问题

这点同样很重要。

梯度累积能补的是：

- 一次更新前信息量不足的问题
- 显存受限导致的 batch 太小问题

它**不能**自动解决：

- 学习率过大
- 数据有 bug
- 数值路径不稳
- 模型容量不够
- 序列长度本身过长导致的其他问题

所以如果训练异常，不要把 accumulation 当成万能补丁。

它只是训练系统中的一个关键杠杆，不是全部。

## 4.18 为什么在小显存项目里，梯度累积常常比“盲目缩短序列”更值得优先考虑

当显存不足时，有两种常见本能反应：

- 把 batch 砍小
- 把序列长度砍短

这两种办法都可能有效，但它们影响的东西不一样。

砍短序列会直接改变模型一次能看见的上下文范围，这可能影响你真正想训练的能力。

而梯度累积主要是在不改变单条样本语义长度的前提下，调整更新规模。

所以在许多情况下，一个更成熟的顺序是：

1. 先确定目标序列长度是否确有必要
2. 再在这个长度下找能放得下的 micro batch
3. 最后用 accumulation 去恢复有效更新规模

这样你更不容易为了显存，过早牺牲任务本身想学的能力。

## 4.19 一个适合受限显存环境的思考顺序

可以把它整理成一个很实用的三步法。

### 4.19.1 第一步：先找出“放得下的最基本单元”

也就是：

- 当前模型
- 当前序列长度
- 当前精度设置

下，设备一次究竟能承受多大的 micro batch。

### 4.19.2 第二步：再决定你希望一次更新有多“厚”

这里想的是 effective batch，而不是表面 batch。

### 4.19.3 第三步：用 accumulation 把二者接起来

如果理想更新规模大于设备单步承受能力，就通过 accumulation 补足差额。

这个顺序的好处是，它把：

- 设备极限
- 优化目标

明确分开了。

## 4.20 梯度累积和后面章节的关系

这一章并不是孤立的。

它和前后很多主题都直接相连。

### 4.20.1 和学习率、warmup 的关系

改变 accumulation，本质上也在改变更新节奏，所以学习率调度解释要跟着调整。

### 4.20.2 和混合精度的关系

如果 AMP 能让你放下更大的 micro batch，那么 accumulation 策略也可能随之变化。

### 4.20.3 和梯度裁剪的关系

累积后的梯度是在更新前统一进入裁剪与优化环节，因此你需要理解裁剪作用在什么时刻、保护的是什么。

### 4.20.4 和 checkpoint / 日志的关系

一旦有 accumulation，训练记录里“step”的定义就更需要严谨。

所以梯度累积不是单纯显存技巧，而是整个训练系统节奏设计的一部分。

## 4.21 常见误区

### 4.21.1 误区一：梯度累积只是“显存不够时临时救火”

它当然能救火，但它不只是应急方案。

它本质上是在显存受限时，重新组织“数据处理节拍”和“参数更新节拍”的关系。

### 4.21.2 误区二：只要累积了，就完全等价于真实大 batch

通常能近似，但不应神化成绝对无差别。

### 4.21.3 误区三：用了 accumulation，学习率和日志都不用改理解

恰恰相反，accumulation 会直接改变你对 step、warmup 和更新频率的解释。

### 4.21.4 误区四：accumulation 越大越好

太大意味着更新节拍过慢、训练时间拉长、调度口径更复杂。

它是权衡工具，不是无脑拉满按钮。

### 4.21.5 误区五：只要引入 accumulation，训练稳定性问题就会自动消失

它能缓解小更新规模带来的噪声，但不能替代：

- 合理学习率
- 正确数据管线
- 稳定数值路径

## 4.22 本章真正要留下的核心心智模型

把这一章压缩成最核心的一句话：

> 梯度累积的本质，是在显存装不下一次性大 batch 时，把“大更新规模”拆成“多次小处理 + 一次统一更新”。

你要牢牢记住：

- 设备一次能放多少，是 `micro batch` 问题
- 一次参数更新前想综合多少信息，是 `effective batch` 问题
- accumulation 的价值就在于把这两者解耦
- 它用更多串行计算换更大的更新规模
- 它会影响学习率解释、日志口径和训练节奏

## 4.23 本章小结

小显存训练最重要的成熟感，不是会抱怨“显存不够”，而是会把问题重新表达成：

```text
在当前显存上，我一次真正能处理多少？
而我又希望一次参数更新综合多少信息？
```

一旦你会这样思考，梯度累积就不再是神秘技巧，而会变成一个非常自然的系统设计手段。
