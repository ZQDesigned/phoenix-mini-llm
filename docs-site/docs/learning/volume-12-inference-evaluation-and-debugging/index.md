# 卷十二 推理、评估与调试

> 本卷属于第五编“训练、推理、评估与调试”，负责解释模型在真实运行时怎样生成、怎样被评价，以及异常行为应当怎样被系统化诊断。

这一卷讨论的是很多初学者最容易产生错觉的一部分。

最常见的错觉是：

> 训练都已经完成了，剩下的不就是把模型拿来生成文本、看几个指标、碰到问题时调一调参数吗？

这个理解几乎总是过于乐观。

因为训练结束，并不等于理解结束。
一台语言模型真正开始“暴露自己”往往恰恰是在运行时：

- 它为什么是一 token 一 token 地往后写
- 它内部直接给出的到底是 logits、概率还是 token
- 为什么同一个 prompt 换一种采样策略，输出就会明显变样
- 为什么 loss 看起来不差，但生成文本读起来仍然不够自然
- 为什么模型会重复、提前停止、偏题或者陷入模板化
- KV cache 到底缓存了什么，它为什么能提速却不改变语义
- perplexity、验证集 loss、少量样例输出，为什么经常给出不完全一致的信号
- 当模型行为异常时，究竟应该先怀疑 tokenizer、推理循环、训练闭环，还是采样策略

也就是说，这一卷并不是“训练后的补充说明”。

更准确地说：

> 它讲的是同一台语言模型在真实运行时怎样工作、怎样被使用、怎样被评价，以及当它表现异常时怎样被系统地诊断。

## 为什么这一卷必须放在模型主体和训练之后

很多人会问：

> 既然推理这么重要，为什么不更早讲？

原因很简单。

如果你还没有真正理解：

- 文本怎样进入模型
- token 预测目标怎样构造
- attention 与 causal mask 在约束什么
- 一个 decoder-only 模型怎样从 embedding 一路走到 logits
- 训练过程怎样把参数逐步推向更好的区域

那么“推理、评估和调试”对你来说就只会是一堆孤立按钮：

- 这里改 temperature
- 那里开 top-p
- 这里看 perplexity
- 那里开 cache

你也许会知道“按哪个按钮会发生什么现象”，但你不会真正理解：

> 这个按钮到底在改哪一层结构，它为什么会带来现在这种外显行为。

因此，本卷之所以排在这里，不是因为它不重要，而是因为：

> 只有在模型主体与训练主线已经建立之后，运行时行为才会从经验碎片重新变成结构化知识。

## 为什么“会 generate”远远不够

很多框架都会提供现成的生成接口。
这当然很方便。

但如果你把“会用 `generate()`”当作推理理解的终点，后面就会不断在细节上撞墙。

因为你仍然可能说不清：

- `generate()` 在每一步实际拿的是什么输入
- 模型当前到底输出的是全序列 logits 还是最后一步 logits
- greedy 和 sampling 的差别到底在数学上发生在哪里
- 终止条件是模型层面的，还是推理协议层面的
- 采样导致的异常是模型没学好，还是解码策略放大了某种偏差

因此，本卷真正希望建立的不是接口熟悉度，而是三种更长期的能力。

## 第一种能力：把生成看成连续的条件概率决策链

用户看到的是一段逐渐长出来的文本。
但模型内部发生的事情更准确地说是：

1. 给定当前前缀
2. 模型计算当前位置的输出分布倾向
3. 推理协议从这些倾向里选出一个 token
4. 新 token 被追加回上下文
5. 下一轮再在更长前缀上重复同样过程

这条链看起来简单，但它会直接决定你怎样理解：

- prompt 的作用
- 自回归的本质
- 采样策略的地位
- 重复与跑偏是怎样被逐步放大的

如果你始终把生成看成这条连续概率决策链，就不会再把推理看成“模型吐答案”的瞬时动作。

## 第二种能力：把评估看成多种证据的组合，而不是寻找唯一数字

语言模型有一个让初学者很容易焦虑的特点：

> 它很难被单一指标完整描述。

这是因为不同证据在回答不同问题。

例如：

- 训练 loss 更像在回答：在当前目标函数下，模型是否在学习
- 验证 loss 或 perplexity 更像在回答：模型在未见分布上的条件概率是否更合理
- 样例输出更像在回答：在人类阅读体验上，文本是否流畅、相关、少重复
- 极小样本过拟合测试更像在回答：训练链路本身是否连通

这些证据彼此相关，但绝不等价。

如果你只看其中一个，就很容易得出偏差极大的判断。

因此，本卷会反复强调：

> 评估不是找一个能代表一切的神奇数字，而是把不同证据组合起来，判断模型到底在哪一层变好、在哪一层仍然有问题。

## 第三种能力：把调试看成信息流排障，而不是玄学试错

很多初学者在模型输出不对时，第一反应是：

- 再调一点 temperature
- 换个 top-p
- 把学习率改一下
- 再跑一遍看看

这种做法的问题在于，它常常在没有定位问题的情况下就直接开始随机干预系统。

更稳的方式是：

> 沿着信息流去排障。

也就是顺着整台机器的运行路径依次追问：

- 文本到 token 的接口对了吗
- token 到 logits 的前向逻辑对了吗
- logits 到采样分布的变换对了吗
- 采样协议有没有放大模型本身的弱点
- 终止条件和重复控制是否合理
- 指标和样例之间有没有互相矛盾的地方

这是一种更像工程诊断的思路，而不是更像许愿的思路。

## 这一卷在整套主线里的角色

如果说卷十主要在回答：

> 一台 decoder-only 语言模型为什么会长成现在这样，它的主体结构怎样运作？

卷十一主要在回答：

> 这台模型怎样在数据上被训练出来，训练动态又会受到哪些因素影响？

那么卷十二就在回答：

> 当这台模型已经存在并且已经训练过之后，它在运行时究竟怎样一步步生成、怎样暴露问题、怎样被评价与诊断？

这个角色划分非常重要。

因为它提醒你：

- 模型主体
- 训练过程
- 运行协议

虽然彼此紧密相关，但并不是同一层事情。

只有把这三层区分开，你后面看代码时才不会混乱：

- 有些逻辑属于模型定义
- 有些逻辑属于训练循环
- 有些逻辑属于推理和评估协议

## 为什么运行时行为常常比训练曲线更“有手感”

训练时，很多现象都被压缩成了数字：

- loss
- perplexity
- token throughput

而运行时不同。
运行时的很多问题会直接长成人类能感受到的行为：

- 文本突然开始重复
- 句子风格变得奇怪
- prompt 里某种模式被过度放大
- 明明没说结束，模型却很快停了
- 明明 loss 不高，但回答依然很空

这种“有手感”的特性会带来两种相反的危险。

第一种危险是过度相信直觉。

你看到几条输出觉得不好，就立刻认定模型整体很差。

第二种危险是过度相信指标。

你看到验证损失不错，就自动认为模型已经足够好。

更成熟的做法，是承认：

- 运行时行为很重要
- 但它也必须和训练证据、验证证据一起读

这就是卷十二存在的原因之一。

## 为什么语言模型推理天然是“协议层”很重的任务

很多模型任务在推理时比较简单。
例如普通分类模型通常做的事情是：

- 给定输入
- 输出分数
- 取最高类别

语言模型不一样。

因为它的输出不是一次性结束的。
它要不断把上一步选出的 token 再送回模型，形成下一步条件。

这意味着语言模型推理不仅有模型主体，还有一层很重要的外部协议：

- 怎样组织 prompt
- 每一步取哪一位 logits
- 用什么策略选下一个 token
- 何时停止
- 是否缓存历史

这层协议会极大影响外显行为。

因此，你不能只说“模型会生成文本”。
更准确的说法应该是：

> 模型在某种自回归运行协议下生成文本。

## 这一卷的章节推进主线

这一卷不是把推理、评估和调试混着讲。
它会沿着一条非常明确的因果链推进：

1. 先讲生成为什么是一 token 一 token 地展开
2. 再讲 logits 怎样变成下一 token
3. 再讲不同采样策略究竟在改什么
4. 再讲终止条件、重复与退化行为
5. 再讲 KV cache 在加速什么
6. 再讲如何组合 loss、perplexity 与定性样例
7. 最后讲如何系统调试整条链路

这个顺序不是随便排的。

因为只有先理解：

- 模型到底如何生成

你才有可能理解：

- 它为什么会在生成时表现出某些异常

而只有先理解：

- 该怎么正确读取这些异常

你才有可能真正调试它。

## 生成为什么必须先从“自回归”讲起

卷十二的最前面一定要先讲自回归，不是因为这是一个术语，而是因为：

> 自回归决定了语言模型运行时最基本的时间结构。

所谓自回归，不是一个华丽名字。
它最直白的意思就是：

- 下一个 token 的预测依赖于前面已经出现的 token
- 一旦新 token 被选出，它又会成为下一轮历史的一部分

这会带来一些非常重要的后果：

### 第一，推理不是单步判断，而是滚动展开

输出不是一下子全部出现，而是一步一步增长。

### 第二，早期错误会被带进后续上下文

这意味着一次不理想的采样选择可能持续影响后面很多步。

### 第三，推理成本会随着序列增长表现出特定形态

这和后面要讲的 prefill、decode、KV cache 都直接相关。

因此，自回归不是入门名词，而是整卷的第一根主轴。

## prefill 和 decode 为什么要被明确区分

很多初学者第一次学习推理时，会把整次生成看成单一过程。

但从运行时视角看，更有解释力的做法是把它拆成两个阶段：

- prefill
- decode

这两个阶段虽然都在“生成相关”范围内，但它们做的事情不完全一样。

### prefill 在做什么

它更像是在让模型先读懂当前已有前缀，并为后续生成准备初始状态。

### decode 在做什么

它更像是在已有历史基础上逐 token 继续往后写。

为什么这层区分重要？

因为它会直接影响你理解：

- 首 token 延迟从哪里来
- 为什么长 prompt 和长生成长度会呈现不同性能特征
- KV cache 主要在优化哪个阶段的重复计算

所以这不是性能术语，而是运行时结构术语。

## logits 为什么不是“答案”，但又几乎包含了答案结构

很多人说“模型输出文本”，这其实太粗糙了。

模型在每一步真正直接输出的，通常并不是：

- 文本字符串
- token 本身
- 最终选定答案

而是：

- logits

如果不把 logits 讲清楚，后面采样、困惑度、重复问题都会显得像黑箱。

logits 最应该被理解成：

> 模型对候选 token 的未归一化相对偏好。

这意味着：

- 它们已经包含了下一步选择的结构信息
- 但它们还不是最终概率
- 也还不是最终 token

在这之后，推理协议才会决定：

- 是否先做 softmax
- 是否调整温度
- 是否裁剪候选集合
- 是否用贪心而不是采样

因此，logits 是模型主体和推理协议的交界面。

## 为什么采样策略会明显改变“模型人格”

很多初学者第一次调整采样参数时，会有一种很强烈的直观感受：

> 好像不是同一个模型了。

这种感觉并不奇怪。

因为采样策略并不是在做无关紧要的后处理。
它实际在改变：

- 你怎样使用模型给出的分布

例如：

- greedy 会把分布压成最保守的单一路径
- 更高的 temperature 会让分布更平，增加低概率候选被选中的机会
- top-k 会硬裁剪候选数量
- top-p 会按累计概率质量动态裁剪候选集合

这意味着同一组 logits，在不同解码策略下，完全可能长成不同风格的文本。

因此，采样策略既不是魔法，也不是装饰。
它是在决定：

> 模型潜在概率空间中的哪一类轨迹更容易真正显现为文本。

## 终止条件为什么也是推理协议的一部分

初学者常常会把“何时停”理解成一个不太重要的小条件。
例如：

- 生成到长度上限就停
- 遇到 EOS 就停

但这实际上也是推理协议的一部分。

因为停止条件会直接决定：

- 模型有没有机会继续展开
- 某些冗长或重复问题会不会被放大
- 生成是否会出现突兀截断

而且“停得不对”经常会被误判成“模型不会写”。

例如：

- 模型本来还能继续合理生成，但你过早停了
- 模型已经在重复空转，但你没有及时停

因此，停止条件不是最后顺手加的边界，而是：

> 推理循环设计的一部分。

## 重复为什么是最值得认真理解的运行时症状之一

语言模型最典型的坏行为之一就是重复。

它之所以重要，不只是因为输出难看，而是因为：

> 重复通常暴露的是模型分布、采样策略、上下文状态和终止协议之间的复杂相互作用。

重复可能来自：

- 模型本身在局部分布上过于尖锐
- greedy 让单一路径被无限强化
- 温度设置让探索过弱
- 终止条件没有及时切断退化循环
- 训练数据或目标结构里存在某些模式偏置

因此，重复不是一个“调一点随机性就好了”的简单问题。

它更像一个窗口，透过它你能看到：

- 训练偏差
- 分布形状
- 解码策略
- 停止协议

在同一行为上共同留下的痕迹。

## KV cache 为什么不是“缓存了理解结果”

KV cache 经常被说得很神秘。

最常见的模糊说法是：

- 它缓存了模型对上下文的理解

这句话在直觉上不完全错，但不够精确。

更准确的说法是：

> KV cache 缓存的是历史 token 在 attention 里会反复用到的 key/value 张量表示，从而避免在每一步 decode 时重复计算整段历史。

这一定义非常关键，因为它说明：

- cache 主要是在节省重复计算
- 它不会改变模型语义目标
- 它是在优化运行协议，而不是在改变模型逻辑

也就是说：

- 没有 cache，模型仍然可以生成同样的东西，只是更慢
- 有了 cache，模型不该变“更聪明”，而应当主要变“更高效”

理解这一点，会帮你避免把性能机制和语义机制混为一谈。

## 为什么评估一定要把“数字证据”和“文本证据”放在一起

这是很多语言模型初学者最容易长期摇摆的地方。

一类人非常信指标。
他们倾向于说：

- 验证 loss 降了，说明模型就是更好了

另一类人非常信样例。
他们倾向于说：

- 我读起来感觉不行，所以模型肯定不行

这两种极端都不够稳。

因为数字证据和文本证据各自有长处，也各自有盲区。

### 数字证据的长处

- 可比较
- 可记录
- 可追踪趋势
- 不容易被单条样例偶然性误导

### 数字证据的盲区

- 它未必完整覆盖人类感知质量
- 它可能掩盖局部风格、重复、模板化等问题

### 文本证据的长处

- 它能直接暴露读者真正关心的体验
- 它能抓住局部异常和风格问题

### 文本证据的盲区

- 样本量太少时很容易误判
- 很容易被 prompt 选择和解码策略影响

因此，本卷会反复坚持一个原则：

> 评估语言模型时，任何单一证据都不够，真正稳妥的是把训练指标、验证指标和定性样例联合起来看。

## 困惑度为什么重要，但不能被神化

perplexity 是语言模型里非常常见的指标。

它之所以重要，是因为它和条件概率质量有非常直接的联系。
直观上说，它在回答：

> 模型面对真实下一个 token 时，平均有多“迷惑”。

一个更低的困惑度，通常意味着：

- 模型给真实 token 分配了更合理的概率

这当然很重要。

但如果把它神化成语言模型唯一总分，又会出问题。

因为一个模型可能：

- perplexity 有改善
- 但生成时仍然显得过保守、重复或风格僵硬

为什么？

因为：

- 训练/验证分布上的平均概率质量
- 人类在开放式生成里的主观阅读体验

并不是完全同一件事。

所以，困惑度应当被认真看待，但不能被当成唯一裁判。

## 极小样本过拟合测试为什么在调试里如此有价值

当你怀疑整条训练链路可能有问题时，一个非常强的诊断方法通常是：

- 让模型去过拟合一小撮极小样本

为什么这个测试重要？

因为它在问一个比“模型最终效果如何”更基础的问题：

> 在最简单的可控环境里，这台训练系统到底能不能把误差信号真正吃进去？

如果连极小样本都过拟合不了，那么问题大概率在：

- 数据目标构造
- 前向逻辑
- loss 计算
- 反向传播
- 优化步骤

而不是在“模型规模还不够”这种更高层解释上。

因此，这个测试很像是训练链路的通断检测。

## 为什么调试语言模型要优先沿着链路拆解，而不是先调超参数

超参数当然重要。
但在真正的排障里，先调超参数往往是最低效的起手式之一。

更稳的顺序通常是：

1. 先确认数据接口是否对
2. 再确认目标构造是否对
3. 再确认前向张量流是否对
4. 再确认 loss 与梯度是否合理
5. 然后再看推理协议
6. 最后才去做更细致的超参数调整

原因很简单。

如果链路早期已经错了，那么你后面再怎么调：

- temperature
- top-k
- 学习率
- weight decay

都只是在错误地基上做花式尝试。

卷十二最后几章真正要训练的，是这种“先定位层，再出手”的纪律。

## 这一卷为什么对初学者尤其重要

初学者最容易出现的一种状态是：

- 代码大体写出来了
- 训练也跑了一会儿
- 似乎能生成点东西

于是就会产生一种危险的半懂感：

> 我差不多已经把模型做出来了。

但只要你稍微深入一点，就会立刻暴露很多问题：

- 这个输出到底算好还是不好
- 为什么加个采样温度就像换了个模型
- 为什么看着还能写字，但一到长输出就开始重复
- 为什么指标变化和主观观感不是同速的
- 为什么一旦出问题，根本不知道该从哪里查

这正说明：

> 训练完成和真正掌握运行时理解之间，还有一段很长的距离。

卷十二就是在补这段距离。

## 读这一卷时最值得保持的三个问题

如果你想避免把这一卷读成“经验参数大全”，建议始终带着下面三个问题来读。

### 第一，这个现象发生在模型主体里，还是发生在运行协议里

例如：

- 重复到底是模型分布问题，还是 greedy 放大了它
- 提速到底来自 cache，还是来自模型更短

### 第二，这个指标到底在衡量什么，不在衡量什么

例如：

- perplexity 擅长读概率质量
- 但不等于完整的人类阅读体验

### 第三，如果现在结果不对，最早出现异常的链路位置在哪里

这个问题会逼你从随机试错转向系统排障。

## 这一卷之后，读者应该获得什么能力

理想状态下，走完这一卷之后，你应当逐步获得至少四种能力。

### 第一种：能把生成讲成连续概率决策过程

你不再只是说“模型在生成”，而能说清：

- 历史前缀
- logits
- 分布
- 采样
- 新 token 回流

这条链是怎样循环的。

### 第二种：能区分模型问题和解码问题

你会更清楚：

- 某些现象源于模型没学好
- 某些现象源于推理协议的使用方式

### 第三种：能组合使用训练指标、验证指标与文本样例

你不再执着于单一数字或单一观感，而会综合判断。

### 第四种：能用链路拆解的方法去调试

这意味着一旦结果异常，你不会只会说：

- “再试试别的参数”

而会开始有条理地定位：

- 输入
- 目标
- 前向
- 分布
- 采样
- 停止
- 指标

分别是否合理。

## 本卷之后去哪里

读完卷十二之后，你最自然的下一步通常是进入：

- [卷十三 从小模型走向更大的模型世界](/learning/volume-13-where-to-go-next/index.md)

因为此时你已经不仅理解：

- 模型是怎样被建起来的
- 模型是怎样被训练出来的

也开始理解：

- 模型是怎样在真实运行时被使用和诊断的

这会让你更有能力去理解：

- 为什么更大的模型在训练、推理和部署上会遇到新的现实约束
- 为什么微调、量化、对齐和部署不是完全新学科，而是同一条主线在更复杂环境下的继续展开

## 小结

卷十二真正要建立的是这样一个认识：

> 语言模型训练完之后，并没有“自动变成一个你已经懂了的系统”。相反，它会在推理、采样、缓存、停止、指标和异常行为里，第一次完整暴露自己作为一台运行中机器的面貌。

只有当你能把：

- 自回归生成
- logits 到 token 的变换
- 采样策略
- 停止条件
- KV cache
- perplexity 与样例输出
- 系统化调试

讲成一条连续主线时，你才算真正开始掌握：

> 一台小型语言模型在“活着运行”时到底是什么样子。
