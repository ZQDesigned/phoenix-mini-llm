# 07. 困惑度、验证集与定性样例怎样一起评估

上一章我们已经建立了一个关键判断：

> loss 很重要，但它只描述系统的一部分真相。

既然如此，接下来的问题就变成：

> 那么一个小型语言模型到底应该怎样被评估，才不至于被单一信号骗过去？

这不是一个“再加几个指标”的问题，而是一个评估哲学问题。

因为语言模型同时具有两种身份：

- 它是一个概率分布预测器
- 它也是一个会连续生成文本的行为系统

概率预测器和行为系统都需要评估，而且评估方式不能完全相同。

这一章我们要建立的是一套适合学习项目、也适合后续工程实践的综合评估框架。它不会追求一个神奇总分，而会帮助你回答四类更本质的问题：

1. 模型在平均 next-token 预测上是否真的变强了？
2. 模型在不参与训练的数据上是否仍然表现更好？
3. 模型滚动生成时的行为是否更自然、更稳定、更少重复？
4. 我该依据哪些信号去选择 checkpoint、判断训练是否值得继续？

## 7.1 评估之前，先明确“你到底在问什么”

很多评估混乱都来自一个源头：

> 你没有先定义问题，就急着找指标。

不同问题，对应的证据并不一样。

### 7.1.1 如果你问的是“模型有没有学到数据分布”

那你应重点看：

- validation loss
- perplexity
- 训练曲线形态

### 7.1.2 如果你问的是“模型写出来的文本像不像样”

那你必须看：

- 固定 prompt 样例
- 结束行为
- 重复程度
- 结构与信息推进

### 7.1.3 如果你问的是“模型适不适合某个具体应用”

那你还需要：

- 目标任务风格样例
- 协议或格式正确率
- 长度与延迟等运行时指标

所以成熟评估的第一步不是算数，而是分清问题。

## 7.2 为什么验证集是语言模型评估的第一根支柱

如果没有验证集，训练过程很容易陷入一种自我陶醉：

- 训练 loss 在降
- 训练样例看起来越来越熟
- 你以为模型在真正变强

可它也可能只是越来越会记住训练集。

验证集的核心作用，就是提供一批：

> 不参与当前参数更新，但来自相近目标分布的数据。

然后你问：

```text
模型在这些“没见过”的样本上，平均预测也变好了吗？
```

如果答案是肯定的，说明模型更可能是在学习可迁移规律，而不只是机械记忆。

## 7.3 一个好验证集需要满足什么

验证集不是“随便切 10% 出来”就万事大吉。

对语言模型而言，你至少要关心三件事。

### 7.3.1 分布相近

如果训练集主要是百科说明文，验证集却大多是论坛碎片对话，那么验证 loss 的解释会变得很混乱。

你无法知道：

- 是模型泛化差
- 还是两边任务本来就不是一回事

### 7.3.2 没有数据泄漏

不要让：

- 完全重复样本
- 同一文档被切成高度重叠片段
- 几乎只是改了标点的版本

同时出现在训练与验证中。

否则验证集会被“污染得过于容易”，你看到的 improvement 会虚高。

### 7.3.3 足够稳定

如果验证集太小，单次评估波动会很大。

你会看到：

- checkpoint A 好像更优
- 下一次又不明显

这时不是模型神秘，而是测量噪声太大。

对学习项目而言，不必追求超大验证集，但至少要保证：

> 它足以反映主要数据风格，而不是被少数样本偶然左右。

## 7.4 validation loss 到底在告诉你什么

validation loss 最直接的含义是：

> 模型在未参与训练更新的数据上，对真实下一个 token 的平均负对数概率。

更口语一点说，它在问：

> 对于“没拿来更新参数”的文本，模型平均还有多惊讶？

如果 validation loss 在下降，通常意味着：

- 模型对相近分布的局部预测更准了
- 这种进步没有被限制在训练样本内部

这非常重要，因为它说明训练带来的提升更可能具有泛化性。

但别忘了上一章的结论：

> 它仍然主要是在测量局部 next-token 预测质量，而不是直接测量长段滚动行为。

## 7.5 perplexity 是什么，为什么它常被一起报告

困惑度（perplexity）本质上是对 loss 的另一种表达。

如果使用自然对数交叉熵，那么：

```text
perplexity = exp(loss)
```

它可以被粗略理解为：

> 模型平均相当于在多少个同样可能的候选中做选择。

如果 perplexity 更低，通常意味着模型更不“困惑”，对真实下一个 token 的分布更集中。

这也是为什么它在语言模型论文和工程日志里如此常见。

不过你需要注意几件事。

### 7.5.1 perplexity 仍然是基于局部概率的指标

它没有逃离 loss 的范畴，只是换了一种更直观的尺度。

### 7.5.2 perplexity 不能跨不同 tokenization 随便横比

如果两个模型：

- token 切分方式不同
- 词表不同
- 评估语料切分方式不同

那么 perplexity 数字不能直接拿来做简单绝对比较。

### 7.5.3 perplexity 很适合纵向比较同一项目

在同一套：

- tokenizer
- 数据处理
- 验证集
- 损失定义

都不变的前提下，perplexity 很适合观察训练趋势与 checkpoint 变化。

所以在学习项目里，最好把它视为：

> 同一实验体系内部的稳定纵向指标。

## 7.6 为什么只看 validation loss / perplexity 仍然不够

即使你的验证指标很漂亮，你还是可能在样例上看到：

- 重复
- 拖尾
- 风格不对
- 结构混乱
- 过早停止

原因就在于：

- 验证指标主要读的是“概率层面”
- 用户真正感受的是“行为层面”

这就像一个学生在选择题上成绩稳定上升，但一到开放题仍然组织混乱。

你不能因此说选择题成绩没用，但你也不能用它代替开放题表现。

所以语言模型评估必须引入第二根支柱：

> 固定 prompt 下的定性样例评估。

## 7.7 什么叫“固定 prompt 样例”

它指的是：

> 你准备一组相对稳定、可重复使用的提示，在不同 checkpoint 或不同设置下反复用它们生成样例并比较。

这听起来很朴素，但价值非常高，因为它把“随手试一条”的主观印象，提升成一种较有秩序的观察方法。

固定 prompt 的价值在于：

- 减少评估输入的随意性
- 便于纵向比较不同 checkpoint
- 能专门覆盖你关心的行为能力

## 7.8 固定 prompt 不应该只是一组“我喜欢的问题”

如果评估 prompt 只是你随手想到的几句，那它很快会变成一种情绪化测试。

更好的做法是把 prompt 组织成类型集合。

例如：

- 事实解释类
- 步骤说明类
- 短续写类
- 长续写类
- 列表组织类
- 总结收尾类
- 格式输出类

这样你观察到的就不只是“这个模型今天写得顺不顺”，而是：

> 它在哪些行为维度上更稳，哪些维度上还容易崩。

## 7.9 定性样例到底要看什么

不要只看“我喜不喜欢”。最好固定几个观察轴。

### 7.9.1 局部流利度

看：

- 语法是否顺
- 搭配是否自然
- 明显断裂是否减少

### 7.9.2 信息推进

看：

- 每句话是否带来新信息
- 是否只是在换说法重复
- 是否出现大量空泛套话

### 7.9.3 结构感

看：

- 开头是否进入主题
- 中间是否有层次
- 结尾是否收束

### 7.9.4 停止与重复

看：

- 是否容易拖尾
- 是否在该停时停
- 是否出现局部或全局重复

### 7.9.5 对 prompt 的响应性

看：

- 是否真的回答了问题
- 是否遵守了篇幅或格式约束
- 是否抓住了提示里的重点

一旦你用这些轴去看样例，评估就会从“感觉好像可以”变成更有判断力的阅读。

## 7.10 为什么定性样例必须“固定协议”

如果你想把样例评估变成可靠信号，而不是一次次情绪波动，就要尽量控制评估协议。

至少要固定下面几件事：

- prompt 集合
- 解码策略
- 最大生成长度
- 随机种子或多次采样规则
- 输出记录方式

否则你看到的变化可能来自：

- prompt 换了
- 温度换了
- top-p 换了
- 这次随机恰好抽到好答案

而不是模型本身真的进步或退步。

## 7.11 单条样例不够，最好观察“同题多次生成”

尤其在采样生成下，单条样例的方差很大。

更稳的方法包括：

- 同一 prompt 生成多次
- 观察最差、平均、最好表现
- 看失败模式是否一致出现

如果某个 checkpoint 偶尔能写出特别好的一次，但大多数时候都不稳，你对它的信任应该有限。

反过来，如果另一个 checkpoint 平均表现都更稳，即使最佳样例没那么惊艳，它往往更适合实际使用。

这也是评估里一个非常成熟的观念：

> 稳定性本身就是质量的一部分。

## 7.12 为什么“结束行为”值得单独成为一个评估维度

在很多初学项目里，人们只看：

- 会不会写
- 写得顺不顺

但忽略了：

- 会不会在该停时停

而停止行为其实非常关键。

你应至少观察：

- 模型会不会自然产生 `EOS`
- 是否经常拖到长度上限
- 是否容易在结尾重复
- 是否会过早收尾导致回答不完整

停止行为差，往往意味着：

- 数据边界不清
- 收尾模式学得不够
- 解码过于保守或过于发散

它不是细枝末节，而是生成系统完整性的核心部分。

## 7.13 为什么“重复”也不能只当作主观抱怨

重复不是一句“这个模型有点啰嗦”就结束的事。

它值得成为专门的评估维度，因为它常常暴露：

- 长程组织能力不足
- 局部高频模板主导
- 停止机制弱
- 采样设置不合理

在固定 prompt 评估中，你可以专门记录：

- 词级重复
- 句法模板重复
- 语义重复
- 是否出现尾部循环

这些现象往往比单纯的“流利度”更早暴露模型的真实上限。

## 7.14 第三根支柱：面向失败模式的针对性测试

除了平均指标与固定样例，还可以再加一类测试：

> 专门针对已知脆弱点设计的任务。

例如：

- 要求严格输出固定格式
- 要求在多段解释后自然总结
- 要求短答，不允许拖尾
- 要求维持前后术语一致
- 要求在较长 prompt 后仍能抓住主问题

这类测试不像 validation loss 那样“全面平均”，但它能精准探查：

> 你最担心模型在哪些地方掉链子。

在学习项目里，这类测试的价值尤其高，因为它能帮助你快速定位小模型的典型失败边界。

## 7.15 怎样把三类证据拼成一个整体判断

到这里，我们已经有三类证据：

1. validation loss / perplexity
2. 固定 prompt 定性样例
3. 面向失败模式的针对性测试

接下来最重要的问题是：怎样把它们联合起来读，而不是互相打架？

一个实用做法是把它们看成三层视角。

### 7.15.1 第一层：平均概率视角

回答：

```text
模型对相近分布的平均 next-token 预测是否在改善？
```

这主要由 validation loss / perplexity 提供。

### 7.15.2 第二层：开放生成视角

回答：

```text
模型在真实滚动生成时，文本读起来怎样？
```

这主要由固定 prompt 样例提供。

### 7.15.3 第三层：边界与脆弱点视角

回答：

```text
模型在我最关心的脆弱任务上，是否容易失败？
```

这主要由针对性测试提供。

当三层证据一起看时，你的判断会稳很多。

## 7.16 几种常见信号组合的解读

把最常见的组合直接列出来，会帮助你后面更快诊断。

### 7.16.1 validation loss 在降，样例和针对性测试都在变好

这是最理想的情形。

说明：

- 局部概率建模在进步
- 这种进步成功传导到滚动文本行为

### 7.16.2 validation loss 在降，样例只略有改善，针对性测试仍很脆弱

这通常表示：

- 模型先学会了局部流利度
- 但长程结构或特定能力仍弱

这在小模型中很正常。

### 7.16.3 validation loss 在降，样例开始更重复

说明你需要重点查：

- 数据模板性
- 停止机制
- 解码保守程度

而不是简单把训练全部否定掉。

### 7.16.4 validation loss 基本持平，但样例更稳、更自然

这并不罕见。

可能是：

- 某个 checkpoint 在整体平均指标上差不多
- 但停止和结构行为更适合你的应用场景

这时未必需要机械追最低 loss。

### 7.16.5 validation loss 继续变好，但目标任务风格反而更偏

说明验证集与目标场景之间存在不完全一致。

这时要重新审视：

- 验证集代表性
- 目标任务评估集合
- 是否需要更贴近应用的验证子集

## 7.17 什么时候应该停止训练，什么时候还值得继续

这也是评估框架服务于决策的地方。

如果你看到：

- validation loss 已长期不再改善
- 固定 prompt 样例也基本无提升
- 失败模式没有明显缓解

那继续训练通常收益有限。

反过来，如果：

- validation loss 还在稳步下降
- 样例仍在从“局部顺”向“整体顺”过渡
- 针对性测试中的错误在逐步减少

那继续训练往往仍然有价值。

换句话说，是否继续训练，不应只看单一曲线，而要看：

> 多个信号是否还在共同指向“系统仍在学习你关心的能力”。

## 7.18 为什么 checkpoint 选择最好写成“评估记录”，而不是凭印象

很多人训练到后面，会凭记忆说：

- “我感觉 8k step 的样例挺不错”
- “好像 12k step loss 更低”

这很容易出错。

更好的做法是为每个关键 checkpoint 记录：

- validation loss
- perplexity
- 固定 prompt 样例
- 停止表现
- 重复表现
- 针对性测试通过情况

这样你在回头选择时，依据的是一组可复查证据，而不是模糊印象。

这不仅帮助你选模型，也帮助你逐渐形成“怎样读训练过程”的能力。

## 7.19 初学阶段最值得建立的评估习惯

如果你不想把评估做得过于复杂，可以至少先建立下面几个习惯。

第一，始终保留一个干净的验证集，不让它参与训练。

第二，固定一组 prompt，覆盖不同长度、不同风格和不同结束难度。

第三，固定评估协议，不要今天贪心、明天高温、后天又换 top-p，然后拿结果横比。

第四，把停止和重复单独记下来，不要只笼统地说“好像有点怪”。

第五，重要 checkpoint 都留记录，避免完全凭感觉回忆。

这些习惯看似朴素，但它们会决定你后面能不能从训练中真正学到东西。

## 7.20 本章应该形成的评估心智模型

这一章最核心的心智模型是：

> 评估语言模型，不是在寻找一个唯一的最终数字，而是在为不同层面的能力收集互补证据。

其中：

- validation loss / perplexity 负责读平均局部预测
- 固定 prompt 样例负责读滚动文本行为
- 针对性测试负责读脆弱边界和失败模式

三者一起，才构成一个足够可靠的判断框架。

## 7.21 本章小结

把这一章压缩成一句话：

> 好的语言模型评估，不是“只看一个最权威指标”，而是让概率视角、行为视角和失败模式视角彼此校验。

如果你能建立这套框架，后面无论是继续训练、选择 checkpoint，还是分析某次异常样例，你都不容易被偶然现象误导。

下一章我们继续往前走，把所有这些评估与观察方法落到最有操作性的环节：

> 当训练或生成出现异常时，怎样用“极小样本过拟合”和系统化排错，把问题真正缩小到可验证范围。
