# 05. KV cache 到底缓存了什么

## 这一章真正想拆掉的误解是什么

很多人第一次听到 `KV cache`，会把它记成一种推理优化黑科技：

- 开了它会更快
- 不开它会更慢
- 大概和 attention 有关

这种记法不算错，但太浅。

如果你只把它当成一个“加速开关”，后面很容易一直说不清下面这些问题：

- 它到底缓存的是什么张量，而不是笼统地“缓存上下文”
- 为什么缓存的是 `K` 和 `V`，而不是 `Q`
- 为什么它不改变模型语义，却会明显改变推理速度
- 为什么它主要在 decode 阶段有价值，而不是一切场景都同样重要
- 为什么上下文越长、输出越长，这个优化越关键

所以这一章的目标不是告诉你：

- 打开 cache 会更快

而是要把它重新讲成：

> 自回归生成在计算结构上必然会逼出来的一种复用机制。

只有当你理解这一点，KV cache 才不会像一条需要死记的工程口诀。

## 先回到最朴素的问题：为什么生成会越写越慢

如果你只从用户视角看语言模型，很容易忽略一个事实：

> 生成并不是一次性写完全部文本，而是一步一步地，在越来越长的历史上重复执行模型。

这听起来简单，但计算上会立刻带来一个问题：

- 每新增一个 token，模型都要再次处理更长的上下文

如果你不做任何复用，那么生成第 1 个新 token、生成第 20 个新 token、生成第 200 个新 token，虽然每次只新增加了一步输出，但它们都涉及：

- 对历史上下文的再次利用

问题就在这里。

历史真的需要每一步都从头重算吗？

`KV cache` 的全部意义，正是围绕这个问题展开。

## 先重新把推理过程分成两段：prefill 和 decode

理解 KV cache 之前，最有用的切法是把推理流程分成两段：

- prefill
- decode

如果这两段不分开，你会很难看清 cache 到底在帮哪一段省事。

### prefill 是什么

`prefill` 指的是：

> 把当前已有的整段输入前缀一次性送进模型，让模型先建立出当前时刻需要的内部表示。

例如用户给了一个 300 token 的 prompt，那么在真正开始生成第一个新 token 之前，模型得先把这 300 token 过一遍。

这一步会做很多事：

- embedding
- 多层 self-attention
- 多层 FFN
- 产生每层每个位置的中间表示
- 最终得到最后一个位置可以用于预测下一 token 的状态

这就是 prefill。

### decode 是什么

`decode` 指的是：

> 在已有上下文的基础上，每次只新增一个位置，并据此生成一个新 token，然后再继续下一步。

也就是说：

- prefill 解决“先把前缀读进去”
- decode 解决“从现在开始一 token 一 token 地往后写”

KV cache 之所以关键，主要就是因为 decode 阶段具有非常强的“重复利用历史”结构。

## 不开缓存时，decode 到底在浪费什么

最容易建立直觉的方法，是先想象完全不开 cache 的朴素生成。

假设：

- prompt 长度是 100 token
- 模型已经生成了 20 个 token

那么当前上下文总长度就是 120。

如果你要生成第 21 个 token，朴素做法是：

1. 把这 120 个 token 全部送进模型
2. 在每一层为它们重新计算需要的表示
3. 取最后一个位置的 logits
4. 选出新的 token

接着要生成第 22 个 token，你又会：

1. 把 121 个 token 再全部送进模型
2. 再次为前 120 个旧位置重算同类中间量
3. 再取最后一个位置的 logits
4. 再选一个 token

你很快就会发现一种非常明显的浪费：

> 新增的只有 1 个位置，但大量旧位置相关计算被一遍又一遍地重复执行。

这不是一点小冗余。
它是自回归朴素实现里的结构性重复劳动。

## 为什么“旧历史其实大部分不用重算”这件事在 causal attention 里成立

要理解这一点，必须重新回到 decoder-only attention 的因果结构。

在 causal self-attention 里，第 `t` 个位置只能看到：

- 自己左边的历史
- 和自己本身

不能看到未来位置。

这意味着，一旦某个历史位置已经存在，它面对自己的可见历史并不会因为未来新增 token 而改变。

例如：

- 第 17 个位置在第一次被处理时，只能看 `1..17`
- 后面无论第 18、19、20 个位置出现什么
- 第 17 个位置自己的内容没有变
- 第 17 个位置在当时形成的某些供未来读取的表示，也不需要因为未来新增而重新定义

更直接地说：

> 对未来位置而言，旧位置的主要职责不是“重新为自己做决定”，而是“作为历史记忆单元被未来读取”。

只要看见这句话，cache 的空间就出来了。

## 再回顾一次 attention：为什么这里偏偏是 K 和 V 值得缓存

虽然前面已经学过 attention，但这里必须从运行时角度再重新看一遍。

对某一层、某一个位置来说，attention 粗略可以理解成三步：

1. 当前位置生成一个 `query`
2. 所有可见位置各自提供一个 `key`
3. 所有可见位置各自提供一个 `value`

然后当前位置会做：

- 用自己的 `query` 去和所有历史 `key` 计算匹配程度
- 得到一组注意力权重
- 用这些权重对所有历史 `value` 做加权汇总

如果用更口语一点的说法：

- `query` 像“我现在想找什么”
- `key` 像“每个历史位置给自己贴的索引标签”
- `value` 像“每个历史位置真正携带的可提供信息”

于是，当新位置要读取历史时，它最需要的其实就是：

> 整段历史已经准备好的 key/value 表。

这正是缓存要抓住的对象。

## KV cache 的最精确直觉：缓存的是“历史可被读取的索引与内容”

一旦回到上面的 Q/K/V 角色分工，你就会发现：

- 未来位置每来一次，都要提出一个新的读取问题
- 但历史位置作为“被读取者”的标签和内容，往往可以复用

因此，`KV cache` 最值得记住的定义是：

> 它缓存的是每一层、每个历史位置产生出来、供未来位置重复读取的 key 和 value 张量。

注意这句话里有四个关键限定：

- 是“每一层”的
- 是“历史位置”的
- 是“供未来读取的”
- 是 `K` 和 `V`，不是其他一切中间量

只要这个定义站稳，后面很多问题会立刻清楚。

## 为什么缓存的是 K 和 V，而不是 Q

这是接触 KV cache 时最常见、也最应该尽早讲清楚的问题。

如果 `Q`、`K`、`V` 都来自隐藏状态，为什么偏偏只缓存 `K` 和 `V`？

原因不在于：

- `Q` 不重要

而在于：

- `Q` 的职责和复用模式不同

### 历史位置的 query 在未来步骤里没有复用价值

第 50 个位置的 `query` 回答的是：

- “第 50 个位置自己此刻想从它左边读什么？”

可到了第 51 个位置，问题已经变成：

- “第 51 个位置现在想从它左边读什么？”

这是一个新问题。
因此需要的是新的 `query`，而不是第 50 个位置旧的 `query`。

### 历史位置的 key/value 则会被未来反复读取

第 51、52、53 个位置都会问：

- 第 50 个位置和我相关吗
- 如果相关，它能给我什么内容

这正对应：

- 第 50 个位置的 `key`
- 第 50 个位置的 `value`

所以只有 `K` 和 `V` 具备：

- 会被许多未来位置重复消费

这种缓存价值，而 `Q` 没有。

## 为什么通常也不直接说“缓存全部 hidden states 就好”

这也是一个常见直觉。

有人会想：

> 既然 K/V 都来自隐藏状态，为什么不把隐藏状态都缓存起来，到时候再重算 K/V 不就好了？

从纯逻辑上并非完全不可行，但从实际推理路径看，这往往不是最合适的复用边界。

原因有两个。

### 第一，未来位置真正直接需要的是 K/V

在每层 attention 里，新的 query 是要直接和历史 K 匹配，再对历史 V 汇总。

因此，把 K/V 作为缓存边界是最贴近后续计算消费接口的。

### 第二，重复从隐藏状态再投影回 K/V，本身就又引入了重复计算

而 cache 的目的恰恰是：

- 尽量把那些“已经为未来准备好了的可读历史张量”直接留下

所以缓存 K/V，本质上是选择了一个：

- 最直接服务 decode 复用

的中间层。

## 从一个四步小例子，直观看懂 cache 到底在发生什么

假设当前 prompt 只有三个 token：

```text
x1, x2, x3
```

先做 prefill。

### prefill 时发生什么

在某一层里，模型会为这三个位置都生成各自的：

- `q1, q2, q3`
- `k1, k2, k3`
- `v1, v2, v3`

然后依照因果约束：

- 位置 1 只能看位置 1
- 位置 2 能看位置 1, 2
- 位置 3 能看位置 1, 2, 3

经过所有层之后，如果启用缓存，我们就会把各层对应这三个历史位置的：

- `k1, k2, k3`
- `v1, v2, v3`

保留下来。

### 第一次 decode 时发生什么

现在模型要生成 `x4`。

它会为新位置生成：

- `q4`
- `k4`
- `v4`

然后 `q4` 会去匹配：

- 缓存里的 `k1, k2, k3`
- 再加上自己当前的 `k4`

并对：

- `v1, v2, v3, v4`

做加权读取。

生成完之后，再把：

- `k4`
- `v4`

追加进 cache。

### 第二次 decode 时发生什么

下一步生成 `x5` 时：

- 只需要新算 `q5, k5, v5`
- 旧历史的 `k1..k4`、`v1..v4` 都已经在 cache 里

于是历史的“被读取材料”不必从头生成。

这个例子揭示了最本质的事情：

> cache 不是在缓存最终答案，而是在缓存未来会反复读取的历史索引与历史内容。

## cache 为什么是“每层一份”，而不是全模型只有一份

这是另一个非常容易被忽略的点。

很多人会粗略地理解成：

- 整个模型有一份 K/V cache

从工程实现层面当然可以把它统一管理，但从概念上更准确的说法是：

> 每一层 attention 都有自己那一层的历史 K/V。

因为不同层的表示含义并不一样。

例如：

- 较浅层可能更接近局部模式
- 中间层可能在表达更复杂的上下文结构
- 较深层可能承载更任务相关的抽象特征

因此，第 3 层的历史 K/V 和第 10 层的历史 K/V 不是一回事。

未来位置在第 3 层读取的，是第 3 层版本的历史；
在第 10 层读取的，是第 10 层版本的历史。

所以更精确的工程图景是：

- 每一层都维护一份随时间增长的历史 K/V 表

这也是为什么上下文越长，cache 占用的总显存会明显上升。

## cache 真正节省掉的计算是什么

这件事最好分层来看。

不开 cache 时，每次 decode 一步，模型往往要为整个历史重新计算很多 attention 前置量。

开 cache 后，被节省掉的主要是：

- 历史位置在各层的 key/value 再次生成
- 以及这些历史位置为未来读取而重复准备的部分工作

仍然必须保留的，则包括：

- 新位置自己的前向计算
- 新位置自己的 query 生成
- 新位置和所有历史 key 的匹配
- 新位置对所有历史 value 的聚合
- 新位置穿过后续层的计算

所以 cache 不是让 decode 变成“只算一个 token 就够了，和历史无关”。
它做的是更具体的事：

> 把历史中那些“已经准备好、以后还会反复被读取的部分”从重复计算里拿掉。

## 从复杂度角度看，cache 为什么如此重要

不做严格论文级复杂度推导，只抓住最关键直觉就够了。

如果不开 cache，那么每新生成一步，历史越长，模型要反复处理的旧位置就越多。

这意味着：

- 生成到后面，单步成本会越来越明显地被历史重算拖累

而开启 cache 后，每一步新增的核心工作更集中在：

- 当前新位置本身
- 以及它对整段历史做一次读取

虽然注意力读取历史这件事仍然随着上下文增长而增长，但：

- 旧位置不必每一步都从头重新准备“被读材料”

这就把 decode 的实际成本结构明显改写了。

因此，cache 的重要性通常会在：

- 长 prompt
- 长输出
- 深层模型

这些场景下变得尤为明显。

## 为什么 cache 不会让模型“更聪明”

这是一个很值得明确的边界。

很多人第一次听见 cache 时，会下意识把它和“记忆能力增强”混在一起。

更准确的说法是：

> KV cache 改变的是计算复用方式，不改变模型学到的语义规则本身。

如果实现正确，那么：

- 开 cache
- 不开 cache

在相同权重、相同输入、相同解码策略下，理论上应该得到相同的输出路径。

cache 主要改变的是：

- 速度
- 吞吐
- 延迟
- 显存占用结构

而不是：

- 模型理解得更深
- 模型记得更牢
- 模型突然会回答更多知识

所以一定要把这条边界守住：

> cache 是运行时优化，不是语义增强模块。

## 为什么 cache 会增加显存占用

加速从来不是没有代价的。

cache 之所以能省时间，是因为它在拿空间换时间。

因为只要历史越来越长，你就必须把更多历史位置在各层的 K/V 张量留在内存里。

这意味着：

- 上下文越长
- 层数越多
- batch 越大
- 头数或隐藏维越高

cache 占用就越明显。

所以一个非常现实的权衡是：

- 不开 cache：算力浪费更多，显存压力相对小一些
- 开 cache：重复计算少很多，但显存中要持续保留历史 K/V

这也是为什么在极长上下文或大 batch 推理里，cache 管理会变成一个非常现实的工程问题。

## 为什么 cache 尤其适合自回归 decode，而不天然等价于训练阶段需求

这条边界也值得讲清楚。

在训练阶段，很多实现会采用：

- teacher forcing
- 整段并行前向

也就是说，一整段序列的很多位置是一次性并行处理的。

而在 decode 阶段，特点则是：

- 每次只新增一个位置
- 历史大量重用

cache 的价值，正是在这种“逐步新增、历史复用”的结构里特别大。

因此，KV cache 主要是：

- 自回归推理优化

而不是“训练里也一样直接同等重要”的概念。

当然，训练中也会有与中间状态复用相关的想法，但它们处理的问题与这里的 decode cache 并不相同。

## beam search、多分支生成时，cache 为什么会更复杂

只要你不再只保留一条单一路径，而是同时保留多条候选路径，事情就会更复杂。

因为不同候选分支在某个时刻可能共享同一段前缀，然后在后面分叉。

这意味着：

- 某些历史 cache 可以共享
- 某些新增位置 cache 必须按分支分开

所以在：

- beam search
- 树状探索
- 多分支生成

这些场景里，cache 不再只是“简单 append 一下”。
它会牵涉：

- 分支复制
- 分支重排
- 候选筛选后的 cache 对齐

这说明 cache 虽然概念上很清楚，但在高级推理协议里会迅速变成真正的系统工程问题。

## 为什么 prompt 一变，cache 就通常不能直接复用

还有一种常见误解是：

> 既然 cache 保存了上下文，那下次类似请求能不能直接拿来用？

一般情况下，不能简单这么想。

因为 cache 对应的是：

- 某个具体前缀
- 在某个具体模型权重下
- 各层历史位置形成的 K/V

只要前缀不同，历史表示通常就不同。

因此：

- 对完全不同 prompt，cache 通常不能直接拿来混用

只有在：

- 相同前缀被多个后续请求共享

这类更特殊场景下，前缀 cache 复用才会变得有意义。

所以不要把 KV cache 想成一种“全局知识缓存”。
它更像是：

- 与具体上下文绑定的运行时前缀状态缓存

## 为什么很多人会误把 cache 理解成“模型对上下文的理解被存住了”

这种说法不算完全错，但太模糊。

更危险的是，它会让人误以为 cache 像某种高层语义摘要。

更精确的说法应该是：

> cache 保存的是各层 attention 在未来读取历史时会用到的 key/value 张量，而不是一段人类可解释的“理解摘要”。

这层区分很重要。

因为如果你把 cache 误解成：

- 模型已经把整段上下文“理解完并浓缩成一句话”

那你会很难正确理解：

- 为什么每层都要有自己的 cache
- 为什么 cache 会这么占显存
- 为什么 future query 仍然必须逐步重新产生

所以最稳的表述永远是：

- cache 是 attention 历史读取接口的一部分

而不是：

- cache 是一个高层语义备忘录

## 工程实现里最常见的 cache 错误有哪些

如果把这个概念落回实现，最容易出错的地方通常有几类。

### 第一，位置顺序错位

如果新 token 的 K/V 追加位置和实际时间顺序不一致，后面读取就会乱。

### 第二，设备或 dtype 不一致

例如：

- 模型在 GPU
- cache 却残留在 CPU

或：

- 模型当前在 bf16
- cache 却是 float32 或 float16

这种错误不一定总是立刻报得很明显，但会带来：

- 性能异常
- 内存异常
- 甚至数值问题

### 第三，忘记在某些分支下同步更新 cache

例如：

- 生成分支被截断
- beam 重排后 cache 未同步重排

### 第四，把 cache 当成跨请求通用资源

导致上下文混淆。

这些都说明：

> cache 虽然概念上是“节省重复计算”，但实现时它实际上是一套严格依赖时间顺序和张量对齐的状态系统。

## 为什么理解 KV cache 会反过来帮助你理解 attention 本身

这件事很有意思。

很多人学 attention 时，只停留在公式层：

\[
\text{softmax}(QK^\top/\sqrt{d})V
\]

而 cache 恰恰会逼你从运行时角度重新理解这个公式。

因为它让你看到：

- `Q` 是当前一步提出的问题
- `K` 是历史位置供匹配的索引
- `V` 是历史位置供读取的内容

一旦 cache 讲清楚，attention 就不再只是一个静态矩阵公式。
它会重新变成：

- 当前一步如何向历史发问
- 历史如何以 K/V 形式被未来复用

的一套动态机制。

这也是为什么很多人真正理解 KV cache 后，反而会更深地理解 attention。

## 初学者在这里最容易犯的几个误解

### 误解一：cache 缓存的是“模型已经理解好的上下文摘要”

更准确地说，它缓存的是各层历史位置的 K/V 张量。

### 误解二：Q/K/V 都应该一起缓存

实际上只有历史 K/V 会被未来反复读取，历史 Q 没有这种复用价值。

### 误解三：开 cache 之后模型会更聪明

实际上它主要会更快，不应该改变语义输出。

### 误解四：cache 只是一个小优化

在长上下文和长生成场景里，它往往是决定可用性的核心优化之一。

### 误解五：cache 没有代价

实际上它在拿显存换时间。

## 读完这一章之后，你应该能稳定回答什么

如果这一章真正起作用了，你至少应该开始能稳定回答：

- 为什么 decode 阶段会有强烈历史重算浪费
- prefill 和 decode 在 cache 价值上有什么区别
- 为什么 cache 的核心对象是每层历史 K/V
- 为什么历史 Q 不值得缓存
- cache 真正节省掉的是哪一部分计算
- 为什么 cache 会增加显存占用
- 为什么它不改变语义结果，只改变运行成本结构
- 为什么多分支或 beam 场景会让 cache 管理复杂很多

只要这些问题能讲清楚，后面你再看：

- 长上下文推理
- 首 token 延迟
- 吞吐问题
- 重复调用优化

就会更顺。

## 本章之后去哪里

最自然的下一步通常是继续回到：

- 训练指标与生成表现之间的关系

因为到这里，你已经清楚了：

- 模型如何一步步输出 token
- 为什么运行时会需要 cache

接下来更大的问题就是：

> 既然模型已经能这样运行了，我们到底该怎样判断它“变好了”？为什么训练 loss 下降了，用户看到的文本却不一定同步变好？

这正是下一章要处理的。

## 小结

本章最核心的结论可以压缩成一句话：

> KV cache 并不是某种模糊的“上下文理解缓存”，它缓存的是各层历史位置在 attention 中会被未来反复读取的 key 和 value 张量；它之所以重要，是因为自回归 decode 每一步只新增一个位置，却会反复用到整段历史，而 cache 恰好把这部分历史读取所需的可复用材料保留下来，用显存换掉了大量重复计算。

一旦这个认识真正站稳，你就不会再把 cache 当成一条需要背下来的推理术语。
你会开始看见：

> 它其实是自回归生成在计算结构上几乎必然会长出来的一种历史复用机制。
