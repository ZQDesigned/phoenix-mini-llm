# 02. Unicode、字节与文本规范化

## 为什么这章看起来“不像大模型”，却必须出现

很多初学者会觉得：

> Unicode、字节、文本规范化这种东西是不是太底层了，和大模型没什么关系？

其实关系非常直接。

因为模型并不直接接触“人类眼中的文本”，它接触的是：

- 文件里的字节
- 解码后的字符序列
- 再进一步切出来的 token

如果这条链前面就不稳，那么后面的 tokenizer 和模型输入都会受到影响。

## 机器最先看到的是字节，不是字符

当你打开一个文本文件时，人类看到的是：

```text
你好，world
```

但在机器底层，这首先是一串字节。

同样一段可见文本，如果编码方式不同，底层字节排列可能也不同。

这意味着：

> “看起来一样的文字”在底层并不一定天然一样。

而数据处理管线真正接触的，往往就是这一层。

## Unicode 解决的是什么问题

如果没有统一字符标准，不同系统、语言和工具对“一个字符”可能会有不同理解。

Unicode 的价值就在于：

> 它为字符提供了统一编号体系，让世界上大量书写系统可以被一致表示。

你现在不需要去背编码标准细节，但至少要稳稳理解：

- Unicode 是字符层的统一标准
- 编码是把这些字符编号具体落成字节序列的方式

把这两者混在一起，是很多文本处理混乱的源头。

## 为什么同一个“字符”不一定只有一种写法

这是文本规范化里最容易被忽视、也最容易导致隐蔽 bug 的点。

看起来相同的字符，在底层有时可能存在不同表示方式。

例如：

- 某些带重音字符可以是单个组合字符
- 也可以是“基础字符 + 附加标记”的组合

从人眼看，它们几乎一样；从程序看，它们未必完全相同。

这就意味着：

> 如果你不做适当规范化，模型和 tokenizer 可能把“看起来一样的文本”当成不同输入。

## 什么叫文本规范化

规范化可以先理解成：

> 在进入 tokenizer 和训练前，把文本转换到一种更一致、更可预测的表示形式。

这可能包括：

- 统一编码解码流程
- 统一换行与空白字符
- 统一某些组合字符形式
- 处理不可见控制字符

它的目标不是“让文本更好看”，而是：

> 让同类文本在数据层面尽量以一致方式进入模型。

## 为什么空白、换行和不可见字符也很重要

人类阅读时，很多不可见字符几乎被自动忽略。

但对模型来说，它们仍然是输入的一部分。

例如：

- 连续空格
- tab
- 不同换行风格
- 某些奇怪的零宽字符

这些东西如果不处理好，可能会导致：

- tokenizer 行为不一致
- 词频统计失真
- 模型学到很多本不该强调的格式模式

因此“清洗文本”里一个重要职责就是判断：

> 哪些不可见差异应该保留，哪些应该统一。

## 规范化不是越狠越好

这也是必须建立的判断。

很多初学者一听到“清洗”，就会本能倾向于：

> 把所有看起来奇怪的东西都删掉。

这并不总是对的。

因为有些形式差异本身携带语义或格式信息，例如：

- 代码缩进
- 段落边界
- 特定标点风格

如果你把这些也粗暴抹平，模型可能会失去本来应该学习的结构。

所以规范化的原则不是“越干净越好”，而是：

> 保留对任务有意义的差异，统一会无谓干扰建模的差异。

## 为什么这会直接影响 tokenizer

tokenizer 不是在抽象文本上工作，而是在你处理后的实际字符流上工作。

如果规范化前后文本变了，那么：

- token 切分会变
- 词表统计会变
- special token 的边界可能会受影响

这说明文本规范化不是 tokenizer 前的独立清洁环节，而是：

> tokenizer 定义的一部分前置条件。

很多“tokenizer 表现奇怪”的问题，根源其实不是 tokenizer 算法本身，而是前面的文本一致性没有处理好。

## 为什么学习项目也需要认真对待这件事

你也许会想：

> 我的项目又不做工业级清洗，是否不用这么认真？

实际上越是学习项目，越需要把这些边界讲清楚。因为当模型出现：

- 某些字符行为异常
- 数据统计和直觉不符
- 文本看起来一样但 token 不一样

如果你没有这层基础知识，就很容易把问题误判成：

- 模型结构 bug
- tokenizer 训练失败
- 框架问题

而真实原因可能只是文本底层表示不一致。

## 这一章真正要记住的核心句子

如果这一章只记一句话，它应该是：

> 模型接触到的不是抽象意义上的“文字”，而是经过编码、解码和规范化处理后的字符流；Unicode、字节和文本规范化之所以重要，是因为它们会直接改变 tokenizer 和后续训练样本的定义。
