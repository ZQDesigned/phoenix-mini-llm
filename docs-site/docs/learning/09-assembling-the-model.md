# 09. 一个完整小型语言模型由什么组成

## 这一章要解决什么问题

前面几章你已经按部件理解了很多内容：

- tokenizer
- 训练目标
- attention
- transformer block
- 位置编码

现在必须再往前一步，把这些内容拼成一个完整系统。

这一章要回答的问题是：

> 一个真正可训练、可生成的小型 decoder-only 语言模型，到底由哪些部分组成？这些部分前后是怎样衔接的？

如果这个问题不清楚，你后面虽然能看懂零散代码，却很难真正掌握完整模型的工作方式。

## 第一件事：完整模型应该被看成一条前向数据流

把一个小型 decoder-only 模型压缩成最常见的路径，大致是：

```text
token ids
-> embedding
-> 多层 transformer block
-> 最终归一化
-> 线性输出层
-> logits
-> （训练时）loss
```

这条路径是整台模型最重要的骨架。

你之后看到的任何具体实现，无论类名和文件怎么组织，本质上都在围绕这条路径工作。

## 第二件事：离散 token 为什么一定要先变成连续向量

模型的输入最开始是一串整数 token id，例如：

```text
[12, 57, 901, 4, 18]
```

这些整数本身只是编号，不携带可微、可学习的连续表示空间。

所以第一步必须通过 embedding，把每个 token 映射成一个向量：

\[
[B, T] \rightarrow [B, T, H]
\]

其中：

- `B` 是 batch
- `T` 是序列长度
- `H` 是隐藏维度

### 为什么 embedding 是必要的

因为模型后面要做的事情是：

- 矩阵乘法
- 相似度比较
- 非线性变换

这些都需要连续向量表示，而不是离散编号本身。

## 第三件事：隐藏维度到底在代表什么

`hidden_size` 常常是初学者最容易机械记数字、却最不理解含义的配置。

更直觉的理解是：

> 它表示每个 token 在模型内部被表示成多宽的向量。

这个向量空间越宽，通常意味着模型能承载的统计特征越丰富，但也意味着：

- 参数更多
- 计算更重
- 显存占用更高

所以隐藏维度不是越大越好，而是要和学习目标、数据规模、训练预算一起平衡。

## 第四件事：为什么要堆很多个 block，而不是只用一个

如果只有一个 block，模型当然也能做上下文交互，但它能进行的信息加工轮次非常有限。

多层堆叠的意义在于：

- 第一层可能先学到一些浅层相关性
- 中间层开始组合更复杂的模式
- 更深层可以形成更抽象的统计结构

你可以把它理解成：

> 模型不是只“看一眼上下文”，而是多轮地读、改写、再读、再改写。

这就是深度的价值。

## 第五件事：完整模型为什么仍然保持形状一致性

虽然模型内部经过很多层处理，但 block 的输入输出通常都保持：

\[
[B, T, H] \rightarrow [B, T, H]
\]

这带来两个好处：

- 便于反复堆叠
- 让每层都能在同一个表示空间中继续加工

最终只有最后的输出头，才会把最后一维从 `H` 映射到词表大小 `V`。

## 第六件事：输出层到底在做什么

经过多层 block 后，每个位置都有了一个上下文感知的隐藏向量。接下来模型要回答的问题是：

> 对于这个位置，词表里的每个 token 分别有多可能成为下一个 token？

因此需要一个输出层，把：

\[
[B, T, H]
\]

映射成：

\[
[B, T, V]
\]

其中 `V` 是词表大小。

这组结果就是 logits。

### logits 不是概率

这一点必须再次强调：

- logits 是未归一化分数
- softmax 之后才得到概率分布

训练时，很多框架会直接用 logits 计算 cross-entropy，而不是先手动转概率。

## 第七件事：为什么完整模型在训练时还需要接上 loss

如果模型只输出 logits，它已经具备了预测能力，但还没有真正形成监督学习闭环。

为了训练，你还需要：

- 把真实目标 token 准备好
- 比较预测分布和真实目标
- 计算损失

这一步常见做法是：

- logits 展平到分类形式
- targets 展平到对应类别 id
- 使用 cross-entropy

所以完整模型从学习角度看，最好同时理解两条线：

- 预测线：输入到 logits
- 学习线：logits 到 loss

## 第八件事：为什么输入 embedding 和输出层常常有关系

很多语言模型会让输入 embedding 和输出层参数形成共享或紧密关联，这常被叫做 weight tying。

### 为什么这是一个合理想法

因为：

- 输入时，模型在学习“一个 token 应该怎样被表示”
- 输出时，模型在判断“当前位置更像词表中的哪一个 token”

这两件事在统计上并不是完全无关的。

### 对学习项目来说最重要的理解

你不需要先钻进所有实现细节，只要知道：

> 语言模型的输入表示空间和输出判别空间之间，常常有很强的结构关系。

## 第九件事：一个小模型到底由哪些超参数定义

如果你要从 0 设计一个小型模型，至少会碰到这些关键参数：

- `vocab_size`
- `max_seq_len`
- `hidden_size`
- `num_layers`
- `num_heads`
- `intermediate_size`
- `dropout`

### 它们分别大致影响什么

- `vocab_size`：输入和输出空间规模
- `max_seq_len`：模型单次可见上下文上限
- `hidden_size`：每个 token 内部表示宽度
- `num_layers`：模型深度
- `num_heads`：多头注意力拆分数量
- `intermediate_size`：FFN 容量
- `dropout`：正则化程度

### 为什么这些参数必须一起看

因为它们不是彼此独立的：

- 增大 `hidden_size` 会影响参数量和注意力计算
- 增大 `num_layers` 会影响深度和显存
- 增大 `max_seq_len` 会显著增加序列相关成本

所以模型设计从来不是“把每个数字单独调大”，而是整体预算平衡。

## 第十件事：参数量为什么不是唯一指标

很多初学者会过早迷恋参数量，例如：

> 这个模型是多少 M？多少 B？

参数量当然重要，但它不是唯一维度。

一个模型是否适合作为学习项目，还要看：

- 你能不能在自己的设备上训练它
- 你能不能完整跑通数据、训练、评估、生成
- 你能不能在出现问题时解释和修改它

因此对学习项目来说，更重要的问题通常不是：

> 它能不能变得尽量大？

而是：

> 它是不是足够完整，且在你的预算内真正可控？

## 第十一件事：为什么完整模型必须同时服务训练和推理

一个真正可用的语言模型，不是只会做一件事。

训练阶段它需要：

- 接收输入序列
- 接收目标序列
- 输出 logits 和 loss

推理阶段它需要：

- 接收 prompt
- 输出下一步 logits
- 支持反复生成

因此，完整模型的“主体结构”通常是共享的，训练和推理的区别更多在于：

- 外层循环怎么调用它
- 是否传入目标
- 是否启用缓存

这也是为什么你应该把“模型结构”和“运行协议”区分开来理解。

## 第十二件事：为什么上下文长度是完整模型设计里的硬边界

`max_seq_len` 不是一个普通超参数，而是完整模型设计中的硬约束。

它直接决定：

- 单个样本能看多长上下文
- 注意力矩阵的规模
- 训练和推理时的内存消耗

尤其在小显存设备上，上下文长度对成本的影响非常大。

所以如果你的学习目标是先完成一个能运行的完整模型，那么上下文长度往往应该先保守一点，再逐步提高。

## 第十三件事：一个“完整小模型”到底意味着什么

对学习阶段来说，一个完整小模型通常意味着它至少具备：

- tokenizer 对应的输入空间
- token embedding
- 多层 transformer block
- 位置信息处理
- 输出 logits 的头
- 可用于训练的损失
- 可用于生成的自回归接口

注意这里的关键词是“完整”，不是“大”。

如果一个模型参数不算夸张，但这些环节都齐全，那么它已经是非常有价值的学习载体。

## 第十四件事：初学者最容易误解的几点

### 误区 1：完整模型就是“把层堆起来”

不对。完整模型是“输入表示、上下文建模、输出分布、学习目标”共同构成的系统。

### 误区 2：只要能输出 logits，就算模型完成

不够。训练损失、推理协议、上下文边界都属于完整性的一部分。

### 误区 3：参数量越大，学习价值越高

通常不是。对初学者来说，可理解、可训练、可调试更重要。

### 误区 4：模型结构和 tokenizer 可以分开看

也不对。tokenizer 决定输入输出空间，是模型定义的一部分。

<Callout title="这一章真正要你建立的全局图景" tone="success">
  一个小型语言模型不是“Attention 的代码实现”，也不是“训练脚本加模型类”的简单组合。它是一条从 token 输入、到多层上下文建模、再到词表分布输出，并能被训练与生成共同使用的完整系统。
</Callout>

3. 输出层为什么必须把最后一维映射到词表大小？
4. 为什么说 tokenizer 也属于完整模型的一部分？
5. 对学习项目来说，为什么“小而完整”往往比“大而失控”更有价值？
