# 11. 生成文本：解码、采样与缓存

这一章属于 `learning` 顶层速读线里的推理总览章。

它的职责不是替代 [Part 10. 推理、评估与调试](/learning/part-7-inference-evaluation-and-debugging) 的分章长文，而是先把“模型怎样从概率分布走向真实文本行为”这条主线梳清楚。

很多初学者在训练阶段结束后，会本能地觉得最难的部分已经过去了。
但真正开始生成时，另一类问题会立刻出现：

- 同一个模型为什么因为采样策略不同而表现像换了性格
- 为什么模型会重复、拖尾、迟迟不结束
- 为什么生成越长通常越慢
- 为什么训练时看起来一切正常，推理时却像另一种生物

这不是“模型突然坏了”。
而是因为：

> 训练和推理虽然使用同一套参数，但它们让模型处在两种完全不同的运行环境中。

所以这一章想先帮助你建立一个关键视角：

> 推理不是把模型输出“展示出来”，而是在模型给出的概率分布上，一步一步做真实决策，并让这些决策反过来塑造后续上下文。

## 11.1 为什么推理和训练不能被当成同一件事

训练阶段，语言模型通常使用 teacher forcing。

这意味着：

- 在当前位置，模型要预测下一个 token
- 但进入下一步时，它仍然会继续看到真实历史

推理阶段不是这样。

当你给模型一个 prompt 时，系统只能做：

1. 读取当前上下文  
2. 预测下一个 token 的分布  
3. 真正选出一个 token  
4. 把它接回上下文  
5. 再来一轮  

也就是说，推理阶段模型开始：

> 吃自己的输出，而不再只吃真实样本。

这件事非常关键，因为它直接解释后面许多现象：

- 为什么错误会累积
- 为什么重复常常越往后越明显
- 为什么单步预测质量不错，不代表长段文本一定自然
- 为什么训练 loss 下降不自动等于生成体验更好

所以推理不是训练的展示层。
它是另一种运行机制。

## 11.2 生成不是“一次性写完一段话”，而是滚动式决策

从用户视角看，你看到的是一段连续文字。

从系统视角看，生成其实是一条离散决策轨迹：

```text
给定当前前缀
-> 预测下一个 token 分布
-> 选出一个 token
-> 把它并回前缀
-> 再预测下一步
```

这叫自回归生成。

它最重要的含义在于：

> 局部决策会累积成全局行为。

这意味着：

- 早期一点点偏差，可能改写整段后续走势
- 某一步选得略保守，后面可能越来越模板化
- 某一步选得略冒险，后面可能逐渐跑偏

所以推理的研究对象不是“最终文本长什么样”这么简单。
更深一层是：

> 这段文本是怎样一步一步被走出来的。

## 11.3 模型每一步先给出的不是词，而是一整张分布

这是推理理解里最基础也最重要的一点。

模型在每一步先输出的不是：

- 一个已经决定好的词

而是：

- 对整个词表的 logits
- 或者等价地，对整个词表的相对偏好

所以在真正看到某个 token 之前，系统先拥有的是一张分布：

- 哪些 token 更可能
- 哪些 token 较不可能
- 当前分布有多尖锐或多分散

这意味着推理天然分成两个阶段：

1. 模型产生分布  
2. 解码器从分布中做选择  

如果你不把这两步分开，就会误以为：

> 模型直接决定了具体句子。

实际上，很多生成风格差异恰恰发生在第二步。

## 11.4 为什么“解码”这个词很容易被误解

初学者常常把 decode 理解成：

```text
token id -> 字符串
```

那只是最终的反 tokenization。

这里更重要的“解码”其实是：

> 如何从当前这张分布里，决定这一步到底选哪个 token。

这一步会深刻影响生成行为。

因为同一张分布，如果你：

- 每步永远选最大值
- 允许小范围随机性
- 在高概率区域里受控随机

最终走出的文本会很不一样。

所以推理并不是“模型决定 + 系统展示”。
而是：

> 模型给出候选空间，解码策略把候选空间变成真实路径。

## 11.5 greedy decoding 为什么是最自然的起点

最简单的规则是：

> 每一步都选择当前概率最高的 token。

这叫 greedy decoding。

它的优点非常明显：

- 简单
- 稳定
- 可复现
- 适合作为基线

它很适合回答一个基本问题：

> 在最保守的选择规则下，模型自己最想怎么往下走？

但它的问题也很明显：

- 容易过于保守
- 容易陷入高频模板
- 长段中更容易重复

所以 greedy 很适合作为分析起点，却不总适合作为最终采样策略。

## 11.6 为什么采样不是“加一点随机性”这么简单

很多人会把采样理解成：

> 别总选第一名，稍微随机一点。

这种说法太轻了。

更准确的理解是：

> 采样是在决定，你要以什么方式从模型当前分布里走出一条真实文本轨迹。

这会直接影响：

- 输出是否稳定
- 输出是否自然
- 输出是否僵硬
- 输出是否发散

所以采样并不是附加娱乐层，而是推理系统的核心组成部分。

## 11.7 temperature 到底在改变什么

temperature 的核心作用，是改变分布的尖锐程度。

直观地说：

- 温度低时，高概率 token 会更占优势
- 温度高时，中等概率 token 更容易获得机会

所以它控制的是：

> 你愿意多大程度上偏离当前最陡峭的概率峰值。

### 温度过低时会怎样

常见结果是：

- 更稳定
- 更保守
- 更模板化
- 更容易陷入重复高频模式

### 温度过高时会怎样

常见结果是：

- 更活跃
- 更有变化
- 但也更容易飘
- 更容易走到低质量尾部

因此 temperature 不是“创意开关”。
更准确地说，它是：

> 分布探索强度调节器。

## 11.8 top-k 和 top-p 为什么都在做“裁掉尾部”

如果你直接从整个词表采样，那么许多极低概率 token 也会留在候选池里。
这很容易让生成出现无意义跳跃。

于是常见做法是先缩小候选空间。

### top-k 在做什么

只保留当前概率最高的前 `k` 个候选。

它在回答：

> 这一步只允许在最可能的这几个选项里随机。

### top-p 在做什么

保留累计概率达到阈值 `p` 所需的最小候选集合。

它在回答：

> 只保留足够覆盖主要概率质量的候选，而不是固定保留多少个。

二者都在做同一类事情：

- 削掉低概率尾部

但方式不同：

- top-k 固定候选数
- top-p 固定累计概率质量

这也是为什么它们带来的生成气质不完全一样。

## 11.9 为什么同一个模型换个采样器，就像换了一个性格

这是初学者第一次真正直观感受到：

> 模型不是只有一个确定答案，而是在输出一个分布。

采样器决定的，是你如何从这个分布里走路径。

所以你会看到：

- greedy 时很保守
- 低温时很稳但更模板
- 中等采样时更自然
- 高温时更活跃但更不稳

这并不意味着模型本身忽好忽坏。
而是说明：

> 文本行为永远是“模型分布 + 解码策略”的联合结果。

## 11.10 为什么停止条件不是小细节，而是推理协议的一部分

如果什么都不做，让模型持续预测下一个 token，它理论上可以一直写下去。

所以推理系统必须回答：

- 什么时候该停
- 谁来决定停
- 自然结束和强制截断有什么区别

这就把我们带到 `EOS` 和停止条件。

### EOS 在做什么

它让“结束”这件事本身也成为一个可被模型预测的 token 事件。

换句话说，模型不仅要学会继续写，还要学会：

- 哪里应该结束

### 运行时规则又在做什么

即使有 `EOS`，现实系统也常常还会设置：

- `max_new_tokens`
- 停止字符串
- 预算上限

因为模型的结束能力永远只是概率性的，而系统需要确定边界。

对应深读：

- [Part 10 / 04. EOS、停止条件与重复](/learning/part-7-inference-evaluation-and-debugging/04-eos-stopping-criteria-and-repetition)

## 11.11 为什么重复问题在推理阶段特别显眼

很多初学者第一次看到模型重复，会直觉觉得：

> 训练是不是哪里完全坏了？

有时确实与训练有关，但更准确地说，重复是推理阶段最容易显现的一类系统现象。

因为：

- 模型在吃自己的输出
- 一旦进入某个高频模式，后续更容易继续强化这个模式
- 解码策略如果过于保守，也会放大循环倾向

所以重复问题往往是多因素共同造成的：

- 训练目标学得还不够稳
- 收尾模式没有学清
- 采样器太保守
- 上下文逐步滑入模板化轨道

这说明推理问题很少只属于“采样器层”或“训练层”之一。
它们常常横跨两边。

## 11.12 为什么生成越长通常越慢

这又是一个很多人第一次见到时会觉得“不太合理”的现象。

直觉上好像模型已经生成了一部分，后面应该越来越轻松。
现实却常常是：

> 越往后生成，总体耗时越明显。

原因在于，自回归推理不是一次性完成的。

它需要：

- 每生成一个 token
- 就再跑一轮新计算

这意味着生成长度直接影响推理轮数。

而如果每轮都重复处理整段历史，成本会非常高。

这就把我们带到 KV cache。

## 11.13 为什么 KV cache 会成为推理主角

KV cache 最值得用一句话先记住的是：

> 它不是在缓存“最终答案”，而是在缓存已经算过的历史上下文表示，避免每步都重算一遍。

这为什么重要？

因为自回归生成每次只多了一个新 token。

如果为了这个新 token，每次都把旧历史整段重新算一遍，代价会非常浪费。

KV cache 的作用，就是让系统复用已经算过的 Key 和 Value 表示，只为新增位置做必要的新计算。

所以它本质上在解决：

> 自回归推理里的重复计算问题。

对应深读：

- [Part 10 / 05. KV cache 真正在节省什么](/learning/part-7-inference-evaluation-and-debugging/05-what-kv-cache-is-actually-saving)

## 11.14 为什么“prefill” 和 “decode” 最好分开理解

推理阶段实际上常常包含两个性质不同的阶段。

### prefill

先把已有 prompt 整段读进去，建立起当前上下文状态。

### decode

再进入一轮一轮生成新 token 的阶段。

这两步看起来都在“跑模型”，但语义不同：

- prefill 更像一次把已有历史写入上下文
- decode 更像在已有上下文上逐步延长文本

把这两个阶段分开理解，会帮助你更清楚地看：

- 为什么首 token 延迟和后续 token 延迟不一样
- 为什么 KV cache 主要影响 decode
- 为什么 prompt 太长会影响起步成本

对应深读：

- [Part 10 / 01. 自回归生成、prefill 与 decode](/learning/part-7-inference-evaluation-and-debugging/01-autoregressive-generation-prefill-and-decode)

## 11.15 为什么训练时正常，不代表推理时自然

这是初学者最需要尽早接受的一点。

训练时模型被放在：

- teacher forcing
- 固定目标
- 可并行的位置预测

的环境里。

推理时模型被放在：

- 吃自己输出
- 一步步决策
- 错误会累积

的环境里。

这两种运行环境差异极大。

所以完全可能出现：

- 训练 loss 看起来不错
- 但长段生成仍然容易重复
- 或者局部合理、整体结构却很散

这不是矛盾。
而是因为：

> 局部 next-token 预测质量和滚动生成行为高度相关，但并不完全等价。

## 11.16 为什么推理应该被看成“运行时系统”，而不是“模型附属界面”

很多人会无意识地把推理理解成：

- 模型已经训练好了
- 现在只是把结果拿出来给人看

这种理解过于低估推理层。

更准确地说，推理本身就是一个系统：

- 有状态
- 有缓存
- 有停止协议
- 有采样策略
- 有时延和吞吐约束

同样一套参数，在不同推理系统设计下可能呈现出很不一样的体验。

这说明推理绝不是展示层。
它是行为层。

## 11.18 本章读完后，你应该建立哪些稳定判断

如果这一章真正读懂了，你至少应该形成下面这些判断。

### 判断一：模型先输出的是分布，不是文本

文本行为总是经过解码策略后才真正落地。

### 判断二：推理是滚动式决策过程，不是一次性写完整段

局部决策会累积成全局行为。

### 判断三：采样器不是外围开关，而是行为塑形器

同一模型换采样器，行为可以明显不同。

### 判断四：停止、重复和 cache 都属于推理协议的一部分

它们不是小优化，而是运行机制的重要组成。

### 判断五：训练正常不自动等于生成自然

因为推理把模型放进了完全不同的运行环境。

## 11.19 如果你现在只能记住这一章的一句话

可以先记住这一句：

> 推理不是把训练好的模型结果直接展示出来，而是在模型给出的概率分布上，一步一步做真实选择，并让这些选择反过来塑造后续上下文，因此文本行为永远是“模型分布 + 解码策略 + 停止与缓存机制”的联合结果。

只要这句话没有丢，后面再遇到采样、重复、拖尾和缓存问题时，你就知道它们都属于同一条推理主线。
