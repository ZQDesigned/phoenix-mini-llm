# 01. 你到底在做什么

## 这一章要解决什么问题

很多人第一次接触“大模型开发”时，思路会立刻掉进实现细节里：

- Attention 代码怎么写？
- 哪个库最适合？
- 数据集从哪里下？
- 训练脚本该怎样启动？

这些问题都重要，但它们都不是最先该问的问题。更靠前、也更决定后续学习质量的问题是：

> 你到底在试图做出一个什么系统？

如果这个问题没有想清楚，后面所有内容都会以碎片形式进入你的脑子。你可能会记住很多词：

- token
- embedding
- transformer
- loss
- sampling

但这些词不会在你脑子里组成一台机器。它们只会像一堆零件散落在桌上。你也许能照着教程把项目搭出来，却很难真正理解：

- 为什么要先做 tokenizer
- 为什么训练目标是 next-token prediction
- 为什么训练和推理明明用的是同一个模型，却表现得像两个过程
- 为什么一个“小而完整”的模型，反而比一个根本训练不动的大模型更适合拿来学习

这一章的目标，就是先把这台机器的轮廓画出来。

你读完之后，应该能明确：

- 语言模型到底在做什么。
- “生成文本”背后的真实任务定义是什么。
- token、参数、上下文窗口、词表这些词分别在限制什么。
- 为什么学习阶段的合理目标不是追求夸张规模，而是追求完整理解。

## 为什么这一步不能跳过

很多初学者会想：

> 我是不是先把代码跑起来，再回头理解概念也来得及？

短期看，似乎可以。但长期看，这种路线会反复把你带回同一个困境：

- 训练不对时，你不知道该怀疑数据、模型还是目标定义
- 输出文本很差时，你不知道是模型没学会，还是采样策略有问题
- 显存不够时，你不知道该缩哪个维度、为什么缩它
- 看到一段 `forward()`，你只能把它当成某种“标准写法”，而不是一个你真正理解的数据流

所以“先搞清你在做什么”不是绕路，而是在给后面所有章节建立坐标系。

如果没有这个坐标系，后面的学习会一直像在拼拼图，但你连最终成品长什么样都不知道。

## 你现在不需要会什么

开始这一章之前，你不需要已经掌握：

- 论文推导
- 深度学习数学证明
- CUDA 编程
- 大规模分布式训练
- 复杂工程架构

你真正需要的只有：

- 一点 Python 基础
- 愿意通过例子慢慢理解概念
- 愿意接受“先把问题定义清楚，比急着写代码更重要”

如果你抱着下面这种心态来读，会很有帮助：

> 我不是来背术语的，我是来学会解释一台小型语言模型为什么这样工作。

## 第一件事：语言模型表面上在“写字”，本质上在“预测下一个 token”

先从你最熟悉的表象开始。

当你在聊天界面输入：

```text
Once upon a
```

模型继续写出：

```text
time there was a small dragon...
```

你最自然的直觉当然是：

> 它会续写文本。

这没错，但作为学习定义，这句话太粗了。

### 更准确的说法是什么

一个典型的 decoder-only 语言模型最根本的任务不是“一次写完一段话”，而是：

> 给定前面的 token，预测下一个 token 的概率分布。

注意这里每个词都很关键。

#### “给定前面的”

模型不是凭空生成内容。它总是基于某个已有上下文做判断。

#### “token”

模型真正处理的不是原始字符串，而是一串离散单位。什么叫 token、为什么不是直接按字或按词处理，后面会展开。

#### “概率分布”

模型每一步输出的不是“唯一答案”，而是对很多候选 token 的偏好分布。

这意味着模型内部更像是在说：

```text
time: 0.41
day: 0.18
night: 0.11
small: 0.03
...
```

然后系统再根据某种规则，从这个分布里选出一个 token，把它接回输入，继续下一步。

所以“写一整段文字”并不是一个单独动作，而是：

> 很多次“预测下一个 token”连续发生的结果。

## 第二件事：为什么这一定义重要到几乎决定整门学习路线

如果你把语言模型想成“会说话的黑箱”，那你后面看到的一切都容易显得像魔法：

- tokenizer 像某种神秘预处理
- logits 像难以解释的中间结果
- cross-entropy 像训练时必须调用的咒语
- sampling 像生成阶段随手加上的玩法

但如果你始终记住：

> 语言模型的根任务，是根据前文预测下一个 token 的分布。

那么后面很多概念会自动归位：

- tokenizer 是在定义“什么叫一个可预测单位”
- logits 是“模型对所有候选 token 的打分”
- cross-entropy 是“衡量模型给正确 token 分了多少概率”
- causal mask 是“防止模型偷看未来答案”
- sampling 是“从分布里选出一个实际 token 的规则”

也就是说，一旦任务定义清楚，很多看似零散的部件都会自动变成同一套系统中的必要角色。

## 第三件事：什么叫“语言模型”

很多人会顺手把它理解成：

> 一个会说人话的程序。

这种说法对日常交流够用了，但对学习不够精确。

### 从统计学习角度看

语言模型是在学习一个序列分布。它希望掌握的是：

- 哪些 token 常一起出现
- 哪类上下文后面更可能接什么
- 文本在不同位置上通常如何延续

如果写成更紧凑的形式，它学习的是一种条件关系：

\[
P(x_t \mid x_{<t})
\]

意思是：

> 在前面已经出现的 token 给定的条件下，第 `t` 个位置最可能出现什么。

你现在不需要深究公式推导，但需要建立这个判断：

> 语言模型学习的不是固定答案表，而是一种“上下文到下一个 token 分布”的映射规律。

### 这和“记住句子”有什么区别

差别非常大。

如果它只是死记训练集，那它面对没见过的上下文时就很难泛化。

而如果它真的学到了一些稳定结构，它就能在很多没完全见过的上下文里，仍然给出合理续写。

当然，真实模型里“记忆”和“泛化”是混合存在的，但学习路线中最重要的是先明白：

> 语言模型的目标不是背书，而是学会条件分布。

## 第四件事：token 到底是什么

这是整个主题里最容易被“听过很多次，但一直没真的搞清楚”的概念之一。

很多新手会自然地把语言单位想成：

- 一个字
- 一个单词

但语言模型里真正被处理的单位一般叫 token。

### token 不是固定等于“词”

token 可以是：

- 一个完整单词
- 单词的一部分
- 常见词缀
- 标点符号
- 某种 byte-level 片段

例如单词：

```text
unbelievable
```

在不同 tokenizer 下，可能被切成：

```text
un | believ | able
```

也可能被切成其他完全不同的片段。

### 为什么不总是按词切分

如果你坚持按词切分，会立刻遇到很多问题：

- 生僻词和新词层出不穷
- 词表会迅速变得非常大
- 不同语言里“词边界”并不总清晰

如果你坚持按单字符切分，又会遇到另一类问题：

- 序列会变得很长
- 模型必须跨很多 token 才能表达一个词

因此现代语言模型常使用“子词级”切分，让模型在：

- 词表大小
- 序列长度
- 表达灵活性

之间取得折中。

### 为什么 token 是模型定义的一部分

这点非常重要。

一旦 tokenization 方案变了，下面这些东西都会跟着变：

- 词表大小
- embedding 尺寸
- 输出层尺寸
- 训练样本的平均长度
- prompt 的编码方式

所以 tokenizer 并不是“模型外部附属工具”，而是在定义：

> 模型到底在以什么单位观察文本世界。

## 第五件事：训练和推理为什么是同一个模型的两种完全不同使用方式

这是初学者几乎一定会混淆的地方。

因为从表面上看，两者都像是在“把 token 输入模型，再拿输出”。但它们的信息条件完全不同。

### 训练时：正确答案已知

假设一段训练文本是：

```text
[BOS, once, upon, a, time, EOS]
```

训练时，模型会在每个位置上回答：

- 看见 `BOS`，下一个最可能是什么？
- 看见 `BOS once`，下一个最可能是什么？
- 看见 `BOS once upon`，下一个最可能是什么？

重点在于：

> 整段正确文本本来就已经在训练数据里。

这意味着即便模型某一步预测错了，下一步训练时仍然继续使用真实 token 序列，而不是使用它自己刚预测出来的错误结果。

这就是后面会讲到的 teacher forcing。

### 推理时：正确答案未知

真实生成文本时，后续 token 并不存在“已知答案”。

你只能：

1. 给一个 prompt  
2. 预测下一个 token  
3. 把这个 token 接回输入  
4. 再预测下一个 token  
5. 不断重复

于是模型推理会出现一个重要特点：

> 一旦某一步选得不理想，后面每一步都会基于这个不理想结果继续滚动。

因此：

- 训练好看，不代表推理一定漂亮
- 训练和推理虽然共享同一套参数，但运行方式并不相同

理解这一点，后面学习 sampling、重复输出、推理偏移时会容易很多。

## 第六件事：参数到底是什么

很多人会说：

> 模型把知识存在参数里。

这个说法方向没错，但很容易被误解成：

> 模型像数据库一样，把句子一条条塞进去了。

这种理解是不准确的。

### 参数是什么

参数本质上就是一大堆可训练数字，分布在不同层里，例如：

- embedding 矩阵
- 注意力投影矩阵
- 前馈网络矩阵
- 归一化权重

训练时真正发生的事情，是这些数字在不断调整。

### 参数不是“显式规则表”

模型不会直接存一条规则说：

```text
如果看到 once upon a，就一定输出 time
```

更准确的说法是：

> 很多参数共同塑造了一套高维统计结构，让模型在某类上下文中更倾向于给某些 token 更高分。

因此，当人们说“模型学到了知识”，更合理的理解通常是：

- 它在参数空间里形成了一种分布式表示
- 这种表示能帮助它更好地预测后续 token

### 为什么参数量会被频繁讨论

参数量越大，通常意味着模型拥有更高的表示容量，也更可能表达复杂结构。

但参数量不是单独决定一切的魔法数字。后面你会不断看到：

- 数据规模
- 训练步数
- 上下文长度
- 结构设计

同样会影响模型实际表现。

## 第七件事：上下文窗口在限制什么

语言模型不是无限回看全部历史。一次前向传播里，它通常只能处理固定长度的 token 序列，这个限制常被叫作：

- context length
- sequence length
- max sequence length

### 这意味着什么

如果上下文窗口是 `256`，那模型在某次计算中最多只能直接看到前面 256 个 token。

### 为什么它远不只是“最多看多长”

它还会直接影响：

- 数据打包方式
- 训练时的显存占用
- Attention 的计算规模
- 推理时的时间成本

### 为什么这个限制对学习项目尤其重要

在学习型项目里，很多人最开始会想：

> 上下文越长越强，那我是不是应该直接设很大？

理论上更长上下文确实可能让模型利用更多历史信息，但代价也会迅速上升。

特别是在标准 attention 下，相关中间张量和注意力矩阵的成本会随着序列长度明显增长。

所以对初学者来说，一个成熟的判断不是“尽量拉长”，而是：

> 先在自己能承受的预算里完成完整闭环，再逐步扩大上下文长度。

## 第八件事：词表大小在限制什么

词表，也就是 tokenizer 定义出来的所有 token 集合，会影响模型很多核心部分。

### 词表越大，会发生什么

- embedding 层更大
- 输出层更大
- 参数量增加
- 稀有 token 的统计可能更分散

### 词表越小，会发生什么

- 文本会被拆得更碎
- 序列更长
- 模型可能需要跨更多 token 才能表达一个词

因此词表大小也是一种折中：

- 大词表：更短序列、更大参数
- 小词表：更小参数、更长序列

后面学到 tokenizer 时，你会更系统地理解这件事。现在你只要先记住：

> 模型不是直接面对“自然语言本身”，而是在一个 tokenizer 定义出来的离散词表空间里工作。

## 第九件事：为什么“生成文本”这个表述既对，又容易误导

说语言模型“会生成文本”当然没错，但它很容易误导你把注意力放错地方。

### 它为什么是对的

因为最终用户看到的，确实是连续文本输出。

### 它为什么又容易误导

因为这个说法掩盖了真正发生的中间过程：

- 文本先被编码成 token
- 模型输出的是 logits
- logits 经由某种采样策略变成 token
- token 再被解码回文本

换句话说：

> “生成文本”是人类视角下的最终结果，而不是模型内部真正操作的对象。

这个区别后面会反复帮你避开很多误会。例如：

- 为什么不同采样策略会改变文本风格
- 为什么同一个 prompt 在不同温度下会得到不同续写
- 为什么模型会重复输出

## 第十件事：什么叫 decoder-only

你在学习小型语言模型项目时，经常会听到这个词：

> decoder-only

### 它大致在说什么

它描述的是一种模型结构路线：

- 模型只依赖前文
- 每个位置预测后文
- 通过因果约束防止偷看未来

这种结构非常适合：

- 自回归文本生成
- next-token prediction 训练目标

### 为什么学习项目常从它开始

因为它有很清晰的主线：

1. 文本切成 token  
2. 用前文预测后文  
3. 用同一个模型做训练与推理  

这让学习路径更集中。

对初学者来说，更重要的不是一开始把“encoder、decoder、encoder-decoder”所有体系都学全，而是先把：

> “只根据前文预测下一个 token”这条主线真正吃透。

## 第十一件事：模型真的“理解”语言吗

这是一个经常被过早问到的问题。

一个更适合学习阶段的问法是：

> 它到底学到了什么样的结构，使它能在很多场景里给出看起来像理解过的输出？

语言模型至少学到了：

- 大量上下文条件下的统计规律
- 某些词法、语法、风格模式
- 一些跨位置依赖关系

在很多任务上，这些结构足以表现出非常像“理解”的行为。

但作为初学者，你现在不必急着陷入哲学争论。更重要的是先搞清：

> 从工程和训练角度，模型为什么能够表现成今天这样。

这套理解才是你后面真正能用来做项目、改代码、查问题的地基。

## 第十二件事：为什么学习阶段最合理的目标是“小而完整”

这是整章最重要的落点之一。

很多人一说“我要学大模型”，脑子里立即出现的是：

- 7B
- 13B
- 70B
- 超大数据
- 超长训练

这对学习项目通常是误导。

### 为什么“大”不适合一开始就追

因为参数规模一上去，你会同时失去很多东西：

- 训练成本快速上升
- 试错速度极慢
- 很多错误看不清
- 很难自己完成全链路

更糟的是，你可能会把大部分时间花在：

- 显存不够
- 安装问题
- 运行环境
- 大量等待

而不是花在真正理解模型为什么这样工作。

### “小而完整”到底是什么意思

它不是说模型要简陋，而是说：

- 数据准备完整
- tokenizer 完整
- 模型主体完整
- 训练闭环完整
- 推理采样完整
- 调试和评估路径也完整

一个规模不算夸张、但链路完整的小模型，已经足够覆盖你真正应该学会的所有关键环节：

- tokenizer
- embedding
- attention
- transformer block
- loss
- optimizer
- sampling
- checkpoint
- 评估
- 缓存推理

这才是学习阶段最宝贵的对象。

> **学习项目的正确目标**
>
>   一个好的小型语言模型学习项目，目标不是“参数量惊人”，而是从数据准备、Tokenizer、模型、训练到采样的整条链路都清晰可读、可修改、可复刻。

## 第十三件事：做一个小型语言模型，真正等于在做什么

到这里可以把整章压缩成一句更完整的话：

> 你不是在“做一个会聊天的黑箱”，而是在构建一个系统：它先把文本切成 token，再把 token 编码为向量，通过多层结构建模前文到后文的统计关系，最后用训练把参数调到更会预测下一个 token，并在推理时通过自回归方式把分布变成文本。

如果这句话你能慢慢拆开，并且每个部分都能大致说出它的职责，那么后面 11 章你就有了真正的入口。

## 常见误区

### 误区 1：语言模型就是“背训练数据”

不准确。它当然可能记住部分内容，但其训练目标是学习条件分布，而不是建立显式句子库。

### 误区 2：训练和推理只是“同一个过程跑两次”

不对。训练时答案已知，推理时答案未知，这会带来根本差异。

### 误区 3：只要模型够大，就自然更适合学习

不对。学习价值来自可理解、可训练、可调试，而不是盲目扩大规模。

### 误区 4：token 就等于单词

不对。token 是 tokenizer 定义出来的离散单位，可能是词、子词、标点或其他片段。

### 误区 5：上下文窗口只是“一个普通长度设置”

不对。它会直接影响训练成本、推理成本和模型可见历史范围。

## 练习题

1. 为什么说语言模型最根本的任务不是“写故事”，而是“预测下一个 token 的分布”？
2. 训练和推理最大的差别，到底是“调用方式不同”，还是“信息条件不同”？
3. 为什么 tokenizer 不应该被当成模型之外的外围小工具？
4. 为什么“小而完整”的学习项目往往比“更大但根本掌控不了”的项目更有价值？
