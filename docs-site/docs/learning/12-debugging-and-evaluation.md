# 12. 评估、调试与迭代

## 这一章要解决什么问题

做到这里，你已经理解了：

- 文本如何变成 token
- 训练目标是什么
- 模型结构如何组成
- 推理时如何生成文本

但真正的学习项目不会在“能跑起来”这一刻结束。你还需要具备一项比继续加公式更重要的能力：

> 当结果不对时，你知道怎么判断问题在哪、怎么缩小范围、怎么一步步修正。

这一章要做的，就是帮助你建立这种评估与调试能力。

## 第一件事：先区分“模型跑起来了”和“模型真的学会了”

一个小型语言模型项目最危险的错觉之一就是：

> 代码能运行、loss 也有数字，所以模型应该已经在正常学习。

这并不一定成立。

因为你可能仍然遇到：

- 目标构造错位
- 数据质量有问题
- 学习率不合理
- 采样策略让输出异常
- 模型在训练集上死记硬背

所以“能运行”只是起点，不是结论。

## 第二件事：评估语言模型时，至少要同时看三类信号

### 1. 训练损失

它告诉你：

> 模型在已经见过的数据上学得怎样。

### 2. 验证损失

它告诉你：

> 模型对未参与参数更新的数据是否也在改善。

### 3. 生成样例

它告诉你：

> 模型最终表现出来的文本行为是否合理。

如果你只看其中一类信号，判断通常会失真。

## 第三件事：为什么 loss 不是唯一标准

loss 非常重要，但它不是全部。

### 为什么重要

因为它是训练目标的直接数值表达，能告诉你模型对真实下一个 token 的平均预测质量。

### 为什么不够

因为你最终关心的不只是“平均分类表现”，还关心：

- 文本是否重复
- 是否容易失控
- 是否会自然结束
- 是否像人话

这些行为虽然和 loss 有关，却不总能从单一数字里直接看出来。

所以一个成熟判断应该是：

> 用 loss 看整体趋势，用生成样例看行为质量。

## 第四件事：perplexity 为什么经常出现

在语言模型领域，你经常会看到 perplexity，也就是困惑度。

对初学者来说，不必一开始沉迷公式，但应该知道：

- 它和语言模型的平均预测不确定性有关
- 它本质上来源于交叉熵或对数似然
- 数值越低通常表示模型对数据越不“困惑”

### 你现在最需要的理解

perplexity 不是另一套完全不同的评估逻辑，它只是把语言模型的预测质量换了一种常见方式表达。

如果你已经理解了 next-token loss，那么理解 perplexity 会容易很多。

## 第五件事：怎样解读训练损失和验证损失的关系

这里有几种非常常见的情况。

### 情况 A：训练损失下降，验证损失也下降

这是最理想的情况，说明模型既在学习训练集，也在验证集上改善。

### 情况 B：训练损失下降，但验证损失停滞甚至恶化

这通常意味着：

- 开始过拟合
- 数据不足
- 训练时间过长
- 模型容量和正则化不平衡

### 情况 C：两边都几乎不降

优先怀疑：

- 数据或目标构造问题
- 学习率不合适
- 训练步数太少
- 模型规模或初始化不合理

### 为什么这种对照非常重要

因为只看训练损失，你很容易把“会记忆”误当成“会泛化”。

## 第六件事：固定 prompt 的样例比较，是观察行为最有效的方法之一

一个非常实用的习惯是：

- 选几个固定 prompt
- 在不同训练阶段反复用它们做生成
- 保持大部分解码参数不变

这样你能更清楚地观察：

- 文本长度有没有变自然
- 重复有没有减少
- 逻辑是否更连贯
- 收尾是否更合理

如果每次都换 prompt、换采样参数、换 checkpoint，你很难形成稳定判断。

## 第七件事：过拟合极小数据，是最强的训练链路检查方法之一

这是小型语言模型学习中极其重要的一招。

### 做法是什么

只拿极少量样本，比如一两个 batch，反复训练很多步，看模型能不能把这些样本拟合得非常好。

### 为什么这一招特别有效

因为如果：

- 数据输入没问题
- 目标构造没问题
- 前向没问题
- 反向没问题
- 参数更新也没问题

那么一个有足够容量的小模型通常应该能快速记住极小样本。

### 如果连这个都做不到

优先怀疑的往往不是“数据太难”，而是：

- loss 构造错了
- 目标错位了
- 梯度没真正更新
- 学习率严重不对
- 模型有实现错误

所以这是一种非常强的链路健康检查。

## 第八件事：调试时一定要先把问题分类

遇到异常时，不要立刻乱改。先问：

### 这是数据问题吗

例如：

- 文本清洗不合适
- tokenizer 粒度不合理
- special token 边界不清
- 训练/验证数据分布差异过大

### 这是模型结构问题吗

例如：

- mask 错误
- 位置编码使用不当
- block 结构缺了关键部件
- 输出层维度不匹配

### 这是训练流程问题吗

例如：

- 学习率过大或过小
- batch 配置不合适
- 训练步数太少
- 梯度累积或 mixed precision 使用不当

### 这是解码问题吗

例如：

- temperature 太极端
- top-k/top-p 过于保守或过于放开
- EOS 处理不合理

### 这是评估方式问题吗

例如：

- 只看 loss 不看样例
- prompt 选得太随机
- 每次比较条件都在变

分类越早，调试越高效。

## 第九件事：为什么“一次只改一个主要变量”几乎是铁律

这是调试中最容易违反、也最值得遵守的规则。

如果你同时改：

- 学习率
- 上下文长度
- 模型层数
- 采样参数

那你最后无法知道到底哪个改动起了作用。

所以一个有效实验应该尽量满足：

- 只改一个主要变量
- 其他条件保持不变
- 记录改动前后的差异

这样你才能建立因果判断，而不是只得到一堆印象。

## 第十件事：为什么生成问题不一定等于训练问题

如果模型生成结果很差，很多人第一反应是：

> 模型没学会。

这有时是对的，但不总对。

生成问题也可能来自：

- prompt 过短或过怪
- greedy 太保守
- temperature 太高导致发散
- top-k/top-p 设置不合适
- EOS 处理不好

所以当你看到输出异常时，要先区分：

- 是模型本身分布学得不好
- 还是你从分布中取样的方法让输出变差了

## 第十一件事：跨平台差异应该怎样理解

如果你在不同设备上实验，比如：

- CPU
- Apple MPS
- CUDA GPU

出现一些差异是正常的。

### 正常差异包括

- 浮点误差细节不同
- 随机采样结果不同
- 混合精度支持和行为不同

### 真正需要警惕的是

- 一边能正常下降，另一边完全不学
- 一边经常数值爆炸，另一边稳定
- 同样条件下行为差异大到无法解释

因此正确目标不是：

> 两边每一步结果逐位完全一致。

而是：

> 逻辑一致、趋势可解释、质量处于同一合理范围。

## 第十二件事：调试时最有用的方法论是什么

把它压缩成一句非常实用的话：

```text
现象 -> 假设 -> 最小复现 -> 修复 -> 回归验证
```

例如：

### 现象

训练损失不降。

### 假设

输入和目标没有正确右移。

### 最小复现

拿一个极小样本，人工检查 token 切片和目标位置。

### 修复

改正样本构造逻辑。

### 回归验证

重新跑：

- 极小数据过拟合实验
- 正常训练若干步
- 固定 prompt 生成对照

这就是成熟调试。不是“这里看着不太对，我顺手再改三个地方看看”。

## 第十三件事：好的实验记录为什么会大幅提高学习效率

很多人觉得记录实验很麻烦，但它的回报非常高。

你至少应该尽量记下：

- 训练配置
- 学习率和 batch 设置
- 训练步数
- 关键 loss 变化
- 生成样例观察

这样你才能回答：

- 这次改动到底带来了什么
- 某次成功结果是怎么来的
- 失败实验为什么失败

否则你很容易反复回到已经验证过的错误路径。

## 第十四件事：初学者最容易误解的几点

### 误区 1：loss 在降，所以一切都对

不对。数据泄漏、目标错位、采样异常都可能被短期 loss 变化掩盖。

### 误区 2：输出文本不好，就一定是模型太小

不一定。训练不足、数据问题、解码设置不当都可能导致差输出。

### 误区 3：测试和评估属于项目最后阶段

不对。越早建立最小评估和最小验证，越容易排除隐蔽错误。

### 误区 4：跨平台差异一定表示有一边错了

不对。先区分正常数值差异和真正逻辑异常。

### 误区 5：一次改很多东西更省时间

通常正好相反。那会直接破坏你的判断力。

<Callout title="这一章真正要你学会的不是“修一个 bug”，而是建立判断方法" tone="success">
  做完一个小型语言模型项目最珍贵的收获，不只是“我训练出了一个模型”，而是“当训练、生成或评估结果不对时，我知道如何分类问题、构造最小复现、逐步缩小范围并验证修复”。这才是从 0 迈向独立实践的真正能力。
</Callout>

## 练习题

1. 为什么评估一个语言模型时，至少要同时看训练损失、验证损失和生成样例？
2. 过拟合极小数据为什么能有效检查训练链路健康？
3. 为什么生成问题不能直接等同于训练问题？
4. 跨平台实验时，什么样的差异是正常的，什么样的差异需要警惕？
5. 为什么调试时“一次只改一个主要变量”几乎是必须遵守的规则？
