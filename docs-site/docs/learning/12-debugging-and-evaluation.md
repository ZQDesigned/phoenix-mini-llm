# 12. 调试与评估

## 这一章要解决什么问题

做出一个能跑的项目，不等于做出一个你能诊断和改进的项目。最后一章的目标，是让你在看到“损失不降”“输出重复”“跨平台结果差异很大”这些现象时，知道自己应该先检查什么。

## 你需要先知道什么

- 已理解训练闭环、采样和 KV cache。
- 已知道项目需要在 macOS 与 Windows CUDA 之间切换。

## 核心概念

### 1. 先用“过拟合极小数据”检查训练链路是否正确

一个非常有效的调试方法是：

- 只取极少量样本
- 训练很多步
- 看训练损失能否快速下降

如果连极小数据都压不下去，问题通常出在：

- loss 构造
- target 错位
- mask
- 学习率
- 梯度没有正确更新

### 2. 训练损失和验证损失要一起看

几种常见现象：

- 训练损失降，验证损失也降：正常
- 训练损失降，验证损失不降：可能过拟合
- 两边都不降：模型或训练流程有问题

### 3. 重复输出通常不是“模型太笨”这么简单

重复可能来自：

- 训练不充分
- 采样过于贪心
- 温度过低
- top-k / top-p 设置不合理
- tokenizer 或 `eos` 处理有问题

### 4. 跨平台差异是正常现象，不是所有差异都算 bug

macOS MPS 和 Windows CUDA 之间，可能会在这些地方出现差异：

- 精度路径
- 随机性
- AMP 支持
- 内存行为

正确目标不是逐步数值完全一致，而是：

- 训练趋势一致
- 代码逻辑一致
- 输出质量处于可解释范围

### 5. 单元测试和运行时检查要配合使用

测试适合抓：

- shape 错误
- cache 行为错误
- checkpoint round-trip 问题

运行时检查适合抓：

- loss 曲线异常
- GPU OOM
- 长文本生成退化

## 最小必要数学

这章没有新的核心公式，但你需要形成一个判断框架：

```text
现象 -> 假设 -> 最小复现实验 -> 修复 -> 回归验证
```

不要一看到输出不理想，就连续改五个参数。那样你最后不会知道到底是哪一处起了作用。

## 最小代码实验

一个很有价值的调试动作是记录固定 prompt 下的生成结果：

```python
prompt = "Once upon a time"

for temperature in [0.7, 1.0, 1.3]:
    text = generate(prompt=prompt, temperature=temperature)
    print(temperature, text)
```

如果输出差异极端异常，你就可以围绕采样策略继续缩小问题范围。

## 常见误区

### 误区 1：loss 在降就不需要看样例输出

不够。数值好看不等于文本行为合理。你需要同时看：

- loss
- 验证结果
- 生成样例

### 误区 2：跨平台差异说明其中一边一定错了

不一定。只要逻辑一致、趋势合理、精度路径解释得通，出现少量数值差异是正常的。

### 误区 3：调试时同时改很多变量更快

通常相反。一次只改一个维度，才有可能建立因果判断。
