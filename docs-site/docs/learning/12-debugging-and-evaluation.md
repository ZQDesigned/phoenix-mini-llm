# 12. 评估、调试与迭代

这一章是 `learning` 顶层速读线的最后一章。

它承担的职责，是把“模型已经能训练、也能生成”之后最关键的能力提炼出来：

> 你如何判断它到底学得怎样，如何解释它为什么会这样，以及当结果不对时如何把问题缩小到真正可验证的范围。

很多初学者在这一阶段最容易犯的错误，是把项目目标理解成：

```text
代码能跑 + loss 有数字 + 样例能出字 = 项目完成
```

这远远不够。

因为真正让你成长为“会做模型项目的人”的，并不是第一次把程序跑通，而是：

- 知道哪些信号值得相信
- 知道哪些现象只是表象
- 知道怎样把模糊异常翻译成可诊断问题
- 知道每次迭代到底让系统更真还是只让你更安心

所以这一章要先建立一个总判断：

> 对语言模型项目来说，评估和调试不是收尾动作，而是训练与推理之后必须持续接上的理解系统。

## 12.1 为什么“能运行”不等于“学会了”

这是学习项目里最危险的错觉之一。

程序能运行，只说明：

- 数据管线没在第一时间崩溃
- 前向和反向至少能走完一轮
- loss 至少有数值

但这并不自动说明：

- 输入和目标构造是对的
- 参数真的在被有效更新
- 模型在验证集上也在改善
- 生成文本已经开始自然
- 当前输出能稳定复现

所以在项目里，“跑起来”只是入口，不是结论。

更成熟的思维方式是：

> 每当你看到一个“看起来还行”的现象，都要立刻追问：它到底证明了什么，没有证明什么？

## 12.2 为什么语言模型评估不能只看一个数字

语言模型同时具有两种身份：

- 它是一个概率预测系统
- 它也是一个会滚动生成文本的行为系统

如果你只看一个数字，例如只看训练 loss，你就只能看到第一种身份的一部分。

但用户真正感受到的，往往是第二种身份：

- 会不会重复
- 会不会拖尾
- 是否真的回答了问题
- 结构是否自然
- 停止是否合理

这说明语言模型评估天然就必须是多视角的。

没有任何单个指标，能替代整个判断体系。

## 12.3 三类最基本的评估信号分别在回答什么

至少在学习项目里，你应该同时建立三类信号。

### 第一类：训练损失

它回答的是：

> 模型在已经参与更新的数据上，平均 next-token 预测学得怎样。

它适合用来看：

- 有没有在学
- 训练过程是否大体稳定
- 某个设置是否完全跑偏

### 第二类：验证损失或困惑度

它回答的是：

> 模型在未参与本轮更新的数据上，平均预测能力是否也在改善。

它适合用来看：

- 有没有泛化迹象
- 是否开始过拟合
- 哪个 checkpoint 更值得保留

### 第三类：固定 prompt 的生成样例

它回答的是：

> 模型作为一个真实生成系统，输出行为到底长什么样。

它适合用来看：

- 是否自然
- 是否重复
- 是否收尾合理
- 是否真的更接近你的任务目标

这三类信号联合起来，才构成一个最基本的评估框架。

## 12.4 为什么 loss 很重要，但永远不是全部

loss 的价值非常高，因为它直接对应训练目标。

如果你完全不看 loss，训练几乎没有仪表。
但如果你只看 loss，也非常危险。

原因在于：

> loss 测量的是平均局部预测质量，而生成质量反映的是这套局部预测滚动展开后的整体行为。

二者高度相关，却不完全同步。

因此你完全可能看到：

- loss 下降了，但样例只略有改善
- loss 下降了，但重复仍然明显
- loss 变化不大，但固定 prompt 的结构稳定性变好了

如果不理解这种“相关但不等价”的关系，你就会不断误读模型状态。

## 12.5 为什么固定 prompt 样例是极其重要的评估工具

很多人会随手输入几个 prompt 来“感觉一下模型”。

这当然比完全不看样例强，但仍然不够稳。

更成熟的做法是：

> 准备一组固定 prompt，在不同 checkpoint、不同超参数、不同采样器下反复比较。

这样你能观察到的不再只是“今天这条看着还行”，而是：

- 哪些问题在稳定改善
- 哪些失败模式反复出现
- 哪些改动只是碰巧更好看
- 哪些进步是真正稳定可复现的

固定 prompt 的真正价值，在于把主观印象变成可对照证据。

## 12.6 为什么停止与重复应该被单独盯住

很多初学者评估时只看：

- 会不会说人话
- loss 是否在降

但对语言模型来说，停止与重复本身就是核心行为维度。

你至少要持续观察：

- 是否经常拖到长度上限
- 是否容易在结尾重复
- 是否会过早结束
- 是否在开放式生成中越写越散

这些问题常常在暴露更深层的系统问题：

- 数据边界不清
- EOS 学得不稳
- 解码策略过于保守或过于发散
- 长程组织能力不足

它们不是“体验细节”。
它们是模型行为结构本身的一部分。

## 12.7 为什么困惑度不是神奇总分

困惑度很常见，也很有用，但不要把它神化成唯一答案。

更稳的理解是：

> 它是验证 loss 在语言模型语境中的一种常见重表达。

它特别适合用来看：

- 模型平均预测是否在变强
- checkpoint 间的纵向变化

但它不能单独告诉你：

- 文本是否自然
- 结构是否清楚
- 是否会重复
- 是否更像你的目标场景

所以困惑度很重要，但只属于评估系统的一部分，而不是全部。

## 12.8 为什么调试最重要的能力不是“试得多”，而是“缩得对”

结果一旦不对，很多人第一反应是：

- 改模型层数
- 改学习率
- 改采样器
- 改 tokenizer
- 改数据清洗

问题不是他们不努力，而是：

> 一下子同时改太多层，会让每次变化都失去因果解释力。

系统化调试的核心不是乱试，而是：

- 缩小问题空间
- 逐层验证假设
- 让每个实验都携带可解释信息

这是调试里最重要的能力。

## 12.9 为什么极小样本过拟合测试如此强大

如果你只能记住一种调试方法，那就先记住这一种。

极小样本过拟合测试做的事情很简单：

> 只拿极少量数据，看看模型能不能在很短时间里把它们记住。

它之所以强，是因为它在检查整条最小学习链路到底通不通：

```text
数据 -> 目标 -> 前向 -> loss -> 反向 -> 参数更新
```

如果模型连非常容易的小样本都过拟合不了，那你就应该优先怀疑：

- 输入与目标是否对齐
- mask 或 loss 实现是否有问题
- 梯度有没有真的更新参数
- 学习率是否严重不对
- 数值路径是否已经崩坏

这比一上来改大型结构更有效得多。

## 12.10 为什么调试时应该按系统层切，而不是按“直觉像哪里坏了”切

成熟调试最有效的方法之一，是按系统层切问题。

### 数据层

检查：

- 原始文本是否合理
- tokenization 是否符合预期
- 样本边界是否正确
- BOS、EOS、padding 是否按设计工作

### 目标层

检查：

- 输入和标签是否右移正确
- ignore index 是否设置合理
- loss 是否只在应有位置计算

### 模型层

检查：

- 张量 shape 是否一路正确
- mask 是否真的生效
- logits 维度是否对词表对齐

### 优化层

检查：

- 梯度是否在传播
- 参数是否真的更新
- 学习率是否过大或过小
- mixed precision 是否引入异常

### 推理层

检查：

- greedy 行为是否合理
- 停止条件是否按预期工作
- cache 是否正确复用
- 采样器是否改变了行为解释

一旦你按层切问题，调试就会从“凭感觉试”变成“带结构排查”。

## 12.11 为什么“这个现象证明了什么”是比“它看起来怎么样”更重要的问题

很多项目在中后期容易陷入一种低质量评估方式：

- 看一条样例觉得不错
- 看一个数字觉得还行
- 看一次训练没崩觉得大概稳了

这种感觉式判断非常脆弱。

更强的做法是每次都追问：

### 这条样例证明的是生成更自然，还是只是刚好碰巧顺了一次

### 这个 loss 下降证明的是训练集更合适，还是泛化也在变好

### 这个 checkpoint 更好，是因为真的更优，还是因为采样器碰巧配合得更好

也就是说，评估和调试真正依赖的是：

> 证据意识。

如果没有证据意识，项目很容易被偶然现象牵着走。

## 12.12 为什么每次迭代都应该尽量只回答一个问题

这是一条非常实用的工作原则。

每次实验如果同时改动：

- 数据
- 模型
- 学习率
- 采样器

你最后即使结果变好了，也很难知道：

- 到底是哪一层起了作用

更好的做法是让每次迭代尽量只回答一个问题。

例如：

- 只验证训练链路是否能过拟合极小样本
- 只验证 warmup 是否改善早期稳定性
- 只验证 top-p 是否减少尾部乱跳

这种做法会让你的项目慢一点点，但理解会快很多。

## 12.13 为什么语言模型项目特别需要“定量 + 定性”联合评估

如果你只做定量评估，容易失去行为层判断。

如果你只做定性评估，容易被偶然样例欺骗。

所以最稳的做法是联合使用：

### 定量信号

- training loss
- validation loss
- perplexity
- step / token 进度

### 定性信号

- 固定 prompt 样例
- 重复与停止行为
- 段落结构
- 风格稳定性

只有两者一起看，语言模型项目才有较稳的解释力。

## 12.14 为什么“评估好坏”和“解释原因”是两种不同能力

这是初学者特别容易混在一起的两件事。

你可能能说：

- 这个 checkpoint 看起来更好

但这还不等于你能解释：

- 它为什么更好

同样地，你可能能观察到：

- 模型经常重复

但这还不等于你已经定位到：

- 重复是来自训练问题、解码问题、还是停止机制问题

所以评估和调试虽然紧密相连，但不是同一件事：

### 评估回答

- 现在状态如何

### 调试回答

- 为什么会这样
- 下一步该如何验证

理解这一点后，你会更容易建立清晰的方法感。

## 12.15 为什么“会复盘”是学习项目里最容易被忽视的高级能力

很多人把项目复盘理解成：

- 写写总结
- 记录踩坑

这些当然有价值，但真正更深的复盘是：

> 回头看每次关键变化时，你是否能解释自己当时为什么判断、依据是什么、后来结果证明了什么。

这类复盘能帮助你沉淀出：

- 哪些信号最可靠
- 哪些指标最容易误导
- 哪些排障路径最有效

长期来看，这种能力比“再多跑几次实验”更重要。

## 12.16 为什么评估体系本身也要被设计

很多初学者会把评估理解成：

- 训练完了再顺便看几眼

但一个成熟项目应该主动设计评估体系。

至少要提前决定：

- 固定看哪些训练指标
- 固定保存哪些 checkpoint
- 固定使用哪些验证集
- 固定比较哪些 prompt
- 固定记录哪些异常

这样做的意义在于：

> 让项目的判断标准在不同迭代之间保持稳定。

没有稳定评估体系，所有实验都很难形成累积知识。

## 12.18 本章读完后，你应该建立哪些稳定判断

如果这一章真正读懂了，你至少应该形成下面这些判断。

### 判断一：能运行，不等于学会了

这是所有后续判断的出发点。

### 判断二：语言模型评估天然必须是多视角的

没有哪个单独指标能替代整个判断系统。

### 判断三：调试的关键不是多试，而是缩小问题空间

没有分层，没有解释，就没有真正的调试。

### 判断四：极小样本过拟合是最强的健康检查之一

它能快速检验最小学习链路是否真的通了。

### 判断五：评估和复盘不是项目收尾，而是迭代能力的核心

项目能不能持续变好，很大程度取决于你是否真的会判断和会排错。

## 12.19 如果你现在只能记住这一章的一句话

可以先记住这一句：

> 在语言模型项目里，真正的进步不是第一次把代码跑通，而是建立起一套能同时判断“现在状态如何”和“为什么会这样”的评估、调试与迭代系统。

只要这句话没有丢，后面无论你继续扩模型、改训练、调采样还是做部署，都会更知道自己在做什么。
