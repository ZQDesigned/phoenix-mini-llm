# 02. Python、命令行与最小实验环境

## 这一章要解决什么问题

很多人一提到“大模型基础”，就立刻把注意力放到：

- Transformer
- Attention
- Tokenizer
- 损失函数

这些当然重要，但如果你连最基本的实验环境都不稳，后面所有知识都会变得很难真正掌握。因为你会不断被下面这些问题打断：

- Python 版本不对
- 包装不起来
- 命令不会跑
- 路径经常写错
- 环境切换后结果混乱

这一章不是要把你训练成 DevOps 工程师，而是要帮你建立一个足够稳、足够轻、足够适合学习的小型实验环境观念。

读完之后，你应该知道：

- 做小型语言模型学习项目，最少需要哪些工具能力。
- 为什么命令行、Python 环境隔离和包管理不是附属知识。
- 什么样的项目环境最适合初学者反复实验和调试。
- 哪些工程复杂度可以先不碰，哪些基础习惯必须尽早养成。

## 第一件事：你真正需要的不是“最强环境”，而是“最稳的最小环境”

很多初学者一开始会犯一个典型错误：

> 想把环境一次性配到最完整、最专业、最像大型研究团队。

这通常会带来反效果。因为学习初期你真正需要的是：

- 能稳定安装 Python 和依赖
- 能在终端跑脚本
- 能明确当前到底用了哪个解释器
- 能重复得到相同结果

换句话说，你的第一目标不是“环境最复杂”，而是：

> 环境足够简单，简单到你能解释它、重建它、修复它。

这和模型学习本身是同一个原则。

## 第二件事：为什么命令行能力是必须的

语言模型学习项目不是纯图形界面任务。你迟早会做这些事：

- 安装依赖
- 运行训练脚本
- 切换配置
- 查看日志
- 执行测试
- 读取和整理数据

这些动作几乎都离不开终端。

### 初学者至少要会哪些命令概念

你不需要一开始就成为 shell 高手，但至少要理解：

- 当前目录是什么
- 如何进入某个目录
- 如何查看文件列表
- 如何执行一个 Python 脚本
- 如何安装一个 Python 包

如果连这些都不熟，后面你会把很多本来属于“模型问题”的困惑，误判成“电脑为什么又坏了”。

## 第三件事：Python 为什么是这类学习项目的主语言

对于从 0 开始实现小型语言模型，Python 是最合适的起点，原因很务实：

- PyTorch 生态成熟
- 文本处理和数据处理库丰富
- 可读性高
- 社区示例和资料最多
- 调试门槛相对低

这并不意味着更底层语言不重要。只是对学习顺序来说，更合理的是：

> 先用 Python 把模型原理、训练链路和推理链路真正跑通，再考虑更底层的性能优化。

如果你一开始就把注意力放在：

- CUDA 扩展
- C++ 推理引擎
- 极致性能调优

通常只会把学习目标打散。

## 第四件事：为什么必须隔离环境

“环境隔离”听起来像工程洁癖，但对学习项目来说，它是避免混乱的最基本手段。

### 什么叫环境隔离

最简单的理解就是：

> 每个项目拥有自己独立的 Python 解释器和依赖集合，而不是和系统里其他项目混在一起。

### 为什么这很重要

如果你不隔离环境，很快就会遇到这些问题：

- A 项目需要某版本 `torch`
- B 项目需要另一个版本
- 你升级了一个包，旧项目突然坏掉
- 你根本说不清现在到底在用哪套依赖

这类问题不会帮你理解模型，只会持续消耗精力。

所以你应该尽早形成习惯：

- 每个项目单独环境
- 尽量用锁文件或固定依赖版本
- 明确解释器路径

## 第五件事：包管理工具的职责是什么

很多初学者把包管理理解成：

> 安装库的那个命令。

这太窄了。包管理工具真正负责的是：

- 安装依赖
- 解析版本关系
- 管理项目环境
- 让别人能较稳定地重建你的开发环境

### 选择工具时最重要的标准是什么

对于学习项目来说，最重要的不是“社区争论谁最高级”，而是：

- 命令是否清晰
- 是否支持虚拟环境
- 是否支持锁定依赖
- 是否足够快、足够稳定

无论你最终选择：

- `uv`
- `venv + pip`
- 其他常见工具

核心目标都应该是：让环境可重复，而不是靠记忆临时拼出来。

## 第六件事：为什么你需要最少量的 Python 工程组织能力

这一章不要求你马上理解大型软件工程，但至少要理解下面这些概念。

### 1. 模块

当你的项目开始包含多个 `.py` 文件时，它们就不再是孤立脚本，而是模块之间的协作。

### 2. 包

如果你把相关模块放进同一个目录，并让它们形成一个可导入的结构，这个目录就成了一个 Python 包。

### 3. 入口脚本

训练、评估、生成通常会分别有自己的入口脚本。这些脚本不是模型本体，而是告诉解释器：

> 现在要执行哪一种任务。

### 为什么这些概念必须尽早知道

因为一旦项目超过一两个文件，如果你还把所有内容塞进一个脚本里，后面只会越来越难读、越来越难改、越来越难测。

## 第七件事：你至少要能看懂这几类 Python 代码

为了继续往后学，你应该能读懂下面这些最基本的模式。

### 函数

```python
def add(a: int, b: int) -> int:
    return a + b
```

你要知道：

- 函数接收输入
- 函数返回输出
- 类型标注只是说明预期，不是魔法

### 类

```python
class Counter:
    def __init__(self) -> None:
        self.value = 0

    def step(self) -> None:
        self.value += 1
```

你要知道：

- `__init__` 是初始化
- `self` 表示对象自身
- 类适合组织“有状态”的行为

### 条件判断与循环

```python
for x in items:
    if x > 0:
        print(x)
```

这些都是后面训练循环、数据预处理、采样逻辑最基本的语法地基。

## 第八件事：文件路径和跨平台意识为什么必须及早形成

如果你只在一台电脑上玩几天脚本，路径问题似乎不重要。但学习项目往往很快会碰到：

- macOS 上开发
- Windows 上训练
- 不同目录结构
- 相对路径和绝对路径混用

### 你应该尽早养成的习惯

- 明确“当前工作目录”和“项目根目录”不是一回事
- 尽量用路径对象而不是手写硬编码字符串
- 不把个人机器上的绝对路径写进项目逻辑

### 为什么这和模型学习有关

因为一旦路径习惯混乱，你很多时间都会浪费在：

- 找不到文件
- 数据加载失败
- checkpoint 保存位置不一致

这些问题和模型原理无关，却会持续阻断学习。

## 第九件事：你不需要一开始就押注 Notebook

很多人做机器学习时习惯先开 Notebook。这当然可以用于：

- 做小实验
- 看几组数据
- 临时可视化

但如果你的目标是亲手做一个完整小型语言模型，尽早把主体逻辑写进普通 Python 文件通常更稳。

### 为什么

因为当项目开始包含：

- tokenizer
- 数据处理
- 模型定义
- 训练循环
- 生成逻辑

Notebook 很容易变得：

- 状态不透明
- 执行顺序混乱
- 代码复用困难

所以更合理的学习顺序通常是：

- Notebook 用于短实验
- 主体逻辑写成 `.py` 文件

## 第十件事：PyTorch 在环境中扮演什么角色

这套学习路线默认使用 PyTorch。你此刻不需要掌握它的全部 API，但要知道：

- 它提供 tensor 运算
- 它提供自动求导
- 它提供神经网络模块
- 它让模型、训练和推理可以在统一框架下实现

因此，一个可用的最小实验环境，通常至少包括：

- Python
- PyTorch
- 基本文本或数据处理依赖
- 测试工具

这并不是在强调“装越多越好”，而是在强调：

> 至少要有一套能支撑后面 12 章实践的基础工具链。

## 第十一件事：什么叫“最小但正确”的学习环境

如果把这一章压缩成一句最实用的话，那就是：

> 你的环境应该足够小，小到你能完全掌控；同时又足够完整，能稳定支撑数据处理、模型训练、评估和生成。

一个好的学习环境通常具有这些特征：

- 一个清晰的 Python 版本
- 一个独立项目环境
- 一套能重建的依赖声明
- 一种你自己能解释的运行方式

而不是：

- 东装一个库，西装一个库
- 不知道当前解释器来自哪里
- 代码能跑，但别人无法复现

## 第十二件事：初学阶段最常见的环境误区

### 误区 1：环境越复杂越专业

不对。复杂不等于专业，复杂往往只意味着更难排错。

### 误区 2：只要我这台机器能跑就行

不够。你应该尽量让环境具备可重复性，否则每次重装和迁移都会很痛苦。

### 误区 3：命令行只是安装工具时临时用一下

不对。后面跑训练、评估、生成、测试都离不开终端。

### 误区 4：Notebook 可以承载整个项目

通常不适合。项目一旦扩大，普通脚本和模块组织会更稳。

### 误区 5：路径问题属于“以后再说”

不对。跨平台、跨目录、跨环境的问题越晚处理，代价越大。

<Callout title="这一章真正想让你形成的习惯" tone="warning">
  先把最小实验环境搭稳，再学模型细节。对初学者来说，一个清晰、独立、可重建的 Python 环境，比一开始追求复杂工具链更重要。
</Callout>
