# 02. Python、命令行与最小实验环境

## 这一章要解决什么问题

很多人提到“大模型基础”，第一反应都会立刻跳到模型本身：

- Transformer
- Attention
- Tokenizer
- Loss

这些当然重要，但如果你连最基本的实验环境都不稳，后面所有学习都会不断被非本质问题打断：

- Python 版本为什么不对？
- 为什么刚才还能跑，现在突然不能跑了？
- 为什么这个包装不上？
- 为什么我明明安装了库，脚本却说找不到？
- 为什么换一台机器、一换目录、一换解释器，结果就全乱了？

这类问题不会帮你理解语言模型，反而会持续偷走你的注意力。

所以这一章的目标不是把你训练成运维或资深工程师，而是帮助你建立一种对学习项目非常关键的判断：

> 对初学者来说，一个“稳、轻、清楚、可重建”的实验环境，比一个“功能齐全但你根本说不清自己在用什么”的环境重要得多。

读完之后，你应该知道：

- 为什么实验环境本身就是学习的一部分。
- 为什么命令行、环境隔离和依赖管理不是外围知识。
- 为什么一个小型语言模型项目需要最少量但明确的工程组织能力。
- 为什么很多初学者不是卡在模型概念，而是先卡死在环境混乱里。

## 第一件事：学习项目真正需要的不是“最强环境”，而是“最稳环境”

初学者很容易犯一个看起来很合理、实际上很常见的错误：

> 既然我要学大模型，那我是不是应该一开始就把环境配得很专业、很重、很完整？

这通常会带来反效果。

### 为什么

因为学习初期你真正最需要的是：

- 能稳定运行代码
- 能明确知道自己现在用的是哪套依赖
- 出问题时能自己定位
- 换台机器或重新创建环境时能较稳定地重现

而不是：

- 工具链越多越好
- 插件越全越好
- 一开始就把所有可能用到的技术全部装上

### 一个重要的学习原则

你在模型结构上追求的是：

> 小而完整。

环境上也一样。你应该追求的是：

> 小而稳。

也就是说：

- 工具不一定最多
- 但路径清楚
- 版本清楚
- 运行方式清楚
- 出问题时你能自己解释

这比“堆出一套看上去很专业的环境”更有学习价值。

## 第二件事：为什么命令行能力不是可选项

如果你的目标只是偶尔点几下图形界面，也许可以完全不碰终端。

但做一个小型语言模型学习项目，几乎一定会反复遇到这些动作：

- 创建项目目录
- 安装 Python 依赖
- 启动脚本
- 切换配置
- 查看日志
- 运行测试
- 检查文件和路径

这些动作天然更适合在终端中完成。

### 命令行到底为什么重要

因为终端提供了一种非常直接的能力：

> 你可以清楚地告诉计算机“现在在什么目录、用什么解释器、执行哪个脚本、带什么参数”。

这对机器学习学习项目尤其关键，因为很多问题都和“上下文”有关：

- 当前在哪个目录
- 当前激活的是哪个环境
- 当前用的是哪个 Python
- 当前脚本实际从哪里读取文件

如果这些上下文不清楚，后面的故障看起来就像随机出现。

### 初学者至少要掌握哪些最基本的终端概念

你不需要一开始就精通 shell，但至少要熟悉：

- 当前目录是什么
- 怎样进入某个目录
- 怎样查看文件列表
- 怎样执行一个 Python 脚本
- 怎样安装一个依赖

这些能力看起来简单，但它们会在整个学习过程中不断保护你不被环境噪声拖走。

## 第三件事：为什么 Python 是最合适的起点

从零做一个小型语言模型，Python 通常是最合适的第一语言。

原因很现实：

- PyTorch 生态成熟
- 文本处理工具丰富
- 社区资料最多
- 代码可读性强
- 调试成本相对低

### 这不意味着别的语言不重要

更底层语言当然重要，尤其在：

- 推理优化
- CUDA kernel
- 高性能运行时

这些方向上。

但学习顺序非常重要。更合理的顺序通常是：

1. 先用 Python 把语言模型的核心链路做通  
2. 真正理解训练、推理、tokenizer、attention 这些概念  
3. 再考虑更底层性能实现

如果你一开始就试图同时面对：

- 深度学习概念
- GPU 编程
- 构建系统
- 复杂工程环境

学习面会立刻过度扩散。

## 第四件事：解释器、环境和依赖，到底分别是什么

很多初学者会把这些词混着用，结果一出问题就完全不知道该查哪一层。

### 1. Python 解释器

解释器是“真正执行 Python 代码的程序”。

当你运行：

```bash
python script.py
```

本质上是在让某个 Python 解释器去读取并执行 `script.py`。

### 2. 项目环境

环境可以理解成：

> 这次运行代码时，解释器身边能看到的一整套依赖和配置上下文。

如果项目有独立虚拟环境，那么这个环境里会包含：

- 某个特定 Python 版本
- 某组已安装包
- 这组包对应的版本关系

### 3. 依赖

依赖就是项目需要使用的第三方库，例如：

- PyTorch
- NumPy
- tokenizer 相关库
- 测试工具

### 为什么要把三者分清

因为常见报错往往属于不同层：

- “命令找不到”可能是解释器路径问题
- “模块找不到”可能是环境没激活或依赖没装
- “版本冲突”可能是依赖解析问题

如果你把它们全部混成一句“Python 出问题了”，排错会极其低效。

## 第五件事：为什么环境隔离几乎是学习项目的底线

“环境隔离”这个词听起来很工程化，但本质并不复杂。它的意思是：

> 让每个项目拥有自己独立的一套 Python 解释器和依赖集合，而不是把所有项目的依赖全部混在系统全局环境里。

### 为什么不隔离会出什么问题

假设你有两个项目：

- 项目 A 需要某个版本的 `torch`
- 项目 B 需要另一个版本

如果你把所有包都装在同一个全局环境里，就很容易出现：

- 更新了 A，B 坏了
- 安装了 B，A 的行为变了
- 你根本不知道现在代码到底是依赖哪套包在跑

### 对学习者来说，隔离的真正价值是什么

不是为了“更专业”，而是为了：

- 让问题边界更清楚
- 让项目更容易重建
- 让不同实验互不污染

这对初学者格外重要。因为你的认知负担本来就已经集中在模型上，不应该再让全局环境随机干扰你。

## 第六件事：包管理工具在解决什么

很多人把包管理工具简单理解为：

> 就是安装库的命令。

这太窄了。

包管理工具真正解决的问题包括：

- 安装依赖
- 解析版本关系
- 创建和管理项目环境
- 尽量让环境具备可重复性

### 你应该怎样选择工具

对于学习项目，最重要的不是加入某种社区“工具之争”，而是选一个你自己能解释清楚、能稳定使用的方案。

一个合适的方案应该尽量满足：

- 命令清晰
- 创建环境简单
- 安装依赖稳定
- 版本可记录
- 重建环境代价低

无论你最终使用：

- `uv`
- `venv + pip`
- 其他常见工具

最核心的目标都不变：

> 让项目环境可被重现，而不是靠记忆和运气临时拼出来。

## 第七件事：为什么“我这台机器上能跑”不等于环境没问题

这是一种非常常见的错觉。

有时你手上的代码确实能跑，但环境仍然可能很糟糕，因为：

- 你说不清当前解释器来自哪里
- 依赖版本没有记录
- 换一个目录或换一台机器就会坏
- 项目成员无法重建相同环境

所以一个真正健康的学习环境，不只是“现在能运行”，还应该尽量满足：

- 你知道它是怎么建出来的
- 你知道它依赖哪些关键组件
- 你能在未来较稳定地重新构建它

这就是“可重复性”的意义。

## 第八件事：你至少需要最少量的 Python 工程组织能力

这一章不是要你一下子学会大型工程架构，但如果你准备做一个完整小型语言模型，下面这些最基本的组织概念必须尽早知道。

### 模块

当你的代码不再只有一个文件，而开始拆成多个 `.py` 文件时，这些文件之间就会形成模块关系。

### 包

当一组相关模块被组织进一个可导入结构时，你就拥有了一个 Python 包。

### 入口脚本

训练、评估、生成通常不是同一个入口。不同任务会有不同的启动点。

### 配置

随着项目变复杂，你不可能把所有超参数和路径都硬写在代码里。配置系统会逐渐出现。

### 为什么这些概念必须尽早形成

因为一个完整小型语言模型项目，很快就会同时拥有：

- 数据处理代码
- tokenizer 代码
- 模型定义
- 训练循环
- 生成逻辑
- 测试

如果你还把所有内容塞进一个文件里，后面几乎一定会越来越难读、越来越难改。

## 第九件事：从学习角度看，脚本和模块各自适合什么

这是一个很实用的区分。

### 脚本适合做什么

脚本适合：

- 启动任务
- 串起流程
- 接收命令行参数

例如：

- 准备数据
- 启动训练
- 做一次评估
- 生成文本

### 模块适合做什么

模块更适合承载可复用逻辑，例如：

- tokenizer 函数
- 模型层实现
- 采样函数
- 训练工具函数

### 为什么这种分层有助于学习

因为它会迫使你不断思考：

- 哪些是“执行入口”
- 哪些是“真正逻辑”

一旦你养成这个区分，后面读模型项目会清楚很多。

## 第十件事：为什么文件路径和目录意识必须及早建立

如果你只写几十行单文件脚本，路径问题看起来好像不重要。

但一旦你开始做完整学习项目，很快就会碰到：

- 数据文件放在哪
- tokenizer 产物放在哪
- checkpoint 保存在哪
- 当前脚本相对谁来找文件

### 初学者常见错误是什么

- 把个人电脑上的绝对路径直接写进代码
- 不清楚当前工作目录和项目根目录的区别
- 换个目录执行脚本就失效

### 为什么这会严重影响学习

因为这些错误会让你把大量时间浪费在：

- 找不到文件
- 读错文件
- 输出写到意料之外的位置

这些问题和模型概念本身无关，却会反复打断你。

所以你应该尽早建立一种路径意识：

> 任何项目里，文件是怎么被找到的、结果是写到哪里的，这些都必须是可解释的。

## 第十一件事：Notebook 的角色应该是什么

很多人做机器学习时第一反应就是打开 Notebook。这当然有它的价值。

### Notebook 适合做什么

- 快速试验一小段代码
- 查看数据样本
- 做可视化
- 做临时推导或小实验

### Notebook 不太适合做什么

当项目开始拥有：

- 多个模块
- 多个入口
- 明确训练流程
- 需要重复执行

Notebook 就容易变得：

- 状态混乱
- 执行顺序不透明
- 难以复现
- 难以测试

所以更合理的做法通常是：

- Notebook 用于局部实验
- 主体逻辑写进普通 Python 文件

这不是在排斥 Notebook，而是在给它一个更合适的位置。

## 第十二件事：什么叫“最小但正确”的学习环境

如果把这一整章压缩成一句最务实的话，那就是：

> 你需要的不是一套最华丽的环境，而是一套你自己能解释、能重建、能排错、能稳定支撑实验的小环境。

一个健康的学习环境通常至少具有：

- 一个清晰的 Python 版本
- 一个独立项目环境
- 一组可声明的依赖
- 一种明确的运行方式
- 一种你自己能理解的目录与路径组织

### 它不需要一开始就具备什么

它不需要从第一天就：

- 覆盖所有平台
- 支持所有硬件
- 有完整 CI/CD
- 拥有复杂部署系统

那些都可以后面逐步加。但基础环境必须先稳。

## 第十三件事：初学者最容易在哪些环境问题上浪费时间

### 1. 不知道自己在用哪个解释器

结果是：

- 安装了包却导入失败
- 同一个命令换个终端行为不同

### 2. 所有项目共用一套全局依赖

结果是：

- 一个项目升级，另一个项目坏掉

### 3. 依赖没有记录

结果是：

- 过一周后自己都复现不出来

### 4. 主体逻辑全塞进 Notebook

结果是：

- 状态错乱
- 执行顺序不可追踪

### 5. 路径写死

结果是：

- 一换目录或一换机器就失败

如果你能尽早规避这些问题，后面的学习节奏会快很多。

## 第十四件事：这一章和后面模型章节的关系是什么

你可能会觉得：

> 这一章似乎没有在讲 Attention、本体模型、训练目标。

但它其实在做一件更基础的事：

> 保证你后面学到的每个模型概念，都能被你放进一个可运行、可试验、可重复的环境里。

否则后面再好的概念，也很容易因为环境混乱而变成“我看懂了，但我做不出来”。

> **这一章真正要你形成的习惯**
>
>   对学习项目来说，环境不是附属物。一个清晰、独立、可重建、可解释的最小实验环境，本身就是你能否真正学会小型语言模型开发的前提之一。

## 练习题

1. 为什么说一个学习项目最需要的是“最稳的最小环境”，而不是“最强的最大全家桶环境”？
2. 解释器、环境和依赖，分别在解决什么问题？
3. 为什么“我这台机器上能跑”并不自动意味着环境健康？
4. 为什么完整项目的主体逻辑通常不适合完全依赖 Notebook？
5. 如果一个人总是写死绝对路径，他后面最容易在哪些地方持续浪费时间？
