# 04. 子词分词、BPE 与 tokenizer 训练

## 为什么现代语言模型很少只用“纯字符”或“纯词”

当你第一次知道 tokenizer 要把文本切成 token 时，一个非常自然的问题就是：

> 为什么不直接按字符切，或者干脆按词切？

看起来这两种方式都很直观。

而且它们都很容易向人解释：

- 按字符切，好像最底层最保险
- 按词切，好像最符合人类直觉

但真正做语言模型时，这两种方式都会很快暴露出明显问题。

这也是为什么现代语言模型通常不把“字符”或“完整词”当作唯一默认答案，而更常落到子词方法上。

所以这章真正要回答的不是“BPE 的步骤是什么”，而是更底层的三个问题：

1. 为什么字符级和词级都不够理想？  
2. 子词到底在试图解决什么矛盾？  
3. BPE 这类方法究竟是怎样从统计结构中学出一套离散积木的？  

## 先看纯字符级：为什么它看起来通用，却常常太碎

字符级方法最吸引人的地方，是它非常“保底”。

如果你把基本单位定义成字符，那么：

- 词表通常比较小
- 理论上几乎不会遇到完全无法表示的新词
- 所有文本都能被拆开

这听起来很美好。

例如一个新词、错拼词、很罕见的人名，都可以被拆成字符序列。

从“覆盖率”角度看，字符级很强。

但它的问题在于：

> 它把很多本来稳定、常见、反复出现的较大语义单位拆得太碎了。

这会带来几个直接后果。

### 第一，序列会变长

原本一个词如果整体可以用一个或两个 token 表示，字符级往往要拆成很多步。

序列一长：

- 训练成本上升
- 上下文窗口更快被用完
- 模型要跨更多位置才能恢复语义单位

### 第二，模型必须花更多步骤重建词义

例如模型要理解“language”这个词，如果它每次都只能看到：

```text
l a n g u a g e
```

那它必须依赖更多层和更多上下文，才能把这些碎片重新组合成稳定的高层语义。

### 第三，很多高频模式得不到压缩

如果某个字符串在语料里反复出现，字符级方法仍然会每次把它完全拆开。

这意味着模型不能直接把它当作一个常见积木使用。

所以字符级并不是不能做，而是常常会导致：

- 序列太长
- 压缩效率低
- 上层语义恢复成本高

## 再看纯词级：为什么它看起来自然，却常常太重

纯词级方法的直觉也很强。

因为在人类直觉里，“词”看起来像最自然的语言单位。

如果一个 token 就对应一个完整词，好处很明显：

- 序列会更短
- 单个 token 通常携带更完整的局部语义
- 看起来更像“模型直接在处理词”

但词级方法也会迅速遇到问题。

### 第一，词表会迅速膨胀

自然语言中的词并不是一个小集合。

一旦考虑：

- 专有名词
- 地名人名
- 低频词
- 术语
- 拼写变体
- 多语言混杂

词表就会膨胀得很厉害。

### 第二，未登录词问题严重

如果测试时出现训练词表里没有的词，纯词级方案会很难处理。

这在真实世界里极其常见，因为：

- 新词不断出现
- 人名地名总在变
- 网络表达变化很快
- 代码标识符组合几乎无限

### 第三，大词表会把学习压力转移到稀有类别上

如果词表非常大，那么很多词会非常低频。

低频词对应的 embedding 和输出类别，就很难被充分学习。

于是你会出现一种尴尬局面：

- 词表很大
- 参数很重
- 但长尾词仍然学不好

所以词级方法的问题不是“不自然”，而是：

> 它在统计和计算层面往往太重，也太难处理长尾和新词。

## 子词方法到底在折中什么

现代语言模型常见的思路是：

> 既不完全退回到字符，也不把所有词都当作不可再分的最小单位，而是在两者之间寻找更合适的分解颗粒度。

这就是子词方法的核心直觉。

它希望同时实现几件事：

- 常见高频片段能被整体表示
- 生僻词、新词仍能被拆开
- 词表规模保持在可控范围内
- 序列长度不要膨胀得太厉害

换句话说，子词方法是在平衡三类东西：

- 压缩效率
- 泛化能力
- 词表成本

如果把字符级看成“太细”，词级看成“太粗”，那子词级就是在尝试寻找：

> 一个对统计学习更友好的中间颗粒度。

## 子词为什么特别适合长尾语言世界

自然语言有很强的长尾特征。

少量片段很常见，大量片段很罕见。

在这种世界里，一个好的离散化方案通常需要满足：

- 高频部分尽量压缩
- 低频部分仍然可表示

子词方法正好符合这种需求。

例如一个常见词可以作为整体 token 存在。

但一个新词即使从未整体出现过，也仍然可能被拆成几个已知子词。

这使得模型不需要在“整个词出现过”与“完全不会表示”之间二选一。

它可以通过更细的拼装继续处理罕见输入。

这就是子词方法真正有价值的地方：

> 它给高频单位压缩通道，也给低频单位保留退路。

## BPE 的核心直觉是什么

BPE 可以先不看算法细节，只抓住它最核心的思想：

> 从较细的基本单位出发，不断把高频共现片段合并成更大的 token。

例如，如果某些相邻片段总是经常一起出现，那么把它们合成一个单位通常是有价值的。

这样做会逐步得到一种折中结果：

- 高频模式被压缩成更大的 token
- 低频或新组合仍然可以回退到更细粒度分解

你可以把它理解成：

> tokenizer 在试图找到一套最适合当前语料统计结构的常用语言积木。

这套积木不是人手写的词典，也不是纯语言学切分规则，而是：

> 从语料共现统计里长出来的一套可重复使用片段。

## BPE 不是“懂语言”，而是在压缩统计结构

这点特别重要。

BPE 看起来有时会切出很像词根、词缀或常见短语的单位，但不要误以为它首先是在做人类语言学分析。

更准确地说，它首先在利用：

- 高频共现
- 压缩收益
- 可重复使用的片段模式

因此 BPE 的很多结果会和语言学单位有一定重合，但它的根本驱动力是：

> 数据压缩与统计复用，而不是先验语法知识。

这也是为什么不同语料训练出来的 tokenizer，即使面对同一种语言，也可能学出不同的切分习惯。

因为它们学到的是：

- 哪些片段在这份语料里高频
- 哪些组合最值得合并

而不是某种全局唯一正确的“语言真理”。

## BPE 这个名字从哪来

BPE 原本来自数据压缩领域，名字是 Byte Pair Encoding。

在压缩语境下，它的基本想法是：

> 找到最常一起出现的相邻单位，把它们编码成一个新单位，从而减少整体表示成本。

当这个思想被借用到 tokenizer 世界时，重点不再只是压缩文件大小，而是：

> 学一套既能压缩高频模式、又能保持可分解性的离散词表。

所以名字虽然来自“字节对编码”，但今天谈 BPE tokenizer 时，你更该把它理解成：

> 一种基于高频相邻片段合并的子词词表学习方法。

## BPE 从什么单位开始

BPE 总得有一套初始基本单位。

这套单位视实现而不同，常见起点包括：

- 字符
- 预分词后的字符片段
- 字节

从什么起点开始，会影响：

- 是否容易出现未知 token
- 对不同语言和符号系统的覆盖性
- 训练出的合并路径

例如如果起点是字节，那么理论上几乎任何文本都可以被表示，因为所有文本底层都能写成字节序列。

这也是为什么现代很多 tokenizer 倾向 byte-level 设计，因为它能极大缓解 OOV 问题。

## BPE 训练到底在做什么

这里的“训练”很容易让人误会成：

> 用梯度下降训练一个神经网络模型。

不是。

tokenizer 训练更接近：

> 基于语料统计，学习一套更合适的词表和切分规则。

所以它不是在学参数梯度，而是在反复回答两个问题：

1. 哪些片段值得保留成词表项？  
2. 哪些相邻单位最值得合并？  

最终训练出来的，不只是一张词表，还包括：

- merge 规则
- token 与 id 映射
- special token 定义
- 常常还有 normalization / pre-tokenization 相关配置

所以 tokenizer 训练的产物是一整套离散化协议。

## 用一个极简例子理解 BPE 的迭代过程

假设我们的初始基本单位非常细，比如字符。

语料里有这些词反复出现：

```text
low
lower
lowest
low
low
```

一开始，系统只能看到类似：

```text
l o w
l o w e r
l o w e s t
```

接下来它会统计哪些相邻对最常一起出现。

很可能：

- `l + o`
- `lo + w`

会很快成为高频组合。

于是它可能先合并成：

```text
lo
```

然后再合并成：

```text
low
```

这样以后再遇到：

```text
lower
lowest
```

模型就不必每次从单字符开始，而可以直接使用更有意义的子词积木：

- `low`
- `er`
- `est`

这个例子体现的重点不是具体合并结果，而是：

> 高频结构会被逐渐提升成更大的单位。

## “最常见相邻对”为什么是一个合理启发

因为如果两个单位经常挨着出现，把它们合并通常有几个好处：

- 更节省序列长度
- 更符合语料真实共现结构
- 更利于把高频局部模式整体复用

这相当于在问：

> 哪些碎片总是在一起，以至于值得提升为一个新的词表单位？

所以 BPE 的合并策略，本质上是在做一种频率驱动的结构压缩。

## BPE 训练的每一步其实都在修改“世界分块方式”

这点很值得建立直觉。

每一次 merge，不只是新增一个 token，而是在改变：

> 今后文本应该优先被怎样切块。

这意味着训练过程的每一轮都在重新定义：

- 哪些模式被整体看待
- 哪些模式仍然保持可分解
- 词表容量应该花在什么片段上

所以 tokenizer 训练不是生成一张静态字符串表那么简单，而是在逐步塑造：

> 模型未来看待文本的基本积木系统。

## merge 顺序为什么重要

在 BPE 里，“先合并什么，后合并什么”非常重要。

因为一旦早期某个高频片段被提升为新单位，后续统计结构就会被改写。

这意味着：

- 相同最终词表大小
- 不同训练语料或不同统计路径

也可能得到不同的切分习惯。

所以 BPE 不只是“找出所有高频片段”，而是：

> 在一个迭代过程中，按顺序塑造合并历史。

这也是为什么保存 merge 规则本身很重要。

因为编码时不只是需要知道“词表里有什么”，还要知道：

> 合并应当按什么历史优先级执行。

## tokenizer 编码时为什么不是暴力乱拆

当 tokenizer 训练完成后，编码阶段通常会根据学到的 merge 规则，把新文本切成最符合这套规则的 token 序列。

这一步的目标不是“随便拆开，只要都在词表里就行”，而是：

> 尽量沿着训练时学出来的高频合并路径，把文本分解成合适的子词单位。

也就是说，训练阶段学到的是规则，编码阶段是在执行规则。

这使得 tokenizer 成为一个确定性的协议系统，而不是随缘切分器。

## 为什么子词方法能处理新词

子词方法最强的现实优势之一，就是：

> 即使某个完整词从没作为整体出现在词表里，它通常也能被拆成较小的已知单位。

例如一个新词可能不在词表中，但它可能可以写成：

- 一个常见词根
- 一个常见后缀
- 若干常见字符片段

于是模型虽然没见过这个完整词作为单个 token，却仍然能通过组合方式处理它。

这比纯词级方案灵活得多。

所以子词方法的泛化能力，不是来自“它认识所有词”，而是来自：

> 它为新词保留了可分解的后路。

## 为什么很多现代方案进一步用 byte-level

如果初始单位是字符，某些复杂文本仍可能受限于字符集合定义。

而如果初始单位是字节，那么几乎所有输入最终都能被分解。

这带来一个很大的工程优势：

> 你几乎不再需要真正意义上的未知文本输入。

所以 byte-level BPE 常被采用，不是因为它听起来更底层更酷，而是因为它让系统在现实世界里更稳：

- 更少 OOV 问题
- 更容易处理奇怪符号
- 更适合混合文本世界

当然，它也会带来一些切分形态上的变化，但从通用性上看很有吸引力。

## 词表大小和 merge 次数之间是什么关系

在 BPE 训练里，你通常会设定一个目标词表规模，或者设定 merge 次数上限。

直觉上可以这样理解：

- merge 越多，词表越大
- merge 越多，高频片段越可能整体化
- merge 越多，序列可能越短
- 但 merge 越多，词表参数成本也越高

所以词表大小不是独立决定的，它和 BPE 训练路径是一起演化的。

换句话说：

> 词表规模其实是在决定：我们愿意用多少离散类别预算，去换取更粗颗粒的高频单位。

## tokenizer 训练为什么会反过来影响模型难度

因为 tokenizer 定义了模型最基础的输入颗粒度。

如果 tokenizer 把很多本应稳定整体出现的单位切得过碎，那么模型需要在更多位置上重新拼装语义。

如果 tokenizer 又把很多低频、偶然组合都强行塞进大词表，模型则会面临：

- 分类空间过大
- 低频 token 学习困难
- embedding 和输出头更重

所以 tokenizer 不是模型前的一次性准备工作，而是：

> 对模型学习难度的提前塑形。

它会直接影响：

- 序列长度分布
- 词表大小
- 罕见词处理方式
- embedding 和输出头规模
- 模型需要花多少层次重建高层语义

## 为什么 tokenizer 训练结果和语料绑定得很紧

因为 BPE 学出来的不是抽象语言真理，而是：

> 这份语料里哪些片段最值得整体化。

如果语料主要是技术文档，学出来的高频 token 可能会偏向：

- 常见术语前缀后缀
- 文件路径模式
- 代码片段结构

如果语料主要是聊天文本，学出来的 token 则可能偏向：

- 高频口语表达
- 常见感叹和语气片段
- 对话中反复出现的短语

所以同一种语言，不同语料训练出来的 tokenizer 也可能有明显差异。

这正说明 tokenizer 训练不是中性过程，而是在吸收：

> 当前语料的统计偏好。

## special token 为什么必须和 tokenizer 训练一起看

有些人会把 special token 看成 tokenizer 训练完之后顺手补上的配置。

更稳妥的理解应该是：

> special token 也是离散协议的一部分，因此它们必须和词表、切分规则一起被一致管理。

例如：

- BOS 和 EOS 决定序列边界
- PAD 会影响 batch 对齐
- 角色分隔符会影响多段文本任务
- 控制 token 会影响任务格式

如果这些定义前后不一致，后面训练样本构造和推理行为都会出问题。

所以 tokenizer 工件从来不只是 merges 和 vocab 两个文件，而是一整套协议组合。

## 为什么同一份模型权重不能随便换 tokenizer

这一点必须反复强调。

一旦 tokenizer 变了：

- 某个 id 对应的 token 变了
- 某段文本切出来的 token 序列变了
- 词表大小和索引空间可能也变了

此时原本训练好的：

- embedding
- 输出头
- special token 语义惯例

都不再和新 tokenizer 的离散世界对齐。

这就是为什么通常要把：

- tokenizer 文件
- 词表
- merge 规则
- special token 定义
- 模型权重

视为同一套工件的一部分。

## BPE 不是唯一答案，但它揭示了最重要的思路

现代 tokenizer 世界不止 BPE 一种方案。

你还会见到：

- WordPiece
- SentencePiece
- unigram language model tokenizer
- byte-level 变体

这些方法在细节和优化目标上不一样，但它们共同在处理的核心矛盾非常接近：

- 词表不能无限大
- 序列不能无限长
- 长尾新词必须有处理方式
- 高频结构最好能整体复用

所以学 BPE 的价值不只在于会一种算法，而在于理解：

> 现代 tokenizer 为什么会落到子词统计学习这一大类思路上。

## 学习项目里该怎样看 tokenizer 选择

对学习项目来说，不需要一开始就把 tokenizer 选择搞成论文竞赛。

更务实的目标通常是：

- 先理解字符、词、子词、字节这几类方案的权衡
- 用一种主流而可解释的子词方法把流程跑通
- 明白 tokenizer 训练结果如何改变模型行为

也就是说，学习阶段最关键的不是“挑出最先进 tokenizer”，而是：

> 真正理解为什么 tokenizer 方案会影响整个模型系统。

只要这条链清楚，后面无论你用哪个主流方案，理解都会稳很多。

## 从这章往后，应该带走哪些判断

读完这章之后，你至少应该开始形成下面这些判断：

- tokenizer 训练不是神经网络训练，但它同样是在从语料统计中学习规则
- BPE 不是语言学分析器，而是统计驱动的离散积木学习器
- 词表大小、序列长度和长尾泛化能力之间存在硬权衡
- 训练好的 tokenizer 与模型权重是绑定工件，不应随意替换
- 子词方案的核心价值在于压缩高频结构并保留低频可分解性

这些判断会在后面所有数据链路里持续复用。

## 这一章真正要记住的核心句子

如果这一章只记一句话，它应该是：

> 子词 tokenizer 之所以在现代语言模型里常见，是因为它在字符级和词级之间提供了更好的折中；BPE 和类似方法本质上是在利用语料统计学习一套更合适的离散积木，而这套积木会直接决定模型的输入难度、词表规模和泛化方式。
