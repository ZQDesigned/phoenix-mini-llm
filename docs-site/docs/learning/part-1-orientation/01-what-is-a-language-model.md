# 01. 什么是语言模型

如果这套知识档案真的要承担“从零带一个读者走到小型语言模型内部”的职责，那么第一章就不能只做一种礼节性的开场白。

它必须先做一件更基础、也更严格的工作：

> 把“语言模型”这个词重新说准。

很多人第一次接触大模型时，先看到的不是定义，而是现象：

- 它会聊天。
- 它会写文章。
- 它会翻译。
- 它会总结。
- 它会解释代码。
- 它会续写故事。

这些说法都不假，问题在于它们都属于结果层的描述，而不是任务层的定义。

结果层的描述只能告诉你这个系统“看起来像什么”，却不能告诉你它在计算意义上究竟在做什么。一旦起点就停在这里，后面大量关键概念都会被读歪：

- 为什么训练目标常常落成预测下一个 token。
- 为什么模型输出是一整排 logits，而不是一句现成答案。
- 为什么推理是一 token 一 token 地往后走。
- 为什么同一个 prompt 可以生成多种不同文本。
- 为什么模型会表现出知识性，却又会一本正经地产生幻觉。

所以这一章的目标，不是介绍一个“很厉害的文本系统”，而是先替整套书定下一条更稳的坐标轴：

> 语言模型首先是一个在给定上下文条件下，为下一个离散符号分配概率的模型；它的各种表面能力，都是这个底层任务不断滚动展开后的外在表现。

后面你看到的 tokenizer、embedding、attention、softmax、cross-entropy、sampling、KV cache，本质上都在围绕这句话展开。

## 从“会说话”到“会建模”：为什么第一定义不能从聊天界面开始

如果你第一次使用大模型的入口是聊天界面，那么很自然会把语言模型理解成一种问答机器。你输入一句话，它回一句话；你继续追问，它继续回答。表面上看，这像一个在和人对话的系统。

但真正的学习不能只停在界面。

从系统内部看，对话并不是一个完全独立的新物种。它只是某种底层建模方式，在特定上下文格式下的一个外在表现。更准确地说，当你看到“模型在对话”时，系统内部通常在做的是下面这件事：

1. 把你当前输入的内容和之前的对话历史拼成一段更长的上下文。
2. 把这段上下文切成一串 token。
3. 根据这串 token，预测下一个位置最可能出现什么 token。
4. 选出或采样出一个 token。
5. 把它接回上下文末尾，再继续预测下一步。

换句话说，聊天只是“不断预测下一步”这个底层机制的一种可见表现。写作、摘要、翻译、代码补全，本质上也都可以重新写成同一类动作：给系统一个前缀，然后让它继续往后生成。

这就是为什么如果第一章把语言模型直接定义成“会聊天的模型”，后面很多结构就会显得像为了聊天临时搭出来的小技巧；但如果你先把它定义成“序列条件概率模型”，那么聊天、写作、翻译、补全这些能力就会重新回到同一条主线上。

## 为什么“语言”必须先被改写成序列

人类日常使用语言时，最先感受到的是意义、语气、句法、主题、修辞和上下文氛围。我们不会把一句话首先看成一串离散符号。对机器来说却恰好相反。

只要你想让机器处理语言，你就必须先完成一个更基础的翻译：

> 把原本连续、含混、富有语义阴影的人类文本，改写成一个有顺序的离散序列对象。

这里最关键的是“有顺序”和“离散”这两个词。

“离散”意味着模型面对的不是一整块不可分割的意义流，而是一个个可枚举的基本单位。这个单位未必等于“词”，它可能是：

- 一个字
- 一个字符
- 一个完整单词
- 一个子词片段
- 一个标点
- 一个空格模式
- 一个特殊控制符

但无论具体形式怎样，它必须是可以被列举、索引和计数的。

“有顺序”意味着同样一批单位，只要排列次序不同，整体含义就可能完全不同。`今天 下雨 了` 和 `下雨 今天 了` 用到的元素几乎一样，但顺序一变，句子就不再一样。这说明语言模型要面对的对象不是“词的集合”，而是“带顺序的符号流”。

一旦这件事成立，后面很多看起来复杂的结构都会开始显得自然：

- 为什么样本里会有序列长度这个维度。
- 为什么模型必须显式或隐式知道位置信息。
- 为什么训练目标不是“理解整段文本”，而是“在前缀条件下预测下一步”。
- 为什么推理会变成不断延长同一条前缀序列。

如果这一层不先立住，后面你会不断误把语言模型想成某种在“整体句意”上直接运算的系统；而那种理解方式会让几乎每一个底层模块都失去位置。

## 语言模型到底在建模什么

现在可以把讨论推进到更严格的一步。

很多人会说，语言模型在“学习文本”。这句话听上去没问题，但仍然太粗。真正准确的问题不是“它学不学文本”，而是“它学文本中的什么关系”。

更稳的说法应该是：

> 语言模型学习的是，在已经观察到一段前文的条件下，哪些后续 token 更可能出现，哪些不那么可能出现。

这句话比“会生成文本”更重要，因为它把建模对象从“结果”转回了“规律”。

如果模型只是保存一堆完整句子，它当然也可以在某些情况下复现文本，但那不是现代语言模型的关键。现代语言模型真正吸收的是文本分布中的结构：

- 局部搭配规律
- 句法延续模式
- 叙述风格习惯
- 主题展开倾向
- 指令与回复之间的统计关系
- 长上下文中的照应和回指

因此，语言模型不是在“背诵一份文本档案馆”，而是在把大量前缀与后续之间的分布规律压进参数里。它看到的是海量前文和后文的对应关系，最终学会的是：

> 在这样的前文下，后面更像会出现什么。

这也是为什么一个模型可以生成从未在训练数据中逐字出现过的新句子。因为它学的不是原句目录，而是产生这些句子的统计结构。

## 什么叫条件概率，为什么它是语言模型的母语

如果把前面的定义再写得正式一点，我们就会得到语言模型最经典的形式：

\[
P(t_{k+1}\mid t_1,t_2,\dots,t_k)
\]

这里的 \(t_1,t_2,\dots,t_k\) 表示已经出现的 token 序列，而 \(t_{k+1}\) 表示下一个位置的 token。

这条式子其实可以读得非常朴素：

> 在我已经看见前面这些 token 的条件下，下一个位置上各个候选 token 分别有多大概率出现？

这就是条件概率在语言模型里最实用的理解。

它之所以重要，是因为自然语言本来就不是一个完全确定的系统。面对同一个前缀，后面往往不止一种合理延续。

例如前缀：

```text
今天 天气 很
```

后面可能是：

- 好
- 冷
- 热
- 不错

这些候选并不是“一个真、其他全错”的关系，而是“都可能成立，但概率不同”。这就决定了语言模型的底层任务不可能是输出一个唯一正确答案，它必须输出一整份关于候选后续的概率结构。

这件事会一路影响后面整本书：

- 因为要输出概率结构，模型最终层不会只给一个答案词，而会给整个词表的分数。
- 因为候选不止一个，采样策略才会显著影响生成风格。
- 因为训练是让真实后续的概率变大，交叉熵和负对数概率才会自然进入损失定义。

如果你能把“语言模型的母语是条件概率”这句话先记住，后面很多看似分散的数学和工程设计就会更好理解。

## 为什么“只预测下一步”却足以生成整段文本

初学者最自然的疑问之一是：

> 如果模型每次只猜下一个 token，它怎么能写出一整段文章，甚至是一篇结构完整的回答？

这个问题的答案建立在一个非常重要的概率事实之上：一段长序列的整体概率，可以被拆成一串局部条件概率的连乘。

如果一段 token 序列是：

\[
t_1,t_2,t_3,\dots,t_n
\]

那么它的整体概率可以写成：

\[
P(t_1,t_2,\dots,t_n)=P(t_1)\cdot P(t_2\mid t_1)\cdot P(t_3\mid t_1,t_2)\cdots P(t_n\mid t_1,\dots,t_{n-1})
\]

你现在不需要记住“链式分解”这个名字，更重要的是理解它背后的直觉：

> 一整段文本并不是必须整体一次性决定出来；它可以被拆成一系列“在已有前缀下做下一步决策”的局部动作。

因此，一个会做

\[
P(t_{k+1}\mid t_1,\dots,t_k)
\]

的模型，只要不断把自己刚生成的 token 接回上下文，就可以逐步把局部能力滚动成整段输出。

这就是自回归生成的本质。它不是“模型突然学会了写长文”的神秘跃迁，而是“局部下一步预测能力”在时间轴上的连续展开。

### 一个直观的生成例子

假设当前前缀是：

```text
风 从 操场 那边 吹 过来
```

模型在这个位置上可能认为以下几个 token 的概率比较高：

- `，`
- `了`
- `时`

如果系统根据当前解码策略选中了 `，`，新的上下文就变成：

```text
风 从 操场 那边 吹 过来 ，
```

然后模型再以这个更长的前缀为条件，重新分配下一步 token 的概率。就这样一步步向后滚动，文本被慢慢长出来。

因此，语言模型不是先在脑中写好一整篇文章再一次性交给你，而是在每一步都根据当前可见前缀重新做局部概率判断。整段文本只是这一串局部判断在时间上的连锁结果。

## 为什么“上下文”这个词其实是核心中的核心

很多人第一次接触语言模型时，会把“上下文”理解成一种背景说明，像是写在题目下面的附加条件。但在语言模型里，上下文不是附属材料，它就是条件项本身。

这件事值得说得非常重：

> 没有上下文，就没有被约束的下一步分布；上下文不是背景，而是模型当前推理位置的输入主体。

这也是为什么同一个问题换一种前缀方式，模型表现会显著变化。你可以把模型理解成一个持续响应上下文变化的分布生成器。前缀一变，下一个 token 的概率结构就跟着变。

比如：

```text
请 用 正式 的 语气 解释
```

和：

```text
请 用 轻松 的 语气 解释
```

这两段前缀只差了几个 token，但模型后续的高概率词分布可能会完全不同。前者会更偏向规整、书面、抽象的延续，后者则更可能走向口语、比喻和轻松表达。

这件事往后会不断以不同名字出现：

- prompt
- system prompt
- conversation history
- few-shot examples
- instruction template

这些东西在更高层接口上看起来不一样，但本质都在做同一件事：

> 修改模型此刻可见的上下文，从而修改下一步 token 的条件分布。

## 为什么模型看到的通常不是“词”，而是 token

到这里还需要再向下走一层现实感。

人类谈语言时，天然会先谈词、短语、句子和段落。但现代语言模型内部真正直接面对的最小离散单位，通常不是这些自然语言对象本身，而是 token。

token 可能是：

- 一个字
- 一个字符
- 一个完整单词
- 一个子词片段
- 一个标点
- 一个特殊控制符

也就是说，当我们说“预测下一个 token”时，这里的 token 绝不是一个可以轻描淡写跳过的术语。它决定了：

- 模型输入空间怎样被切分
- 词表规模有多大
- 序列长度会增长到什么程度
- 一个位置上究竟在预测什么样的基本单位

这也解释了为什么 tokenizer 在整个系统里不是一个外围附件，而是模型定义的一部分。因为一旦 token 切法变了，模型面对的世界也就变了。

## 为什么输出不是“答案”，而是一整排分数

如果语言模型的底层任务是“在当前上下文下比较所有候选 token 的可能性”，那它的输出就不可能天然是一个现成答案词。它更自然的形式是：

> 对词表里所有候选 token 给出一组相对偏好分数。

这些分数通常叫 logits。

logits 的意义在于：

- 它们还不是概率
- 它们可以为负，也可以很大
- 它们表达的是模型对各个候选的相对偏好

再经过 softmax 之后，这组分数才会被压成一套合法概率分布。也就是说，模型在最后一步真正给出的，不是“我选这个词”，而是：

> 在这个位置上，我更偏向哪些 token，我对这些偏好的强弱关系怎样。

只要这一层先立住，后面的 softmax、交叉熵、temperature、top-k、top-p 才会真正变得自然。否则你会一直误以为这些都是附加在输出层上的小技巧，而不是任务定义直接推出来的结构结果。

## 为什么同一个 prompt 可以有多种合理输出

一旦你真正接受“模型给的是分布，不是唯一答案”，很多表面现象就会突然顺起来。

例如，同样一个 prompt：

```text
请 写 一个 秋天 开头 的 短段落
```

模型完全可能生成很多不同版本：

- 有的更偏抒情
- 有的更偏叙事
- 有的更偏简洁
- 有的更偏细节描写

这不是系统“不稳定”的证据，而恰恰是概率建模在开放任务上的自然表现。因为在这种上下文下，世界本来就不只允许一个唯一正确答案。

当然，某些场景下我们也希望模型更确定，例如数学步骤、结构化输出、严格格式约束等。可即便如此，底层机制仍然没变：只是当前上下文把分布压得更尖了，而不是模型突然从“概率系统”变成了“确定系统”。

## 语言模型为什么会表现出“知识感”

很多初学者在第一接触中最震惊的一点，是模型会给出看起来像知识的回答，于是很容易得出一个过快结论：

> 它是不是像数据库一样存了很多事实？

这个说法只对了一小部分。

语言模型并不是一个普通的显式知识库。它没有把所有知识点按“问答对”这种方式整齐存在某个可直接检索的表格里。更准确的说法是：

> 它在训练中大量接触了文本分布，于是把很多事实模式、表述方式、概念关系和推断倾向压进了参数。

这意味着它表现出来的“知识感”，并不是纯粹的显式查表，而更像一种：

- 统计结构中的事实共现
- 表达模式中的常见关系
- 语言上下文中的推断惯性

也正因为如此，语言模型会一边表现得懂很多东西，一边又会在某些地方出现非常自信的错误。因为它的底层任务始终不是“验证真伪”，而是“在当前上下文下继续生成更高概率的后续”。

这层差别后面会非常重要。因为它解释了为什么：

- 模型会回答问题，却不等于它内置了严格事实检验器。
- 模型会生成流畅文本，却不保证每句话都对应外部世界的真实状态。
- 模型的知识性和它的幻觉风险，会长期同时存在。

## 为什么“语言模型”和“聊天助手”不是同一层概念

从用户体验上看，很多人第一次接触大模型，接触到的就是一个聊天助手。所以“语言模型”和“聊天助手”很容易在心里被画上等号。

但从概念层看，这两者不是同一层东西。

“语言模型”描述的是底层建模对象：一个针对序列条件概率进行学习和生成的模型。

“聊天助手”描述的是产品形态：把这种模型放进一个对话接口里，再结合：

- 指令模板
- 角色设定
- 安全策略
- 工具调用
- 检索增强
- 输出约束

所形成的一种交互系统。

这就像“发动机”和“整车”不是同一层概念一样。整车当然离不开发动机，但整车绝不等于发动机本身。

这层区分非常重要，因为后面你在学习小型语言模型时，真正要学的是更靠底层的那一层。只有先把“发动机”看清楚，后面再去理解聊天模板、工具增强和代理系统，才不会本末倒置。

## 为什么训练阶段和推理阶段会表现得像两种不同世界

对初学者来说，还有一个很容易困惑的地方是：

> 训练时模型在看整段序列，推理时却是一 token 一 token 地往后走，这两件事怎么会是同一套系统？

这个问题的答案，要先回到语言模型的定义。

训练阶段的目标，是让模型学会在很多真实前缀下，把真实后续 token 的概率拉高。所以训练时可以把整段序列送进去，并通过右移标签和因果约束，一次并行地学很多个“下一步预测”。

推理阶段则不同。推理时没有标准答案可供对齐，系统只能根据当前已经生成的前缀，再做下一个 token 的条件预测。于是它表现成逐步展开的自回归过程。

这说明训练和推理看上去不同，但底层任务并没有变：

- 训练是在大量已知答案的前缀上学习条件分布。
- 推理是在没有现成答案的前缀上实际使用这个条件分布。

只要这个桥先搭起来，后面你看到 causal mask、teacher forcing、prefill 和 decode 时，就不会觉得它们属于彼此无关的世界。

## 为什么“下一 token 预测”听起来简单，实际却足够强

第一次听到“预测下一个 token”时，很多人会有一种轻视感：

> 就这？这听上去像个很局部的小任务，怎么会长出这么多复杂能力？

这个轻视感非常自然，但它来自一个误会：把“局部决策”误看成“局部能力”。

真正关键的不是每一步只预测一个 token，而是：

- 这个 token 是在很长前缀条件下预测的
- 这种预测会被重复很多步
- 上一步生成的结果会立刻进入下一步条件
- 大量局部条件关系叠起来，会形成很复杂的整体结构

这和国际象棋里“一次只下一步棋”有点相似。单看一步动作很局部，但一连串局部动作会滚成极复杂的全局局面。

所以“下一 token 预测”不是弱任务，而是一种足够基础、足够统一、又足够能滚成复杂行为的任务形式。它之所以强，不是因为每一步本身华丽，而是因为：

> 局部条件建模的连续展开，足以承载宏观文本结构。

## 语言模型不是在“理解语言”吗

这是一个几乎一定会被问到的问题，而且非常值得正面回答。

如果从人类直觉出发，你可能会问：

> 如果它只是做下一个 token 概率分配，那它到底算不算“理解语言”？

这个问题之所以难，是因为“理解”本身就是一个容易滑动的词。

如果你把理解定义成：

- 拥有主观意识
- 对世界具有和人类等价的概念体验
- 能保证事实正确并自知其真假

那语言模型当然不能简单等同于这种意义上的理解。

但如果你把理解定义得更工程化一些，比如：

- 能否利用上下文形成对后续的约束
- 能否在大量任务中表现出稳定模式提取与泛化能力
- 能否在新的前缀条件下组合已学结构生成合理延续

那么语言模型显然又在某种层面上展现出很强的“可操作理解”。

这也是为什么这本知识档案会尽量避免在第一章就用哲学化的大词去盖住问题。对你当前的学习目标来说，更重要的不是给“理解”下终极定义，而是先把下面这件事看清楚：

> 语言模型的可见能力，首先来自它对条件分布结构的学习和使用。

先把这一层站稳，后面你再回头讨论“它到底理解到了什么程度”，才不会把问题谈虚。

## 初学者在这里最容易犯的几个误解

这里把几个最常见的误解集中拆掉。

第一个误解是：语言模型就是会聊天的软件。

不对。聊天只是产品界面和使用形态，底层更基本的对象是序列条件概率模型。

第二个误解是：语言模型每次都在输出一个唯一答案。

不对。更准确地说，它在为词表中的候选 token 分配概率质量，然后再通过某种解码策略选出后续。

第三个误解是：模型内部处理的是词和句子的“整体意义”。

不够准确。模型更直接面对的是 token 序列，以及这些序列中的条件结构。

第四个误解是：既然只预测下一步，模型能力应该很局限。

不对。局部条件预测在时间上的连续展开，足以滚成长文本和复杂任务行为。

第五个误解是：模型像数据库一样直接存着事实。

不对。它更像是在参数里压缩了大量文本分布结构，因此会显得有知识性，同时也会伴随统计式错误和幻觉风险。

## 这一章真正要记住的核心句子

如果只能记住一句话，请先记住这一句：

> 语言模型首先不是一个“会聊天的程序”，而是一个在给定前缀条件下，为下一个离散 token 分配概率的序列模型；聊天、写作、翻译、补全等能力，都是这个底层机制不断滚动展开后的表面形态。

## 读完这一章之后，你应该能稳定回答这些问题

- 为什么第一定义不能从“会聊天”开始？
- 为什么语言必须先被改写成有顺序的离散序列？
- 语言模型到底在建模什么关系？
- 条件概率为什么是语言模型的母语？
- 为什么只预测下一步却足以生成整段文本？
- 为什么输出是一整排 logits，而不是直接给答案？
- 语言模型和聊天助手为什么不是同一层概念？

## 如果现在只能先记住一个阅读姿势

请先养成这个姿势：

> 后面遇到任何模块，都先问它是在为“给定前缀预测下一个 token”这件事服务，还是只是你还没看清它和这件事之间的桥。

只要这个姿势稳定下来，后面的 tokenizer、attention、loss、sampling 就会顺很多。

## 小结

这一章真正搭起来的，不是一个流行名词的通俗解释，而是一整套后续章节要反复依赖的任务定义：

- 语言必须先被写成序列
- 序列必须先被写成离散 token
- 模型面对的是条件概率分布
- 输出首先是候选后续的相对偏好
- 生成是局部下一步预测的滚动展开

后面你学到的几乎所有技术细节，最终都会回到这里。因为不管系统表面能力多丰富，语言模型在底层始终在做同一类事：

它在根据已经看见的前文，不断决定后面更可能出现什么。
