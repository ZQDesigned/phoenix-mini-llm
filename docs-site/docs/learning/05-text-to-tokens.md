# 05. 语料、文本清洗与 Tokenizer

## 这一章要解决什么问题

前面你已经知道：

- 模型训练依赖前向、损失、反向和参数更新
- 模型真正接收的是张量，而不是自然语言字符串

现在必须继续追问一个更靠前的问题：

> 现实世界里的人类文本，究竟怎样一步一步变成语言模型可以学习的训练对象？

这个问题如果没有讲透，后面几乎所有事情都会变得摇摇晃晃。因为你会不断遇到这些疑惑：

- 什么叫语料？
- 是不是随便抓很多文本就能训？
- 原始文本为什么还要清洗？
- 为什么不能直接按字符或按单词去学？
- token 到底是什么？
- 词表大小为什么会影响模型成本和效果？
- special token 到底在帮模型学什么？
- 一长段文本最后为什么会变成固定长度训练块？

这一章要做的，就是把“文本进入模型之前”的整条知识链讲清楚。

## 第一件事：语言模型面对的不是“语言意义”，而是“序列数据”

这听起来有点反直觉，因为我们日常使用语言时，总是先从意义出发。

但对语言模型来说，一切的起点不是：

- 文学鉴赏
- 世界知识
- 段落主题

而是：

> 一串可以被观察、切分、建模的符号序列。

### 这意味着什么

模型并不会一上来“理解句子意思”，它首先看到的是：

- 哪些片段经常一起出现
- 某种上下文之后通常会接什么
- 哪些结构反复出现
- 语言在位置上如何延续

所以从学习角度看，语言模型最初处理的其实是：

> 文本的序列统计结构。

这也是为什么在文本进入模型之前，必须先把它变成一串稳定、可计算、可离散表示的单位。

## 第二件事：什么叫语料

“语料”就是你拿来训练模型的文本集合。

这个定义听起来简单，但它非常重要，因为它回答了：

> 模型到底从什么世界里学习语言规律？

### 语料不只是“一堆文本”

它还隐含着很多决定模型行为的因素，例如：

- 文本风格
- 文本领域
- 文本长度分布
- 语言种类
- 叙事方式
- 噪声水平

例如，如果你的语料主要是童话故事，模型学到的延续风格就可能更偏叙事、重复和故事化；如果语料主要是技术文档，模型学到的语言组织方式又会完全不同。

### 为什么语料选择本身就是建模决策

因为你不是在向模型输入“中性的语言”，而是在向它提供一个经过筛选的语言世界。

这意味着：

- 模型能生成什么风格
- 它最熟悉什么结构
- 它在哪些文本类型上更稳定

都和语料直接相关。

所以语料从来不是训练前随手找的一批文件，而是：

> 整个模型行为边界的最上游来源。

## 第三件事：为什么语料不是越大越好

很多初学者会自然地想：

> 语言模型不是靠数据学吗？那当然数据越多越好。

这句话在大规模工业训练里有其道理，但对学习项目来说，往往是误导。

### 对学习者来说，最重要的不是“总量最大”

而是：

- 数据风格相对稳定
- 数据噪声不要太大
- 数据规模能支撑实验
- 预处理和训练成本在你能掌控的范围内

### 为什么一开始就上极大语料反而常常更糟

因为你会同时失去几个关键优势：

- 看不清 tokenizer 在做什么
- 很难快速迭代实验
- 训练太慢，反馈周期太长
- 数据清洗问题被大规模噪声掩盖

学习阶段最宝贵的不是“数据规模压到最大”，而是：

> 让你能看见从语料到 tokenizer、再到训练样本的整个过程。

如果数据量一开始就大得让你看不清过程，学习效率反而会下降。

## 第四件事：什么叫“适合学习”的语料

一个适合学习项目的语料，通常应该满足以下特征：

- 语言风格较集中
- 文本长度适中
- 噪声不至于太重
- 数量足以支撑模型学习
- 规模又不至于大到让预处理和训练完全失控

### 为什么风格集中反而有利于学习

因为风格相对稳定时，你更容易观察：

- tokenizer 把什么当成高频片段
- 模型能不能学到特定叙事或表达规律
- 训练损失和生成样例是否在变好

如果语料本身极端混杂，很多现象会变得难以解释。

### 这是不是说以后都该只用“干净的小数据”？

不是。

这里只是在强调：

> 对从 0 开始学习的人来说，可理解性和可实验性比盲目扩大规模更重要。

## 第五件事：原始文本为什么通常需要清洗

现实世界中的文本几乎从来不是天然适合直接喂给模型的。

你常会遇到：

- 异常空格
- 混乱换行
- 控制字符
- 编码问题
- 网页残片
- 重复模板噪声
- 破碎格式

### 文本清洗的目标是什么

不是“让文本看起来更好看”，而是：

> 去掉明显无意义或破坏性的噪声，让模型学习的统计结构更稳定。

### 为什么这件事如此重要

因为模型没有常识去自动判断：

- 这是语言本身的一部分
- 还是某段垃圾格式造成的噪声

如果你把大量无意义噪声直接保留进训练语料，模型就会认真学习这些模式。

## 第六件事：为什么又不能过度清洗

清洗不足会让噪声污染训练，清洗过度又会带来另一类问题：

- 破坏原始语言分布
- 丢掉真实文本边界信息
- 让训练和推理环境脱节

### 哪些东西虽然看着“杂”，却可能有价值

例如：

- 标点
- 大小写
- 段落换行
- 引号
- 括号
- 列表符号

这些都可能在真实文本中承担结构作用。

如果你只是为了“文本整齐”，把这些东西全抹掉，模型最后学到的语言世界就会变得失真。

### 一个非常实用的原则

文本清洗更合理的目标通常是：

> 去掉明显无意义的噪声，而不是把文本改造成一种人工理想化语言。

## 第七件事：为什么模型不能直接吃字符串

这是语言模型学习中最核心、也最容易被“听多了就当成理所当然”的问题。

对人类来说，字符串就是文字。

但对神经网络来说，字符串并不是一种可以直接拿来做：

- 矩阵乘法
- 查表
- 梯度更新
- 连续表示学习

的数值对象。

模型需要的是：

- 整数编号
- 向量
- 张量

所以文本必须先经过一个映射过程，变成一串离散 id。

而这个映射过程的核心产物，就是 token 序列。

## 第八件事：token 到底是什么

token 不是天然等于：

- 一个字
- 一个词
- 一个汉字
- 一个字符

更准确的说法是：

> token 是 tokenizer 选定出来、供模型学习和预测的离散基本单位。

### 这个定义为什么重要

因为它强调了一件事：

> token 是设计与训练出来的单位，不是自然语言里先验写好的单位。

在不同 tokenizer 下，一个 token 可能是：

- 单个字符
- 常见子词
- 完整单词
- 标点组合
- 某种 byte 片段

因此，“模型到底在以什么粒度观察世界”，本身就是需要被定义的问题。

## 第九件事：为什么不直接按字符处理

按字符处理当然不是不行，但它有明显代价。

### 优点

- 词表很小
- 很少有“未登录词”问题
- 几乎不需要复杂分词规则

### 缺点

- 序列会非常长
- 模型必须通过很多字符组合，才逐渐理解一个词
- 长距离依赖压力更大

对于学习项目来说，字符级方法在某些极小实验里可以帮助你理解概念，但作为更通用的小型语言模型起点，它通常不是最实用的折中。

## 第十件事：为什么不直接按单词处理

按单词处理看起来也很自然，因为人类阅读时很容易把词当成基本单位。

但它也会很快暴露问题：

- 词表会迅速膨胀
- 稀有词太多
- 新词、拼写变体、复合词处理困难
- 不同语言的词边界并不总清楚

所以词级 tokenizer 的问题在于：

> 它把很多本来应该通过组合处理的语言变化，直接丢给了一个越来越巨大的词表。

这对小型模型尤其不友好，因为：

- 参数变重
- 稀有词统计更不稳定

## 第十一件事：为什么子词级切分会成为主流折中

子词级 tokenizer 通常介于字符级和词级之间。

它的核心思路是：

> 不强迫所有单位都细到字符，也不强迫所有单位都完整到单词，而是让高频片段作为整体保留，低频片段则被拆开。

### 这样做的好处是什么

- 常见词可以保持较完整形态
- 生僻词还能通过更小片段拼出来
- 词表规模更可控
- 序列长度也不会像字符级那样极端拉长

这正是为什么子词 tokenizer 在现代语言模型里非常常见。

对学习项目来说，它也是一个很好的平衡点：

- 足够真实
- 足够常见
- 又不会把复杂度一下子推太高

## 第十二件事：BPE 的核心直觉是什么

BPE，也就是 Byte Pair Encoding，是最常见的子词构造方法之一。

你现在不需要死记算法细节，但必须掌握它的直觉：

> 从较小单位出发，不断把训练语料中高频共同出现的片段合并成更大的单位。

### 为什么这个思路合理

因为语言中本来就存在很多高频重复片段，例如：

- 常见单词
- 常见词根
- 常见后缀
- 标点搭配

如果这些片段总是反复一起出现，让它们成为一个更完整的 token 往往是合理的。

### BPE 真正帮你获得了什么

- 词表大小更可控
- 序列不至于太长
- 高频模式能以更稳定的单位存在

对初学者来说，把 BPE 先理解成：

> 让高频片段自己“长出来”的一种方法

已经足够有用了。

## 第十三件事：词表到底是什么

词表就是 tokenizer 最终确认下来的：

- token 集合
- token 到整数 id 的映射关系

你可以把它理解成：

> 模型之后所能认识、生成和评分的离散符号空间。

### 为什么词表不是一个无关紧要的副产品

因为它直接定义了：

- 模型的输入空间
- 模型的输出空间
- embedding 表的行数
- 输出层的类别数

也就是说，词表一旦定了，模型的某些基本形状和成本边界也跟着定了。

## 第十四件事：词表大小为什么会改变模型训练行为

词表大小会直接影响以下几个方面：

- embedding 参数量
- 输出层参数量
- 稀有片段的统计稳定性
- 序列平均长度

### 如果词表太小

会发生：

- 很多词被拆得很碎
- 序列变长
- 模型要跨更多 token 才能表达一个词

### 如果词表太大

会发生：

- embedding 和输出层变重
- 很多 token 出现次数太低
- 稀有 token 更难学扎实

因此词表大小不是“越大越高级”，而是要和：

- 数据规模
- 语言特性
- 模型预算
- 训练目标

一起平衡。

## 第十五件事：special token 为什么不是“奇怪符号附属品”

很多初学者第一次接触 special token 时，会把它们看成一些工程补丁，例如：

- `BOS`
- `EOS`
- `PAD`
- `UNK`

这种理解太浅了。

更准确的说法是：

> special token 是模型协议的一部分。

### `BOS` 在做什么

告诉模型：

> 这里是一个新序列的开始。

### `EOS` 在做什么

告诉模型：

> 这里是一个序列应该结束的位置。

### `PAD` 在做什么

帮助不同长度样本在 batch 中对齐。

### `UNK` 在做什么

为词表之外或无法表示的输入提供一种兜底编码。

### 为什么这会影响训练和推理

因为这些 token 会直接影响：

- 序列边界
- 样本构造
- batch 对齐
- 生成何时停止

所以它们不是小补丁，而是训练与推理共同依赖的结构信号。

## 第十六件事：为什么训练样本通常不是“一整篇文本对应一个样本”

现实文本长度差异非常大，但神经网络训练更喜欢规则张量。

因此常见做法不是：

- 一整篇文章就是一条训练样本

而是：

- 先把文本转成 token 流
- 再把 token 流切成固定长度块

### 为什么这样做

因为这样更利于：

- 统一张量形状
- 高效 batch 训练
- 明确控制上下文长度

这意味着模型训练时面对的，并不是“原始文章对象”，而是：

> 从更长文本流中切出来的一段段固定长度训练片段。

## 第十七件事：为什么常见打包长度是 `seq_len + 1`

如果模型训练目标是：

> 用前面的 token 预测后面的 token

那么一个长度为 `seq_len` 的输入，就需要对应一个同样长度的目标。

最直接的构造方式是：

- 先拿到一个长度为 `seq_len + 1` 的 token 块
- 输入取前 `seq_len`
- 目标取后 `seq_len`

也就是：

```text
input  = tokens[:-1]
target = tokens[1:]
```

这一步看起来像样本打包技巧，但其实它直接属于训练目标本身。因为它定义了：

- 模型到底看什么
- 模型到底为哪个位置负责

## 第十八件事：为什么 tokenizer 其实属于模型定义的一部分

这是整章最需要牢牢记住的一句话之一。

很多人会把 tokenizer 理解成：

> 模型之前的预处理工具。

但更准确的说法是：

> tokenizer 是模型系统的一部分，因为它定义了模型所观察和生成的基本单位。

它会影响：

- 输入怎么编码
- 输出怎么解码
- 词表多大
- special token 怎么安排
- 模型怎样理解序列边界

如果你换一个 tokenizer，同样的模型结构也会面对一个不同的离散语言世界。

所以 tokenizer 不是外围杂务，而是模型定义的一部分。

## 第十九件事：从学习角度看，什么叫“好的 tokenizer 方案”

初学者很容易问：

> 我是不是该先找一个最先进的 tokenizer？

学习阶段更有价值的问题通常是：

> 这个 tokenizer 是否足够可理解、可控，并能稳定支撑训练闭环？

一个适合作为学习项目起点的 tokenizer 方案，通常应该满足：

- 切分粒度逻辑你能解释清楚
- special token 语义明确
- 词表大小和模型预算匹配
- 对主要语料风格表现稳定
- 能顺利支撑编码、训练和解码完整流程

学习阶段最重要的往往不是“最前沿”，而是：

> 先建立对整个文本到 token 过程的可解释掌控。

## 第二十件事：数据入口最常见的错误有哪些

### 错误 1：语料太杂

结果是：

- tokenizer 学到的片段缺乏稳定性
- 模型行为更难解释

### 错误 2：清洗过度

结果是：

- 原始语言分布被改坏
- 模型学到的人造文本结构太强

### 错误 3：清洗不足

结果是：

- 大量无意义噪声进入训练

### 错误 4：tokenizer 粒度选得太极端

结果是：

- 要么词表爆炸
- 要么序列过长

### 错误 5：special token 语义混乱

结果是：

- 序列边界不清
- 训练和生成逻辑变得脆弱

### 错误 6：不知道固定长度训练块是怎么来的

结果是：

- 后面几乎一定会在训练目标上搞混

## 第二十一件事：把整章压缩成一句完整的话

如果你想把这一章的核心压缩成一句话，可以记成：

> 语言模型不是直接从“自然文本”开始学习的，而是先从一份经过选择和适度清洗的语料出发，用 tokenizer 把文本映射成离散 token 序列，再通过 special token 和固定长度打包，把这些序列组织成模型真正可学习的样本。

这句话里的每个环节，都是后面训练闭环能够成立的前提。

> **这一章真正要你建立的判断**
>
>   文本不是天然就适合进入模型的对象。语料选择、清洗边界、切分粒度、词表规模、special token 语义和样本打包方式，一起定义了模型到底在观察什么、用什么单位学习、以及后面训练目标能否被正确建立。

## 练习题

1. 为什么说语料不是“越大越好”，而要看是否适合学习目标？
2. 为什么文本清洗必须克制，不能把真实文本改造成一种理想化人工语言？
3. 字符级、词级、子词级三种切分方式各自最核心的优缺点是什么？
4. 为什么词表大小会同时影响模型成本和建模效果？
5. 为什么 special token 和固定长度样本打包都属于训练主线的一部分，而不是小工程细节？
