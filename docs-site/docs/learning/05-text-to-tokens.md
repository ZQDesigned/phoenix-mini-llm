# 05. 语料、文本清洗与 Tokenizer

## 这一章要解决什么问题

前面你已经知道：

- 训练是前向、损失、反向和参数更新组成的闭环
- 模型接收的是 tensor，而不是原始字符串

现在必须继续回答一个更基础的问题：

> 真实世界里的文本，究竟怎样一步一步变成语言模型可以学习的训练对象？

如果这个问题没有讲透，后面即使你会写模型，也很容易在最早的数据入口就失去方向。因为你会不断遇到这些疑问：

- 什么样的文本可以拿来训练？
- 原始文本要不要清洗？
- 模型为什么不能直接按字符或单词原样学习？
- token 到底是什么？
- 词表大小为什么重要？
- special token 为什么会影响训练和生成？

这一章要做的，就是把“文本进入模型之前”的这整段知识链讲清楚。

## 第一件事：语言模型学的不是“句子长什么样”，而是“文本中符号如何连续出现”

先把直觉摆正。

语言模型面对的训练数据，本质上是一大批文本序列。模型要从这些文本中学到的是：

- 哪些片段经常一起出现
- 某段上下文之后通常接什么
- 某种写作风格会如何展开
- 语法、词法、叙事结构如何在序列中体现

也就是说：

> 模型学习的入口不是“语义解释”，而是“序列统计结构”。

因此，文本在进入模型之前，必须先被转成模型可处理的离散符号序列。

## 第二件事：什么叫语料，为什么语料不是越大越好

“语料”就是你拿来训练模型的文本集合。

### 初学者最容易犯的误解

很多人会想：

> 那我是不是应该直接抓尽可能多的文本，越大越强？

对大型工业训练也许如此，但对学习项目来说，这个想法常常有害。因为你此时最重要的不是“数据量最大”，而是：

- 数据风格相对稳定
- 数据质量足够可控
- 数据规模足够让你完成实验
- 数据不会让预处理和训练成本失控

### 为什么适中的语料更适合学习

合适的语料能让你更清楚地观察：

- tokenizer 在干什么
- 模型是否在学习
- 训练与生成输出是否合理

如果你一开始就上极大、极杂、极脏的数据集，很多问题会被淹没在复杂度里，反而不利于学习。

## 第三件事：原始文本为什么通常需要清洗

现实世界文本往往包含很多并不适合直接喂给模型的部分，例如：

- 杂乱空格
- 异常换行
- 控制字符
- 编码问题
- 重复噪声
- 格式残片

### 文本清洗的目标是什么

不是把文本“修饰得更漂亮”，而是：

> 让训练数据的统计结构更稳定，避免模型把无意义噪声当作重要模式学进去。

### 但为什么不能过度清洗

因为文本中的很多细节本来就是语言的一部分：

- 标点
- 大小写
- 段落边界
- 引号和括号

如果你过度清洗，可能会：

- 丢掉有价值的信息
- 让训练分布和真实使用场景脱节

所以清洗的原则通常是：

> 只去掉明显无用或破坏性的噪声，不要为了“整齐”过度改写文本。

## 第四件事：为什么模型不能直接吃字符串

这是语言模型学习中最核心、也最容易被理所当然接受的一点。

计算机里的字符串对我们来说是“文本”，但对神经网络来说，它不是可直接计算的数值结构。

模型要做矩阵乘法、查表、梯度更新，它需要的是：

- 整数 id
- 向量
- 张量

所以必须先把文本映射成一串离散编号。

这一步的结果，就是 token 序列。

## 第五件事：token 到底是什么

token 不是固定等于：

- 一个字符
- 一个单词
- 一个汉字

更准确地说：

> token 是 tokenizer 选定的离散基本单位。

在不同设计下，一个 token 可能是：

- 单个字符
- 单词的一部分
- 完整单词
- 常见词组
- 标点

这也是为什么“token”这个词比“单词”更准确。它强调的是：

> 模型实际学习和预测的单位，取决于你如何切分文本。

## 第六件事：字符级、词级、子词级分别意味着什么

理解 tokenizer，最好的方式之一就是先理解常见切分粒度。

### 字符级

字符级把文本拆成一个个字符。

优点：

- 词表很小
- 没有未登录词问题的极端版本

缺点：

- 序列会很长
- 模型要自己学会把很多字符组合成词和短语

### 词级

词级把文本直接拆成单词。

优点：

- 每个 token 语义更完整

缺点：

- 词表容易爆炸
- 稀有词和新词处理困难
- 不同语言和分词规则问题复杂

### 子词级

子词级通常介于两者之间，把文本拆成频繁出现的子片段。

优点：

- 词表规模可控
- 能兼顾常见词整体保留与稀有词拆分
- 现代语言模型中非常常见

对初学者来说，最重要的结论是：

> 小型语言模型项目里，子词 tokenizer 往往是最实用的起点。

## 第七件事：BPE 的核心思想是什么

BPE，也就是 Byte Pair Encoding，是一种非常常见的子词构造方法。

你现在不需要记住它的全部算法细节，但必须理解它的核心直觉：

> 从较小单位开始，反复把训练语料中高频共同出现的片段合并成更大的 token。

### 为什么这样做合理

因为语言里很多片段会反复出现，例如：

- 常见单词
- 词根词缀
- 标点搭配
- 常见前后缀组合

让高频片段作为更完整的 token 存在，可以同时获得：

- 更短的序列长度
- 更强的统计稳定性
- 更可控的词表大小

### 你应该保留的最小理解

当你说“我们训练一个 BPE tokenizer”时，本质上是在说：

> 让数据自己告诉我们，哪些片段值得成为较稳定的离散单位。

## 第八件事：词表大小为什么会影响模型训练

tokenizer 训练完之后，会得到一个词表，也就是所有 token 与整数 id 的对应表。

词表大小直接影响：

- embedding 矩阵大小
- 输出层大小
- 模型参数量
- 稀有片段如何被拆分

### 词表太小会怎样

- 很多词会被拆得很碎
- 序列会变长
- 模型需要跨更多 token 才能表达一个词

### 词表太大会怎样

- embedding 和输出层参数明显增大
- 稀有 token 统计不稳定
- 训练数据不足时，很多 token 学不扎实

所以词表大小不是“越大越高级”，而是要和：

- 数据规模
- 语言特性
- 模型大小
- 训练预算

一起平衡。

## 第九件事：special token 为什么是模型协议的一部分

很多初学者第一次接触 special token 时，会把它们看成“额外插进去的几个奇怪符号”。这理解太浅了。

special token 的作用是给模型引入一些结构化边界信息。

常见的包括：

- `BOS`：序列开始
- `EOS`：序列结束
- `PAD`：对齐用的填充
- `UNK`：未知或未覆盖 token

### 为什么它们重要

因为它们会直接影响：

- 序列从哪里开始学习
- 序列什么时候该停
- batch 对齐如何处理
- 未知输入如何表示

如果 special token 语义模糊，后面的训练和生成都会出现异常。

## 第十件事：为什么训练样本通常不是“一整篇文本对应一个样本”

现实中的文本长度差异很大，而神经网络训练通常更适合固定长度 batch。

因此训练语言模型时，常见做法不是：

- 一条完整故事 = 一个样本

而是：

- 把很多 token 连成流
- 再切成固定长度块

### 为什么要这么做

因为这样更利于：

- batch 训练
- 张量形状统一
- 计算效率

但这也意味着你必须非常清楚：

> 一段训练样本中的 token 边界、BOS/EOS 插入位置、上下文长度到底怎样定义。

## 第十一件事：为什么常见打包长度是 `seq_len + 1`

如果模型训练目标是：

> 用前面的 token 预测后一个 token

那么一个长度为 `seq_len` 的输入，必须对应一个同样长度的目标。

最直接的构造方式就是：

- 先拿到长度 `seq_len + 1` 的 token 块
- 输入取前 `seq_len`
- 目标取后 `seq_len`

也就是：

```text
input  = tokens[:-1]
target = tokens[1:]
```

这一步看起来像工程细节，其实它直接属于训练目标定义本身。

## 第十二件事：tokenizer 不是预处理附属物，而是模型定义的一部分

这是非常重要的一句判断。

为什么说 tokenizer 属于模型定义的一部分？因为它决定了：

- 模型看到的基本单位是什么
- 词表大小是多少
- special token 编号如何安排
- 推理时 prompt 如何编码
- 输出文本如何解码

同一套模型结构，换一个 tokenizer，实际上就已经不是同一套学习对象了。

这也是为什么你不能把 tokenizer 当成训练前随手跑一下的工具，而要把它视为模型系统的重要组成部分。

## 第十三件事：从 0 开始学习时，应该怎样理解“好的 tokenizer”

初学者很容易把目标理解成：

> 找到一个最先进的 tokenizer。

这不是当前阶段最有用的思路。对学习项目来说，一个“好的 tokenizer”更应该满足：

- 基本切分逻辑能解释清楚
- special token 语义明确
- 词表大小和模型规模匹配
- 对主要语料风格表现稳定
- 能顺利支撑训练和解码闭环

换句话说：

> 学习阶段更重要的是“可理解”和“可控”，而不是盲目追求花哨。

## 第十四件事：数据入口最常见的错误有哪些

### 错误 1：清洗过度

把原文删改得太狠，导致模型学到的文本分布失真。

### 错误 2：tokenizer 粒度选得太极端

词表太小导致序列过长，词表太大导致参数和稀有 token 问题恶化。

### 错误 3：special token 语义混乱

开始、结束、填充、未知 token 的角色不清晰，后续训练和推理就容易乱。

### 错误 4：训练和推理用的 tokenizer 不一致

这会直接破坏整个系统闭环。

### 错误 5：不知道样本是怎样从长文本被切成固定块的

如果你说不清这一点，后面几乎一定会在目标构造上出错。

<Callout title="这一章真正想让你建立的判断" tone="note">
  文本不是天然就能被模型理解的对象。语料选择、清洗策略、tokenizer 粒度、special token 语义和样本打包方式，一起定义了模型到底在学习什么。这里任何一步含糊，后面的模型、训练和生成都会受到影响。
</Callout>
