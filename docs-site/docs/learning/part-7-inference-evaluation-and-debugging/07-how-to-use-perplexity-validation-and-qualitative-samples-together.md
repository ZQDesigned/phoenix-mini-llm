# 07. 困惑度、验证集与定性样例怎样一起评估

## 为什么语言模型评估不能只盯一个数字

做小型 LLM 学习项目时，很多人都会急着寻找一个“最终分数”：

- 有没有一个最权威的指标
- 有没有一个数字能告诉我模型好不好

现实通常没这么简单。

因为语言模型最终既是：

- 一个概率分布预测系统

也是：

- 一个会滚动生成文本的系统

所以一个成熟评估必须同时观察：

- 模型对真实数据的平均预测质量
- 模型在真实生成时的外显文本行为

这也就是为什么：

- perplexity
- validation loss
- 固定 prompt 样例

应该被一起使用，而不是互相替代。

## 先说验证集：它到底在回答什么

验证集最核心的作用是：

> 在不参与当前参数更新的数据上，观察模型是否也在改善。

它帮助你回答：

- 模型是真的学到了可迁移规律
- 还是只是在越来越会记训练集

如果没有验证集，训练过程就像只有油门没有仪表：

- 你知道自己在更新参数
- 却不容易知道这种更新是不是在向更可靠方向走

## 为什么验证集必须和训练集分开

因为训练集已经参与了参数更新。

如果你始终只看训练损失，就很容易把下面两件事混淆：

- 学到规律
- 记住样本

验证集的存在，相当于在问：

> 对于没有直接拿来更新参数的样本，模型也能表现更好吗？

这正是泛化判断的最基础版本。

## perplexity 到底是什么

对初学者来说，最实用的理解是：

> perplexity 是把语言模型平均预测质量换一种常见尺度表达出来的指标。

它与：

- 交叉熵
- 对数似然

紧密相关。

如果模型对真实下一个 token 预测得越准、越不“困惑”，那么 perplexity 往往越低。

所以它可以被理解为：

> 模型在面对验证数据时，平均有多不确定。

## 为什么 perplexity 不是一套完全不同的真理

很多初学者第一次看到 perplexity 会误以为：

> 这是比 loss 更高级、更接近语言能力本体的指标。

不完全对。

perplexity 的底层仍然来自 token 级预测质量。

它不是在绕开 loss，而是在：

> 用更符合语言模型传统的方式，表达平均 next-token 预测效果。

所以如果你已经理解了：

- validation loss
- negative log-likelihood

那么 perplexity 并不是另一门课，而是同一条线上的一个常见投影。

## 为什么 perplexity 值低，不自动等于文本就一定好读

这和上一章讲的核心区别直接相关。

perplexity 反映的是：

- 对真实数据的平均预测不确定性

但它并不直接等于：

- 生成时是否重复
- 是否自然收尾
- 是否维持长程逻辑

所以 perplexity 很重要，但它不会替你做完全部评估工作。

如果你只看 perplexity，很可能会错过：

- 采样下的行为异常
- 某些固定 prompt 上的明显缺陷
- 结构性重复问题

## 为什么固定 prompt 样例必须进入评估体系

因为语言模型最终是会生成文本的系统。

很多重要现象只能通过样例直接观察：

- 会不会反复绕圈
- 会不会突然风格断裂
- 会不会在几句之后明显失控
- 收尾是否自然

这些现象即使和指标有关，也很难被单个平均数字完整替代。

所以定性样例不是“好玩展示”，而是：

> 对生成系统外显行为的必要观测。

## 为什么样例比较必须固定条件

如果你想让样例真正具有评估意义，必须尽量固定比较条件。

至少应尽量固定：

- prompt
- 采样参数
- 最大生成长度

否则你很难分清：

- 是 checkpoint 真变好了
- 还是只是 prompt 更容易答
- 还是采样参数换了

一个很实用的方法是维护一组固定 prompt 集：

- 短叙述 prompt
- 问答 prompt
- 格式化输出 prompt
- 较容易诱发重复的 prompt

然后在多个 checkpoint 间重复比较。

## 为什么“看起来像人话”也不能单独当成结论

样例很重要，但也不能只靠样例做全部判断。

因为样例天然存在：

- 运气成分
- 选择偏差
- 单一 prompt 偏差

一个 checkpoint 可能在某个 prompt 上运气不错，但总体预测质量并不稳定。

所以成熟做法不是“只看数字”或“只看样例”，而是：

> 用数字观察整体趋势，用样例观察外显行为。

两者互相纠偏。

## 一个实用的三层评估框架

对小型学习项目来说，一个非常实用的评估框架是：

### 第一层：训练曲线

看：

- 训练 loss 是否下降
- 有没有明显失稳

### 第二层：验证指标

看：

- validation loss
- perplexity

判断是否在真正泛化。

### 第三层：固定 prompt 定性样例

看：

- 可读性
- 重复
- 收尾
- 主题维持

这三层合起来，才更接近完整评估。

## 如何解读几种常见组合

### 情况一：验证 loss 下降，样例也更自然

这是最理想的信号组合。

通常说明：

- 平均预测质量在进步
- 这种进步也开始体现到生成行为上

### 情况二：验证 loss 下降，但样例变化不明显

这并不罕见。

可能意味着：

- 提升还主要体现在局部 token 预测
- 长程生成能力还没明显改善
- 当前采样方式还不足以把差异显露出来

### 情况三：样例偶尔更好看，但验证指标没改善

这时要小心。

可能只是：

- 采样更讨巧
- 某个 prompt 运气更好

不一定代表模型平均能力真的提高了。

### 情况四：训练 loss 降、验证 loss 升、样例也开始怪

这通常是在提醒你：

- 过拟合
- 训练过头
- 泛化在变差

## 为什么 checkpoint 选择不能只看最后一步

因为最后一步未必就是最好一步。

有时会发生：

- 后期训练损失继续下降
- 但验证损失已经开始恶化

这意味着最佳 checkpoint 可能出现在中间某个阶段。

因此评估体系还承担一个现实职责：

> 帮你决定哪一个 checkpoint 值得保留和继续分析。

这也是为什么“定期评估 + 定期保存”要配套出现。

## 对学习项目来说，什么是足够好的评估习惯

不需要一上来就建立大而全的 benchmark 平台。

一个足够好的起点通常是：

- 始终保留训练 / 验证双曲线
- 在验证集上计算 loss 或 perplexity
- 维护一小组固定 prompt
- 对比多个 checkpoint 的定性输出

只要这几个习惯稳定下来，你对模型好坏的判断就会比“看一次随机生成”可靠得多。

## 这一章最该带走的判断

请把下面这件事牢牢记住：

> validation loss / perplexity 负责告诉你平均预测质量是否在改善，固定 prompt 样例负责告诉你这些改善是否真正长成了更自然的生成行为。

评估成熟的标志，不是找到一个万能数字，而是：

> 知道哪些问题该由数字回答，哪些问题必须由样例回答，然后把两者放在一起解释。
