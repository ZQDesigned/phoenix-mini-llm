# 08. 极小样本过拟合与系统化排错

## 为什么“结果不对”时最重要的能力不是继续改结构

真正的学习项目到了后面，最考验人的往往不是再往模型里塞更多结构，而是：

> 当结果不对时，你能不能把问题迅速缩小到可验证范围。

很多初学者在模型表现异常时会立刻开始：

- 改超参数
- 改层数
- 改采样
- 改 tokenizer

这样做的问题不是“你不够努力”，而是：

> 你一下子同时改了太多层，等于放弃了因果判断。

这一章的任务，就是把调试这件事从“乱试”变成“系统缩小问题空间”。

## 为什么极小样本过拟合测试如此重要

这是小型语言模型学习里最有价值的健康检查之一。

它的核心思想非常简单：

> 如果整条训练链路都是对的，那么一个有足够容量的小模型，通常应该能很快记住极少量样本。

这里说的“极少量样本”可以是：

- 1 个 batch
- 2 个 batch
- 或一小段被反复重复的数据

这项测试的价值不在于证明模型泛化，而在于证明：

> 数据、目标、前向、反向、优化、更新这一整条最基本链路到底是不是通的。

## 为什么它比直接上完整语料更有效

如果你一上来就用完整语料训练，任何异常都可能来自很多来源：

- 数据太杂
- 训练时间太短
- 学习率不合适
- 模型容量不够
- 某个实现细节有错

而极小样本过拟合测试主动把任务变得非常容易。

于是如果模型连这么容易的任务都记不住，那你就能更有把握地推断：

> 问题大概率不在“任务太难”，而在训练链路本身。

这会极大提高排查效率。

## 极小样本过拟合测试到底在验证什么

它并不是只验证一个点，而是在同时验证多层事实：

### 第一，数据输入有没有进模型

例如：

- token id 是否合理
- batch 形状是否对
- input / target 是否对齐

### 第二，loss 构造是否正确

例如：

- target 有没有右移错位
- ignored positions 是否处理错了

### 第三，梯度是否真的在回传

例如：

- backward 是否真的执行
- 参数是否真的拿到了梯度

### 第四，优化器是否真的在更新参数

例如：

- `optimizer.step()` 是否真正改变了权重
- 学习率是否低到几乎没变化

换句话说，它是在验证：

> 从 token 到 loss，再到参数更新，这整台机器最小闭环是否成立。

## 如果连极小样本都过拟合不了，优先怀疑什么

这时不应该先说：

> 也许这组数据太难。

更合理的优先怀疑顺序通常是：

1. 数据与 target 构造  
2. loss 计算  
3. mask 是否正确  
4. 梯度是否真的存在  
5. 优化器与学习率是否有效  

这比继续扩大模型或继续训练更有意义。

## 调试时为什么一定要先分类

只要结果不对，最重要的第一步不是立刻改代码，而是先问：

> 这更像是哪一层的问题？

一个非常实用的分类方式是把问题先分成五类。

### 第一类：数据问题

例如：

- 文本清洗异常
- tokenizer 与 metadata 不一致
- special token id 错位
- 训练 / 验证切分有问题

### 第二类：模型结构问题

例如：

- causal mask 错
- position 处理不对
- 输出头维度不匹配
- cache 路径与非 cache 路径行为不一致

### 第三类：训练流程问题

例如：

- 学习率太大或太小
- gradient accumulation 写错
- AMP 路径不稳
- `zero_grad` / `step` 顺序错

### 第四类：解码问题

例如：

- 采样太保守
- 停止条件不合理
- EOS 没正确接入

### 第五类：评估问题

例如：

- 只看一次随机样例
- prompt 比较条件不一致
- 把训练 loss 当成全部真相

这个分类本身就能帮你显著缩小问题空间。

## 为什么“一次只改一个主要变量”几乎是铁律

如果你同时改：

- 学习率
- 序列长度
- 层数
- 采样温度

然后结果变了，你其实并不知道：

- 哪个改动有效
- 哪个改动无关
- 哪个改动只是在掩盖真正问题

所以有效调试通常必须做到：

- 每次只动一个主要变量
- 保持其他条件尽量固定
- 记录改动前后变化

这听起来慢，但从总时间看通常更快，因为它能真正产生知识，而不是只产生猜测。

## 为什么固定 prompt 和固定 batch 都很重要

调试时你最怕的不是结果不好，而是条件漂移。

如果你每次：

- 用不同 prompt
- 用不同 batch
- 用不同 checkpoint

那你几乎失去了稳定对照基准。

所以无论是生成调试还是训练调试，都应尽量先固定一组最小基准：

- 固定几条 prompt
- 固定一小批训练样本
- 固定一组解码参数

这样变化才更容易解释。

## 一个非常实用的缩小问题顺序

当模型行为异常时，一个成熟缩小顺序通常是：

### 第一步：先缩小数据规模

先别用整套语料，改用：

- 极小批数据
- 极短上下文

让问题尽可能便于重现。

### 第二步：先关闭高级优化

例如先关闭：

- AMP
- cache
- 复杂采样

让系统先回到更保守、更易解释的路径。

### 第三步：先确认最小闭环

检查：

- loss 能否正常下降
- 参数是否真的更新
- 极小样本是否能过拟合

### 第四步：再逐层加回复杂度

例如：

- 先加更长上下文
- 再加 AMP
- 再加 cache
- 最后再加更复杂采样

这样任何新问题出现时，你都更容易知道是在哪一层引入的。

## 为什么“代码能跑通”不是调试终点

很多 bug 不会直接报错。

最危险的一类问题恰恰是：

- 代码能运行
- loss 也有值
- 但语义已经悄悄漂移

例如：

- tokenizer id 对不齐
- target 右移错一位
- stop criterion 不合理
- 训练和推理使用了不一致的 special token 约定

这类问题如果只靠“程序没报错”是发现不了的。

所以成熟调试必须同时看：

- 数值信号
- 行为样例
- 配置一致性

## 为什么调试日志本身也是工具

一个真正有用的日志不只是记录结果，更是在帮助你缩小问题。

例如：

- 当前 step
- 当前 loss
- 当前 learning rate
- 当前 grad norm
- 当前样例输出

这些信息能帮助你判断：

- 问题是从一开始就存在
- 还是在某一步之后突然出现
- 是否与某次学习率变化同步
- 是否只在某类 prompt 下触发

所以日志不是“跑完后看看”，而是动态定位工具。

## 学习项目里最应该形成的调试态度

不是“我再多试几个配置”，而是：

> 我先把问题压缩成最小可解释实验，再让每一次改动都能回答一个明确问题。

这就是从“调包式试错”走向“真正会做系统调试”的关键分界线。

## 这一章最该带走的判断

请牢牢记住：

> 极小样本过拟合测试是验证训练最小闭环是否成立的利器，而系统化排错的核心不是多改，而是先分类、先缩小、一次只改一个主要变量。

只要这个判断稳定下来，你在后面真正做项目时，就会比只会盲调配置的人快得多，也更接近真正掌握这台小型语言模型。
