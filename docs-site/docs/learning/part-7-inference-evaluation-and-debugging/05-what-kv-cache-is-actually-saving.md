# 05. KV cache 到底缓存了什么

## 为什么生成越长通常会越慢

如果你从最朴素的方式实现自回归生成，每一步都会这样做：

1. 把当前整段上下文重新送进模型  
2. 重新计算所有位置的注意力相关表示  
3. 取最后一个位置的 logits 决定新 token  

这会带来一个很明显的问题：

> 旧历史会被一遍又一遍重复计算。

当上下文越来越长时，这种重复会迅速变得昂贵。

于是你就得到一个非常现实的问题：

- prompt 越长，prefill 越重
- 已生成 token 越多，后续每步越慢

KV cache 就是对这个问题的直接回应。

## 先回到 Attention 本身

在 decoder-only Transformer 里，一个位置要读取历史时，核心依赖的是：

- query
- key
- value

其中：

- query 来自当前位置当前需求
- key / value 来自可见历史各位置

当你在第 `t` 步生成新 token 时，过去 `1...t-1` 的 key / value 本质上已经算过了。

如果你每一步都把这些旧 key / value 重新算一遍，就会做大量重复劳动。

## KV cache 的核心思想是什么

它最本质的思想就是：

> 过去位置已经计算好的 key / value 先存起来，后续生成时直接复用，而不是整段重算。

这意味着在 decode 阶段：

- 新 token 仍然需要产生自己的 query / key / value
- 但旧历史的 key / value 不用再重复生成

于是每一轮真正新增的计算量显著下降。

## 为什么叫 KV cache，而不是 QKV cache

因为缓存的重点通常不是 query，而是：

- key
- value

原因在于：

- query 是当前这一步的新需求
- 它天然依赖当前最新位置，不能提前替你算好

而过去位置的 key / value 一旦已经确定，只要上下文没有改写，它们就可以持续复用。

所以缓存的价值主要来自：

> 历史可读内容的重用，而不是当前查询需求的重用。

## prefill 和 decode 在缓存上的角色为什么不同

理解 KV cache 时，最容易豁然开朗的一点就是：

> prefill 和 decode 的缓存角色不一样。

### prefill

第一次输入完整 prompt 时，历史还不存在缓存。

所以模型必须：

- 读取整段 prompt
- 为每一层、每个位置建立 key / value

这个阶段的任务更像是：

> 先把现有前缀全部“装进缓存体系”里。

### decode

之后每来一个新 token，你只需要：

- 为这个新 token 计算新增的 key / value
- 再让它去读取已有缓存中的历史

这个阶段缓存才真正开始节省重复计算。

## 为什么 KV cache 不会改变模型输出逻辑

很多初学者第一次接触缓存时会误以为：

> 既然不再整段重算，那结果会不会已经变了？

在正确实现下，不会。

因为 KV cache 改变的是：

- 计算复用方式
- 推理效率

而不是：

- 任务定义
- 可见上下文
- 当前位置读取历史的内容范围

更准确地说，缓存是在保证语义等价的前提下：

> 避免对同一段历史反复做相同工作。

## 为什么 cache 特别适合自回归生成

因为自回归生成的历史有一个非常重要的特征：

> 一旦某个 token 已经生成出来，它就会稳定地留在左侧上下文中。

这意味着过去位置的 key / value 通常不会被“重写”。

所以它们很适合作为缓存对象。

如果任务不是这种单向不断扩展历史的形式，缓存机制就没这么自然。

这也是为什么 KV cache 和 decoder-only 推理如此契合。

## cache 到底节省了什么成本

最直接节省的是：

- 历史 key / value 的重复生成成本

但更重要的是，它改变了 decode 阶段的复杂度体验：

- 不是每步都像第一次那样再处理整段 prompt
- 而是把大头计算前移到 prefill

所以你常会看到一种体验：

- 第一次响应前会有较重 prefill
- 之后 token 可以一枚枚持续吐出

这背后就是缓存的作用。

## 为什么 cache 也会带来代价

缓存不是没有成本，它也会引入新的资源占用：

- 需要额外内存存历史 key / value
- 上下文越长，缓存也会越大

所以 KV cache 的本质并不是“白拿提速”，而是：

> 用更多内存换更少重复计算。

这也是为什么长上下文推理会同时面临两个现实问题：

- 没有 cache 太慢
- 有 cache 会占更多显存 / 内存

## 为什么长上下文下 cache 会越来越占空间

因为每新增一个 token，都要为每一层追加对应的 key / value。

也就是说：

- 历史越长
- 层数越多
- hidden / head 维度越大

缓存总量就越高。

这说明 KV cache 虽然极其有用，但它不是“和长度无关的免费优化”。

它依然受：

- 上下文长度
- 模型规模
- 设备内存

这些因素约束。

## 为什么 prompt 变化会使旧 cache 失效

缓存依赖一个前提：

> 当前生成轨迹的左侧历史没有改变。

如果你换了 prompt，或者中间修改了已有 token，那么原先对应的历史 key / value 就不再匹配新上下文了。

这意味着：

- cache 不是通用知识库
- 不是可以在任意 prompt 间共享的“模型记忆”

它只是：

> 针对当前这条生成轨迹的局部历史缓存。

## 为什么学习项目里必须把“缓存”与“正确性”分开看

很多人一上来就急着加 KV cache，希望生成更像工业系统。

这本身没错，但顺序上要特别小心。

如果你的基本生成循环都还没验证正确，就贸然加缓存，会让调试难度大幅上升。

一个更稳妥的顺序通常是：

1. 先让无缓存生成逻辑正确  
2. 再确认输出行为、停止条件、采样都健康  
3. 再加入 KV cache 做性能优化  

这样一旦加缓存后输出变了，你更容易判断：

- 是缓存逻辑错了
- 而不是整个生成定义没想清楚

## 这一章最该带走的判断

请牢牢记住：

> KV cache 缓存的是历史位置已经算过的 key / value，它改变的是 decode 阶段的效率，而不是模型任务本身。

只要这个判断稳了，后面你再看：

- prefill 为什么比 decode 重
- 为什么长上下文需要 cache
- 为什么 cache 又会占内存
