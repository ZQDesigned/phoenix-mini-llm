# 04. EOS、停止条件与重复问题

这一章开始，我们把视角从“模型怎样被训练出来”转到“模型真正开始生成文本时，到底在发生什么”。

很多初学者在第一次写生成循环时，会同时撞上三件事：

- 模型似乎不会自己停
- 模型常常会重复
- 你明明只是想“让它多写一点”，结果它越写越像在原地打转

这三件事不是偶然凑在一起的。

它们实际上来自同一个根部事实：

> 语言模型本身只是在不断回答“下一个 token 是什么”，而不是在直接回答“这段话什么时候该结束、怎样才算一段完整的表达”。

一旦你把这个差别想清楚，后面关于 `EOS`、停止规则、重复惩罚、采样策略、提示词设计的大量工程现象，都会变得容易理解得多。

## 4.1 从任务定义开始：语言模型天然是“开放式继续”

先把问题拉回最原始的形式。

一个 decoder-only 语言模型在每一步所做的事情，都可以写成：

```text
给定当前前缀 x1, x2, ..., xt
预测下一个 token xt+1 的条件概率分布
```

请注意这里没有出现下面这些概念：

- 这段话是否已经“说完了”
- 现在是否应该“收尾”
- 该不该“另起一段”
- 用户是不是“已经得到答案了”

这些都是更高层的人类意图。

模型在数学上看到的，首先只是一个条件分布问题。

所以如果你把最朴素的生成循环写成：

```text
while True:
    预测下一个 token
    把这个 token 接到上下文后面
```

它当然会继续下去。

这不是 bug，而是你给它定义的工作本身就是无限可继续的。

很多人第一次遇到“模型不停止”时，会把它理解成某个边缘错误。更准确的理解是：

> 停止从来不是一个自动免费获得的性质，而是生成协议里必须被显式设计的一部分。

这里的“生成协议”包括两层：

1. 模型内部有没有学到“这里适合结束”
2. 运行时系统外部有没有提供“最迟必须停止”的规则

这两层缺一不可。

## 4.2 `EOS` 是什么，它为什么重要

`EOS` 是 *End Of Sequence* 的缩写，通常表示“序列结束标记”。

从表面看，它只是词表中的一个特殊 token；但从训练意义上看，它承担的是下面这个角色：

> 把“结束”也变成一个可以被学习、可以被预测的事件。

如果训练数据里只有普通文本，没有任何明确的结束信号，那么模型会看到大量局部片段，却未必知道“这一段在这里已经完整了”。

而一旦我们在样本结尾放入 `EOS`，训练目标就会变成：

```text
在适当的上下文之后，给 EOS 更高概率
```

于是“停下来”不再只是外部程序的强制，而会部分进入模型自己的分布结构。

这件事极其重要，因为真正自然的结束，不能只靠外部粗暴截断。

例如下面两种情况完全不同：

```text
情况 A：模型自己生成出一句完整结尾，然后给出 EOS
情况 B：模型本来还没结束，但你因为长度上限把它截断
```

二者都会让程序“停”，但文本质量完全不是一回事。

## 4.3 `EOS` 不是“按一下结束按钮”，而是“在某些上下文中结束的概率”

初学者容易误会 `EOS` 的机制，好像模型体内存在一个单独的“结束开关”。其实不是。

对模型来说，`EOS` 和普通 token 一样，仍然只是词表里的一个候选项。

某一步生成时，模型给出的仍然是：

- “的”的概率
- “是”的概率
- “，”的概率
- 换行的概率
- `EOS` 的概率
- 其他 token 的概率

也就是说，模型不是“检测到该结束，于是跳到一个外部分支”，而是：

> 在当前位置，它把“结束”作为所有可能下一个 token 中的一个候选，并为它分配一个概率。

所以 `EOS` 是否会被选中，取决于很多因素：

- 数据里这类上下文是否经常在这里结束
- 模型有没有学会这种分布规律
- 当前解码策略是否倾向于选择高概率 token
- 有没有其他 token 的概率暂时压过 `EOS`

这就是为什么：

- 有时模型会过早结束
- 有时模型应该结束却不结束
- 有时它会继续绕圈，而不愿意给出 `EOS`

这些现象都不是魔法，只是 `EOS` 在当前分布里没有按你期待的那样胜出。

## 4.4 `EOS` 想学得好，训练样本必须先组织得好

如果你想让模型学会自然结束，最前面的工作不是先去调采样参数，而是先问：

> 你的训练样本到底有没有把“结束”这件事表达清楚？

这涉及到数据切分的基本原则。

### 4.4.1 什么样的数据更容易学到结束感

以下类型的数据通常更容易让模型学到自然结束：

- 本来就有完整边界的句子、段落、回答
- 一问一答式样本，每条样本都有明确结尾
- 文档片段在切分时保留了合理的段落边界
- 样本末尾显式加入 `EOS`

这些数据共同的特点是：

> “一个样本就是一段完整表达”。

模型看到足够多这样的例子后，会逐渐把某些语义与结构模式和“收尾”联系起来。

例如：

- 总结句之后结束
- 列表收尾后结束
- 问答中回答完问题后结束
- 故事在句号、段落、收束语后结束

### 4.4.2 什么样的数据会破坏结束感

如果你的训练样本主要是这样切出来的：

- 在固定长度处生硬截断
- 一段话中间随便切开
- 只保留连续文本块而没有结尾标记
- 把多个样本拼接在一起，却没有边界 token

那么模型会学到一种很危险的世界观：

> 文本大多数时候都只是“被切断了”，而不是“自然结束了”。

在这种分布下，模型自然就不擅长生成收束。

它可能会：

- 喜欢继续往后写
- 不知道何时该停
- 用重复拖延结束
- 在本来该收尾的地方又开一个新分句

所以停止质量首先是一个数据问题，其次才是一个推理问题。

## 4.5 `EOS`、`PAD`、换行、句号，不是一回事

训练和推理阶段还常常把几类“特殊边界信号”混在一起。要先把它们区分清楚。

### 4.5.1 `EOS`

表示“这个样本到这里结束了”。

它属于语义上或结构上的结束。

### 4.5.2 `PAD`

表示“这是为了对齐 batch 长度而补出来的位置”。

它不代表内容结束，更不应该被模型当成真实文本的一部分去学习。

如果 `PAD` 与 mask 处理不当，模型甚至会把 padding 当成普通上下文，这会污染训练。

### 4.5.3 换行符

换行只是排版结构，常常表示：

- 另起一行
- 另起一段
- 列表换项

它可能与结束相关，但绝不等于结束。

### 4.5.4 句号或终止标点

句号表示一句话完成，不等于整个样本完成。

一个完整回答通常包含很多句号，但只在最终收尾时才应该出现 `EOS`。

如果这些概念在设计数据或分析样例时混在一起，你就会很难判断：

- 模型究竟是“句子写完了”
- 还是“回答写完了”
- 还是“只是换了一行”
- 还是“程序该停了”

## 4.6 为什么仅有 `EOS` 还不够

即使模型已经学到了某种程度的结束能力，真实系统里也几乎总会额外设置停止条件。

原因非常现实。

### 4.6.1 模型的结束能力永远只是概率性的

模型不会向你保证：

- “我一定会在 43 个 token 内结束”
- “我一定会在答案讲完之后立刻给出 EOS”
- “我绝不会因为某个提示而一直拖长”

它只能给出概率分布。

而工程系统需要确定性边界。

所以必须有外部的“护栏”。

### 4.6.2 小模型尤其容易在结束阶段变得不稳定

参数量较小的模型通常：

- 对长程结构的掌握较弱
- 对“已经回答够了”的感觉不稳定
- 更容易在结尾附近回到安全高频模式

所谓“安全高频模式”，就是模型不确定时，会倾向于回到它最熟悉的词、最熟悉的句法、最熟悉的过渡短语。

于是你会看到它在答案尾部出现：

- 空泛总结
- 再次解释同一件事
- 重复前一句的句法模板
- 一直追加“此外”“同时”“需要注意的是”

这本质上是在用熟悉模式拖延结束。

### 4.6.3 运行时必须对资源负责

就算你完全不关心文本质量，系统也必须关心：

- 推理时间
- 显存占用
- 上下文窗口长度
- 每次请求的成本

这意味着生成系统必须能够说：

> “哪怕模型还想继续，我也得在这里停。”

所以一个成熟的停止系统往往是多层组合，而不是单靠 `EOS` 一条规则。

## 4.7 运行时常见的停止层

可以把停止机制想成一个从“最自然”到“最强制”的层级结构。

### 4.7.1 第一层：模型自己生成 `EOS`

这是最理想的停止方式，因为它说明：

- 模型内部认为这里已经结束
- 文本和停止行为是一致的

如果数据、训练与解码都比较健康，这种停止通常最自然。

### 4.7.2 第二层：命中特定停止字符串

有些场景会约定：

- 生成到某个分隔符就停
- 生成到某个对话角色标记就停
- 生成到某个特定模板尾标就停

例如多轮对话中，看到下一个说话人的角色前缀就可以停止当前回答。

这类规则常见，但它本质上是在说：

> 我们不完全信任模型会用 `EOS` 恰好停在理想位置，所以补一层基于文本模式的截断。

### 4.7.3 第三层：`max_new_tokens`

这是最常用、也最粗暴的一层。

它不关心内容有没有写完，只关心：

> 最多允许你再生成这么多 token。

它非常必要，因为这是资源与安全的底线。

### 4.7.4 第四层：时间、预算或窗口约束

在真实系统中还可能存在：

- 最长推理时间
- 最大总 token 数
- 上下文即将超窗

这些都可能触发停止。

你可以把它理解成：

- `EOS` 管自然结束
- 停止字符串管协议结束
- `max_new_tokens` 管资源上限
- 其他预算规则管系统约束

## 4.8 停止不是越“自然”越好，而是要看你在解决什么任务

初学者常有一种理想主义：既然 `EOS` 更自然，那是不是最好完全依赖 `EOS`？

不一定。

任务不同，对停止的要求也不同。

### 4.8.1 开放式写作

例如让模型续写故事、描述场景、自由解释概念。

这时你通常更希望：

- 给模型较大的发挥空间
- 让它尽量自然收束

所以你可能更依赖 `EOS`，而不是很早截断。

### 4.8.2 结构化生成

例如：

- 只输出一个标签
- 只输出一段 JSON
- 只输出一行答案

这类任务更重要的是协议正确，而不是文风自然。

此时停止字符串、格式约束和长度限制就更重要。

### 4.8.3 对话式问答

对话通常介于两者之间。

你既想要内容完整，又不希望它没完没了。

所以常见策略是：

- 允许 `EOS` 自然结束
- 同时设定合理的 `max_new_tokens`
- 在检测到下一个角色标记时停止

从根本上说，停止机制不是文学审美问题，而是任务定义问题。

## 4.9 为什么重复会和停止问题绑在一起出现

现在进入第二个现象：重复。

很多人起初会把“模型重复”和“模型不停止”看成两类不同故障。其实它们经常是一体两面。

因为当模型没有明确把握如何结束时，它非常容易退回高概率、低风险的局部模式。

而最容易维持高概率的局部模式之一，就是重复。

换句话说：

> 重复经常不是模型“故意要绕圈”，而是模型在缺乏清晰全局走向时，用局部最稳的路径把生成继续下去。

这就是为什么很多重复都发生在答案后段，特别是本来应该开始收束的时候。

## 4.10 重复有很多种，先不要把它们混成一种

如果你只说“模型重复了”，其实信息量很低。因为不同类型的重复，对应不同根因。

### 4.10.1 词级重复

例如：

```text
非常非常非常重要
```

或某个短词不断连发。

这常常与局部分布塌缩、采样过于保守、温度太低有关。

### 4.10.2 短语级重复

例如：

```text
需要注意的是，需要注意的是，需要注意的是
```

这比单词重复更常见，通常说明模型抓住了一种高频模板，反复套用。

### 4.10.3 句法模板重复

例如连续几句都以同一结构开头：

```text
首先……
其次……
最后……
同时……
此外……
```

这未必是严格逐字重复，但读起来会感觉模型在原地踏步。

### 4.10.4 语义重复

模型用不同措辞反复说同一件事。

这时从 token 角度看不一定重复很多，但从读者角度看已经没有新增信息。

### 4.10.5 段落级循环

模型写完一段后，又重新开启一轮近似相同的解释框架，好像整篇文章在绕圈。

这是小模型很典型的问题，因为它难以维持较长的全局计划。

只有先分清这些重复类型，你后面才知道该从哪里诊断。

## 4.11 重复的第一来源：训练目标只在局部上奖励“看起来合理”

训练时，交叉熵损失奖励的是：

> 在真实下一个 token 上给更高概率。

这个目标非常重要，但它不是直接奖励：

- 全文不重复
- 全文信息密度高
- 全文结构紧凑
- 回答在恰当位置收尾

这些都是更高层的长程性质。

于是会出现一个典型现象：

模型在局部上总能给出“很像人话”的下一个 token，但从长段滚动角度看，却可能逐渐滑向：

- 模板化
- 啰嗦
- 自我重复
- 收尾拖延

这不是因为损失函数“错了”，而是因为：

> 局部 next-token 正确性，并不自动等于全局篇章质量。

## 4.12 重复的第二来源：推理时模型要吃自己的输出

训练阶段，模型通常总是在“正确历史”上做预测。

可到了推理阶段，模型看到的上下文逐渐变成：

> 它自己刚刚生成出来的内容。

如果其中某一步稍微偏向了某个高频模板，后面几步就会继续在这个模板上展开，于是自我强化。

例如：

1. 某一步生成了“需要注意的是”
2. 下一步看到这个短语后，最熟悉的延续仍然是某种解释模板
3. 解释模板又导向下一个“需要注意的是”

于是就形成闭环。

这解释了为什么有些重复不是一开始就出现，而是越往后越严重。

因为随着生成长度增加，模型越来越多地在自己的轨迹上前进，而不是在真实样本轨迹上前进。

## 4.13 重复的第三来源：解码策略太保守

即使模型内部概率分布没有严重问题，解码策略也可能把它推向重复。

典型情形包括：

- 温度过低
- 只取极少数高概率 token
- 过于偏向贪心选择

当系统过度追求“安全”，模型就更可能反复选择：

- 最熟悉的连接词
- 最常见的句法模式
- 最不冒险的续写方式

这和人类写作很像。

如果一个人对自己要说什么并不完全确定，又被要求“绝不能说错”，他就会倾向于：

- 说套话
- 重复确认
- 一遍遍用熟悉结构兜圈

低温、过窄采样窗口下的模型，也是类似状态。

## 4.14 重复的第四来源：训练数据本身就有模板性和循环性

不要把所有重复都怪到推理参数头上。

很多重复其实深深刻在训练数据里。

例如：

- 列表式文章大量使用相同过渡句
- 某类问答数据反复用固定句式起头
- 抓取的数据里存在标题、页脚、导航文本重复
- 清洗不彻底的语料包含模板化广告或版权声明

模型会忠实学习这些统计规律。

于是当它不确定如何继续时，就会优先回到这些高频模板。

所以如果你发现重复具有非常鲜明的固定话术风格，不要只盯着采样器，要回头检查数据分布。

## 4.15 为什么小模型比大模型更容易重复

这不是神秘玄学，而是容量与表示能力共同造成的结果。

小模型通常面临几个限制：

- 对长程依赖建模较弱
- 对上下文中细微差别的分辨率较低
- 对复杂篇章计划的承载能力更有限

于是当它不确定时，更容易退回“平均而言最安全”的表达方式。

从信息论角度看，这像是在分辨率不足的情况下，把很多不同情境都压缩到几个共同模板上。

模板越少，复用就越频繁，读者就越容易感觉到重复。

所以在小模型项目里，重复不是某个偶发瑕疵，而是一种应该预期、应该系统管理的常见行为。

## 4.16 怎样判断你面对的是“该结束却没结束”，还是“内容根本没组织好”

很多人看到模型越写越长，就直接归因于“停止条件不够强”。这有时是对的，但并不总是对。

你需要先区分两类问题。

### 4.16.1 类别 A：内容其实已经说完了，但模型还在拖尾

这种情况表现为：

- 关键信息已经给完
- 后面新增内容信息密度很低
- 反复做总结、提醒、补充
- 读者觉得“已经可以停了”

这时问题更偏向停止与收尾机制。

### 4.16.2 类别 B：模型从中段开始就已经失去组织能力

这种情况表现为：

- 话题漂移
- 句间逻辑松散
- 结构感消失
- 不只是拖尾，而是整段一直在散开

这时单纯加强停止规则，只能更早把它截断，并不能解决组织能力不足。

这类问题通常还涉及：

- 训练不足
- 数据结构太杂
- 模型容量不够
- prompt 缺乏足够约束

## 4.17 一个实用心法：先判断“重复是症状，还是策略”

重复有时是纯粹的病态症状，但有时也是模型在有限能力下的“求稳策略”。

什么叫“求稳策略”？

就是模型面对不确定延续时，主动回到熟悉结构，以避免更大的错误。

这时如果你只是机械加入强惩罚，可能会得到另一个问题：

- 表面上重复少了
- 但文本更发散、更怪异、更不连贯

所以处理重复时，不要只追求“看起来不重复”，而要同时追求：

- 信息是否在推进
- 结构是否在收束
- 文本是否仍然自然

换句话说，真正要解决的是“篇章行为”，不是“去掉某几个重复词”。

## 4.18 控制重复与停止，可以从四层入手

把干预手段分层，会比“随便试几个参数”更有效。

### 4.18.1 数据层

关注：

- 样本是否有明确边界
- 是否存在大量模板废话
- 是否保留了自然结尾
- 是否有足够多结构完整的高质量短文、段落、回答

如果数据层不健康，后面所有干预都只能部分缓解。

### 4.18.2 训练层

关注：

- 模型是否训练足够
- 是否过早停止训练
- 验证集上是否真的学到了收尾模式
- 是否只是把局部高频模式学得更牢了

训练不足时，模型尤其容易在结尾阶段退化为模板复读。

### 4.18.3 解码层

关注：

- 温度是否过低
- top-k / top-p 是否太窄
- 是否有重复惩罚或 n-gram 约束
- 是否总是采用过于贪心的选择

这是最容易实验、反馈也最快的一层。

### 4.18.4 运行时协议层

关注：

- `EOS` 是否启用
- 停止字符串是否合理
- `max_new_tokens` 是否设置得过长或过短
- 对结构化任务是否提供了明确输出边界

很多“模型坏了”的问题，其实只是协议没有设计完整。

## 4.19 提示词也会强烈影响停止与重复

提示词不仅在告诉模型“写什么”，也在暗中影响“怎么结束”。

例如下面两种提示完全不同：

```text
请详细谈谈机器学习。
```

```text
请用 3 个自然段解释机器学习的基本概念，
最后用一句话总结它与传统规则程序的区别。
```

第二种提示给出了：

- 篇幅预期
- 结构预期
- 收尾预期

这会显著降低模型在后段迷航的概率。

所以如果你想减少拖尾和重复，一个常被低估的办法是：

> 让任务边界在提示词中更清楚，而不是把所有希望都押在采样参数上。

## 4.20 “自然结束”到底长什么样

这是一个很值得培养的判断力。

所谓自然结束，通常不是“突然消失”，而是几个信号同时出现：

- 内容上的问题已经回答完
- 结构上的小节已经收束
- 语言上出现结论句、总结句或闭合句
- 分布上 `EOS` 变得合理甚至高概率

也就是说，自然结束是语义、结构和分布共同对齐后的结果。

如果缺少其中某一层，就容易出现不自然情况：

- 语义未完却被截断
- 语义已完但模型继续拖尾
- 结构收束了，但分布仍不肯给出 `EOS`

真正成熟的训练与推理设计，就是尽量让这几层重新对齐。

## 4.21 初学阶段最值得做的观察实验

为了真正理解停止与重复，建议你做下面几类小实验，而不是只看单次样例。

### 4.21.1 固定 prompt，改变停止规则

保持同一个提示不变，只改变：

- 是否允许 `EOS`
- `max_new_tokens`
- 是否加入停止字符串

观察文本是怎样被截断、怎样自然结束、怎样拖尾的。

### 4.21.2 固定 prompt，改变采样保守程度

例如比较：

- 贪心
- 低温采样
- 中等温度采样

看重复是减少还是增加，收尾是更自然还是更混乱。

### 4.21.3 按类别收集重复样例

不要只记录“有重复”。要记录它属于：

- 词级
- 短语级
- 结构级
- 语义级

你会很快发现，不同重复对参数变化的敏感度并不一样。

### 4.21.4 观察结尾附近的模式

把注意力放在：

- 模型通常在什么位置开始拖尾
- 是先重复，还是先失去结构
- 是迟迟不给 `EOS`，还是根本没有收束句

这些观察会帮助你判断问题更偏向数据、训练还是解码。

## 4.22 一个容易犯的错误：把所有停止问题都交给“更短的长度上限”

当生成效果不好时，最容易立刻起作用的方法就是把 `max_new_tokens` 调短。

但这往往只是把问题藏起来，而不是解决它。

如果模型本该在第 90 个 token 自然结束，却总是拖到 180 个 token，你把上限改成 96，表面上确实看不到后面的废话了。

可模型并没有学会更好的收束。

一旦换个更长问题，或者需要更长回答的场景，问题会重新出现。

所以更短上限是运行时保护，不是停止质量的根本修复。

## 4.23 另一个容易犯的错误：看到重复就立刻上强惩罚

重复惩罚或 n-gram 限制当然有用，但如果用得过猛，可能导致：

- 句子变得支离破碎
- 合法重复也被错误压制
- 文风变怪
- 局部语法受损

因为自然语言里本来就存在合理重复：

- 术语反复出现
- 代词与实体多次出现
- 列表结构中词形有规律地重复

所以真正高质量的目标不是“彻底不重复”，而是：

> 不出现无意义、无推进、无收束价值的重复。

## 4.24 这一章应该形成的稳定心智模型

学完这一章，你最好把下面几个判断固定下来。

第一，语言模型天然是开放式继续系统，不会自动免费获得停止能力。

第二，`EOS` 的本质是把“结束”变成一个可学习的下一个 token 事件。

第三，自然停止依赖数据边界、训练质量、解码策略和运行时协议共同配合。

第四，重复往往与结束困难相伴出现，因为模型在缺乏全局把握时会退回局部高概率模板。

第五，真正要优化的不是“少几个重复词”，而是“更好的篇章推进与收束行为”。

## 4.25 本章小结

这一章你可以把它记成一句话：

> 模型只会继续，结束与不重复都需要被认真设计出来。

更具体地说：

- `EOS` 让“结束”第一次进入模型可学习的分布空间
- 外部停止规则为系统提供确定的资源与协议边界
- 重复常常暴露的是局部预测与全局篇章之间的落差
- 数据、训练、提示词、采样和运行时规则都会共同影响最终的停止与重复表现
