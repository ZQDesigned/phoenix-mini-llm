# 01. 自回归生成、prefill 与 decode

## 为什么训练完模型之后，还必须单独理解“生成过程”

很多初学者会自然地以为：

> 既然模型训练目标是预测下一个 token，那训练完成之后，生成文本应该只是自动发生的结果。

这句话只对了一半。

模型确实已经学会了某种 next-token 分布预测能力，但“让这种能力变成一段真正输出的文本”还需要另一层理解：

- prompt 怎样进入模型
- 模型怎样一步步扩展上下文
- 什么时候该继续，什么时候该停
- 为什么推理阶段和训练阶段看见的信息根本不同

也就是说，生成不是训练的附属尾声，而是：

> 把条件分布预测机制真正运行起来的一套过程。

## 先把最根本的差别说清：训练阶段和推理阶段不是同一件事

训练阶段，语言模型通常使用一种非常重要的机制：`teacher forcing`。

它的核心是：

- 模型在每个位置预测下一个 token
- 但下一个位置继续看到的，仍然是真实数据里的 token

换句话说，即使模型刚才预测错了，训练下一步也不会把那个错误结果喂回去，而是继续使用真实序列。

这和推理阶段完全不同。

推理时没有“已经写好的真实后续”可用，你只能：

1. 给模型当前上下文  
2. 让模型预测下一个 token 的分布  
3. 按某种规则选出一个 token  
4. 把这个 token 接回上下文  
5. 再继续下一轮  

这就是所谓的自回归生成。

## 什么叫自回归

“自回归”这个词最实用的理解是：

> 模型当前的输出，会被作为后续输入的一部分，再次进入模型。

对语言模型来说，这意味着：

- 第一个新 token 是根据 prompt 预测出来的
- 第二个新 token 是根据 “prompt + 第一个新 token” 预测出来的
- 第三个新 token 是根据 “prompt + 前两个新 token” 预测出来的

所以整段生成文本并不是一次性冒出来，而是：

> 由许多轮局部 next-token 决策滚动拼接出来。

## 为什么推理阶段常常比训练阶段更脆弱

因为推理阶段会不断把自己刚刚产生的输出重新喂给自己。

这意味着：

- 如果某一步走偏，后面上下文就已经被污染了
- 一旦进入某种重复循环，后面更难自动跳出
- 训练里看起来不错的局部预测，到了长程滚动时不一定还能维持质量

因此，生成行为常常会暴露出：

- 训练里没完全显露的问题
- 解码策略引入的额外行为
- 长上下文滚动后的稳定性限制

这也是为什么“loss 看着还行”并不自动等于“生成效果就会很好”。

## prompt 到底是什么

在用户视角里，prompt 通常是一段文字。

但从模型内部视角看，prompt 首先会经历：

- 文本规范化
- tokenizer 编码
- 得到 token id 序列

进入模型时，它不再是“自然语言句子”，而是：

> 当前已经存在的一段离散上下文。

模型的任务不是“理解用户提问”这种抽象描述，而是：

> 在这串已有 token 之后，继续给出下一位置的条件分布。

所以 prompt 更准确的定义是：

> 生成开始时模型已经拥有的上下文前缀。

## 为什么 prompt 不是“喂给模型一次，然后模型自动写完”

很多人日常使用聊天模型时，会形成一种错觉：

> 我输入了一段文字，模型像一个完整写作器一样直接把后文写出来。

底层并不是这样。

即使你最后看到的是一整段输出，模型内部通常仍然是按 token 一步步展开：

- 先处理输入前缀
- 再产生一个新 token
- 再基于扩展后的前缀产生下一个 token

这意味着“生成整段文本”只是很多轮小决策的结果，而不是一次单步推断。

## 什么是 prefill

当你第一次把完整 prompt 送进模型时，模型需要做的是：

> 基于整段已知前缀，把当前每个位置的表示和最后一个位置的下一个 token 分布准备好。

这一步常被称为 `prefill`。

它的直觉可以理解成：

- 先把用户已经给出的上下文“读进去”
- 让模型内部建立起与这段前缀对应的隐藏状态和注意力缓存基础

因为此时还没有任何缓存可用，所以第一次计算通常必须处理完整 prompt。

## prefill 和 decode 的区别是什么

这是理解现代推理的关键分界线。

### prefill

- 输入是一整段 prompt
- 目标是把已有上下文完整编码进去
- 通常计算量较大，因为要一次处理整个前缀

### decode

- 在已有前缀基础上继续逐 token 生成
- 每轮只新增很少的输入，通常就是一个最新 token
- 借助缓存后，不需要每步重算整段历史

所以很多推理优化讨论都会把推理拆成：

- prefill 阶段
- decode 阶段

它们属于同一模型，但计算负担和性能瓶颈并不完全一样。

## 为什么生成阶段通常只关心最后一个位置

模型一次前向时，常常会为当前输入序列中的每个位置都产出 logits。

例如输入长度是 `T`，那么输出常见形状会是：

\[
[B, T, V]
\]

这里：

- `B` 是 batch
- `T` 是序列长度
- `V` 是词表大小

但在生成阶段，你真正想知道的是：

> 在当前整段前缀之后，下一个位置该出现什么 token。

因此我们关心的，通常只是最后一个位置对应的 logits。

训练时不同，因为训练会同时利用所有位置上的监督去计算平均 loss；而生成每一轮只需要：

> 当前最后一个可决策位置的分布。

## 为什么自回归生成会不断变长

假设初始 prompt 长度为 `T`。

生成第一个 token 后，当前上下文长度变成：

\[
T + 1
\]

再生成一个，就变成：

\[
T + 2
\]

也就是说，生成过程天然在增长上下文。

这会带来两个非常重要的后果：

- 生成越久，历史上下文越长
- 如果没有缓存和停止条件，推理成本会不断上升

所以推理不只是“继续写”，也是“不断维护一条越来越长的上下文轨迹”。

## 因果约束在推理阶段为什么仍然重要

训练阶段我们说过，decoder-only 语言模型依赖 causal mask，保证当前位置不能偷看未来。

到了推理阶段，这个约束依然存在，而且更加自然。

因为推理时本来就没有未来 token 可看。

模型真正能用的信息只有：

- 已有 prompt
- 之前已经生成出来的 token

所以生成过程本身就和 causal 任务定义完全一致：

> 每一步都只能基于左侧历史继续扩展。

这也是为什么 decoder-only 模型能很自然地从训练目标过渡到生成行为。

## 为什么生成长度必须被显式控制

如果模型只是不断继续预测，它理论上可以一直写下去。

现实里通常需要至少一种终止机制：

- 达到 `max_new_tokens`
- 生成了 `EOS`
- 命中了某种外部停止条件

这说明生成并不是“自然会停”，而是：

> 模型分布和外部控制规则共同决定何时结束。

如果你完全不控制终止，哪怕模型局部预测还不错，也可能出现：

- 文本拖得很长
- 逻辑已经说完却继续绕圈
- 根本没有自然收尾

## 为什么同一个 prompt 不一定生成同样结果

这取决于你后面怎样从分布里选 token。

如果你使用贪心解码，结果通常更稳定。

如果你使用带随机性的采样，哪怕 prompt 一样：

- 只要分布里有多个可行候选
- 采样策略允许它们被选中

输出就可能不同。

这再次说明：

> 模型学到的是一个分布，不是一篇固定答案。

## 把生成过程写成最朴素伪代码

如果把细节折叠掉，最核心的生成循环可以写成：

```text
context = prompt

while not stop:
    logits = model(context)
    next_token_distribution = logits[last_position]
    next_token = decode(next_token_distribution)
    context = context + next_token
```

这段伪代码看起来很简单，但后面整卷 Part 7 都是在把它展开：

- `decode` 到底如何从分布变成 token
- `stop` 到底由什么决定
- `model(context)` 怎样在长上下文里不至于越来越慢
- 如何判断这条循环本身是不是健康

## 这一章最该带走的是什么

请把下面这条链牢牢记住：

1. 训练阶段使用 teacher forcing，推理阶段没有真实后续可喂  
2. 推理是一个自回归滚动过程  
3. 第一次完整处理 prompt 是 prefill，后续逐 token 扩展是 decode  
4. 每一轮真正决定输出的，通常只有最后一个位置的分布  

只要这条链稳定下来，后面你再看采样、KV cache 和调试，就不会把它们误看成分散技巧，而会知道它们都在服务同一套生成循环。
