# 01. 自回归生成、prefill 与 decode

## 这一章真正要解决的问题

在用户眼里，模型输出通常是一段连续出现的文字。

但在模型内部，生成并不是：

- 一次性写完一段文本

而是：

> 根据当前上下文，先决定下一个 token，再把它接回上下文，然后继续下一轮。

如果这条最基本的运行直觉没有真正建立，那么后面很多内容都会看起来很零碎：

- 为什么训练时可以并行，推理时却常常要串行
- 为什么 prompt 明明是一整段文本，生成却是一 token 一 token 地往后滚
- 为什么推理延迟常常分成 prefill 和 decode 两部分
- 为什么 KV cache 能极大提速，但又不改变模型语义

所以这一章要回答的核心问题非常明确：

> 训练好的 decoder-only 语言模型，到底怎样从“会预测下一个 token 的网络”变成“会滚动生成文本的系统”？

## 先把一个最重要的区别讲清：训练和推理不是同一种运行条件

很多初学者第一次学到这里时，会有一种隐含直觉：

> 训练和推理的主体网络既然一样，那运行方式应该也差不多。

这只对了一半。

主体网络的确一样，但它所处的外层运行协议差别很大。

训练阶段，模型通常使用的是：

- teacher forcing
- 并行监督整段序列

推理阶段，模型面对的则是：

- 没有真实后续可供查看
- 只能不断使用自己刚刚生成出来的 token 作为未来输入的一部分

这个差异不是工程细节，而是会直接改变：

- 模型每一步能看到什么
- 错误如何传播
- 为什么长程生成比训练指标更容易暴露问题

## teacher forcing 到底在帮什么忙

训练时，假设序列是：

```text
x1 x2 x3 x4 x5
```

模型会学习：

- `x1 -> x2`
- `x1 x2 -> x3`
- `x1 x2 x3 -> x4`
- `x1 x2 x3 x4 -> x5`

但关键在于：

> 即使模型在某一步预测错了，下一步训练时看到的前缀仍然是真实数据里的 token，而不是它自己刚才猜出来的错误 token。

这就是 teacher forcing 的本质。

它带来几个巨大好处：

- 训练更稳定
- 可以把整段序列并行送进模型
- 不会让早期错误立刻滚雪球污染后续每一步

但也正因为如此，它和推理阶段不是同一种条件。

## 推理时发生了什么根本变化

推理时，没有人再把“标准答案的后半句”偷偷交给模型。

模型必须真的靠自己往后写。

具体来说：

1. 先拿到一段已有上下文  
2. 根据这段上下文计算下一个 token 的分布  
3. 选出一个 token  
4. 把这个 token 拼接回上下文  
5. 再对扩展后的上下文做下一轮预测  

这意味着：

> 推理阶段的未来，是由模型自己一步步制造出来的。

而不是像训练那样始终有真实历史兜底。

## 什么叫“自回归”

“自回归”这个词最值得保留的直觉不是统计学定义，而是：

> 当前输出会回流到后续输入里，成为未来决策条件的一部分。

对 decoder-only 语言模型来说，这具体体现为：

- 第一个新 token 来自 prompt
- 第二个新 token 来自 `prompt + 第一个新 token`
- 第三个新 token 来自 `prompt + 前两个新 token`

所以生成不是一次性得到一段完整后文，而是：

> 一长串局部 next-token 决策滚动拼接出来的结果。

## 为什么推理阶段比训练阶段更脆弱

这点必须从根上讲透。

训练时，模型虽然也在每个位置做 next-token prediction，但它不会“吃到自己犯过的错”。

推理时则完全不同。

一旦某一步生成偏了，下一步的上下文就已经被污染。

于是会出现连锁效应：

- 本来局部还算合理的模型，长程生成时越写越歪
- 某种轻微偏差会被后续几轮不断强化
- 一旦进入重复环，模型就可能越来越难自己跳出来

所以推理不是训练的简单展示，而是：

> 对模型局部决策质量、上下文鲁棒性和采样协议的一次放大检验。

## prompt 在模型内部到底是什么

日常使用时，prompt 看起来是一段“人类写给模型的话”。

但从模型内部视角看，它首先只是：

> 一段已经存在的 token 前缀。

它会经历：

- 文本规范化
- tokenizer 编码
- 得到 token ids

之后才进入模型主体。

所以 prompt 更准确的定义不是“问题句子”，而是：

> 生成开始时模型已经拥有的离散上下文前缀。

模型并不会抽象地理解“用户在问什么”这种人类表述，它做的是：

> 在这段已有 token 序列之后，继续预测下一个 token 分布。

## 为什么 prompt 不是“喂进去一次，模型自动写完”

用户界面很容易制造一种错觉：

> 我输入一段 prompt，模型内部像整段补全器一样一次性算完全部答案。

底层并不是这样。

即使最后展示给你的是一整段输出，内部也通常仍然是在重复：

- 计算下一步分布
- 选一个 token
- 追加回上下文
- 再继续

也就是说，“一整段输出”只是：

> 许多次 next-token 选择在时间上连起来后的结果。

这个认识特别重要，因为后面所有采样、停止条件、KV cache、流式输出都建立在这条循环上。

## 先把整条生成循环写成最小伪代码

如果把所有复杂实现折叠掉，一个最朴素的自回归生成循环可以写成：

```python
context = prompt_ids

for _ in range(max_new_tokens):
    logits = model(context)              # [1, T, V]
    next_logits = logits[:, -1, :]       # [1, V]
    next_token = sample(next_logits)
    context = append(context, next_token)

    if next_token == eos_id:
        break
```

这段伪代码已经揭示了几个本质事实。

### 第一，模型每轮都被重新调用

不是算一次，然后“自动续写”。

### 第二，每轮真正关心的是最后一个位置

因为那才对应“当前上下文之后的下一个 token”。

### 第三，停止并不是自然发生的

需要：

- EOS
- 最大长度
- 或其他显式停止规则

只要这个最小循环你心里站稳了，后面很多工程细节都会变得清晰。

## 为什么每轮通常只看最后一个位置的 logits

假设当前上下文长度是 `T`，模型前向常见输出形状是：

\[
[B, T, V]
\]

其中：

- `B` 是 batch size
- `T` 是当前序列长度
- `V` 是词表大小

这意味着：

- 对当前输入中的每个位置
- 模型都给出了一份词表打分

但在推理中，真正要决定的是：

> 在当前整段前缀之后，下一个还没出现的位置该是什么。

这个决策对应的正是：

\[
logits[:, -1, :]
\]

也就是最后一个位置的输出。

所以推理阶段“只取最后一步”不是某种偷懒，而是任务定义本来就决定了：

> 当前只需要新增一个 token。

## 为什么上下文会在生成中不断变长

假设初始 prompt 长度是 `T`。

生成一个 token 后，长度会变成：

\[
T + 1
\]

再生成一个，就变成：

\[
T + 2
\]

所以生成本质上是在维护一条：

> 不断增长的上下文轨迹。

这会带来两个直接后果。

### 第一，模型拥有的历史越来越长

这解释了为什么模型能在后续继续引用自己刚刚写出的内容。

### 第二，如果不做缓存，计算代价会越来越大

因为每次你都在把更长的上下文重新送进模型。

这正是 KV cache 后面要解决的问题之一。

## causal 约束在推理时为什么仍然成立

训练时，我们通过 causal mask 明确规定：

> 当前位置只能看左侧历史，不能偷看未来。

推理时，这条规则其实更自然了。

因为未来 token 根本还不存在。

模型能看到的只有：

- prompt
- 以及此前已经生成出来的 token

所以推理天然符合：

> 只根据已知前缀继续生成。

这也是为什么 decoder-only 模型能够很自然地从训练目标过渡到生成循环。

## 什么是 prefill

现在进入现代推理里最常见的两个术语：

- prefill
- decode

先说 prefill。

当你第一次把完整 prompt 送进模型时，模型需要做的是：

> 处理这整段已有前缀，让内部隐藏表示、注意力读写关系和后续生成所需的基础状态都建立起来。

这一步通常被称为：

> prefill

你可以把它理解成：

- 先把用户已经给出的上下文“吃进去”
- 先让模型在这段前缀上完成一次完整前向
- 为之后真正逐 token 生成做好起点准备

## prefill 的计算特点是什么

prefill 的特点是：

- 输入通常是一整段 prompt
- 需要处理这整段前缀里的所有位置
- 往往在推理时是一次较重的计算

如果 prompt 很长，prefill 往往是首次响应延迟的重要来源。

这也是为什么在真实系统里，“首 token 延迟”和“后续 token 吞吐”常常要分开讨论。

## 什么是 decode

当 prefill 完成之后，模型已经拥有：

- 当前前缀对应的上下文状态
- 或至少拥有能支持后续增量计算的缓存基础

接下来就进入：

> decode

也就是逐 token 地往后生成。

decode 的典型模式是：

- 每轮只新增一个很短的输入
- 通常只需要计算最新一步
- 借助缓存避免重复处理整段历史

所以 decode 更像是：

> 在已有前缀基础上不断向前滚动一步。

## prefill 和 decode 的根本区别是什么

可以把它们并排看。

## prefill 更像“整段读入”

它的目标是：

- 把已有 prompt 全部处理进去

它的特点是：

- 一次输入长
- 首次计算重
- 常对应首 token 延迟

## decode 更像“逐步续写”

它的目标是：

- 基于已有前缀继续生成新 token

它的特点是：

- 一次新增很短
- 步数多
- 常对应持续生成时的吞吐性能

这就是为什么现代推理系统里经常把性能拆成：

- prefill performance
- decode performance

因为它们虽然都属于“推理”，但瓶颈完全不同。

## 为什么 prefill 和 decode 不能混成一个性能概念

如果你只说“这个模型推理很快”而不区分 prefill 和 decode，往往信息是不够的。

因为两个系统可能出现：

- A 的 prefill 很快，但 decode 一般
- B 的 prefill 一般，但 decode 很快

这对真实用户体验影响很大。

例如：

- 长 prompt 问答更在意 prefill
- 长篇续写更在意 decode

所以从工程角度看，理解生成过程不能停留在“模型在输出”，还要看到：

> 输出前的整段读入，与输出时的逐步续写，是两个不同的计算阶段。

## 为什么 decode 阶段如果没有 cache 会很浪费

假设你已经有长度为 `T` 的上下文，现在要生成第 `T+1` 个 token。

如果每次都从头重新算整段前缀，那么：

- 第一次用长度 `T` 算
- 第二次用长度 `T+1` 再从头算
- 第三次用长度 `T+2` 再从头算

这会造成大量对历史位置的重复计算。

而这些历史位置中，有很多内容其实没有变。

因此，从计算重用角度看，decode 阶段的最自然优化就是：

> 尽量复用已经算过的历史 key / value 等中间结果。

这就是 KV cache 会出现的根本动机。

## 流式输出为什么能成立

用户看到的“模型边写边吐字”，本质上也是自回归循环的直接结果。

因为模型每轮都会产生一个新的 token 选择结果，所以系统完全可以：

- 刚生成一个，就先显示一个
- 再继续下一轮

因此流式输出并不是另一种模型，而只是：

> 把自回归循环中的中间结果及时暴露给用户。

这个点看似简单，但很值得记住，因为它再次说明：

> 界面体验本质上是模型运行协议的外显形式。

## 为什么生成一定需要停止条件

如果只看自回归循环，模型原则上可以一直往后写。

所以系统必须定义某种终止规则。

常见有：

- 生成到 EOS
- 达到 `max_new_tokens`
- 命中某些外部 stop sequences

这意味着：

> 生成不是“自然写完就自动停”，而是模型分布和外部协议共同决定何时结束。

这也是为什么停止条件会和模型行为紧密耦合，而不是外围 UI 小选项。

## 为什么同一个 prompt 有时每次都不一样

这并不是因为模型主体变了，而是因为：

> 从 logits 到 token 的决策规则可能带有随机性。

如果你总是：

- 取 argmax

那么相同输入通常会更稳定。

如果你使用：

- temperature
- top-k
- top-p
- 随机采样

那么即便 prompt 一样，每次也可能沿不同高概率路径继续展开。

所以“同一 prompt 不同输出”的根源，不是在生成循环本身，而是在：

> 每轮如何从分布里选 token。

这正是下一章和再下一章要详细展开的内容。

## 一个更稳的生成直觉：模型不是在“写整段话”，而是在“维护一条前缀”

如果这一章只留下一个最稳的直觉，应该是：

> decoder-only 生成不是一次性写出整段后文，而是在不断维护一条越来越长的 token 前缀，并在每一步只决定“接下来再加一个什么 token”。

这个直觉一旦建立：

- prefill 就变成“先建立已有前缀”
- decode 就变成“在前缀后面再迈一步”
- sampling 就变成“如何为这一步做决策”
- KV cache 就变成“如何不重复处理旧前缀”

你会发现后面整卷的内容几乎都能自动接上。

这一章解决的是：

> 生成循环怎样成立。

但它还没有详细回答两个关键问题：

### 第一，模型每步到底直接输出了什么

也就是：

- logits 到底是什么
- 为什么它还不是 token

这会在下一章展开。

### 第二，从这份分布里到底怎样选 token

也就是：

- greedy
- temperature

- top-p

这些采样策略到底在动哪里。

这会在再下一章展开。

## 常见误区

### 误区一：训练好的模型会自动一次性补全整段文本

不对。

真实生成通常是 token 级自回归循环。

### 误区二：训练和推理只是同一件事的快慢区别

不对。

两者最大差异在于：

- 训练时有 teacher forcing
- 推理时只能吃自己刚刚生成出来的历史

### 误区三：prompt 是“自然语言问题本身”

不够准确。

对模型来说，它首先只是已有 token 前缀。

### 误区四：prefill 和 decode 只是两个实现名词，没什么概念区别

不对。

一个是整段读入，一个是逐步续写，计算形态和性能瓶颈都不同。

### 误区五：生成阶段如果只看最后一个位置，说明前面位置没用

不对。

前面所有位置都已经通过上下文建模影响了最后一个位置的 logits。

### 误区六：KV cache 是另一种模型模式

不对。

它是对 decode 阶段历史结果的复用，不是另一台模型。

## 这一章真正要记住的核心句子

如果你只记住本章六句话，应该记住下面这些。

1. 推理阶段和训练阶段共享同一主体网络，但运行条件完全不同：训练有 teacher forcing，推理只能吃自己刚生成的历史。  
2. 自回归生成的本质是：当前输出回流为后续输入的一部分，因此整段文本是很多轮 next-token 决策滚动拼接出来的。  
3. prompt 在模型内部首先只是一个已有 token 前缀，而不是抽象的人类问题句。  
4. prefill 负责把整段已有前缀处理进去，decode 负责在这个前缀基础上逐 token 继续展开。  
5. 生成每一轮真正关心的通常只是最后一个位置的 logits，因为那对应“当前前缀之后的下一个 token”。  
6. 理解生成最稳的方式，是把模型看成一直在维护一条不断变长的 token 前缀。
