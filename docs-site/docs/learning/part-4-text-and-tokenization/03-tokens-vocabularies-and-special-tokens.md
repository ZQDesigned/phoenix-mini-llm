# 03. Token、词表与 special token

## 为什么文本不能直接进神经网络

前面我们已经知道：

- 神经网络处理的是数值张量
- 模型输出的是分布
- 文本文件底层是一串字符和字节

于是接下来必须解决一个非常现实的问题：

> 文本怎样变成模型可以处理的离散输入单位？

这就是 token 化问题。

很多初学者会下意识地觉得：

> 文本既然已经是字符了，模型直接看字符不就行了吗？

或者：

> 文本既然本来就是一句一句、一个词一个词的，为什么还要专门定义 token？

这些直觉都很自然，但还没有进入模型视角。

对模型来说，真正重要的不是“人觉得一句话长什么样”，而是：

> 输入空间怎样被切分成一组可枚举、可索引、可嵌入、可预测的离散单位。

这组单位，就是 token。

## 什么是 token

token 可以先理解成：

> 模型输入输出空间里的基本离散单位。

它不一定等于：

- 一个字
- 一个词
- 一个英文单词
- 一个自然语言学上的形态单位

它可能是：

- 单个字符
- 子词片段
- 标点
- 带空格前缀的字符串片段
- 某些结构控制符号
- 某些特殊边界标记

所以当你听到“预测下一个 token”时，必须立刻意识到：

> 这个 token 不是自然语言天然就给好的单位，而是模型世界里人为定义出来的离散观察颗粒度。

这个判断是整个 tokenizer 章节的核心之一。

## token 为什么不是“人类直觉上的词”

因为“词”这个概念本身就没有你想象得那么稳定。

例如：

- 中文没有天然空格分词边界
- 英文里的缩写、标点、复合词都有不同切法
- 多语言混写时“词”的边界更复杂
- 代码、路径、URL、表情符号都不适合直接用日常“词”的直觉处理

如果模型强行要求：

> 每个 token 必须对应一个人类定义的词。

那么它会立刻遇到很多问题：

- 新词怎么办
- 罕见词怎么办
- 拼写变体怎么办
- 词表规模会不会爆炸

因此现代语言模型更常做的是：

> 找到一种对计算和统计学习都更合适的离散颗粒度，而不是追求人类语言学意义上的“词”。

## token 化为什么是一种建模选择

很多初学者会把 tokenizer 当成纯预处理器，好像“随便选一个都差不多”。

这是不对的。

tokenizer 的选择会影响：

- 输入长度
- 词表大小
- 稀有词处理方式
- 模型在不同语言现象上的学习难度
- embedding 和输出头的参数规模
- 推理阶段的生成粒度

也就是说，token 化不是外壳，而是：

> 你如何切开语言、如何定义模型观察世界的基本颗粒度。

所以 tokenizer 从来不是“模型之外的脚手架”，它本身就是模型设计的一部分。

## 为什么模型一定要先有一套离散单位

因为训练目标要求模型在某一位置上，从一组候选里给出分布。

这个“候选集合”必须是有限可枚举的。

也就是说，模型需要先知道：

- 世界里有哪些可预测单位
- 每个单位对应哪个 id
- 输出头应该对哪些类别打分

如果没有一套离散 token 定义，后面的很多环节都无从谈起：

- embedding 查表无法建立
- logits 的维度无从定义
- cross-entropy 的类别空间无法确定

所以 token 的作用不是“把文本切开这么简单”，而是：

> 把原始语言世界投影成一个有限离散分类空间。

## 从文本到 token，其实是在定义模型的观察分辨率

你可以把 token 化理解成一种“分辨率设定”。

如果颗粒度很粗：

- 单个 token 包含更多局部语义
- 序列会更短
- 但词表可能更大

如果颗粒度很细：

- 词表会更小
- 新词更容易表示
- 但模型需要跨更多位置重建语义

所以 tokenization 本质上在回答：

> 模型一次应该看多大的语言积木？

这跟图像里的像素分辨率有一点类似。

分辨率太粗，细节丢失。

分辨率太细，处理成本高，而且上层结构要靠更多步才能恢复。

token 的设计，就是语言世界里的这类权衡。

## 字符级、词级、子词级到底在权衡什么

### 字符级

优点是：

- 词表小
- 几乎不会遇到真正无法表示的新词
- 构造简单

缺点是：

- 序列会很长
- 模型需要跨更多位置才能拼出词义
- 高层语义单位被拆得很碎

字符级不是不能用，而是通常会让：

- 训练成本上升
- 长程依赖压力变大
- 语义恢复更困难

### 词级

优点是：

- 单个 token 更接近人类直觉中的“一个词”
- 序列长度相对更短

缺点是：

- 词表容易膨胀
- 稀有词和新词问题严重
- 多语言和拼写变体很麻烦

### 子词级

这是一种折中方案。

它试图在：

- 词表规模
- 序列长度
- 稀有词可分解性

之间取得更平衡的结果。

所以今天大量模型使用 BPE、SentencePiece 一类方法，并不是“因为大家都这么做”，而是因为它们在实践上常常更合适。

## 什么是词表

词表就是：

> tokenizer 允许模型识别和输出的全部 token 集合。

每个 token 在词表中都有自己的 id，于是模型看到的输入序列通常会变成：

```text
[42, 119, 7, 803, ...]
```

这说明词表不是一本单纯的“字符串清单”，而是：

- 输入空间
- 输出空间
- embedding 查表空间
- 最终分类空间

的共同定义。

所以只要词表一变，很多东西都会一起变。

## id 到底意味着什么

对于模型来说，字符串本身并不是直接可计算对象。

真正参与训练和推理的是 token id。

例如一个 token 可能叫：

```text
"pho"
```

但模型并不会直接把 `"pho"` 这个字符串送进神经网络。

它先被映射成某个整数 id，例如：

```text
4812
```

然后这个 id 再用来：

- 查 embedding
- 进入后续张量计算
- 在输出端被当成类别索引

也就是说，字符串是给人看的，id 是给模型用的。

这也是为什么：

> 同一个 token 字符串只要 id 改了，整个参数对齐关系也就跟着变了。

## 为什么词表大小是个关键超参数

词表越大：

- 单个 token 可能携带更丰富的局部语义
- 序列长度往往更短
- 但 embedding 和输出头会更重
- 最终分类空间也会更大

词表越小：

- 参数压力变小
- 模型类别空间变小
- 但序列会更长
- 模型需要在更多 token 上拼装词义

所以词表大小不是“越大越高级”，而是要和：

- 语料语言特征
- 模型规模
- 上下文长度
- 训练预算

一起平衡。

## 词表大小为什么会直接影响参数量

这点很重要，因为很多人只把词表理解成“切词规则的副产品”。

但在神经网络里，词表大小通常直接进入两个大部件：

- 输入 embedding
- 输出 logits 头

如果 hidden size 是 `d`，词表大小是 `V`，那么仅 embedding 相关参数规模就和 `V * d` 强相关。

输出头如果不共享权重，也同样会和 `V * d` 强相关。

这意味着词表不是“抽象语言设计”，它会直接影响：

- 参数总量
- 显存占用
- 输出分类难度

所以 tokenizer 设计和模型资源预算之间其实是硬连接关系。

## 高频 token 和长尾 token 为什么是个核心矛盾

真实语料里的 token 分布几乎总是长尾的。

也就是说：

- 少量 token 非常高频
- 大量 token 很低频

这会带来一个重要矛盾。

如果你把很多低频片段也都放进词表：

- 词表会越来越大
- 低频 token 的参数很难充分学好
- 输出空间更稀疏

但如果你完全不允许这些低频片段以较大单位存在，又会：

- 让序列变长
- 让模型需要更多步重建语义

所以词表设计本质上是在和语言的长尾分布打交道。

这就是为什么现代 tokenizer 几乎都会强调：

> 让高频片段能整体出现，让低频片段可退回到更细粒度组合。

## 什么是 special token

special token 指的是那些不主要承载普通自然语言词义，而是承担结构或控制作用的 token。

常见例子包括：

- BOS：序列开始
- EOS：序列结束
- PAD：补齐占位
- UNK：未知 token
- 分隔符
- 说话人角色标记
- 任务控制标记

这些 token 的价值不在于“它们也属于词表”，而在于：

> 它们定义了模型如何理解边界、结构、开始、结束和格式控制。

所以 special token 从来不是装饰，而是协议。

## BOS 和 EOS 到底在告诉模型什么

### BOS

BOS 通常表示序列开始。

它的作用不是为了“看起来完整”，而是：

> 给模型一个明确的起点上下文。

模型从 BOS 之后开始解释后续 token，很多训练样本和生成流程都会围绕它建立起始状态。

### EOS

EOS 通常表示序列结束。

它的作用非常关键，因为它告诉模型：

> 在某些上下文下，结束本身也是一个合法且重要的预测目标。

如果没有这种结束标记，模型就不容易在训练中学到“什么时候自然停住”。

这会直接影响后面推理阶段的停止行为。

## PAD 为什么经常和 batch 有关

在批量训练里，不同样本长度常常不一致。

为了把它们拼成统一张量，通常需要补齐。

PAD token 就是为此服务的。

它的作用更接近：

> 结构占位符。

模型训练时通常不应该把 PAD 当成正常语义内容来学，所以它往往要和：

- mask
- ignore index
- loss 过滤

这些机制配合使用。

如果 PAD 处理不对，后果可能不是“小误差”，而是：

> 模型开始把补齐垃圾当成正常预测目标。

## UNK 为什么有时重要，有时又几乎消失

UNK 表示未知 token。

在较早或较粗的 tokenizer 方案里，它用于处理：

> 词表里没有的输入片段。

但现代很多 byte-level 或更细粒度方案里，UNK 的重要性会下降，因为几乎任何字符串都能被拆成更基础的单位。

这提醒你：

> special token 的需求并不是绝对固定的，而是和 tokenizer 设计共同决定的。

所以不要把某些 token 机械背成“任何模型都必须有”。

更好的问题是：

> 在这套 tokenizer 方案下，模型需要哪些边界和控制协议？

## 角色 token、分隔符和控制 token 为什么会越来越重要

随着模型任务变复杂，token 不再只是承载词义。

它还越来越常承担：

- 区分用户和助手
- 区分系统提示与正文
- 分隔多段输入
- 标记结构化区域
- 引导特定任务格式

这类 token 的重要性在对话模型、指令模型、多段输入任务里尤其明显。

它们说明：

> token 世界里不只有“语言内容单位”，还有“交互协议单位”和“格式控制单位”。

所以 special token 是模型协议的一部分，不是附属插件。

## 为什么 special token 不是小细节

很多模型行为其实都依赖这些边界标记。

例如：

- EOS 会影响模型是否知道该停
- 分隔符会影响模型怎样区分不同段落或不同说话人
- PAD 会影响 batch 对齐和 mask
- 角色 token 会影响模型怎样理解对话结构

所以如果 special token 定义不稳，后果可能不是“输出有点怪”，而是：

> 任务边界本身被定义错了。

这会让后面的训练、评估、推理全部连锁受影响。

## tokenizer 为什么属于模型定义的一部分

这是必须牢牢记住的判断。

如果你换了 tokenizer，哪怕模型结构一个字没改，很多事情也已经变了：

- 输入 token 序列变了
- 词表 id 变了
- embedding 含义变了
- 输出头类别空间变了
- special token 协议也可能变了

这说明 tokenizer 不是“模型外部的预处理插件”，而是：

> 模型输入输出协议的一部分。

因此，一个 checkpoint 往往不能随便脱离原 tokenizer 使用。因为它们本来就是一套共同定义。

## 为什么同一份权重不能随便换 tokenizer

这件事对初学者特别关键。

一旦 tokenizer 变了：

- 某个 id 对应的 token 可能变了
- 某段文本切出来的 token 序列变了
- 词表大小和索引空间可能也变了

于是原来训练好的：

- embedding
- 输出头
- special token 语义习惯

都不再和新 tokenizer 的离散世界对齐。

这就像你训练的是一套法语词典索引，结果推理时突然拿了一套德语词典索引去查，同样的 id 已经不再表示同样的东西。

所以通常要把：

- tokenizer 文件
- 词表
- special token 定义
- merge 规则
- 模型权重

视为同一套工件的一部分。

## token 边界会改变什么

很多初学者知道 token 会影响“序列长度”，但低估了它影响的范围。

实际上 token 边界会改变很多事：

- 一个概念需要多少步才能表达
- 罕见词会被当成整体还是被拆开
- 模型在哪些位置更容易积累监督信号
- 同样长度的上下文里能容纳多少语义内容
- 生成时局部连续性表现如何

所以 tokenization 不是前处理小技巧，而是在定义：

> 模型到底用什么语言积木去理解和生成世界。

## 词表、embedding、输出头为什么是一个系统

现在可以把这三者连起来看了。

### 词表

定义有哪些离散类别存在。

### embedding

把离散类别映射到连续向量空间。

### 输出头

把连续表示再映射回词表类别分数。

这三者一起构成：

> 从离散输入世界进入连续表示世界，再从连续表示世界返回离散输出世界的完整接口。

所以只要词表变了：

- embedding 的对齐就变了
- 输出类别空间也变了

这再次说明 tokenizer 是模型本体的一部分。

## 多语言和代码场景为什么会让 token 设计更难

当语料不仅是单一自然语言，而是包含：

- 多语言混写
- 代码
- 数字
- URL
- 特殊符号

时，token 设计会更困难。

因为你需要同时平衡：

- 不同语言的高频单位
- 不同脚本系统的边界习惯
- 标点与空白的语义作用
- 代码中的标识符和操作符

这也是为什么现代 tokenizer 往往更偏向：

- 子词级
- byte-level
- 更强的通用可分解性

它们未必最“人类直观”，但通常更适合复杂真实输入世界。

## 对学习项目来说，最重要的不是选最先进 tokenizer，而是理解影响链

在学习项目里，不需要一上来把 tokenizer 选择做成研究竞赛。

更务实的目标通常是：

- 先理解字符、词、子词、字节这些方案的权衡
- 理解词表大小和序列长度之间的拉扯
- 理解 special token 其实是协议定义
- 理解 tokenizer 如何和模型权重牢牢绑定

也就是说，学习阶段最关键的不是：

> 挑出最先进 tokenizer。

而是：

> 真正理解为什么 tokenizer 方案会影响整个模型系统。

只要这条链清楚，后面无论你用 BPE、SentencePiece 还是其他方案，理解都会稳很多。
