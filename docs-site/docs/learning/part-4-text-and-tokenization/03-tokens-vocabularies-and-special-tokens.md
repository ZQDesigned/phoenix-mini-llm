# 03. Token、词表与 special token

走到这一章，文本已经经历了两次很关键的认知重写。

前一章告诉你：

- 模型学习的不是抽象“语言整体”，而是一份具体语料所呈现出来的统计世界
- 机器也不会天然读懂文字，它先面对的是字节、编码和被规范化后的文本表示

现在问题终于推进到真正贴近模型输入的地方：

> 当文本已经被稳定地表示出来之后，它到底怎样变成模型可以读、可以嵌入、可以预测的离散单位？

这就是 token 的问题。

很多初学者第一次听到这里时，会下意识地说：

> 文本不就是字吗？或者不就是词吗？为什么还要额外发明 token 这种说法？

这个反应非常自然。
但它恰好暴露了人类阅读直觉和模型建模视角之间的一条重要断裂。

对人类来说，“字”“词”“一句话”这些单位看起来非常自然。
可对模型来说，真正重要的问题并不是：

> 人类平时最习惯怎样理解文本单位，

而是：

> 我们要把文本世界切成怎样的一组离散积木，才能让模型稳定地输入、输出、计数、嵌入和预测？

只要你用这个问题去看 token，很多原本显得神秘的事情都会变得自然：

- 为什么 token 不一定等于词
- 为什么词表大小会影响参数量
- 为什么同一份权重不能随便换 tokenizer
- 为什么 special token 不是附带标记，而是协议的一部分

这一章真正要建立的，就是这种视角转换。

## 模型并不直接处理“文本意义”，它首先需要一个有限、可枚举、可索引的离散空间

前面我们已经说过，神经网络处理的是张量，而不是人类主观意义上的文字。

这句话如果继续往前走，就会变成更具体的一个要求：

> 模型输入和输出都必须最终落到一个有限、可枚举、可索引的离散空间上。

为什么？

因为训练时，模型并不是在一个无限开放的语言宇宙中模糊地“猜一句话”。
它常常是在某个位置上做这样的事情：

> 给一组候选离散单位打分，再形成下一步的概率分布。

要做到这一点，至少要先知道三件事：

- 候选单位有哪些
- 每个候选单位对应哪个 id
- 输出头到底对哪一组类别打分

如果这组离散单位没有先被定义出来，那么后面的很多环节都无从谈起：

- embedding 查表无法建立
- logits 维度无法确定
- cross-entropy 的类别空间无法定义

所以 token 从来不是“文本切一切”的附带手工活。
它本质上是在定义：

> 模型究竟以什么颗粒度观察语言世界。

## token 不是自然语言天然给好的单位，而是建模时人为选择的一种观察颗粒度

如果要用一句最关键的话来概括整章，可以先提前说出来：

> token 不是语言世界本来就摆在那里的天然原子，它是我们为了建模而人为定义的离散观察单位。

这句话非常重要，因为初学者最容易落入的误解，就是把 token 当成“人类词汇概念的程序翻版”。

实际上，token 可以是很多东西：

- 单个字符
- 子词片段
- 一个完整词
- 某个常见前后缀
- 一个标点
- 一个带前导空格的字符串片段
- 一个特殊控制标记

也就是说，token 的边界不由语言学直觉自动决定。
它首先由建模需要决定。

你可以把 token 想成模型搭积木时使用的基本砖块。
砖块切得粗一些，单块承载的局部意义更多，但种类会变多。
砖块切得细一些，种类可能更少，但搭出完整语义要用更多块。

所以 token 问题不是在问：

> 文本真正的自然原子是什么？

它更像是在问：

> 对当前这套建模目标、计算资源和统计学习方式来说，怎样切分文本，会让模型最容易有效地学习？

## 为什么 token 不能简单等于“人类直觉中的词”

初学者最自然的想法，通常是：

> 文本既然本来就由词构成，那 token 直接等于词不就好了？

这在某些局部场景里看上去很合理。
但一旦进入真实语言世界，这个想法会迅速遇到很多困难。

第一，很多语言的词边界本来就没有想象中稳定。

中文通常没有天然空格分词。
日文和泰文也不像英文那样天然用空格分隔。
这意味着“词”本身就需要额外定义。

第二，哪怕在英文里，“词”也没有表面上那么简单。

例如：

- 缩写怎么切
- 连字符复合词怎么切
- 标点贴在哪一边
- URL、路径、表情、代码标识符算不算词

第三，词级单位会很快遭遇长尾问题。

真实语料里总会有：

- 稀有词
- 新词
- 拼写变体
- 专有名词
- 混合词形

如果每个完整词都必须单独进词表，那么词表会膨胀得非常快，而稀有词仍然覆盖不足。

第四，多语言和跨领域文本会让词边界更加复杂。

代码、数学、口语、缩写、文件路径和多语言混写文本，并不会温柔地配合你的“一个词就是一个单位”的幻想。

所以今天的大多数语言模型不会执着于：

> token 必须尽可能像人类心中的词。

它们更关心的是：

> token 切分之后，模型能否在统计上有效学习，能否控制词表规模，能否处理长尾现象，以及能否在计算成本上承受。

## token 化本质上是在定义模型的观察分辨率

理解 token 的一个很好办法，是把它看成一种观察分辨率设定。

如果颗粒度很粗，那么单个 token 往往包含更多局部意义，序列长度会更短，但类别空间通常会更大。

如果颗粒度很细，那么类别空间可能变小，未登录形式更容易被拆开表示，但序列会拉长，模型必须跨更多位置才能重建更高层语义。

这件事和图像建模有一点相似。

分辨率过粗，你会丢掉很多细节。
分辨率过细，你会让上层结构恢复变得更吃力。

所以 token 不是随手切一切。
它是在给模型回答一个非常实在的问题：

> 一次应该给你多大的语言积木，才最利于后续学习？

只要这个类比站稳，你后面再看字符级、词级、子词级、字节级，就不会把它们看成若干并列术语。
你会知道它们是在不同分辨率之间做权衡。

## 字符级、词级、子词级和字节级并不是“谁更先进”，而是在不同约束下的不同取舍

这一点必须主动说清，因为初学者很容易把 tokenizer 方案学成“排行榜”。

实际上，这些方案更像不同约束下的不同妥协。

字符级的优点很明显：

- 词表小
- 新词几乎总能表达
- 不太依赖显式分词词典

但它的问题同样明显：

- 序列很长
- 模型要跨更多位置拼出词义
- 更高层语义需要更多步才能浮现

词级方案也有直接吸引力：

- 单个单位更接近人类直觉
- 序列相对更短

可它很快就会碰到：

- 词表爆炸
- 长尾词难处理
- 新词和变体不稳定

子词级方案之所以成为现代主流，并不是因为它神秘更高级。
而是因为它在很多现实场景里比较均衡地处理了这几组矛盾：

- 词表规模
- 序列长度
- 长尾词可表达性
- 多语言与新词适应能力

字节级方案则把单位继续往更底层压。
它可以在某些方面避免未登录文本问题，但也会把建模负担更多地压回到序列长度和上层表示恢复上。

所以这里真正重要的不是背诵哪种方案叫啥。
而是理解：

> tokenizer 方案选择，实质上是在不同分辨率、不同词表大小、不同长尾压力和不同计算成本之间做取舍。

## 词表不是字符串清单，而是模型输入空间、输出空间和参数规模的一部分定义

当你说“词表”时，很多人脑中会浮现出一本单纯的字符串列表：

```text
hello
world
token
model
...
```

这当然不算错，但它严重低估了词表在模型里的地位。

更准确的说法是：

> 词表定义了模型允许自己识别和输出的全部离散单位集合。

这意味着词表不只是阅读字典。
它同时决定了：

- 输入空间里有哪些合法 token
- 每个 token 对应哪个整数 id
- embedding 查表空间有多大
- 输出头最终分类空间有多大

所以词表不是“数据文件之一”。
它更像模型边界条件的一部分。

一旦词表变化，很多东西都会一起变化：

- token id 映射变化
- embedding 对应关系变化
- 输出 logits 的类别含义变化

这也是为什么 tokenizer 变化通常不能被看成独立外部替换件。

## id 不是附属编号，而是字符串进入神经网络之前的真正桥梁

模型并不会直接把某个字符串送进神经网络。

例如，一个 token 可能写作：

```text
"pho"
```

但神经网络不会直接处理这个字符串对象。
真正参与计算的，是它对应的 token id，比如：

```text
4812
```

然后这个 id 再被用于：

- 查 embedding 表
- 形成输入张量
- 作为 target 类别标签
- 对应输出头的某一维 logits

所以 id 的意义并不是“为了程序方便编号”这么简单。
它是在做一件非常关键的桥接工作：

> 把人类可读的 token 名称，变成模型可计算的离散索引。

只要这层关系站稳，你就会更容易理解后面很多常见现象：

- 为什么同一个字符串换一个 tokenizer，id 完全可能不同
- 为什么同一份权重不能脱离原 tokenizer 单独解释
- 为什么预测下一个 token，本质上是在预测下一个 id 所对应的类别

## 词表大小为什么不是简单的“词越多越好”，而是直接牵动模型成本和学习压力

很多初学者谈词表大小时，会自然地说：

> 词表越大，认识的东西越多，不是更好吗？

这不完整。

词表变大，当然意味着更多局部单位可以被更直接地表示。
但它也同时会带来几类成本。

第一，参数成本。

embedding 层大小和词表通常直接相关。
输出头的类别空间也和词表直接相关。
词表越大，这两处参数压力通常越大。

第二，统计成本。

词表一旦太大，很多 token 会非常稀有。
模型就必须在更稀疏的类别空间里学习分布。

第三，长尾问题。

如果词表很大但仍覆盖不完现实世界的新词和变体，问题不会自动消失。
它只是换了一种形状继续出现。

第四，建模粒度问题。

有些词表扩大，实际上是在用更粗的单位去减少序列长度。
但这种粗化也会改变模型理解和组合语言结构的方式。

所以词表大小从来不是“多就是好”或者“小就是好”。
它是在不同成本之间平衡：

- 参数量
- 序列长度
- 稀有形式可表达性
- 统计学习难度

## 高频与长尾的矛盾，正是 tokenizer 设计为什么无法只靠直觉完成的核心原因

现实文本分布有一个长期存在的事实：

> 少数单位极其高频，大量单位则极其长尾。

这在词级世界里尤其明显。

例如常见功能词会出现得非常多。
而专有名词、技术术语、拼写变体、罕见组合则可能只偶尔出现一次两次。

如果你把每个完整词都单独收进词表，那么：

- 高频词当然受益
- 但大量低频词会让词表迅速膨胀
- 仍然会有大量未覆盖形式

而如果你完全压到非常细的单位，长尾问题虽然缓和一些，但序列会变长，模型又要承担更多组合负担。

这正是 tokenizer 设计真正棘手的地方。
它不是语言学猜谜。
它是在对抗长尾分布：

> 我们怎样让高频模式能被高效表示，同时又不让低频和新出现的形式变成完全无法处理的黑洞？

只要这个矛盾被看清，后面学 BPE、SentencePiece 等方法时，你就会自然知道它们到底在试图解决什么。

## special token 不是附属标记，而是模型协议中的控制点与边界声明

到了这里，必须专门讲一讲很多人最容易轻视的一类 token：special token。

初学者第一次见到它们时，很容易把它们想成：

- 一些库附带的小标记
- 为了让程序更方便的控制符
- 不是正文内容，所以不太重要

这个判断太轻。

special token 之所以重要，是因为它们经常承担协议性角色。

它们不是“普通语言内容”。
它们往往在告诉模型：

- 一段序列从哪里开始
- 一段序列在哪里结束
- 哪些位置只是填充，不该算作有效内容
- 多段内容之间的边界在哪里
- 某个角色、某种模式或某类控制上下文是否切换

也就是说，special token 很多时候是在做：

> 结构声明与控制语义。

它们虽然不是自然语言正文的一部分，却常常深刻影响模型如何理解训练样本边界和推理时的上下文协议。

## BOS、EOS、PAD、UNK 之类的 token，本质上是在给模型定义序列制度

先看几个最常见的 special token。

`BOS` 往往可以理解成“序列开始”声明。
它告诉模型：

> 现在开始进入一个新序列或一个新上下文单元。

`EOS` 则更像“序列结束”声明。
它不仅是终止标记，也是在向模型说明：

> 某种可预测的文本延续已经在这里收束。

`PAD` 的作用通常和 batch 对齐有关。
它不是正文内容。
它更像是在说：

> 这里为了让多个样本能堆成同形张量而补了位置，但这些位置不应被当作真实语言内容学习。

`UNK` 在某些传统系统里很重要，因为它在表达：

> 这里出现了词表外单位，我们先用一个统一占位符表示。

只不过在现代很多子词或字节级方案里，这种“彻底未知单位”的压力被显著减轻了。

如果从更高层看，这些 token 的共同作用并不是“补充一些特殊类别”。
它们是在定义：

> 序列如何开始、如何结束、哪些位置有效、哪些位置只是结构辅助。

所以它们不只是 token 表中的边缘角色。
它们是在帮助模型形成训练和推理时的基本制度感。

## tokenizer 属于模型定义的一部分，不是训练前后可以随手互换的小工具

这一点必须说得非常明确。

很多初学者会下意识觉得：

> tokenizer 只是把文本转成 id 的工具，模型本体还是权重本身。

这种想法很容易导致后面大量混乱。

更准确的理解是：

> tokenizer、词表、token id 映射、embedding 表和输出头类别空间，本来就是同一个系统的不同侧面。

为什么同一份模型权重不能随便换 tokenizer？

因为权重学习时依赖的，是原词表定义出来的输入输出空间。

一旦 tokenizer 变了，通常就意味着：

- 文本被切成了不同 token
- token 对应的 id 变了
- embedding 查表含义变了
- 输出 logits 每一维对应的类别也变了

这不是换一个外壳而已。
这几乎是在改写模型与文本世界之间的接口协议。

所以更稳的说法不是：

> tokenizer 配合模型。

而是：

> tokenizer 本来就是模型定义的一部分。

## 词表、embedding 和输出头为什么必须被看成一个整体

理解这件事的最好办法，是把它们写成一条很短的链：

1. 词表定义有哪些 token
2. token 被映射成 id
3. id 用来查 embedding 表
4. 模型内部表示再经过输出头回到词表类别空间

这意味着：

- 词表决定类别空间
- embedding 决定这些类别如何进入模型
- 输出头决定模型如何回到同一套类别空间上做预测

所以这三者不是松散零件，而是前后对接的一条闭环。

如果你只看词表，不看 embedding 和输出头，会低估它对参数量和语义接口的影响。
如果你只看 embedding，不看词表，会忽略它在服务哪一组离散单位。
如果你只看输出头，不看词表，会忘记 logits 每一维都要落回一套明确 token 类别上。

这也是为什么词表设计会直接影响模型体积和学习难度。
它从来不是“字符串选择题”那么简单。

## 多语言、代码和混合文本之所以让 tokenizer 更难，是因为“合理颗粒度”本来就不是单一世界里的答案

当语料只在单一、相对规整的自然语言中活动时，token 设计已经不简单。
一旦进入更复杂的文本世界，问题会变得更尖锐。

例如多语言语料会遇到：

- 脚本系统差异
- 词边界差异
- 高频单位结构差异

代码语料会遇到：

- 标识符组合自由度高
- 符号密集
- 格式结构重要
- 长尾字符串形式很多

对话和控制格式语料又会强调：

- 角色边界
- 分隔符
- 结构标记

这说明 tokenizer 设计没有一个脱离语料世界的永恒最佳答案。

更准确的说法是：

> 不同文本世界，会把“什么颗粒度更合理”这个问题推向不同方向。

这也是为什么学习 tokenizer 时，不能只背某种方法名字。
更重要的是学会问：

> 当前这份语料、这类任务、这套资源约束，到底在奖励哪种切分取向？

## 对学习项目来说，真正重要的不是找“最先进 tokenizer”，而是理解它会如何改写后面的整个训练系统

初学者最容易掉进的另一个误区，是把 tokenizer 选择学成“选型焦虑”。

他们会问：

> 哪种 tokenizer 最先进？
> 哪种最像大模型在用？
> 哪种能一劳永逸？

这类问题都太快了。

在学习项目阶段，更有价值的问题通常是：

- 这个 tokenizer 把文本切成了什么样的单位
- 这会怎样影响序列长度
- 这会怎样影响词表规模
- 这会怎样影响长尾词处理
- 这会怎样影响 embedding 和输出头规模
- 这会怎样影响后续 next-token prediction 空间

只要这条影响链没有看清，哪怕你“用了最流行的方法”，也不真正理解它。

所以学习项目里，最重要的不是追求最先进名词。
最重要的是：

> 把 tokenizer 看成定义观察颗粒度和离散预测空间的前置制度。

一旦这个视角站稳，后面你再看 BPE、样本打包、右移目标和输出头设计时，就会自然很多。

## 这一章真正想留下的主线

如果把整章压缩成最核心的一条链，可以写成：

> 语言模型不能直接处理人类意义上的文本，它首先需要一个有限、可枚举、可索引的离散空间，于是 token 才成为建模的基本单位；但 token 并不是自然语言天然给好的原子，而是为了训练和预测而人为选择的观察颗粒度，因此它未必要等于人类直觉中的词；字符级、词级、子词级和字节级方案之间并不存在脱离语料与任务约束的绝对优劣，它们本质上是在词表规模、序列长度、长尾处理和计算成本之间做不同取舍；词表不只是字符串清单，而是模型输入空间、输出空间和参数规模的一部分定义，token id 则是字符串真正进入神经网络之前的桥梁；special token 不是附属标记，而是在声明序列边界、无效位置和控制语义；词表、embedding 和输出头必须被看成同一个闭环系统，因此 tokenizer 属于模型定义的一部分，而不是可以随手互换的小工具。

这条主线站稳之后，你后面再看：

- tokenizer 训练
- 词表大小
- embedding 参数量
- 输出 logits 空间
- BOS / EOS / PAD

就不会把它们看成分离知识点。
你会知道它们都在服务同一件事：

> 把真实文本世界切成一组对统计学习和神经网络计算都可操作的离散积木。

## 读完本章后，你应该能稳定回答什么

如果这一章真正读稳了，你应该能够不用背定义，而是用自己的话稳定回答下面这些问题：

- 为什么模型必须先拥有一套有限离散单位，训练才成立
- token 为什么不能简单等于人类直觉中的词
- 怎样理解 token 化其实是在定义观察分辨率
- 字符级、词级、子词级和字节级分别在权衡什么
- 词表为什么不是普通字符串列表
- token id 到底在模型系统中扮演什么角色
- 为什么词表大小会直接牵动参数量和学习压力
- 高频与长尾的矛盾为什么会逼出 tokenizer 设计问题
- special token 为什么属于协议，而不是附属装饰
- 为什么 tokenizer、词表、embedding 和输出头必须被看成一个整体

只要这些问题能够稳定答出来，这一章就已经完成了最重要的任务：

> 它让“token、词表与 special token”不再像 tokenizer 工具说明书，而变成了你理解语言模型到底以什么离散单位观察和预测文本世界的基础章节。
