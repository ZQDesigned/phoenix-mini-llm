# 04. 子词分词、BPE 与 tokenizer 训练

## 为什么现代语言模型很少只用“纯字符”或“纯词”

当你第一次知道 tokenizer 要把文本切成 token 时，一个自然问题是：

> 为什么不直接按字符切，或者干脆按词切？

看起来这两种方式都很直观。

但实际做语言模型时，它们各有明显问题。

### 纯字符级的优点和代价

按字符切的优点很明显：

- 词表可以很小
- 理论上几乎不会有“遇到一个新词就完全没法表示”的问题

但它带来的代价也很重：

- 序列会变得很长
- 许多本来属于词或短语层面的结构，要被拆成很多步才能重新拼回来
- 模型需要花更多上下文和更多层次，才能恢复出较稳定的词义单位

对学习项目来说，这种方案并不是不能做，而是通常会让：

- 训练成本上升
- 上下文长度压力变大
- 语义单位过碎

### 纯词级的优点和代价

按词切的好处也很直观：

- 单个 token 往往更接近人类直觉中的“一个词”
- 序列长度相对更短

但问题在于：

- 词表会迅速膨胀
- 稀有词、新词、拼写变体会非常棘手
- 多语言场景下问题更严重

这意味着纯词级方法很容易把输入空间做得过大，也更容易让大量低频词变成难学、难泛化的类别。

## 子词方法为什么成为折中方案

现代语言模型常见的思路是：

> 既不完全退回到字符，也不把所有词都当作不可再分的最小单位，而是在两者之间寻找更合适的分解颗粒度。

这就是子词方法的核心直觉。

它希望同时实现几件事：

- 常见高频片段能被整体表示
- 生僻词或新词仍能被拆开
- 词表规模保持在可控范围内
- 序列长度不要膨胀得太厉害

换句话说，子词方法是在平衡：

- 压缩效率
- 泛化能力
- 词表成本

这也是为什么很多现代模型最终会选择 BPE、WordPiece、SentencePiece 或 unigram 类方案。

## BPE 的核心直觉是什么

BPE 可以先不看算法细节，只抓它最核心的思想：

> 从较细的基本单位出发，不断把高频共现片段合并成更大的 token。

例如，某些片段如果总是经常一起出现，那么把它们合成一个单位通常是有价值的。

这样做会逐步得到一种折中结果：

- 高频模式被压缩成更大的 token
- 低频或新组合仍然可以回退到更细粒度分解

你可以把它理解成：

> tokenizer 在试图找到一套适合当前语料统计结构的常用语言积木。

## BPE 并不是“懂语言”，而是在压缩统计结构

这一点很重要。

BPE 看起来有时会切出很像词根、词缀或常见短语的单位，但不要误以为它首先是在做人类语言学分析。

更准确地说，它首先是在利用：

- 高频共现
- 压缩收益
- 可重复使用的片段模式

因此 BPE 的很多结果会和语言学单位有一定重合，但它的根本驱动力是：

> 数据压缩与统计复用，而不是先验语法知识。

这也是为什么不同语料训练出来的 tokenizer，即使面对同一种语言，也可能学出不同的切分习惯。

## tokenizer 训练到底在训练什么

这里的“训练”容易引起误解。

当我们说训练 tokenizer 时，不是在用梯度下降训练一个神经网络模型。

它通常更接近：

> 基于语料统计，学习一套更合适的 token 切分词表和分解规则。

这套规则会回答：

- 哪些片段应该作为词表项保留
- 哪些词该整体出现
- 哪些低频组合应该拆开
- 如何在压缩和泛化之间平衡

因此 tokenizer 训练的输出不仅是一张词表，还包括：

- 切分规则
- special token 定义
- 某些预处理约定

## 为什么 tokenizer 训练结果会反过来影响模型能力

因为 tokenizer 定义了模型最基础的输入颗粒度。

如果 tokenizer 把很多本应稳定整体出现的单位切得过碎，那么模型需要在更多位置上重新拼装语义。

如果 tokenizer 又把很多低频、偶然组合都强行塞进大词表，模型则会面临：

- 分类空间过大
- 低频 token 学习困难
- 参数浪费

所以 tokenizer 不是模型前的一次性准备工作，而是：

> 对模型学习难度的提前塑形。

它会直接影响：

- 序列长度分布
- 词表大小
- 罕见词处理方式
- embedding 和输出头规模

## special token 为什么必须在 tokenizer 训练前后一起考虑

有些人会把 special token 看成训练完 tokenizer 之后随手补上的几项设置。

更稳妥的理解应该是：

> special token 也是输入输出协议的一部分，因此它们必须和词表、切分规则一起被一致管理。

例如：

- BOS 和 EOS 决定序列边界
- PAD 会影响 batch 对齐
- 角色分隔符会影响多段文本任务

如果这些定义前后不一致，你后面训练样本构造和推理行为都会出问题。

## 为什么同一份模型权重不能随便换 tokenizer

这件事对初学者非常关键。

一旦 tokenizer 变了：

- 某个 id 对应的 token 变了
- 某段文本切出来的 token 序列变了
- 词表大小和索引空间可能也变了

此时原本训练好的 embedding 和输出头，就不再和新 tokenizer 的离散世界对齐。

这就是为什么通常要把：

- tokenizer 文件
- 词表
- special token 定义
- 模型权重

视为同一套工件的一部分。

## 学习项目里该怎样看 tokenizer 选择

对学习项目来说，不需要一开始把 tokenizer 选择搞成研究论文竞赛。

更务实的目标通常是：

- 先理解纯字符、纯词、子词三者的权衡
- 用一种主流而可解释的子词方法把流程跑通
- 明白 tokenizer 训练结果如何改变模型行为

也就是说，学习阶段最关键的不是“挑出最先进 tokenizer”，而是：

> 真正理解为什么 tokenizer 方案会影响整个模型系统。

## 这一章真正要记住的核心句子

如果这一章只记一句话，它应该是：

> 子词 tokenizer 之所以在现代语言模型里常见，是因为它在字符级和词级之间提供了更好的折中；BPE 和类似方法本质上是在利用语料统计学习一套更合适的离散积木，而这套积木会直接决定模型的输入难度、词表规模和泛化方式。
