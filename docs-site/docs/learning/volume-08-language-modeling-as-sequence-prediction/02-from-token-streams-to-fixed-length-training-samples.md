# 05. 从 token 流到固定长度训练样本

## 为什么 tokenizer 做完之后，训练仍然还没有开始

很多初学者第一次把文本成功变成 token id 之后，会很自然地松一口气：

> 文本已经变成数字了，现在是不是直接喂给模型就行？

这一步当然很重要，但它还远远不等于训练已经准备好。

因为 tokenizer 交给你的，通常只是下面两类对象之一：

- 一篇篇文档各自对应的 token 序列
- 或者把很多文档串起来之后得到的一条很长的 token 流

而模型训练真正需要的，并不是“任何一段 token 序列”，而是：

> 一批长度受控、边界定义清楚、形状整齐、能组成张量并直接附着监督目标的训练样本。

这句话里每个词都带着后面真正会影响训练的约束。

- `长度受控` 关系到显存、计算成本和可训练的上下文范围
- `边界定义清楚` 关系到模型会把哪些 token 当成同一段连续历史
- `形状整齐` 关系到 batch 如何高效堆叠
- `能附着监督目标` 关系到 loss 到底在哪些位置成立

所以从“token 化完成”到“可以开始训练”，中间仍然隔着一整层很关键的对象重组。

这一章讲的就是这层重组。

## 先分清三个层次：文档、token 流、训练样本

如果不先把对象区分开，后面非常容易越讲越乱。

在这一章里，至少要同时看清三个层次。

### 第一层：文档

文档是原始语料世界里的自然单位。

它可以是：

- 一篇新闻
- 一段论坛帖子
- 一条聊天记录
- 一章小说
- 一份代码文件

文档天然带着边界。
人类也很容易直觉地把它当成“一个完整对象”。

### 第二层：token 流

文档经过 tokenizer 之后，就变成了 token 序列。

例如：

```text
[104, 88, 912, 17, 53, 221, ...]
```

这时对象已经不再是“文章正文”那样的语言学单位，而是：

- 离散符号编号构成的序列

如果把多篇文档串在一起，它甚至会变成一条更长的 token 流。

### 第三层：训练样本

训练时，一次前向真正消费的，通常不是整篇文档，也不是整条超长 token 流。

真正被模型作为一个输入单元处理的，往往是：

- 从 token 流中切出来的一段固定长度或近似固定长度的窗口

这段窗口才是训练样本。

所以最重要的区分是：

> token 化并不等于样本化。

你把文本切成 token，只是把语言对象转成了可计算的离散序列。
而把这些离散序列组织成训练样本，才是在真正定义模型每次看到什么。

## 为什么训练喜欢固定长度样本，而自然语言本身并不固定长度

现实文本天然长度不一致。

- 一条评论可能只有十几个 token
- 一段对话可能有几百个 token
- 一篇长文可能有几千甚至几万个 token

但神经网络训练，尤其是 GPU 上的批量训练，极度偏爱形状规整的张量。

原因并不神秘。

只要样本长度高度不一致，就会立刻出现很多问题：

- batch 难以高效堆叠
- 内存占用不稳定
- attention 计算开销剧烈波动
- 吞吐量不稳定
- 不同 batch 的有效 token 数差异太大

因此，语言模型训练里一个非常常见、也非常重要的做法就是：

> 把 token 流切成固定长度的连续窗口。

例如，你规定：

- 每个训练样本长度都是 256
- 或 512
- 或 1024

这样模型每次前向看到的输入形状就稳定了。

这不是因为自然语言天生就应该被切成 256 或 512 长度。
而是因为：

> 训练系统更喜欢长度规则、成本可预测、可以高效组成 batch 的对象。

## 固定长度样本不是自然语言的自然单位，而是计算系统偏好的单位

这一点必须单独强调。

因为很多初学者第一次看到固定长度样本时，会隐约带着一种误解：

> 既然训练这样做，那是不是语言本来就应该被这样切？

不是。

在很多情况下，训练样本边界根本不等于：

- 句子边界
- 段落边界
- 文档边界
- 语义完整单元边界

一个长度为 256 的训练样本，很可能只是：

- 从连续 token 流里截出来的一段窗口

它在人类看来，也许恰好从一个句子的中间开始，又在另一个句子的中间结束。

这看起来很“粗暴”，但它之所以依然有效，是因为自回归模型本来就在学：

- 条件续写结构

只要窗口内部保留了真实的局部连续性，它就仍然可以提供大量真实监督信号。

所以这里最值得记住的判断是：

> 训练样本首先是计算对象，其次才是语言对象。

当然，语言结构仍然重要。
但你必须接受：

- 训练系统与人类语言直觉偏好的“完整单元”
- 并不总是一致

## 为什么“整篇文档作为一个样本”通常不可行

这是初学者最容易产生的一个自然想法：

> 文档明明天然有边界，那为什么不直接一篇文档就是一个样本？

听起来很合理，但大多数时候会很快碰到现实约束。

### 第一，长度差异会非常大

如果一篇文档只有几十个 token，另一篇有几千个 token，那么这两者几乎没法被优雅地放进同一个高效 batch。

### 第二，超长文档会迅速推高计算成本

自注意力的计算与内存开销会随着序列长度上升得很快。

### 第三，超短文档会让 batch 利用率很差

大量短样本如果都单独成样本，就会让 padding 或样本浪费变得很严重。

### 第四，训练通常需要稳定的吞吐和成本预测

而“每篇文档长度任意”会让这一点变得很差。

因此，文档虽然是语义上很自然的单位，但它并不天然适合直接成为 GPU 训练时的一次前向对象。

样本重组的本质，其实是在协调两种完全不同的边界：

- 语言世界喜欢的边界
- 计算系统喜欢的边界

## 从 token 流构造训练样本，核心其实是在定义“模型每次能看到多长的历史”

只要你开始按固定长度切窗口，你其实就在定义一个非常关键的东西：

- 上下文长度

这不是单纯的数据工程参数。
它会直接决定：

- 一个样本里模型最多能利用多少左侧历史
- 训练期间模型接触到的局部依赖跨度有多大
- attention 的时间和空间成本有多高

因此，“把 token 流切成长度 T 的样本”在更深层上其实是在说：

> 在训练时，我们愿意为每个位置提供最多 T 左右范围内的可见历史，并为此支付对应的计算成本。

这就是为什么 `context_length` 或 `max_seq_len` 从来不只是实现参数。
它是建模能力与计算预算之间的一次显式选择。

## 上下文长度为什么不是越大越好

直觉上，很多人会觉得：

> 上下文越长，模型能看到的信息越多，当然越好。

这只对了一半。

更长的上下文确实可能带来潜在好处：

- 能利用更长距离依赖
- 更少因为窗口太短而截断重要信息
- 更接近真实长文场景

但它同时也会带来明显成本：

- 训练更慢
- 显存消耗更高
- batch size 变小
- 实验迭代速度下降
- 在小模型、小显存条件下更容易得不偿失

因此，上下文长度从来不是一个抽象上的“越大越先进”。
更准确地说，它是在回答：

> 在当前模型规模、当前数据形态和当前硬件预算下，我们希望模型主要练习怎样长度范围内的条件预测？

这也是为什么学习项目往往会先从较短上下文开始。

不是因为长上下文不重要，而是因为：

- 先把整条训练链跑通
- 再逐步增加上下文范围

通常比一开始就追求很长窗口更理性。

## 样本切法其实是在定义“哪些 token 有资格成为同一上下文”

只要你开始把 token 组织成窗口，就必须问一个很根本的问题：

> 在这个窗口里，哪些 token 被允许彼此视为连续历史？

这个问题看起来像在问边界，实际上是在问监督语义。

例如，如果你把两篇互不相关的文档直接拼接：

```text
文档 A 的尾部 + 文档 B 的开头
```

并且中间什么标记都不加，那么模型看到的就只是一条连续序列。

它不会天然知道：

- 这里本来换文档了
- 前一句和后一句并不存在真实语义延续

于是模型就可能被训练去学习一些并不真实的跨文档相邻关系。

所以，一旦你做样本切片，你就不只是在决定：

- 长度怎么切

你同时也在决定：

- 哪些相邻关系会被当成真实训练信号

## 两种常见路线：按文档独立切块，或者跨文档拼接后切块

从 token 流构造训练样本时，最常见的有两类思路。

### 路线一：每篇文档各自 token 化并在内部切块

这种做法的直觉很强：

- 文档边界天然保留
- 不容易产生跨文档污染
- 语义连续性更干净

但它也有明显代价：

- 每篇文档末尾可能剩余不足一整块的 token
- 这些尾部 token 要么浪费，要么需要特殊处理
- 如果语料里短文很多，利用率会受影响

### 路线二：把很多文档连接成连续流，再统一切块

这种做法的优点主要是效率：

- token 利用率高
- 流式处理方便
- 数据管道更简单

但代价是：

- 必须显式处理边界语义
- 否则模型会在错误的地方学习连续性

因此，这两条路线没有绝对的“永远正确”。
真正关键的问题是：

> 你是否明确知道这种切法让模型学到了哪些相邻关系，又忽略了哪些边界信息。

## 为什么 special token 经常会出现在样本边界附近

只要你意识到边界本身也是一种信息，就会明白为什么很多训练语料会插入特殊标记，例如：

- `BOS`
- `EOS`
- 文档分隔符

这些 token 的作用并不只是“方便程序识别”。
更重要的是，它们在向模型声明：

- 一个序列从哪里开始
- 一个序列在哪里结束
- 两段本来无关的内容在哪里被人为拼接

如果没有这类标记，模型就更难区分：

- 自然连续
- 和管道拼接连续

也就是说，边界标记实际上是在帮助模型学习：

> 哪些相邻是语言世界本来就有的，哪些相邻只是数据组织阶段制造出来的。

## 什么时候应该浪费一点 token，也不该把边界处理得太粗糙

数据工程里有一个很常见的诱惑：

> 尽量让每个 token 都被用上。

这当然是合理目标，但并不总能压倒一切。

有时候为了让 token 利用率更高，过度粗糙的跨文档拼接会引入比“少浪费一点 token”更糟的问题：

- 模型学到虚假的续写关系
- 文档收尾和开头被错误绑定
- 生成时更容易出现奇怪跳转

因此，数据利用率不是唯一目标。
更成熟的想法是：

> token 利用率、边界语义、实现复杂度和训练效率之间，需要一起权衡。

这也是为什么一些实现会宁可接受少量尾部浪费，也要保持更干净的边界定义。

## 固定窗口是怎样从一条长序列里切出来的

现在把视角暂时收窄，只考虑：

- 我已经有了一条很长的 token 流

那么最简单的切法就是：

- 从头开始，每隔固定长度切一段

例如设窗口长度是 `T = 8`，序列是：

```text
t0 t1 t2 t3 t4 t5 t6 t7 t8 t9 t10 t11 t12 ...
```

那么最朴素的切法可能是：

- 样本 1：`t0 ... t7`
- 样本 2：`t8 ... t15`
- 样本 3：`t16 ... t23`

这就是不重叠窗口。

它的好处很简单：

- 实现容易
- token 不会重复进入多个样本
- 训练吞吐高

但它也有局限：

- 某些跨窗口边界的依赖会被切断
- 一个 token 左右的上下文视野会强烈依赖它刚好落在哪个窗口里

因此，窗口切法本身也在影响模型接收到的上下文分布。

## 为什么有时会使用重叠窗口或 stride 小于窗口长度的切法

为了缓解不重叠切片带来的边界切断问题，有些训练或分析场景会使用：

- 重叠窗口

也就是让两个样本共享一部分 token。

例如：

- 样本 1：`t0 ... t7`
- 样本 2：`t4 ... t11`

这里的 stride 就是 4，而窗口长度是 8。

这样做的好处是：

- 同一段局部内容可以在不同左上下文条件下被多次观察
- 窗口边缘被切断的问题有所减轻
- 某些中等跨度依赖被覆盖得更平滑

但代价也非常明显：

- 数据重复增加
- 有效训练 token 数会被“放大”
- 训练成本增加

因此，是否重叠切片，不是单纯的数据增强小技巧。
它是在决定：

> 你愿意为更平滑的上下文覆盖，付出多少重复计算。

## token 会不会被重复使用，本质上是在问样本覆盖分布是什么样

只要你考虑 stride，就会发现一个很重要的事实：

- 同一个 token 是否只出现一次
- 或出现在多个训练样本里

并不是无关紧要的实现差别。

它改变的是：

- 模型在训练中究竟如何反复接触不同局部模式

如果完全不重叠：

- 每个 token 基本只在一个窗口里扮演一次局部上下文成员

如果有重叠：

- 某些 token 会在多个不同窗口位置反复出现

这会影响：

- 样本相关性
- 有效数据利用方式
- 梯度统计特性

因此，数据切样方式本身也在悄悄影响训练动力学。

## 短文档为什么会引出 padding、拼接或丢弃三难题

现实世界里，很多文本非常短。

如果你的窗口长度是 512，但某篇文档只有 80 个 token，就会立刻出现一个问题：

> 这 80 个 token 怎么变成一个可训练样本？

常见思路通常有三类。

### 第一类：padding 到固定长度

优点是：

- 结构整齐
- 实现简单

代价是：

- 大量位置其实没有真实监督意义
- 需要 mask 掉无效位置
- 如果短文很多，token 利用率很差

### 第二类：与其他短文档拼接

优点是：

- 利用率更高
- 更节省显存与计算

代价是：

- 必须认真处理边界
- 否则模型会学习错误连续性

### 第三类：直接丢弃太短片段

优点是：

- 管道简单

代价是：

- 数据浪费
- 短文本分布可能被系统性削弱

所以短样本从来不是“顺手补点 padding”那么简单。
它涉及：

- 训练资源
- 语料分布保真
- 边界语义

三者共同的权衡。

## padding 为什么不是简单补零，而是“无效位置声明”

当你使用 padding 时，最容易犯的错误是把它想成：

- 只是把样本补长一点

更准确的理解是：

> padding 是在说：这些位置存在于张量里，但不应像真实 token 那样参与建模和损失。

这意味着 padding 一旦出现，你通常还必须同步处理至少两件事：

- attention 或可见性逻辑
- loss 统计逻辑

否则模型可能会开始：

- 把 padding 当成真实上下文
- 甚至去预测 padding 本身

这会直接污染训练目标。

所以 padding 不是长度修补。
它是一种：

- “这个位置只是占位，不代表真实语言事件”

的显式声明。

## batch 为什么要求样本不仅长度一致，还要语义布局一致

当我们说样本要整齐，很多人第一反应只是：

- 长度一样

但真正进入 batch 之后，你会发现仅仅长度一样还不够。

更完整的要求是：

> batch 中每一条样本，不仅要在形状上能堆叠，还要在语义布局上具有一致性。

例如，如果一个 batch 张量形状是：

```text
[batch_size, seq_len]
```

那么你隐含地在说：

- 第 0 维是不同样本
- 第 1 维是同一类“时间顺序上的 token 位置”

只要这层语义一致性不成立，张量虽然能堆起来，训练意义也会出问题。

因此，从 token 流到训练样本的工作，并不只是“切成一样长”。
它还包括：

- 让这些样本在 batch 里扮演同构对象

## 训练样本一旦被定义，后面的“右移目标”才真正有落脚点

这一点和下一章直接相连。

只有当你已经从 token 流里切出了：

- 一个长度明确的输入窗口

你才有可能进一步定义：

- 这段窗口里每个位置该预测谁

换句话说，训练样本的定义，先回答的是：

- 一次前向到底看哪一段 token

而右移一位目标进一步回答的是：

- 这段 token 里每个位置到底为哪个下一个 token 负责

所以这两章不能分开理解。

前一章讲：

- 样本边界

下一章讲：

- 样本内部监督对齐

两者合在一起，才构成语言模型训练数据对象的完整定义。

## 如果窗口从句子中间开始，模型会不会“看不懂”

这是一个非常自然的问题。

既然训练样本可能从句子中间切入，那么模型会不会缺少完整语义，导致学得很差？

答案通常是：

- 局部上会丢掉窗口左边更早的历史
- 但整体训练并不会因此失效

原因在于，语言模型训练关注的是分布上的大量局部条件预测。

虽然某个窗口的最左边位置可能缺少更久远的历史，但：

- 这个 token 在别的窗口里也可能曾经以更靠右的位置出现
- 海量样本会让模型反复看到各种不同截面的局部历史

因此，窗口切片带来的历史截断确实存在，但并不会自动毁掉训练。
更合理的理解是：

> 训练是在用许多局部可见历史的样本，近似覆盖整条语料分布中的条件预测事件。

## 样本边界会直接影响模型学到的“开头”和“结尾”概念

很多初学者低估了边界对模型行为的影响。

但只要你认真看训练对象，就会发现：

- 样本从哪里开始
- 样本在哪里结束
- 是否显式放入 `BOS` 或 `EOS`

都会改变模型看到的序列结构。

例如：

- 如果大量样本总在随机中间位置开始，模型就更少把“序列开头”当作强结构
- 如果样本结尾总是硬截断而没有终止标记，模型对“自然结束”可能学得更弱
- 如果跨文档处使用明确分隔符，模型就有机会学到“这里是一个边界事件”

也就是说，边界不仅在数据工程层面重要。
它还会渗透进模型后面的生成行为：

- 何时更像开场
- 何时更像收尾
- 在不连续内容之间是否会出现奇怪衔接

## “一条样本到底是不是完整语义片段”并不是唯一重要问题

初学者常常会执着于：

> 这一条样本是不是完整的一句话或一段话？

这当然是有意义的问题，但并不是唯一关键问题。

对于语言模型训练而言，同样重要甚至更重要的还有：

- 这条样本内部的 token 连续性是否真实
- 边界是否被诚实地表达出来
- 上下文长度是否与预算匹配
- batch 组织是否高效
- 损失是否只落在有效位置

也就是说，一条好的训练样本不一定是：

- 最符合人类阅读直觉的语义块

它更常是：

- 在语言连续性、监督信号完整性和计算效率之间取得平衡的计算对象

## 样本打包不是后勤事务，而是在决定模型训练分布

这一点值得再强调一次。

很多人把数据样本化理解成：

- 训练开始前的后勤准备

这会严重低估它的重要性。

更准确的说法应该是：

> 你怎样从 token 流里定义训练样本，就在怎样定义模型将反复接触到的条件分布切片。

因为模型并不是直接看“整部语料库”。
它真正反复接触的，是：

- 你切出来的窗口
- 你保留的边界
- 你构造的 batch

所以样本打包并不是外围技术活。
它是在具体决定：

- 模型训练时到底在看什么世界

## 一个更成熟的心智模型：训练样本是“局部历史观察窗口”

如果你想用一句话把整章装进脑子里，一个很有用的心智模型是：

> 训练样本就是语言模型反复打开的一扇局部历史观察窗口。

这个窗口有四个关键属性：

### 第一，它是局部的

模型不是一次看完整个世界，而是不断看窗口。

### 第二，它有长度

窗口长度决定模型能看到多少历史。

### 第三，它有边界

边界决定哪些 token 被允许视作同一连续上下文。

### 第四，它可批量堆叠

只有这样它才能真正高效进入训练。

一旦你把训练样本理解成“局部历史观察窗口”，后面的很多内容都会顺下来：

- 为什么要定上下文长度
- 为什么要处理边界
- 为什么要考虑 stride
- 为什么 padding 要配 mask

## 初学者在这一章最容易犯的几个误解

### 误解一：token 化完成就等于可以训练

其实 token 流离训练样本还差一整层组织工作。

### 误解二：固定长度样本就是自然语言的天然分段

其实它首先是计算系统偏好的窗口对象。

### 误解三：跨文档拼接只影响效率，不影响建模

其实它会直接影响模型学到哪些连续性。

### 误解四：padding 只是补长，不会改变训练语义

其实 padding 位置若处理不好，会直接污染监督信号。

### 误解五：样本打包只是预处理杂务

其实它是在定义模型真正看到的局部条件分布。

## 读完这一章之后，你应该能稳定回答什么

如果这一章真正起作用了，你至少应该逐步能回答下面这些问题：

- 文档、token 流、训练样本三者到底有什么区别
- 为什么训练通常喜欢固定长度样本
- 为什么固定长度窗口不等于自然语言天然分段
- 为什么上下文长度会同时影响建模能力和计算成本
- 为什么跨文档拼接会变成监督语义问题
- 为什么 padding 与边界标记都不是小细节
- 为什么样本打包本质上是在定义模型训练分布中的“局部观察窗口”

如果这些问题你能稳定讲出来，那么下一章里“为什么训练目标看起来要右移一位”就会非常自然。

## 小结

本章最核心的结论可以压缩成一句话：

> 把文本变成 token 之后，训练还没有真正开始；你还必须把这些 token 组织成长度可控、边界清楚、可批量堆叠、并能承载监督目标的局部历史窗口，而这一步本身就在定义模型会学习到怎样的上下文连续性与条件分布切片。

一旦这个认识站稳，你就不会再把：

- 上下文长度
- 文档边界
- 跨文档拼接
- padding
- batch 组织

看成离语言模型很远的工程细节。

它们其实都在同一件事上发力：

> 决定一台语言模型在训练时，究竟一次次看到了什么样的世界。
