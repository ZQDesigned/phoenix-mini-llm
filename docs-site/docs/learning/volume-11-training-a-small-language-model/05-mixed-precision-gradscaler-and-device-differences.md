# 05. 混合精度、GradScaler 与设备差异

## “开 AMP 更快更省显存”这句话方向没错，但远远不够

很多人第一次接触混合精度训练，听到的第一句话通常是：

> 打开 AMP，可以更快，还更省显存。

这句话并不错误，但它太像一句“性能宣传语”，不足以支撑你真正理解后面会踩到的坑。

因为一旦进入真实训练，混合精度影响的绝不仅仅是速度。

它还会直接影响：

- 张量到底以什么数值格式存在
- 某些运算是否更容易溢出或下溢
- 梯度在反向传播中是否容易丢失
- 不同设备后端上的行为是否一致
- 调试时你到底该先怀疑模型逻辑，还是先怀疑数值路径

也就是说，混合精度不是一个“加速按钮”，而是：

> 对训练数值系统本身的一次重新配置。

所以这一章要解决的问题不是“怎么调用 API”，而是：

> 精度到底是什么、为什么训练想降低精度、这样做会引入什么风险、GradScaler 在补什么，以及为什么不同设备后端不能被当成完全等价。

## 先从最基础的问题开始：训练中的“数”不是无限精确的

当你在纸上写一个实数时，默认好像可以无限精细。

但计算机里的张量不是这样。

在神经网络训练里，张量中的每个数都要被存储在某种有限位宽的浮点格式中。这意味着：

- 它能表示的数值范围有限
- 它能保留的有效精度有限
- 很大的数可能上溢
- 很小的数可能下溢
- 很接近的两个数也可能因为精度不足而被混淆

所以“精度”并不是一个抽象口号，而是在回答：

> 训练中的每个数字，究竟以怎样的浮点格式存在。

## 常见浮点格式到底在说什么

在深度学习里，最常见的几种浮点格式可以先粗略理解为：

- `float32`
- `float16`
- `bfloat16`

对当前阶段，你不需要先背所有比特分配细节，但一定要先建立一个最基本的判断：

> 不同格式的差别，主要体现在可表示范围、有效精度以及硬件支持路径上。

这三者会直接决定某种格式在训练里：

- 是否稳定
- 是否高效
- 是否容易踩坑

## float32 为什么长期是“保守默认值”

`float32` 之所以长期是训练默认值，不是因为它“最高级”，而是因为它在稳定性和通用性上很平衡。

它通常意味着：

- 数值范围更宽松
- 小数精度更稳妥
- 很多运算行为更容易预测
- 跨设备和跨框架行为相对成熟

如果你只是想先把训练逻辑跑通，`float32` 往往是最容易解释和调试的起点。

所以从学习角度说，FP32 的价值不是慢，而是：

> 它提供了一条更少数值意外、更多概念可解释性的基线。

## float16 为什么诱人

`float16` 的吸引力非常直接。

如果单个数占用更少位数，那么很多东西都会更省：

- 激活值
- 中间张量
- 某些反向传播缓存
- 显存带宽压力

而在现代 GPU 上，很多低精度矩阵运算还会得到专门硬件优化，于是：

- 吞吐更高
- 速度更快
- 同样显存下能放更大 batch 或更长序列

这就是为什么一谈到 6GB 显存、一谈到训练提速，大家很快就会想到混合精度。

## 但 float16 的问题也不是小问题

低精度从来不是“只赚不赔”。

如果说 FP16 主要换来了：

- 更小存储
- 更高吞吐

那么它的代价通常来自：

- 表示范围更紧
- 更容易让小量丢失
- 某些运算中数值稳定性更脆弱

换句话说，FP16 的问题不是“理论上可能有点误差”，而是：

> 在训练这种高度依赖连续数值传播的系统里，它可能真实改变反向传播和更新的健康程度。

这就是为什么你绝不能把 AMP 当成“无脑加速器”。

## bfloat16 为什么常常单独被提起

`bfloat16` 经常和 `float16` 一起出现，但它并不是简单换个名字。

从高层直觉看，它试图在某些场景下做到：

- 保留较低存储与高吞吐的优势
- 同时在数值范围上更不那么脆弱

因此在某些硬件和软件栈上，BF16 往往会表现出一种很吸引人的特性：

> 比 FP16 更不容易因为数值范围问题踩坑，同时仍保有低精度带来的不少性能收益。

但它是否真的适合你，还取决于：

- 设备是否支持
- 后端实现是否成熟
- 具体算子路径是否健壮

所以它不是抽象更优答案，而是：

> 在某些硬件生态里特别值得优先考虑的一种低精度格式。

## 为什么训练会想降低精度

如果只是从“别踩坑”角度看，直接全程 FP32 好像更省心。

那为什么大家还要费这么大劲搞混合精度？

因为收益往往非常现实。

### 第一，显存压力下降

对于小显存学习项目，这一点尤其关键。

当你把部分计算或中间张量切换到较低精度时，常常会直接换来：

- 更大的 micro-batch
- 更长的上下文长度
- 更少的 OOM
- 更宽松的激活缓存空间

### 第二，吞吐提升

很多现代 GPU 对低精度矩阵乘加有明显优化。

于是同样一套模型，在合适条件下，低精度路径往往能让：

- 每秒处理 token 更多
- 单步时间更短

### 第三，小显存环境下更容易“跑起来”

对于 6GB 这种紧张显存环境，混合精度经常不是锦上添花，而是决定你能否在合理 batch 下把训练跑起来的重要因素之一。

这就是为什么训练卷里必须认真讲它。

## 为什么不能简单“全程统一低精度”

这是理解“混合精度”三个字的关键。

如果低精度这么好，为什么不直接把：

- 参数
- 激活
- 梯度
- 优化器状态
- 所有算子

全部无脑切到 FP16？

因为这样很容易把训练数值系统推到不稳定状态。

问题在于：

- 有些运算更敏感
- 有些状态更需要稳定范围
- 有些梯度太小，直接会被吞掉
- 有些聚合运算对舍入误差更敏感

所以成熟方案通常不是“一刀切低精度”，而是：

> 在不同部位使用不同精度策略，让性能收益和数值稳定性折中。

这正是“混合精度”这个名字真正想表达的内容。

## “混合”到底混了什么

最实用的理解是：

> 不是所有张量、所有运算都统一降到一种低精度，而是根据算子的敏感性和硬件支持情况，让不同部分采用不同策略。

例如常见思路包括：

- 某些前向矩阵运算使用低精度
- 某些关键累计或状态保留在更稳精度
- 梯度更新时使用更谨慎的处理

当前阶段，你不需要记住每类算子具体归谁管理，但一定要建立这个判断：

> AMP 从来不是“全面降精度”，而是一种精度分配策略。

只要这一点记稳，后面你看到 autocast、GradScaler 等机制时，就不会再把它们误当成互不相关的零件。

## 低精度训练真正最危险的地方：不是算错，而是算没了

很多初学者第一次听“数值风险”，会以为问题主要是：

> 结果不够精确，所以最后 loss 多一点少一点。

这太温和了。

低精度训练里一个更要命的问题是：

> 某些很小但本来有意义的数值，直接在表示过程中被压没了。

这尤其容易发生在梯度上。

因为梯度本来就可能很小，如果浮点格式可表示的分辨率或动态范围不够，它们可能会：

- 被舍入得过于粗糙
- 直接下溢成 0

一旦发生这种事，问题就不是“有点误差”，而是：

> 某部分学习信号根本没能穿过去。

这就是为什么低精度训练里，梯度保护会成为一个单独主题。

## 什么叫上溢、下溢，为什么训练会怕它们

先用非常直觉的话说：

- 上溢：数太大，超出可表示范围
- 下溢：数太小，小到表示系统干脆把它压成 0 或极粗糙形式

在训练里，这两类问题都很危险。

### 上溢可能导致

- `inf`
- `NaN`
- 某些中间张量彻底坏掉

### 下溢可能导致

- 小梯度直接消失
- 某些参数长期学不动
- 梯度分布严重失真

因此，混合精度带来的核心挑战不是单一的“误差增大”，而是：

> 整个反向传播链路中，有些信号会因为数值格式受限而被扭曲甚至中断。

## 为什么小梯度特别脆弱

这对理解 `GradScaler` 至关重要。

在很多深层网络里，并不是所有参数都每步得到巨大梯度。

有些参数的梯度可能天然就很小，尤其在：

- 深层传播后
- 某些相对冷门的参数维度上
- 某些接近收敛阶段

这些小梯度在 FP32 中也许还能被稳定表示，但在更低精度中，就更容易：

- 被舍入掉
- 被压到 0

这意味着模型会出现一种非常隐蔽的问题：

- 训练在跑
- 反向传播也没报错
- 但某些真正有用的学习信号其实已经损坏了

这正是 GradScaler 出场的背景。

## GradScaler 在补什么

`GradScaler` 的核心思想其实非常朴素：

> 如果低精度环境下小梯度太容易被吞掉，那就在反向传播前先把 loss 放大，让梯度也一起放大，等更新前再按相同比例缩回去。

这句话里最重要的是“先放大，再还原”。

它并不是在改变目标函数本身，也不是在偷偷增大学习率，而是在保护：

> 梯度穿过低精度表示路径时，不至于因为太小而直接消失。

所以你可以把 GradScaler 理解成：

> 低精度反向传播里的梯度信号保护层。

## 为什么“放大 loss”不会改变真正优化目标

初学者第一次听到“把 loss 放大”，往往会立刻担心：

> 那不是把任务目标改了吗？

关键在于：

- 反向传播前整体放大
- 更新前再整体按对应比例缩回去

这样做的目的不是改变优化问题，而是：

> 让本来太小的梯度在低精度表示里先保住形状和存在性，再在真正更新时回到合理尺度。

可以把它看成一种“先搬大箱子，到了门口再拆回原尺寸”的过程。

真正想保住的是内容，不是把大小永久改掉。

## GradScaler 实际上在监控什么

除了做缩放，GradScaler 通常还会承担一个重要任务：

> 观察当前缩放策略是否导致了数值异常，并在必要时自动调整缩放尺度。

为什么要这样？

因为缩放不是越大越好。

- 缩太小，小梯度仍可能被吞掉
- 缩太大，某些值又更容易上溢

所以 GradScaler 本质上不是一个固定常数，而更像：

> 在低精度训练中动态寻找较合适梯度缩放尺度的控制器。

这也解释了为什么它不是“一个小工具函数”，而是和整个混合精度路径深度绑定的训练组件。

## autocast 在这套系统里扮演什么角色

在很多框架中，你会看到 autocast 和 GradScaler 常常一起出现。

两者职责不同：

### autocast 更像在决定

> 当前这段前向计算，哪些算子适合走低精度，哪些仍然应该保守一点。

### GradScaler 更像在决定

> 低精度反向传播过程中，梯度怎样被保护，避免太小直接坏掉。

所以它们是配合关系，不是同一个东西。

可以粗略理解成：

- autocast 管前向时“哪些地方降精度”
- GradScaler 管反向时“低精度梯度怎样保住”

这对理解 AMP 非常关键。

## 为什么很多项目里 GradScaler 和 CUDA 绑定最紧

你会经常看到一种现实实践：

- CUDA 上开启 autocast + GradScaler
- 其他后端先保守处理

原因并不是说其他后端绝对不能做混合精度，而是因为现实工程中存在很明显的成熟度差异：

- 硬件低精度矩阵单元支持不同
- 框架后端实现成熟度不同
- 某些设备上的低精度路径测试覆盖更充分
- 某些设备上的行为更容易预测

因此，对许多小型学习项目来说，更稳妥的做法通常是：

> 把正式性能优化集中在主要训练后端上，而不是一开始就要求所有设备低精度路径完全统一。

这和你的项目设定正好契合：

- macOS 常用于开发、验证、单元测试和小规模运行
- Windows + NVIDIA CUDA 更适合正式训练和显存压力测试

## 为什么 MPS 和 CUDA 不能被视作完全等价后端

这是跨平台训练时非常重要的一条现实原则。

很多人会自然地以为：

> 都是“GPU 后端”，那数值行为应该大差不差。

实际并不可靠。

不同后端可能在下面这些方面存在明显差异：

- 算子实现路径
- 混合精度支持程度
- 舍入和累积误差行为
- 内存调度方式
- 某些优化是否启用

这意味着：

- 同一段代码在 MPS 上能跑，不等于在 CUDA AMP 上一定同样稳
- 同一组种子和超参数，跨设备 loss 轨迹也不一定逐点一致

所以跨设备开发的正确预期不是：

> 逐步完全一样。

而应该是：

> 逻辑一致、趋势一致、接口行为一致、最终训练链路可解释。

## 为什么初学阶段不该把混合精度当成默认前提

如果你的训练系统还没有完全稳住，而你又同时引入：

- 新模型结构
- 新数据管线
- 新 tokenizer
- 混合精度
- 跨设备差异

那么一旦 loss 异常，你就很难判断问题到底来自哪里。

这种时候，混合精度会显著增加调试维度。

所以一个非常成熟的顺序通常是：

1. 先用更保守精度跑通训练逻辑  
2. 确认 loss 对齐、mask、梯度链路和生成逻辑都正确  
3. 再引入 AMP 和 GradScaler 做性能优化  

这不是拖延优化，而是在保护可解释性。

对于学习项目，调试可解释性比早一点多拿 15% 吞吐更重要。

## 为什么“不开 AMP 正常，一开 AMP 崩”是非常有信息量的现象

这类现象往往不是随机倒霉，而是在明确提示你：

> 模型逻辑也许没问题，但当前数值路径对低精度过于敏感。

这时你应该优先想到：

- 某些运算在低精度下不稳定
- 梯度缩放策略不合适
- 学习率太激进
- 当前设备后端上的 AMP 支持路径不够稳

而不是立刻归咎于：

- 模型结构整体有根本逻辑错误

当然两者也可能同时存在，但“FP32 正常、AMP 异常”本身就是一条很强的诊断信号。

## 哪些现象应该优先怀疑是精度路径问题

下面几类症状都非常值得把混合精度列为首要嫌疑项：

### 症状一：不开 AMP 一切正常，开了以后 loss 迅速爆炸

这通常说明数值范围、缩放或某些算子路径出现了问题。

### 症状二：训练中频繁出现 `inf`、`NaN`

这不一定全是 AMP 的错，但低精度 definitely 是要优先排查的一层。

### 症状三：某些参数几乎不更新，像“学不动”

有时这意味着小梯度被吞掉了。

### 症状四：MPS 上小规模验证正常，CUDA AMP 上正式训练突然变得很怪

这常常是设备后端差异与低精度路径共同造成的。

### 症状五：只在较大 batch、较长序列或较高学习率时出现异常

这提示当前数值系统在资源压力更大时，稳定性边界被打破了。

## 为什么低精度和学习率、梯度裁剪、初始化是联动的

混合精度从来不是孤立开关。

它会和训练系统中的其他稳定性因素强烈耦合：

- 学习率越大，某些值越容易冲到不稳定区间
- 梯度裁剪会影响极端更新是否被抑制
- 参数初始化尺度会影响早期激活和梯度范围
- batch 大小与 loss 统计也会改变数值分布

所以如果你看到 AMP 路径不稳，不要只盯着 AMP API 本身，还要把它放回训练系统整体里看。

更准确地说，问题往往不是：

> AMP 单独坏了。

而是：

> 当前这套模型、学习率、batch、设备后端和低精度格式组合起来，数值边界被踩穿了。

## 为什么 BF16 常被视作“更舒服”的低精度路径

在很多现代硬件和框架生态里，BF16 之所以越来越受欢迎，一个重要原因是它常常能在：

- 保留低精度吞吐与存储优势

的同时，

- 减少某些 FP16 的数值范围痛点

这会让很多训练过程显得更“省心”。

但一定要注意：

> “更省心”不是“完全不需要理解数值问题”。

它只是说明在某些硬件支持良好的平台上，BF16 常常给你更大的稳定性余量。

如果你的硬件不支持或路径不成熟，这个优势也未必能兑现。

## 为什么小显存项目更容易被迫早学混合精度

如果你在宽松显存环境里做教学示例，也许完全可以长期用 FP32 慢慢来。

但在 6GB 这类紧张显存环境中，现实情况常常是：

- 不开混合精度，batch 太小
- 或者上下文长度太受限
- 或者训练速度慢得难以迭代

这就使得混合精度在小显存项目里更早进入主线。

可正因为它进入得更早，你更需要把它理解对。

否则你会陷入一种很危险的状态：

> 我必须开它，但我又不知道它到底改变了什么。

这就是为什么本章要把它放在训练卷里系统讲，而不是当成附录小技巧。

## 一个成熟的使用顺序应该是什么

对从零学习的小型 LLM 项目，一个非常稳妥的顺序通常是：

### 第一步：先用更保守精度建立正确性基线

先确认：

- forward 正常
- loss 对齐正常
- 梯度链路正常
- 小样本能过拟合

### 第二步：再在主要训练设备上打开 AMP

通常优先在正式训练设备上启用，而不是要求所有设备同时一致。

### 第三步：观察是否出现新的数值症状

例如：

- loss 震荡是否加剧
- 是否出现 NaN
- 吞吐是否确实提升
- 显存是否确实下降

### 第四步：必要时再结合 GradScaler、裁剪和学习率细调

这样你就能清楚分辨：

- 哪些问题是逻辑问题
- 哪些问题是精度路径问题

## 为什么“性能优化”和“数值系统设计”在这里不能分家

很多性能优化都不会改变任务本身，只是让程序更快。

但混合精度比较特殊。

它虽然经常被归类为“性能优化”，却直接改变了训练中数字存在和传播的方式。

这意味着它既是：

- 性能优化

也是：

- 数值系统设计

这种双重身份，正是它容易被低估的原因。

如果你只把它当优化，你会忽略训练稳定性；
如果你只把它当数值问题，你又会忽略它对小显存训练能否落地的现实意义。

成熟的理解必须同时容纳两者。

## 常见误区

### 误区一：混合精度只是更快更省显存

它当然带来这些收益，但它同时也改变了数值稳定性条件。

### 误区二：AMP 就是把所有计算都降成 FP16

不是。

混合精度的“混合”恰恰意味着不同部位采用不同精度策略。

### 误区三：GradScaler 是某种可有可无的小工具

它本质上是在保护低精度反向传播中的梯度信号。

### 误区四：MPS 和 CUDA 都是 GPU，所以低精度行为应该差不多

现实中后端实现、算子路径和数值细节差异都可能很大。

### 误区五：既然最终正式训练会用 AMP，那一开始就应该默认开着

对学习项目来说，这通常会增加调试复杂度。先建 FP32 正确性基线更稳妥。

## 这一章真正要记住的核心句子

如果这一章只记一句话，它应该是：

> 混合精度不是一个“更快一点”的简单开关，而是在有限显存和现代硬件上，用更低精度换取吞吐和容量、同时重新设计训练数值路径的系统选择；GradScaler 的职责是在这条低精度路径上保护梯度信号，而不同设备后端则决定这套策略能否稳定兑现。

4. 低精度训练最危险的问题为什么常常不是“算得不够准”，而是“有些信号直接没了”？

## 自测问题

如果现在不看任何 API，只让你用自然语言解释下面三件事，你应该能够尽量稳定地讲清楚：

- 为什么混合精度同时属于性能优化问题和训练数值系统问题
- 为什么 GradScaler 的核心是保护小梯度穿过低精度路径，而不是“让 loss 变大”
- 为什么在跨设备开发的小型 LLM 项目里，先建立 FP32 正确性基线，再逐步打开 AMP，通常比一开始就默认混合精度更稳妥
