# 01. batch、token、step 与 epoch 到底在统计什么

## 这一章要完成的过渡

很多初学者第一次看训练日志时，最先感到混乱的，不是模型结构，而是计量单位。

屏幕上会同时出现：

- `batch size`
- `micro batch`
- `step`
- `global step`
- `tokens seen`
- `epoch`

这些词如果只是零散记忆，后面几乎所有训练讨论都会变得含糊。

因为训练不是一个抽象动作，而是一段有节奏、有尺度、有成本的动态过程。
你必须知道：

> 模型每更新一次，究竟看了多少数据；训练进行到一半时，又应该用什么口径描述“已经做了多少工作”。

这一章的任务，就是把训练里的这些计量单位重新排成一张连贯地图。

如果这一章不稳，后面你会不断碰到一种情况：

- 会看见术语
- 会模糊地觉得自己见过
- 但一旦比较实验、解释曲线或对齐日志，就立刻糊掉

所以这一章虽然不讲炫目的结构创新，却在为整卷训练主线打地基。

## 为什么训练必须先有“计量学”

很多初学者会不自觉地说出下面这些看起来很自然、但技术上并不够准确的话：

- “我多训练了一点”
- “这次 batch 更大”
- “这个实验跑得更久”
- “这个模型看了更多数据”

这些话的问题在于，“更多”到底指什么，并不清楚。

它可能指：

- 参数更新次数更多
- 一次更新前看到的样本更多
- 一次更新前累计的 token 更多
- 数据整体被扫过了更多轮

这些量彼此相关，但绝不相同。

所以训练一开始就需要一种计量学。

这并不是学术姿态，而是现实需要。
因为只要你没有稳定口径，下面这些最基本的问题都会变得难以回答：

- 两次实验是否真的可比
- 一个模型到底是“跑得更久”，还是“每步吃得更多”
- 某条 loss 曲线的横轴到底代表时间、更新次数，还是数据预算
- 你现在看到的是设备处理节拍，还是参数更新节拍

因此，训练一开始必须先问：

> 这台系统到底按什么单位消耗数据、推进时间和修改参数？

这就是本章的出发点。

## 从最粗的训练循环开始：先分清有哪些层次

一个极简训练循环可以写成：

```text
从数据中取一批样本
-> 前向计算
-> 算 loss
-> 反向传播
-> 更新参数
-> 再取下一批样本
```

这张图看起来简单，但里面已经藏着很多本章要拆开的层次：

- “一批”到底有多大
- “样本”到底是什么
- 一次更新前是否只处理一批数据
- 数据进度到底按样本数、按 token 数，还是按遍历轮数统计

只要这些问题还没有明确口径，你后面看到的每一条训练日志都只能是半透明的。

因此，本章的真正任务不是定义几个术语，而是把训练循环拆成几层不同对象：

- 原始数据层
- 训练样本层
- 并行处理层
- 参数更新层
- 总预算层

一旦这些层次站稳，训练日志就会突然变得好懂很多。

## 第一层：原始语料、训练样本和 batch 不是同一个东西

训练里最常见的混乱之一，就是把不同层次的数据对象混着说。

你最好先把它们严格分成三层。

第一层是原始语料。

这指的是你最初收集到的文本材料，例如：

- 一篇文章
- 一段对话
- 一页代码
- 一本书中的段落

在这一层，它们仍然是“人类文本材料”，还不是模型能直接吃进去的训练单元。

第二层是训练样本。

原始文本经过：

- 清洗
- 规范化
- tokenizer 编码
- 切片或打包

之后，才会变成真正进入训练循环的 sample。

在 decoder-only 语言模型里，这种 sample 往往是一段固定长度或近似固定长度的 token 序列，以及相应的右移目标。

所以训练样本不是“整篇文章”，也不一定是“一个自然句子”。
它是：

> 一条能够直接进入模型前向与 loss 计算的训练单元。

第三层才是 batch。

batch 是把多条 sample 组织在一起，形成一次并行前向和反向所使用的数据块。

如果每条样本长度为 `T`，一次拿 `B` 条，那么常见输入张量形状就是：

\[
[B, T]
\]

于是三层关系非常清楚：

- 原始语料是素材
- training sample 是可训练单元
- batch 是一次并行处理的一组训练单元

如果这三层不分清，后面关于 epoch、tokens seen、batch size 的讨论几乎必然会打结。

## sample 不是“自然句子”，而是“训练视角的单元”

这点值得单独强调，因为它会影响你对后面很多训练单位的直觉。

很多人会下意识认为 sample 就是一句话、一段问答或一段自然边界明确的文本。
在某些数据组织方式下，这样理解可能勉强成立。
但从训练系统角度看，这个定义太窄了。

更稳的定义应该是：

> sample 是一条已经被整理成可直接进入模型前向和 loss 计算的训练单元。

这意味着它通常具有两个特点。

第一，它已经是 token 级表示，而不是原始字符串。

第二，它已经被组织成适合当前训练设置的长度和边界。

因此，一条 sample 可能来自：

- 一整个短文本
- 长文的一段切片
- 多个短片段重新打包后的拼接

这说明 sample 是“训练视角”定义出来的对象，而不是“自然语言边界视角”定义出来的对象。

一旦你接受这件事，后面关于 epoch 和样本数的很多困惑都会自然减轻。

## 为什么 batch 会成为训练的基本工作单元

既然 sample 已经是训练单元，为什么还要再把很多 sample 组成 batch？

原因并不神秘，但非常重要。

第一，硬件擅长并行处理同构计算。

如果你一次只送一条样本进 GPU，那么大量并行能力会被浪费。
把多条同形状样本堆成 batch，可以让：

- 矩阵乘法更高效
- 吞吐更高
- 每次设备启动的固定开销更值得

第二，梯度估计会更稳定。

一次只看一条 sample，梯度很容易被这条样本的偶然性强烈影响。
把多条样本一起看，相当于对多条局部信号做平均，更新方向通常会更平滑一些。

第三，训练节奏更容易组织。

一旦有了 batch，训练就有了某种明确节拍：

- 取一批
- 算一批
- 累积或更新

这使得：

- 日志记录
- 学习率调度
- 设备吞吐测量

都能拥有统一口径。

所以 batch 不是纯粹的“加速技巧”。
它已经进入了训练系统的组织语言。

## `batch size` 到底在说什么

`batch size` 最直接的含义是：

> 一次前向 / 反向中同时处理多少条 sample。

如果每条样本长度固定，那么 `batch size` 越大，通常意味着：

- 一次并行处理的序列越多
- 单次前向 / 反向显存压力越大
- 梯度估计平均得更充分

但对语言模型来说，只说“batch 更大了”仍然不够。

因为语言模型真正做预测的对象，不是“样本条数”本身，而是：

> 序列中的 token 位置。

这就把我们带到下一层更关键的训练单位：token。

## 为什么在语言模型里，token 常常比“样本条数”更重要

在很多表格任务里，一条样本就是一个结构固定的对象，因此“样本数”本身很自然。

而语言模型不同。

语言模型的监督信号最终落在每一个 token 位置上。
也就是说，loss 不只是由“有多少条样本”决定，更由：

> 一共参与预测了多少个 token 位置

决定。

看下面两个设置：

```text
设置 A：batch size = 8, sequence length = 128
设置 B：batch size = 4, sequence length = 512
```

虽然设置 A 的样本条数更多，但设置 B 每步经过的 token 数量可能更大。

因此，在语言模型里一个非常关键的问题是：

> 每次处理，模型到底真正看了多少 token？

而不是只问：

> 这一步里有几条 sample？

一旦你开始这样看问题，后面很多训练单位都会自然统一到 token 预算上。

## 训练时真正被模型“看见”的，往往是 token 预算

当我们说“模型看了更多数据”时，在语言模型语境下，更成熟的说法往往是：

> 模型在训练过程中累计看见了更多 token。

为什么？

因为参数更新所依赖的监督信号，最终是由一个个 token 位置贡献出来的。

这意味着比较两个实验时，如果只说：

- 一个跑了 2 个 epoch
- 一个跑了 10k step

你仍然很可能不知道谁真的“看了更多东西”。

因为不同实验的：

- batch size
- sequence length
- gradient accumulation

都可能不同。

而这些因素共同决定了：

> 实际 token 消耗量。

所以语言模型训练里，token 是比“样本条数”更接近实际监督预算的单位。

## 什么是 step：训练里最容易被随口说乱的词

训练中的“step”是一个特别危险的词，因为它听起来太自然，结果反而最容易被混用。

它至少可能指两种不同含义。

第一种是数据处理意义上的一步。

也就是：

> 每处理一个 batch 或一个 micro batch，算作一步。

第二种是参数更新意义上的一步。

也就是：

> 每调用一次 `optimizer.step()`，算作一步。

在没有梯度累积时，这两种含义通常重合，所以问题不明显。

但一旦引入梯度累积，它们就会彻底分开。

因此，更成熟的做法是：

- 要么明确说 `micro step`
- 要么明确说 `optimizer step` 或 `update step`

否则很多关于 global step、warmup、学习率调度的解释都会立刻变得模糊。

## 为什么“处理了一个 batch”不一定等于“更新了一次参数”

这是理解训练日志最关键的分界线之一。

如果没有梯度累积，训练流程通常是：

```text
取一个 batch
-> 前向
-> backward
-> optimizer.step()
```

这时你可以近似把：

- “处理一个 batch”
- “更新一次参数”

看成同一节拍。

但一旦引入梯度累积，流程会变成：

```text
取一个 micro batch
-> 前向
-> backward
-> 先不更新
-> 再取下一个 micro batch
-> 再 backward
-> ...
-> 累积够若干次后才 optimizer.step()
```

这时你已经“处理了很多小批次”，但参数只更新了一次。

所以必须建立一个很稳的判断：

> batch 处理次数和参数更新次数，本来就不必相同。

只要这个判断没站稳，后面任何关于 accumulation、global step、learning rate schedule 的话都会越来越难懂。

## `global step` 为什么常常更接近“参数更新步”

在很多训练代码、日志系统和 checkpoint 命名里，`global step` 常常更接近下面这个定义：

> 从训练开始到现在，参数已经被更新了多少次。

为什么这个口径通常更有用？

因为很多训练机制关心的不是“你处理了多少个 micro batch”，而是：

> 参数已经经历了多少次真正的更新事件。

例如：

- warmup 常按 update step 数推进
- 学习率衰减常按 update step 数推进
- checkpoint 常按 update step 间隔保存
- 验证常按 update step 间隔触发

所以当你看到某个项目里的 `step` 时，最应该先问的不是“这个数字大不大”，而是：

> 这里的 `step` 到底指 micro batch 次数，还是 optimizer.update 次数？

这一步先问清，后面很多日志解释才不会走偏。

## 什么是 epoch，它为什么在语言模型里有时显得没那么“中心”

`epoch` 的经典定义是：

> 训练集中的每个样本都被完整使用过一遍。

在中小型、静态数据集任务里，这个定义非常自然。
但在语言模型里，epoch 的地位常常没有其他任务里那么强，原因至少有三层。

第一，语料可能极大。

在较大语料上，“完整扫一遍”本身就可能非常昂贵。
于是训练常常按：

- 总 step 数
- 总 token 数

来规划，而不是死盯 epoch。

第二，样本本身常是训练视角下的构造物。

原始文本经过 packing、切片、滑窗或重组后，所谓“一个样本”并不一定是天然稳定的自然对象。
这会削弱 epoch 的直觉感。

第三，很多训练控制机制天生按 step 组织。

例如：

- warmup 500 step
- 每 1000 step 验证一次
- 每 2000 step 保存一次

它们根本不需要借助 epoch 才能运作。

所以在语言模型里，epoch 仍然有用，但通常不是唯一核心单位。

## epoch 不是没用，而是要知道它在回答什么

epoch 之所以仍然值得保留，是因为它仍然能回答一个朴素但重要的问题：

> 相对于当前这份训练数据，模型大约已经扫过了多少轮？

这在下面这些场景里依然有价值：

- 数据集规模不大
- 样本切分较稳定
- 你想观察是否出现明显过拟合

但如果你的数据管线高度流式化，或者训练主要围绕 token budget 规划，那么 epoch 的解释力就会下降。

所以对 epoch 最稳的态度不是神化，也不是抛弃，而是：

> 保留它，但清楚它只在回答“相对于这份数据大致扫了多少轮”，而不是替代全部训练进度语言。

## 为什么 micro batch 会单独出现

一旦显存不够，训练里就会出现另一个特别重要的单位：

> `micro batch`

它通常表示：

> 一次真正送进设备、完成一次前向和反向的那一小批样本。

为什么要单独强调它？

因为你理想中希望一次更新整合的样本量，未必能在显存里一次性放下。

这时你就不得不把大批次拆成若干更小的 micro batch 来处理。

于是训练系统里会第一次明显出现两种不同节拍：

- 设备处理节拍
- 参数更新节拍

micro batch 这个词，就是为了让你把第一种节拍看清楚。

## 梯度累积到底把什么拆开了

梯度累积最值得抓住的，不是公式，而是它在系统层面到底拆开了什么。

它拆开的，其实是两只原本常被默认为同步的时钟。

第一只时钟是数据处理时钟。

每处理一个 micro batch，就会发生一次：

- 前向
- backward

第二只时钟是参数更新时钟。

只有累积足够多个 micro batch 后，才会发生一次：

- `optimizer.step()`

这意味着训练系统从此不再只有“一步”。
它开始同时拥有：

- processing step
- update step

这是后面很多主题的根节点。

因为只要这两只时钟被拆开，你就必须重新理解：

- global step
- 学习率调度
- effective batch
- tokens per update
- 吞吐统计

梯度累积不是“为了省显存多写几行代码”。
它本质上是在重组训练节拍。

## effective batch 到底是什么

一旦有了 micro batch 和梯度累积，就必须再引入一个更接近“更新语义”的单位：

> `effective batch size`

它表示：

> 从优化器角度看，一次参数更新前综合吸收了多少条样本的信息。

在单机单卡、小型学习项目里，最朴素的关系可以写成：

```text
effective batch size
= micro batch size × gradient accumulation steps
```

如果还有多设备并行，还要再乘上设备数。

但在你当前这种小模型学习场景里，先记住上面这条简单关系就足够了。

它的重要性在于：

> effective batch 比单独一个 micro batch，更接近“这次参数更新到底综合了多少信息”。

因此，比较实验时，如果只看 `micro_batch_size` 而不看 accumulation，往往会得出很片面的判断。

## 为什么 effective batch 比表面 batch 更接近“更新语义”

这其实就是刚才那两只时钟差异的直接后果。

优化器并不是在每个 micro batch 后都更新，而是在累积结束后才更新。
所以从“这次参数修改究竟参考了多少信息”的角度看，更有解释力的是：

> effective batch

而不是单个 micro batch。

当然，“effective batch 相同”也不意味着两个实验完全等价。
因为：

- 随机顺序
- dropout
- 数值路径
- 实现细节

仍然会造成差异。

但至少在高层理解上，effective batch 明显比只看一眼 micro batch 更接近真实更新规模。

## 语言模型里一个最关键的统计量：每次更新消耗多少 token

到这里，我们终于可以把多个单位真正连起来了。

假设：

- `micro_batch_size = B`
- `sequence_length = T`
- `gradient_accumulation_steps = A`

那么一次参数更新前，模型大致会处理：

\[
B \times T \times A
\]

个 token 位置。

这就是为什么语言模型里一个非常重要的量是：

> tokens per update

它直接把下面三件事绑在了一起：

- batch 规模
- 序列长度
- 累积步数

这也是为什么真正成熟的训练者，几乎从来不会只报一个孤零零的 batch size。
因为 batch size 离真正的更新语义还差了一整层 token 预算信息。

## 为什么“样本数一样”不等于“训练工作量一样”

看下面两个设置：

```text
设置 A：batch = 8, seq_len = 128
设置 B：batch = 8, seq_len = 512
```

虽然 batch size 都是 8，但一次前向 / 反向经过的 token 数差了 4 倍。

再看：

```text
设置 C：micro batch = 2, accumulation = 8, seq_len = 256
设置 D：micro batch = 8, accumulation = 2, seq_len = 256
```

两者的 effective batch 都是 16，但：

- 单次设备负载不同
- 更新节拍不同
- 显存压力不同
- 日志解释方式也不同

这说明训练中的“工作量”至少有多个维度：

- 每次设备处理多少数据
- 每次更新整合多少数据
- 总共处理了多少 token
- 参数一共更新了多少次

所以如果有人只报一句“batch 是 8”，你几乎还没有得到任何足够稳的训练描述。

## `tokens seen` 为什么在语言模型里经常特别重要

当训练越来越久时，你会越来越发现：

- step 本身不能完整描述训练进度
- epoch 在大语料上也不一定稳定

这时 `tokens seen` 往往会成为一个非常稳的进度口径。

它表示：

> 从训练开始到当前时刻，模型总共已经处理了多少 token。

这个指标特别重要，因为它更接近：

- 实际监督信号总量
- 训练预算的真实消耗
- 跨不同 batch / seq_len 设置的比较基础

例如，如果两个实验的 step 数一样，但：

- 一个用更长的 sequence length
- 一个用更大的 effective batch

那么它们真正消耗的 tokens seen 可能完全不同。

这时仅看 step 会严重误导你。

所以在语言模型里，`tokens seen` 往往比“跑了多少轮”更接近真实训练预算语言。

## 为什么 step 和 tokens seen 最好一起记录

这两个量并不互相替代，它们分别在回答不同问题。

`step` 更接近训练控制语义。

很多机制按 step 组织：

- warmup
- scheduler
- checkpoint
- validation

而 `tokens seen` 更接近训练预算语义。

它回答的是：

- 模型到底看了多少内容
- 两个实验是否真的用了相近的数据预算

所以最稳的做法不是在二者之间二选一，而是：

> 同时记录，并清楚知道它们分别在回答什么。

这也是日志设计里一个特别常被低估的好习惯。

## 为什么比较实验时必须先统一口径

很多表面上的实验结论其实站不住脚，不是因为模型本身复杂，而是因为比较口径根本没统一。

例如有人说：

> 实验 X 更好，因为它训练了更多 step。

但如果实验 Y 每步处理的 token 更多，这个结论就不完整。

又例如有人说：

> 实验 A 的 batch 更大，所以更稳定。

但如果实验 B 用了梯度累积，它的 effective batch 也许并不小。

因此，比较实验前，至少要尽量统一下面几类口径：

- micro batch size
- sequence length
- gradient accumulation steps
- optimizer step 的定义
- tokens seen 的统计方式

没有统一口径，很多实验比较看起来像是在比较训练，其实是在比较不同计量系统。

## 对 6GB 级别显存学习项目，哪些口径最实用

如果你是在受限显存环境里做小模型学习项目，最少建议稳定记录下面几项。

`micro_batch_size`

它回答：

> 一次真正塞进设备多少条样本？

`sequence_length`

它回答：

> 每条样本有多长？

`gradient_accumulation_steps`

它回答：

> 多少个 micro batch 才合成一次参数更新？

`global_step`

它回答：

> 到当前为止，参数已经真正更新了多少次？

`tokens_seen`

它回答：

> 模型累计已经处理了多少 token？

这几项一起，基本就能把你的小型语言模型训练节奏描述清楚。

如果缺了其中任何一项，很多看似简单的问题都会突然难以解释。

## 一个具体例子：把所有单位真正连成一张图

假设你的设置是：

```text
micro_batch_size = 4
sequence_length = 256
gradient_accumulation_steps = 8
```

那么：

- 每个 micro batch 会处理 `4 × 256 = 1024` 个 token
- 8 个 micro batch 累积后才更新一次参数
- 所以每次参数更新前，大约综合了 `8192` 个 token 的监督信号

如果此时日志显示：

```text
global_step = 1000
```

那意味着从优化器角度看，模型已经完成了 1000 次参数更新。

而如果粗略估算 `tokens_seen`，则大约是：

\[
1000 \times 8192
\]

这个量级。

这就是为什么真正有解释力的训练日志，几乎从来不是只写一个 `step=1000` 就结束。

因为你还必须知道：

- 这一步到底代表哪种 step
- 每步消耗多少 token
- 这些 step 在什么显存组织方式下发生

## 为什么训练曲线必须和这些单位一起读

单看 loss 曲线，你只能知道：

- 数值在降还是在升

但你并不知道：

- 它经过了多少次参数更新才降到这里
- 每次更新前看了多少 token
- 不同实验的下降速度是否真的可比

所以更成熟的看法是：

> 训练曲线是数值轨迹，而计量单位是解释这条轨迹的坐标系。

没有坐标系，轨迹本身的解释力会大幅下降。

这也是为什么很多人明明看了很多 loss 曲线，仍然说不清实验到底发生了什么。
因为他们看的只是曲线形状，没有配套读懂横轴到底在计量什么。

## 这一章其实在为后面所有训练章节打地基

你很快会发现，后面几乎每个训练主题都依赖这一章的计量框架。

例如：

- 讲优化器时，要知道更新事件何时发生
- 讲 warmup 时，要知道 scheduler 通常按哪个 step 推进
- 讲梯度累积时，要知道 micro batch 和 effective batch 是什么关系
- 讲 checkpoint 时，要知道保存的是哪一种 step 位置
- 讲实验比较时，要知道 tokens seen 为什么比 epoch 更稳

如果这一章没稳住，后面你会觉得每章都懂一点，却总是连不起来。

所以这章看起来像术语澄清，其实在做更根本的事情：

> 给整卷训练系统提供统一坐标系。

## 一个更稳的训练心智模型：训练里其实有三只时钟

到这里，可以把本章最想留下来的心智模型压成一张图。

训练里至少有三只彼此交织的时钟。

第一只是数据处理时钟。

每来一个 micro batch，系统就吃进一小批数据，做一次前向和 backward。

第二只是参数更新时钟。

只有累积够一定量的处理事件后，优化器才真正改一次参数。

第三只是预算累计时钟。

无论更新是否已经发生，模型总共已经看见了多少 token 这个量都会持续增长。

于是，训练前进不是单线程的一条刻度，而是三种节奏同时在推进：

- 处理节拍
- 更新节拍
- 预算节拍

只要这个模型进脑子里了，后面很多训练日志会突然清晰很多。

## 常见误区

### 误区一：sample、batch、语料差不多，反正都是数据

不对。

它们属于不同层次：

- 语料是原始材料
- sample 是可训练单元
- batch 是并行处理的一组 sample

### 误区二：step 总是同一个意思

不对。

在有梯度累积时，处理 step 和更新 step 会分开。

### 误区三：epoch 就是最权威的训练进度指标

不对。

在语言模型里，epoch 仍有用，但常常不如 step 和 tokens seen 稳定。

### 误区四：batch size 越大，实验之间就天然可比

不对。

sequence length 和 gradient accumulation 也会明显改写真实更新语义。

### 误区五：一个 batch 就天然等于一次优化

不对。

小显存训练里，这个等式最先失效。

### 误区六：训练曲线只看 loss 就够了

不对。

loss 必须和 step、tokens seen、更新节拍一起读，才有解释力。

## 这一章真正要记住的核心句子

如果你只记住本章八句话，应该记住下面这些。

1. 原始语料、训练样本和 batch 是三层不同对象，不应混着说。  
2. 在语言模型里，token 往往比“样本条数”更接近真实监督预算单位。  
3. `step` 至少可能指处理步或参数更新步，在有梯度累积时必须区分。  
4. `global step` 常常更接近“参数已经更新了多少次”。  
5. `epoch` 仍然有用，但在大语料语言模型里不总是最核心的训练进度语言。  
6. `micro batch` 表示单次真正塞进设备的一小批样本，而 `effective batch` 更接近一次更新综合吸收了多少信息。  
7. `tokens seen` 往往是语言模型里最稳的训练预算口径之一。  
8. 训练曲线本身只是轨迹，batch、step、tokens seen 才是解释这条轨迹的坐标系。
