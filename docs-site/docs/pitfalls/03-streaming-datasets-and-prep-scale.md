# 03. 流式数据集与子集规模

## 发生背景

学习项目往往既想“像真实项目一样使用公开语料”，又想“本地能很快跑通”。TinyStories 很适合小模型，但如果你一开始对数据规模和 streaming 行为没有想清楚，准备数据阶段就会变得又慢又难调。

## 现象

可能出现的现象包括：

- 数据准备时间远超预期
- 你以为只取了子集，实际上却在遍历过大的数据流
- train / validation 规模不平衡，导致验证结果不稳定

## 一开始的错误判断

常见误判是：

- “数据集库太慢”
- “机器磁盘有问题”
- “一定要把全量语料都下完才算认真”

这几个判断都会把你推向更重的解决方案，而不是更清晰的约束设计。

## 最终原因

问题的核心不在于数据集本身，而在于：

- 你是否明确规定了 `max_train_examples`
- 你是否明确规定了 `max_validation_examples`
- streaming 模式下是否真的在达到上限后及时停止收集

## 诊断过程

最关键的不是盯日志，而是先检查配置和收集函数：

```python
def collect_text_examples(records, text_key, limit):
    ...
    if len(texts) >= limit:
        break
```

如果没有这样明确的边界，所谓“子集模式”就可能只是名字上的子集。

## 修复方式

1. 在 `DatasetConfig` 里明确区分训练集和验证集上限。
2. 让下载函数始终返回 `list[str]`，并在达到上限后停止收集。
3. 把语料规模写进 metadata，方便后续核对。

## 如何避免再次踩坑

- 不要把“更像真实生产”误解成“必须全量跑一遍”。
- 学习项目优先保证可控、可迭代和可验证。
- 数据准备完成后，优先记录样本条数，而不是凭感觉判断“应该差不多了”。

<Callout title="正确的学习取向" tone="note">
  对小模型学习项目来说，能稳定地准备一份可复现、规模受控的子集，远比匆忙接入超大语料更有价值。
</Callout>
